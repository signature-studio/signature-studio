# dpi240-stop: Issue #1354 の調査(受理ではない。差し戻し)

測定の値は runner の値。この機械とは別枠。nproc = 4。測定の終わりの loadavg は 0.06 / 0.19 / 0.53。

## 判定

- 差し戻し。停止の原因は、窓の応答ではなく、FL のループを lift が入れ子の呼び出しに変換したこと。閉路の入口は特定した(節 2)。
- 製品の差分は無い(診断は全て外した)。DPR 2.5 と 3.0 は engine-idle に届かないので、受け入れは通らない。
- 窓の応答(LOGPIXELSY・GetSystemMetrics・GetDpiForMonitor)は、すべて Windows の式どおり(節 4)。直す応答は見つからなかった。

## 1. 停止の時点のスタック(実測)

- 停止の表示: `[js] fle thread 2 failed: RangeError: Maximum call stack size exceeded`(DPR 2.5 と DPR 3.0 の両方)。
- 方法: `Error.stackTraceLimit` を 1e6 にして、停止の時の JS の枠(wasm の関数番号 `wasm-function[N]` と、C の関数)を全て出した。枠は 9,437 件。N は `lift/out-app/gen/wasm-func-names.tsv` の index 列で引いた。
- 表で引けなかった物: 底から 60 件のうち 5 件(表の kind が `-`。名前が無い番号。いずれも閉路の外)。閉路の中の番号は全て名前が引けた。

## 2. 閉路と入口

閉路(呼び出しの向き。表の名前)は 8 枠で、9,408 枠の中に 1,176 回繰り返す(枠の列の完全な周期):

```
fle_dispatch -> f_27ad527 -> f_27ad54a -> f_27ad56d -> f_27ad590 -> f_27ad5b3 -> f_27ad5d6 -> f_27ad5f8 -> fle_dispatch -> ...
```

閉路の入口(最初に現れる閉路の関数): `f_27ad527`。その呼び出し元は `fle_dispatch`、さらに `f_27acd60`(平均の計算の入口)。底からの呼び出しの連鎖:

```
fle_wasm_thread_entry -> fle_call_guest -> f_412ae0 -> fle_dispatch -> f_5251b0 -> fle_dispatch -> f_71da40
  -> (fle_hyb_dispatch と、名前の無い枠) -> f_6ca7b0 -> ... -> f_2743af0 -> f_27abd80 -> f_27acd60
  -> fle_dispatch -> f_27ad527 (閉路の入口) -> ... (閉路を 1,176 回)
```

`f_27abd80` は `0x27abf2b` で `f_27acd60` を呼ぶ(gen/src/m1-04.c の該当行)。

### 閉路の中身(gen/src/m1-04.c の生成 C)

- `L_27ad514`〜`L_27ad525`: バイト表(0x1ecf840)から飛び先のオフセットを読み、`R[0] = 0x27ad527 + byte` とし、`fle_dispatch(R[0]); return;` で飛ぶ(`fe-lift/src/tailjmp.rs` の `jmp reg` の変換)。飛び先は関数の入口。
- `f_27ad527`〜`f_27ad5d6`: 各々が 16 バイトの要素 1 個(単精度 4 個)を `addss` で X[12]〜X[15] に積算し、末尾で次の関数を `f_next(); return;` で呼ぶ(関数の境界をまたぐ続きは、呼び出しとして出る)。
- `f_27ad5f8`: 最後の要素を積算し、`L_27ad525` に戻る。

つまり、要素を 1 個ずつ足す FL のループ(Duff の装置の形)で、後戻りの飛びが全て入れ子の C の呼び出しになっている。ループの深さが、そのまま枠の数になる。

### ループの回数

`f_27acd60` は、二つの寸法の積 N(`imul`)を作り、`1/N`(`divss`)を求めてから、N 個の要素を積算する(平均)。反復の回数は N。閉路の 1 回で 7 要素を進めるので、このループは約 8,200 要素(1,176 × 7)を回った(推定)。枠が 9,437 で尽きた。

N の出どころ(`f_27abd80` が渡す二つの寸法)は、この実行では追えていない(未特定)。

## 3. 閉路を導く応答

- 閉路そのものは、窓の応答を読まない(`CreateWindowExW` の後の計算だけ。文字の計量の API は呼ばれない)。閉路の深さを決めるのは N。
- N を作る寸法の出どころは未特定。候補は、画面の寸法の応答(`GetSystemMetrics` の SM_CXICON・SM_CXCURSOR)か、FL 自身のビットマップの寸法。推定: 96 DPI で 36 × 36 画素の物が DPI に比例して拡大する(240 DPI で 90 × 90 = 8,100 要素。閉路と合う)。推定。
- 閉路の深さと DPI の関係(推定。実測の枠の数から): 96 DPI と 216 DPI は枠の上限に届かず、240 DPI と 260 DPI は届く。LOGPIXELSY を 96 に戻すと届く(#1347 の結果と一致)。

## 4. Windows の仕様との照合

- LOGPIXELSY(90)・GetDpiForMonitor: 240 = MulDiv(96, 250, 100)。DPR 2.5 の式の値と一致(#1347 の表)。
- GetSystemMetrics(SM_CXCURSOR = 13): 80 = MulDiv(32, 240, 96)。Windows の GetSystemMetricsForDpi の式と一致(`lift/runtime/fle_sysmetrics.c` の `fle_sm_scaled`)。
- AdjustWindowRectEx: 非クライアント領域を 0 とする既存の仕様(`fle_win.c`)。この閉路には関与しない。

結論: 応答は Windows と同じ値で、直す応答は無い。閉路の入力は正しい寸法(DPI に比例した画素数)で、閉路の深さが lift の表現(後戻りを入れ子の呼び出しにする)で、JS のスタックを超える。

## 5. 直す場所(未実施)

- 原因の所在: `lift/crates/fe-lift/src/tailjmp.rs`(`jmp reg` を `fle_dispatch(t); return;` にする)と、関数の境界の切り方(表の飛び先ごとに関数を分け、続きを `f_next(); return;` にする)。
- 候補 A(lift の変更): バイト表による飛びを `switch` と `goto` で、同じ C 関数の中の飛び先にする。続きも `goto` にし、要素の積算がネイティブの再帰にならないようにする。再 lift(engine の作り直し 30 分)とテストが要る。
- 候補 B(ビルドの変更。未検証): `-mtail-call` と最適化(-O1 以上)で、`f_next(); return;` と `fle_dispatch(t); return;` を wasm の return_call にし、ネイティブのスタックが伸びないようにする。JSPI・longjmp・`fle_call_guest` との関係を確かめる必要がある。製品全体のコンパイル設定の変更になる。
- 閉路を隠す回避(深さの上限、N の抑え、特定のループの関数を C で置き換える、など)は、制約により採らない。
