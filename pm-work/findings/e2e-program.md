# E2E の全体計画(依頼者の指示 2026-11-26 に応える)

依頼者の指示(原文): 「そうではなく、存在する機能について、考えうる限り全ての E2E テストを追加してください。」(前の発言: 「非常にクラッシュしやすいのですが、本当に十分な数のテストシナリオを用意し、Playwright による E2E テストを実施しているのですか?」)

## 1. 方針

- **機能の一覧(インベントリ)を軸にする**。存在する機能(FL のメニューの項目・窓・上部バーの部品・設定の選択欄・プラグイン・言語・テーマ・テンプレート・demo・ページの機能・配信の物)ごとに、**期待する結果を持つ** E2E のシナリオを足す。
- 網羅は、一覧に対する `coverage.json` で測る(覆われた機能の割合。領域ごとに `tools/e2e/features/<領域>.min` の下限を置く)。
- 「クラッシュを探す走査」を目的にしない。`tools/crash-hunt/`(停止だけを見る走査)は残す。
- シナリオは、`tools/e2e/scenarios/<領域>/` の下に 1 本ずつ置く。共有の表・共有の判定を編集しない(領域の Issue どうしが衝突しない)。
- 全ての Issue の修正は、対応する領域に、E2E のシナリオを 1 本以上足す(回帰)。

## 3. 実行の形と予算

- **起動は 1 シャードで 1 回**。4K の起動は、この runner で約 24 秒(`tools/e2e/README.md`)。シナリオごとに再読み込みすると時間が足りないので、シナリオの間は、File > New や窓の閉じ方で初期化する(初期化の結果は、窓の表と画素で確かめる)。再読み込みは、保持(file)と耐久(resilience)の領域だけ。
- **シャード**: `--shard i/n`(シナリオの決定的な分割)。1 ジョブ 40 分以内を守る。既定の n は 8。全体で 16 シャードまで増やしてよい(`deploy.yml` の上限は 1 ジョブ 40 分 × シャード数)。注意: `deploy.yml` の e2e の matrix(1be44905)は、表示ごとの 3 シャード(`smoke-dpr1`・`smoke-dpr2`・`smoke-random`)で、`--shard i/n` とは別物。E0 は matrix の args を変えない。
- **見積もり**: crash-hunt の実績は 562 件 / 17 分 ≈ 33 件/分(停止だけを見る)。期待値を判定するシナリオは 1 件 数秒〜数十秒と見込み、1 シャード(40 分)で約 100 件。1,670 本の最小は、8 シャードで 1 回り(表示 2 点の場合は 16 シャード)。
- **表示**: 既定は DPR 1 と、乱数の DPR(1.01〜3.00 の 2 点)。重い物は DPR 1 だけにしてよい(理由を `notes` に書く)。DPR の指定 `--displays dpr:<数>` は E0 が足す。
- **門(deploy)**: `tools/e2e/judge.jq`(smoke)と、回帰の集合(#1408)。網羅の集合は、1 ジョブの上限のため、門には入れない。網羅の判定(`judge-coverage.jq`)は、全シャードの結果を合わせて PM が行う。

## 4. 欠陥が見つかった時

- **既知の欠陥**(Issue が在る): シナリオに `expectFail: '#<Issue の番号>'`。`ok` は問わないが、`pageErrors`・`consoleErrors`・`failedRequests` は 0 であること。
- **新しい欠陥**: `expectFail: 'new'`。報告に、欠陥の一覧(シナリオの ID・症状・停止の理由・run の出力の行)を書く。PM が Issue にして、番号に置き換える。
- **印の無い失敗は、門を落とす**(`run.mjs` の `rowPasses` と `judge.jq` の規則は変えない)。
- 製品(`app/`・`lift/`)は、E2E の領域の Issue では直さない。見つけた欠陥は `expectFail` で記録する。

## 5. 期待する結果の書き方

- 「止まらなかった」だけで終わらない。次の、測れる形で判定する: 窓のクラスと題名(窓の表)・画素のハッシュ(変わった・変わらなかった)・ゲストのメモリの文字列・engine のログの行・DOM・音声の PCM・ネットワークの要求。
- 文字は、OCR で読まない(禁止)。メニューの項目の名前は、ゲストのメモリの文字列から取る(一覧の生成。取れない項目は番号で扱う)。
- 期待値に、実行時の値(DPR・DPI・窓の位置)を定数で書かない。窓の表と画素から取る。

## 6. 一覧(インベントリ)の出どころ

- 実行中の FL から: メニュー(全階層)・窓のクラス・上部バーの部品(`TWPControl`)・設定の 16 頁と選択欄・ブラウザのタブ・ミキサー・チャンネルラック・プレイリスト・ピアノロールの子窓。`tools/e2e/inventory.mjs` が `tools/e2e/features/generated/` に書く(E0)。
- リポジトリから: `inputs/plugin-classes.tsv`・`inputs/external-plugins.tsv`・`lift/plugins/`・`inputs/fl-installer-files.tsv`(テンプレート・demo・言語・テーマ)・`app/src/` のモジュール・bundle の `manifest.json` の lazy。
- 手で書く物: 領域の Issue が `tools/e2e/features/<領域>.tsv` に、その領域の機能(操作・期待する結果の種類)を書く。他の領域のファイルは編集しない。

## 7. 規則

- 1 シナリオ = 1 ファイル。`defineScenario({ id, area, covers, displays, expectFail, run })`。`covers` に機能の ID を置く。
- 製品に、テストのための環境変数・`#ifdef`・URL パラメータ・ビルド変数を足さない。
- Python と OCR を使わない。AI のベンダー名と Cloudflare の識別子を、ファイルに書かない。
- 一覧の機能が増えた時(新しいプラグイン・窓)は、インベントリの再生成で、`coverage.json` の母数が変わる。PM が、母数の変化を報告に書く。

## 8. 進め方

起票の結果(2026-11-26): #1485(E0)だけが起動した(blocked_by なし)。#1486〜#1498 は、`blocked_by` の #1485 が閉じるまで起動しない。

1. E0(#1485。下書き 199)が通る(基盤・一覧・網羅率・見本 39 本)。
2. 領域 200〜212 が並行に入る(E0 の後に起動)。各領域は、受け入れ(最小のシナリオ数・1 シャードの実行)を通し、残りを次の作業で足す。
3. PM が、全シャードの結果から `coverage.json` を作り、`judge-coverage.jq` で領域ごとの下限を見る。下限に届かない領域は、続きの Issue を起票する。
4. 欠陥(`expectFail: 'new'`)は、PM が Issue にし、直しの Issue に、対応するシナリオの `expectFail` の印の番号を付ける。
