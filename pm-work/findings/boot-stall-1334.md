# 起動直後の途切れ(#1334): 公開が止まる原因、修正、計測

数字は runner の値(Chrome 157、nproc 4、loadavg 0.1〜1.7)。この機械とは別枠。「実測」は道具の出力、「推定」は読みと推論。

## 1. 結論

- **止まっていた原因(実測と読みで確定)**: 外部の音声の消費者(AudioWorklet)があるとき、スケジューラの締切に音声の時刻が 1 つも入らなかった。`fle_audio_tick_of_frame` が外部のとき 0 を返すため、`fle_audio_next_tick` も 0 を返していた(`lift/runtime/fle_audio_ring.c`・`fle_dsound.c`)。アイドルの待ち(`lift/harness/fruity_idle.c` の `fle_idle_wait`)は、次の締切が無いと、入力が来るまで眠る。音声の補充(`audio_sync` → `fle_js_publish`)は、スケジューラの点でしか呼ばれないので、眠っている間は止まり、リングが干上がった。
- **修正**: 外部の消費者があるときだけ、(a) 読み取り位置までの時刻を、今から実時間で求める(`fle_audio_tick_of_frame`)、(b) 補充の締切(書き込み済みの先読みの半分を読み終える時刻)を締切の集合に入れる(`fle_audio_next_tick`)。ネイティブと、消費者が無いときの動作は変えない。
- **結果(実測)**: 受け入れの 3 回で `bootLast60sAt70s` は 0。押下の時刻 0・0.5・1・5・30 秒の 5 回も、すべて 0。前回(4 回目)の 3 回は、3 回とも 20,661 だった。
- **受け入れの未達(実測。製品ではなく式の問題)**: `screenDevicePx` が `3240x1864` で、受け入れの式(切り捨て)の `3240x1863` と合わない。製品の `chooseGuestScreen` は #1347(32a318c2)で `Math.round` に変わった。Issue の式は切り捨て前提で書かれている(3 回目・4 回目の 1863 は切り捨ての製品の値)。1836×1056 CSS px の部屋では、丸めの製品で 3240x1863 を出す DPR は、受け入れの式と両立しない(§7)。PM の判断が要る。
- **残った途切れ(実測)**: 最初のアイドルの約 9 秒後まで、エンジンは計算で 100% 塞がる(§5)。その間、消費者が動いていれば途切れる(押下の時刻に依らず、最後の途切れは最初のアイドルの 9.1〜9.5 秒後)。+10 秒より後は途切れ 0。これは #1352 の対象。

## 6. 計数の定義の検証(作業の順序 4)

- `maxRefillStallMs` は、エンジンの起動からの、公開の間隔の最大(`fleAudioWorkerState.maxPubGapMs`)。トレースの最初の行(t = 395 ms)で既に 430.8 ms で、窓(+10 秒以降)の中では増えない。よって窓の値ではない。受け入れの `maxRefillStallMs` の目標(60 ms 以下)は、この定義では測れない(#1352 で扱う)。
- 連続 underrun の最長(`trace-stats.mjs`)は、窓の中の連続で、9.1 秒の計算(§5)の間に起きた。`maxRefillStallMs` とは別の量(起動時の最大の間隔 430 ms と、計算の間の連続の途切れ 9 s)。
- 途切れの数え方(`app/src/audio/fle-out.worklet.js`): 再生中の quantum で、`WR − RD` が 128 未満のもの。トレースの fill のサンプル(50 ms 間隔)は、途切れの間にも 1,750〜2,646 frames だったが、サンプルの欠けた区間(826 ms〜8,571 ms)に途切れが集中した。サンプルが欠けるのは、engine の Worker の CDP の応答が、計算の間は返らないため(推定)。

## 7. 受け入れの画面の寸法の式(PM の判断が要る)

- 受け入れの式: `Math.floor(1836 × dpr) × Math.floor(1056 × dpr)`(`dpr` は道具の既定 30/17 ≈ 1.764706)。
- 製品の式(`app/src/ui/screen-fit.ts`の `chooseGuestScreen`。#1347 以後): `Math.round`。30/17 で `1836 × 30/17 = 3240.0`、`1056 × 30/17 = 1863.53`。丸めると 3240x1864。
- 式が通るための条件(計算): 製品の丸め(round)と式の切り捨て(floor)が、幅と高さの両方で一致する必要がある。幅 3240 で一致するのは d ∈ [1.764706, 1.764979)、高さ 1863 で一致するのは d ∈ [1.764205, 1.764678)。この 2 つは交わらない。よって、この式は、幅 3240・高さ 1863 のどの DPR でも通らない。
- Issue の画面 3240x1863 は、丸めの製品では d ∈ [1.764432, 1.764678) で出る。しかし、その DPR では式が幅 3239 を期待するので、通らない。切り捨ての製品(#1347 以前)なら 30/17 で 3240x1863 になっていた(3 回目・4 回目の実測)。
- 道具の既定の DPR(30/17)は変えていない(Issue の条件のまま)。式を変えるか、期待値を 3240x1864 にするかは PM が決める。

## 11. 6 回目の試行: 公開が止まる欠陥の原因と修正(runner の値。nproc 4、loadavg 0.4〜1.9。この機械とは別枠)

### 11.1 5 回目の修正が、この版では効かなかった(実測)

- 5 回目と同じ作業ツリーを、ビルドし直して受け入れを実行(ACCEPT_EXIT=1。落ちたのは `bootLast60sAt70s` の 0 の判定)。
  - `bootLast60sAt10s` 3381・3350・3353、`bootLast60sAt70s` 20662・20671・20658、`quantaDelta` 20672〜20675、`maxRefillStallMs` 659・672・701。
- トレース(押下 0、`--trace`。`.tmp-1334/trace-a.tsv` 相当): 公開の回数 `publishes` は、最初のアイドルの時点で固まり、窓の終わりまで 0 増加(`trace-stats`: `publishesDelta` 0、最長の連続 underrun が窓の全体 69.7 s)。
- 5 回目の受け入れ(0 ×3)と一致しない。違いは未確認(ビルドの違い、負荷の違いの両方が候補)。

### 11.2 原因(推定。一部は実測)

- 実測: 最初のアイドル(`idleCount` の初回報告)の後、ドライバは締切を受けてアイドルを回す(1〜2 ms の締切。ワーカーの一時計測で 7 回。製品には残していない)。7 回目の再開の後はアイドルに戻らず、公開も増えない。
- 推定: 再開後に公開が増えないのは、スケジューラが `poll_waiters` → `fle_audio_poll` → `audio_sync` を通っても、`audio_sync` が `play_count() == 0` で戻るため(公開は再生中のバッファがあるときだけ行われる)。同じ条件の `fle_audio_next_tick` も、外部の消費者の締切より先に `play_count() == 0` で 0 を返す。よって、再生中のバッファが無い間は、外部の消費者があっても、締切も補充も無い。締切の残りはゲストのスレッドの待ちだけになり、それが尽きるとエンジンは入力まで眠る。
- 未確認: `play_count()` の直接の値。リングの状態はページで `playing`(`deviceState`)と表示されるので、状態の遷移の読み(再生中のバッファがあるときだけ PLAYING)とは両立しない。この食い違いは未解決。

### 11.3 修正(製品。`lift/runtime/fle_dsound.c`。旗は足さない)

- `audio_sync`: 先頭の `if (play_count() == 0) return;` を `if (play_count() == 0 && !fle_audio_external()) return;` にした。外部の消費者(AudioWorklet)があるときは、再生中のバッファが無くても補充する(`mix_chunk` は出力を 0 で始めるので無音になる)。
- `fle_audio_next_tick`: 先頭の `if (play_count() == 0) return 0;` を `if (play_count() == 0 && !fle_audio_external()) return 0;` にした。外部の消費者があるときは、補充の締切(既存の外部の分岐)を返す。
- ネイティブと消費者が無いときの動作は変えない。切り替え点は足していない(#1352)。先読み(`FLE_AUDIO_LEAD_MS`)は変えない。
