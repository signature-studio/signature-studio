## 2. 枚数を数える方式: 選んだ物と、試して使えなかった物

- (a) `HeadlessExperimental.beginFrame`(`--enable-begin-frame-control` あり・なし): **使えなかった**。Chrome 157 の `--headless=new` に `HeadlessExperimental` のドメインが無い(`'HeadlessExperimental.enable' wasn't found`)。page の対象と、ブラウザの対象の両方で確かめた。
- (b) `Tracing`(カテゴリ `viz`、`Display::DrawAndSwap` を数える): **採用**(`presentedPerSec`)。コンポジタが画面に描いた枚数の記録。試験: 待機中の製品の page で 3 秒に 19 件(約 6 枚/秒)、動く canvas の試験(カテゴリを広げた版)で 3 秒に 182 件(約 61 枚/秒)。変化の無い枚数は出ない。ただし、page 自身の UI の再描画も入る(下の (c) との差)。

## 4. 代理の指標の意味と限界

- `cpuPerPresentMs` は、renderer プロセスの CPU 時間を、その秒の engine の提示で割った値。実機の 120 fps の予算(8.33 ms)に対する比(`budgetRatioP95`)として使う。
- 含むもの: 主スレッド(入力の処理、desk の受け取り、page の UI)、engine の Worker(guest の周と入力の処理)、render Worker(compose と put)、コンポジタ。含まないもの: GPU プロセス(別プロセス。notes に別記)、ブラウザプロセス(入力の経路とトレース)。
- 限界(推定を含む):
  - 実機には GPU がある。put(テクスチャの転送)は GPU 側で軽くなり、compose の一部も GPU 側になる。runner では WebGL2 がソフトウェア描画になる(推定: SwiftShader)。GPU プロセスは窓の間に約 57〜60 秒(約 2 コア分)を使った。この CPU は cpuPerPresentMs に入らないが、4 コアの取り合いで engine の速さに影響しうる(推定)。
  - CPU は wall 時間ではなく CPU 時間(cpuTime は 10 ms 単位。/proc のスレッドの時間も 1/100 秒の単位)。
  - 提示数は page の `deskStats` から読む(100 ms ごとに更新)ので、1 秒ごとの比には読みの誤差が ±10% 程度ありうる(推定)。p50・p95 は 30 個の 1 秒の値の分布。
  - スレッドの内訳は名前で分けた。`chrome` を主スレッドと見た(推定)。DedicatedWorker は engine と render Worker の合計で、分けられない。
- 入力の定義: 答えた提示は、入力が画面の変化を起こした物だけ。窓の中に engine へ送った入力は 14,365〜15,558 件で、答えた物は 599〜2,930 件(表 B)。画面を変えない入力(ポインタの移動だけ)には答えが無い。

## 7. 入力の届き方(#1349 に効く所)

- ポインタは 1200 Hz で送り、ページの `pointermove` は 1186〜1200 件/秒で届いた(各 1 秒の最小〜中央値。30 秒の全てが 1000 以上)。
- ページが受けた件数は 30 秒で約 36,000。engine へ送られた入力は 14,365〜15,558 件(約 480〜520 件/秒)。受けた件数の約 2.4 件に 1 件が engine へ入っている(推定: ブラウザが移動を 1 回の呼び出しにまとめて届けたと見る。呼び出しの数は測っていない)。製品の tracker は、呼び出しごとに 1 件の入力を送る。このため、1000 Hz のポインタでも、engine が受け取る入力は約半分になりうる(推定)。#1349 の 1000 Hz の道具は、この点を考慮する必要がある。
