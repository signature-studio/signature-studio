## 原因として確認できたことと修正

1. **ゲストが実行を続けるとWorkerのイベントループへ戻らず、描画要求が届きにくい。** 共有メモリの要求をゲストのスケジューラ地点で受け取るようにしました。小規模プロジェクトの連続入力では描画更新が大幅に改善しました。ただし初期の更新数はrAF周期で重複排除していなかったため、物理表示FPSとして扱いません。
2. **ファイル選択待ちがゲスト全体を止め、再生を妨げる。** 非同期の選択処理と協調的なゲスト待機へ分離しました。小規模プロジェクトの再生中にダイアログを10秒開く検証では、音声枯渇・欠落・遅延書き込みを検出しませんでした。
3. **音声データ準備前に再生状態を公開する。** バッファを準備してから再生状態へ移るようにしました。
4. **連続入力中に通常のidleへ戻らないと、仮想時計が実時間から遅れる。** 実行中のスケジューラ地点でも同期し、実測の仮想時間/実時間はほぼ1になりました。
5. 連続した保留中のマウス移動を統合しました。ボタン・キー・ホイールをまたいでは統合しません。
6. コールバック中にスレッド切り替えを延期する経路でも、公開済み音声のポーリングを行うようにしました。
7. DirectSound通知位置をサンプル境界だけに限定していた別の仕様不具合を修正しました。25件のネイティブテストが通っています。指定FLPでこのAPIが原因だったかは未確認です。

## 音切れカウンター0でも正常再生とは限らない

音声出力は続いていても、新しいPCMの生成が足りず、古いバッファを循環する場合がありました。実際のバッファは8192フレーム、書き込みは4096フレーム単位です。

各条件は単発の探索測定です。測定関数内で8秒の出力収録を開始し、20秒の測定区間と同期させました。非無音部分の左右両サンプルが8192フレーム前と完全一致する割合と、新規書き込み量/消費量を併せて確認しています。波形そのものは投稿・コミットせず、集計値だけを残します。

| ランタイム・条件 | 新規書き込み量/消費量 | 8192フレーム前との完全一致 | 音声枯渇quanta |
|---|---:|---:|---:|
| 優先度無効・切り替え深度上限1、無入力 | 0.4991 | 47.17% | 0 |
| 同上、合成入力約1249Hz | 0.05191 | 94.15% | 0 |
| 優先度有効・深度上限2の実験、無入力 | 0.9990 | 1.63% | 0 |
| 同実験、合成入力約1249Hz | 0.8636 | 4.97% | 0 |

変更前の無入力では遅延書き込み損失も15,702フレームありました。深度2の実験では両条件とも枯渇・欠落・遅延書き込み損失は0でしたが、入力中の生成不足は残っています。

これは古いPCMの再利用を強く示す結果です。ただし、ループ音源ではバッファ再利用自体が正しい場合もあるため、書き込み比率だけで音声の正しさを判定しません。完全なプラグイン構成と実際の出力の検証が必要です。

## 実験中の変更と安全性

通常のブラウザ起動経路では、保存されたスレッド優先度がスケジューラで無効でした。また、通常のウィンドウ処理はコールバック深度2に入り、疑似プリエンプションを抑止していました。これらが音声生成不足に関係しています。

ただし、深度2を全面許可すると、hook chainの共有状態やtimer queueのslot再利用などに再入の懸念があります。**全面許可版は最終版として採用しません。** 現在、深度1からの`DispatchMessageW`のWndProc/TIMERPROC呼び出しだけを許可し、深度3以上や他のコールバックは保護する版を準備しています。レジスタ・SIMD・フラグの保存復元と、別スレッドへ許可状態を引き継がないテストを含め、関連ネイティブテスト79件が通過しています。実際のDispatch経路の追加検証も進めています。

サイズ優先のwasm最適化を速度優先へ変える比較も実施中です。wasmは約169MBから約189MBへ増え、キャッシュ済みの起動でfirst pixelは約5.7秒でした。連続入力中の新規書き込み量/消費量は約0.758、同一波形の一致は約30.1%で、今回の単発比較では改善しませんでした。採用を見送る方向です。

## 目標に対する現在地

- **P3: 未達・評価制限あり。** 指定FLPではFruity Wrapper、FLEX、Frequency Shifter、Soundgoodizer、Fruity Parametric EQ2の5種類が開けません。サンプル不足警告はありませんが、完全な曲としての合格判定はできません。Serum側の個別ビルド工程も復旧中で、最初のimport解析・生成工程は実DLLで動作しました。個別wasmを背景ロードする方針を維持し、メインwasmへの一括組み込みで済ませないようにします。
- **P2: 継続操作での合格は未確認。** 深度2実験の再生中canvas更新は無入力約37.8回/秒、合成MOVE約45.5回/秒でした。ただし、画素変化の少ない条件の更新数をUI全体の最大FPSとは見なしません。通常DOMポインター経路の短い操作では120回/秒超の更新も記録しましたが、直近20件の入力→rAFはp95約39msで17ms基準を超えています。物理表示の120fpsを証明したものではありません。
- **P1: キャッシュ済みではfirst pixel約5.5〜5.9秒。** 初回取得を含む起動と、起動10秒時点で操作・再生なしの音声途切れ0は、最終構成で再検証が必要です。

## 次の方針

1. 安全な呼び出し点に限定した切り替え版を実FLPで比較し、音声生成とGUIの両方を確認します。
2. 速度優先最適化と、出力を変えない描画計算の削減を別々に測ります。小さなベンチマークで効果がなければ採用しません。
3. 欠落プラグインの個別ビルド・接続を進め、完全な評価条件に近づけます。
4. 一時診断の出力を外した構成で、連続再生、継続した通常入力、起動を再検証します。音声枯渇0だけを合格条件にしません。

検証済み修正と計測コードは作業ブランチの[`5b3934ef`](https://github.com/signature-studio/signature-studio/commit/5b3934ef)までpush済みです。スケジューラ・描画・最適化の実験差分は未採用です。追加調査の手順と詳細はリポジトリ外の`[リポジトリ外のメモ]`にも記録しています。約24時間の継続作業の指示を維持し、引き続き改善と検証を進めます。
