## 5. 区間 1 と区間 2〜5 の食い違い(確かめた結果)

## 6. 切り替え点の場所・方式・理由

- 場所: Blend2D の塗りの行ループ(上流の `src/blend2d/pipeline/reference/fillgeneric_p.h` の 4 か所。`FillBoxA_Base` の 2 本の `while (h)`(不透明・マスク)、`FillMask_Base` の走査線の `for (;;)`、`FillAnalytic_Base` の `L_Scanline_Init`)。パッチは `lift/harness/b2d1/b2d4-tick.patch`(新規)。`fe-build` の Blend2D の段で、`b2d3-compop.patch` の後に当てる。
- 方式: `fle_b2d_tick(units)`(`lift/harness/b2d1/b2d_swap.cpp`)。units は行の幅に比例(px / 128 + 1)。`fle_loop_count` に units を足し、`fle_loop_limit` に届いたら `fle_loop_slice()`(既存の後ろ向きの分岐の切り替えと同じ関数)。
- 占有: Blend2D の入口(`fle_swap_*` の 18 本)で `B2dEntry`。他のスレッドの呼び出しは、占有中の塗りが終わるまで `fle_thread_switch()`(譲る)で待つ。Blend2D の状態はランタイムの中にあるため、途中の切り替えで別のスレッドが入らないようにする。
- 理由: Blend2D の塗りは 1 回で数十〜百数十 ms 続き(実測の区間 173.7 ms、前段の 68〜75 ms)、その間に補充が出ないと、+10 s までの underrun になる(基の版で 17〜35。実測)。コールバックの中(深さ 2 以上)では、切り替えは音声の補充だけ行う(既存の規則。窓の手続きの中の塗りでも補充が出る)。
- 仮想時計: 進めない(`fle_loop_slice` は進めない)。計数の粒度(`FLE_LOOP_SLICE_BACKEDGES` 1,024)は変えていない。units の換算だけ(1 単位 = 128 px 程度)。決定 0147・0279 との関係: 仮想時計の進む速さは変わらない。
- 設計との関係(推定): `fle_progress_slice` の説明は、切り替えはゲストのコードからだけ行い、ランタイム関数の途中では行わない、としている。Blend2D の塗りはランタイム関数なので、この切り替え点は設計の前提の外。占有で、他のスレッドの Blend2D 呼び出しを待たせることで補う。占有の外の共有状態(BLContext 以外)は未確認。
- 占有で止まりが増えたか: 90 起動で 0 件(実測)。受け入れの条件は満たす。「ロックを持たない区間に限る」案は、止まりが増えた時の代替として残すが、今回は採らなかった。
