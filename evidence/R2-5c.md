## 4. 結論(事実の並べ)

(i) 読めたこと
- 元の trace は旧ワークツリーに残っている。13,572 呼び出し、171 種(実測と `a4-six-module-executed-apis.txt` 1 行目の記述が一致する)。
- seq 5219 の GetProcessDpiAwareness は、FLEngine の間接呼び出し(guest-ind)で、戻り値 0。直前の seq 5218 が shcore の GetProcessDpiAwareness の擬似 VA を返している。
- seq 5219 は、最初の CreateWindowExW(516)より後、最初の GetDeviceCaps(299)より後にある。
- GetDpiForMonitor・MonitorFromWindow・MonitorFromPoint・SetProcessDpiAwareness・SetProcessDPIAware・GetDpiForWindow・BeginPaint・ShowWindow は、この trace に 0 件。

(ii) 読めなかったこと
- 最初の idle と、seq 5219 の前後関係(idle の印が無い)。
- MonitorFromWindow と GetDpiForMonitor の前後関係。両方とも 0 件のため、0144 の「MonitorFromWindow の直後」の呼び出しは、この trace では確かめられない。
- この trace は native の lift 実行の記録で、Windows 上の FL の記録ではない。そのため、FL が Windows で DPI を問い合わせる時刻は読めない。
- 旧 trace-report の「GetProcessDpiAwareness=UNAWARE(0)」の記述は、trace の応答値 0 の解釈であり、Windows の値との照合ではない(同 0 節 17 行目)。この記録では根拠に使わない。

(iii) 次に何があれば読めるか(名前だけ)
- idle の印を含む呼び出しの記録
- MonitorFromWindow と GetDpiForMonitor を含む呼び出しの記録
- 実機 Windows 上の FL の呼び出しの記録
