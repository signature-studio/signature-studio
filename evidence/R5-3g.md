## 1. `.pdata` の項目(実測。python3 の `struct`)

- ImageBase 0x400000、SizeOfImage 0x18c0000、`.pdata` は RVA 0x1607000・サイズ 0xa9620(57816 項目)。
- RUNTIME_FUNCTION の begin・end は RVA。VA = RVA + 0x400000。
- `R5-3f` 5.2 の「`.pdata` 0x5dfba0〜0x5dfc47」は VA で、RVA では 0x1dfba0〜0x1dfc47。

| 項目 | begin RVA(VA) | end RVA(VA) | 注 |

## 2. 逆アセンブル(実測。`objdump -d -M intel`。各箇所 20 行以内)

### 2.1 関数 0x5dfba0 の先頭

```
5dfba0: push rbx
5dfba1: sub rsp,0x20
5dfba5: lea rcx,[rip+0x9c]        # 0x5dfc48
5dfbac: call 0x4235b0
5dfbb1: mov rbx,rax
5dfbb4: test rbx,rbx
5dfbb7: je 0x5dfc41
5dfbbd: mov rcx,rbx
5dfbc0: lea rdx,[rip+0x95]        # 0x5dfc5c
5dfbc7: call 0x4235f0
5dfbcc: mov QWORD PTR [rip+0xdfa36d],rax   # 0x13d9f40
```

- `lea rcx` の番地は 0x5dfba5(`push rbx` の 1 バイトと `sub rsp,0x20` の 4 バイトの後)。命令は 7 バイトなので、次の番地は 0x5dfbac。参照先 = 0x5dfbac + 0x9c = **0x5dfc48**(python3 で計算。実測)。0x5dfc48 は UTF-16LE の `ole32.dll`(python3 で読んだ)。
- 0x5dfba0 から 7 バイトの命令とした前提(reviewer の指摘)は、この命令の番地と一致しない(実測)。

### 2.2 書き込み 0x5dfbe2 の周辺

```
5dfbd6: lea rdx,[rip+0xa5]        # 0x5dfc82
5dfbdd: call 0x4235f0
5dfbe2: mov QWORD PTR [rip+0xdfa35f],rax   # 0x13d9f48
```

- `lea rdx` の参照先 0x5dfc82 は、UTF-16LE の `CoInitializeEx`(python3 で読んだ)。0x5dfc82 は**名前の文字列の番地**で、命令ではない。
- 0x5dfbe2 の store は、直前の `call 0x4235f0`(0x5dfbdd)の戻り値を P(0x13d9f48)に入れる(実測の命令列)。

### 2.3 0x5dfc50〜0x5dfc90 の範囲

- この範囲は UTF-16LE の文字列データで、命令として読むと意味が無い(実測の逆アセンブルの出力)。0x5dfc5c の `CoCreateInstanceEx`・0x5dfc82 の `CoInitializeEx` などは、この範囲にある文字列。

### 2.4 関数の後半(実測)

```
5dfc0e: mov QWORD PTR [rip+0xdfa343],rax   # 0x13d9f58
5dfc24: mov QWORD PTR [rip+0xdfa335],rax   # 0x13d9f60
5dfc3a: mov QWORD PTR [rip+0xdfa327],rax   # 0x13d9f68
5dfc46: ret
```

### 2.5 0x4235f0(`GetProcAddress` へのラッパー。実測)

```
4235f0: push rbp ... (引数を [rbp+0x20] と [rbp+0x28] に保存)
42360d: shr rax,0x10
423611: test rax,rax
423614: jne 0x423629        # rdx の上位 16 ビットが非 0 = 文字列
423629: lea rcx,[rbp+0x38]
423634: call 0x4139f0       # 文字列の長さを数える(読み)
423639: mov rcx,QWORD PTR [rbp+0x38]
42363d: call 0x414000       # 中身は未確認
423649: call 0x4235e0       # jmp [IAT] = kernel32!GetProcAddress(objdump -p で確認)
42364e: mov QWORD PTR [rbp+0x30],rax
42365c: mov rax,QWORD PTR [rbp+0x30]
```

- `0x4235f0` は、呼び出し先の結果(`rax`)を `[rbp+0x30]` に入れ、そのまま返す(実測)。したがって、P に入るのは `GetProcAddress` の戻り値。
- `0x4235e0` の `jmp QWORD PTR [rip+0x154e01a]` は、VA 0x1971600 = RVA 0x1571600 の IAT(`objdump -p` の `GetProcAddress`。実測)。
- `0x4235b0` の `jmp` は VA 0x1971368 = RVA 0x1571368 の IAT(`objdump -p` の `GetModuleHandleW`。実測)。

### 2.6 呼び元と間接呼び出し(実測)

- `0x1331c80` は、P の値を確かめずに `call [rax]` する(実測の命令列。P と 0 の比較は無い)。`xor ecx,ecx; mov edx,2` は `CoInitializeEx(NULL, COINIT_APARTMENTTHREADED)` の形(読み)。

## 5. P に入る値の出どころ(読めた範囲)

- P に入るのは `GetProcAddress` の戻り値(2.5 の実測の命令列)。
- `lift/runtime/fle_modules.c` の 467〜476 行(実測): 応答表 `fle_resp_table` に `(dll, name)` の行があれば `va` を返す。無ければ `FLE_ERROR_PROC_NOT_FOUND` を立てて `R[0] = 0` を返す。
- `fle_resp_table` の行の出どころ(実測): `lift/crates/fe-lift/src/imports_table.rs` の 837〜867 行。`TABLE`(同ファイル内の行)と、`fe-lift lift ... --extra-imports` で渡すファイルの行の和。`R5-3f` 5.3 は応答表を seed の行から作られるかを未確認としていた。この読みでは、`imports_table.rs` の `TABLE` と `--extra-imports` の行が出どころで、seed は後者の入力になりうる物(読み)。
- `CoInitializeEx` の行の有無(実測):
  - `imports_table.rs` の `TABLE` に `CoInitializeEx` は無い(`expire_grep` の `ole32` の行は `CoInitialize`・`OleInitialize` など)。
  - リポジトリの `*.txt` で `CoInitializeEx` を含む物は 0 件。
  - `lift/` で `CoInitializeEx` を含むのは、`lift/runtime/fle_ole.c` の注釈(40・43・69・378 行)、`lift/crates/fe-lift/tests/wall_fr11.rs` の注釈、`lift/harness-docs-tools/alpha1/gen-wrap.py` の 24 行(`'CoInitializeEx': 'NONE'`。役割は未確認)。
- 読み: 上の応答表に従えば、`GetProcAddress("ole32.dll", "CoInitializeEx")` の戻り値は 0 で、P にも 0 が入る。すると 2.6 の `call [rax]` は 0 番地を呼ぶ。`R5-3f` 5.5 の 4 番の読みと同じ。
- 未確認: 実際に走ったビルドの応答表(どの `--extra-imports` を使ったか)。P の実行時の値。

## 6. R5-3f の疑い(reviewer の項目 4)の結果

- (a) 5.1 と 5.2 の番地
  - 「P への書き込みは 0x5dfbe2 の 1 件」: 一致(3 節の `expire_grep`)。
  - 5.2 の「`CoInitializeEx` の結果の格納先 P を 0x5dfc82 に置く」: 記述の誤り。0x5dfc82 は文字列の番地で、P への store は 0x5dfbe2(2.2 の実測)。
  - 5.2 の箇条書きで「呼び出しの番地」として挙げた 0x5dfc5c・0x5dfc82・0x5dfca0・0x5dfccc・0x5dfcfa・0x5dfd24: 誤り。これらは文字列の番地。呼び出しの番地は 0x5dfbc7・0x5dfbdd・0x5dfbf3・0x5dfc09・0x5dfc1f・0x5dfc35(2.1 と 4 節の実測)。
  - 5.2 の関数範囲「`.pdata` 0x5dfba0〜0x5dfc47」: 一致(1 節の実測)。
  - 「0x5dfc5c〜0x5dfd24(6 つの GetProcAddress 呼び出し)はその範囲の外」: 文字列の番地としては範囲の外で一致。ただし 6 つの呼び出しは範囲の内(0x5dfbc7〜0x5dfc35)。記述の誤り(文字列と呼び出しを取り違えた)。
- (b) `lea rcx` の参照先: 一致(0x5dfc48)。reviewer の前提(0x5dfba0 から 7 バイト)は、この命令の番地と一致しない(2.1 の実測)。
- 項目 7: 6 つの関数名の割り当ては、文字列の読み(4 節)。`R5-3f` 5.2 の「実測の読み」は、命名の部分では強すぎる。
- 項目 8・9: `R5-3f` 本文の 16 進のバイト列と、ホームのパスは、本文に残してある(本文は書き換えていない)。先頭の注で場所を書いた。
- 項目 10: 「CoInitializeEx の結果が P に入る」は、番地の面では解けた(4 節)。P の値の出どころは 5 節のとおり、読みのまま。
