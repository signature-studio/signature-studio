## 1. `guest return` の意味(読み)

- `lift/harness/fruity.c` 576 行: `printf("fruity:   caller chain #%llu: %s (guest return %#llx)\n", ...)`。`trace_frame` が取った戻りアドレスをそのまま出す。
- `lift/runtime/fle_modules.h` 19 行: `FLE_EXE_HANDLE` は `UINT64_C(0x400000)`(ImageBase。`lift/runtime/fle_modules.h`)。
- `lift/runtime/fle_dispatch.h` 36〜40 行: `fle_dispatch_miss(uint64_t va)` が `indirect call to %#llx is not a known function entry` を出す。この `va` は ゲストの VA。
- `lift/crates/fe-lift/tests/census.rs` 282・285 行: `indirect call to 0x1100400 …`(import の擬似 VA)と `indirect call to 0 …`(null)の期待値(実測)。

よって、`guest return 0x1331c94` はゲストの VA と読める。RVA と読むと `.bss`(RVA 0x11e6000〜)に入るので、VA と読む方が、この PE の配置と合う(読み)。

## 2. PE の表(実測)

コマンド: 22 行目までの Python で `struct` から PE ヘッダを読んだ(ファイルオフセット 0x100 の `PE\0\0`)。

- machine 0x8664(x64)、optional header 0x20b(PE32+)、ImageBase 0x400000、エントリ RVA 0xf76820、セクション 10 個。
- 主要なセクション(VA・仮想サイズ・RawPtr・RawSize):

| セクション | VA | VSize | RawPtr | RawSize |
|---|---|---|---|---|
| .text | 0x1000 | 0xfa34b0 | 0x400 | 0xfa3600 |
| .data | 0xfa5000 | 0x240008 | 0xfa3a00 | 0x240200 |
| .idata | 0x156f000 | 0x670e | 0x11e3c00 | 0x6800 |
| .reloc | 0x157a000 | 0x8c590 | 0x11ebe00 | 0x8c600 |
| .pdata | 0x1607000 | 0xa9620 | 0x1278400 | 0xa9800 |

- 戻りアドレス 0x1331c94 の RVA は 0x1331c94 − 0x400000 = **0xf31c94**。これは `.text`(0x1000〜0xfa44b0)の中。
- 0xf31c94 のファイルオフセットは、0xf31c94 − 0x1000 + 0x400 = **0xf31094**(`.text` の RawPtr と VA から換算。読み)。

- 関数は `.pdata` の RUNTIME_FUNCTION(0xf31c80〜0xf31cb0、RVA。VA では 0x1331c80〜0x1331cb0)に入っている(実測。Python で `.pdata` を読んだ)。

## 4. 呼び先の形と由来

### 4.1 呼び先の形(読み)

- `rax = [0x15e0fb8]`(`mov rax, [rip+0x2af326]`)。このスロットの VA は 0x19e0fb8(ImageBase + 0x15e0fb8)。
- `call [rax]` は、`[0x15e0fb8]` に入っている値を呼ぶ。値が 0 なら、戻りアドレス 0x1331c94 を積んだまま 0 番地へ飛ぶ。停止 message の `indirect call to 0` と合う(読み)。
- 呼び先の引数は `ecx = 0`、`edx = 2`。この関数の後の `test eax,eax`・`cmp eax,1`(`S_FALSE`)・`cmp eax,0x80010106`(`RPC_E_CHANGED_MODE`)という比較から、`CoInitializeEx(NULL, COINIT_APARTMENTTHREADED)` の形に見える(読み。`lift/runtime/fle_com.h` 14 行で `FLE_HR_RPC_E_CHANGED_MODE` が定義されている)。確定ではない。

### 4.2 スロットの由来(実測と未確認)

- `0x15e0fb8` は IAT(0x15709c8〜0x1572198、データディレクトリ 12。実測)の外。遅延ロード表(データディレクトリ 13。17 個の DLL。実測)のどの IAT の slot とも一致しなかった(実測)。
- `0x15e0fb8` は `.reloc` セクション(0x157a000〜)の仮想範囲に入っている(実測)。ただし、再配置ブロックのページ 0x15e0000 の項目は見つからなかった(実測)。`.reloc` の仮想範囲と、スロットの値の関係は未確認。
- 逆アセンブル全体で `# 0x15e0fb8` を rip 相対で参照する命令は、0x1331c8b の 1 件だけ(実測。`objdump -d | grep "# 0x15e0fb8"`)。
- 同じスロットへの**書き込み**(`mov [rip+…], reg`)は、逆アセンブル全体で見つからなかった(実測)。
- 絶対アドレス 0x19e0fb8 を即値で持つ命令も 0 件(実測)。
- 逆アセンブル全体のうち、`CoInitializeEx` の文字列は DLL の中に 0 件(実測。`d.count(b'CoInitializeEx\x00') = 0`)。`CoInitialize`・`OleInitialize` は各 1 件。
- よって、このスロットに入る関数の名前は、この DLL のコードからは確定できなかった(未確認)。スロットの値が何で埋まるかも、この読みでは確定できなかった(未確認)。

### 4.3 呼び元(実測と読み)

- `0x1331c80` を直接呼ぶ `call` は 1 件: `0x1334c20`(`e8 5b d0 ff ff`、`call 0x1331c80`)(実測。E8 の全走査)。
- 呼び元の関数は VA 0x1334be0〜0x1334c73(`.pdata` の RUNTIME_FUNCTION。実測)。
- 呼び元の先頭(0x1334be0〜0x1334c20)は、`[rbp+0x58]`(フラグ)で `call 0x410320` と `call 0x134b720` を条件付きで呼び、`mov BYTE PTR [rax+0x30],0x0` の後に `call 0x1331c80` を呼ぶ形(読み)。
- 呼び元の関数の内側には、rip 相対で参照する文字列がなかった(実測)。

### 4.4 名前の応答表(読み)

- `lift/runtime/` に `CoInitializeEx` の名前の応答(GetProcAddress の表の行)は見つからなかった(実測。`expire_grep` で `"CoInitializeEx"` を検索。一致は `lift/harness-docs-tools/alpha1/gen-wrap.py` 24 行(生成補助のリスト)と、`fle_ole.c` の注釈だけ)。
- ただし、この関数の呼び出しが `CoInitializeEx` だとは、上の 4.2 で確定していないため、応答表の欠落が原因かどうかは判断しない(未確認)。
- `lift/runtime/fle_modules.c` は、`ole32.dll` を仮想モジュール表に持つ(実測。29 行)。`GetProcAddress` の応答表の行の検索は、この記録では行っていない(未確認)。
