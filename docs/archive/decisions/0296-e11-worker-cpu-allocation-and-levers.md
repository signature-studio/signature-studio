## 4. 仮想 s/実 s に要る削減率(式)

### 4.1 式(当て嵌め)

Worker が idle なのは**全ゲスト thread が眠っているとき**で、そのとき仮想時計は実時間と 1:1 で進む(IdleDriver の deadline 待ち)。稼働中の仮想時計は課金(スライスごとの 2,500 ticks)でしか進まない。よって

- **v = c·b_s + I**(c = charge÷run、b_s = スライスの CPU の割合、I = idle の割合)。0278: E9 の c = 0.483(測定)、稼働 0.876、idle 0.124(測定)で、b_s を E11 の割合(稼働の 89%)で借りると v ≈ 0.49(測定 0.55、b_s は借り物の推定)。E11 の c は**未計測**(pst の run が無い)。v・b_s(0.76 = 稼働 0.856 − JS 0.031 − (program) 0.064)・I(0.144)から暗黙値は 0.57。
- idle の割合 I と v の比が一定: **I = s·v、s ≈ 0.265**(E10: 0.1415/0.505 = 0.280、E11: 0.1443/0.575 = 0.251、プールして 0.265)。= **ゲストが自分の仮想時間の約 26.5% は眠っている**。窓 30〜50 s の v を idle から予測すると E10 0.534(測定 0.505、+6%)、E11 0.545(測定 0.575、−5%)。10 s 窓ごとに見ると外れが大きい(50〜60 s は idle 0.117 → 0.44、測定 0.71)ので、**全体の傾向の当て嵌めで、窓ごとの予測式ではない**。
- **他のビルドでの検算**(0278 の 60 s の series A/B。Worker CPU ÷ 壁 から idle = 1 − 値): E8(課金 10,000 ticks/スライス)は **v = 1.01 のとき idle 0.232 / 0.245**(s = 0.23 / 0.24)、E9 は v = 0.54 / 0.56 のとき idle 0.125 / 0.123(s = 0.23 / 0.22)。= **s は E8〜E11 で 0.22〜0.28(4 ビルドの平均 0.247)**。E8 は『v = 1.0 を実際に取れていて、そのとき idle が約 23%』の実例(ただし r = 0.40 で音を大きく諦めていた)。
- 結論: **v = 1 は『idle ≈ 22〜28% かつ稼働 ≈ 72〜78%』のときだけ**(中央 s = 0.265 で 26.5% / 73.5%)。c を上げても(課金を重くしても)v は上がる代わりに r が落ちる(0281: E7b は v = 1.0 で r = 0.33)。**課金の定数は (v, r) の組を動かす梃子ではなく、CPU の削減だけが両方を上げる**。

- **N1 に対して wasm(E11)は約 2 倍速い**(ミキサー 0.43〜0.49、Elastique の計算カーネル 0.22〜0.65)。PM の基準(2〜3 倍なら取れる余地が小さい、10 倍近いなら構造的な余地)に当てると、**N1 との比では『wasm が速い側』なので、生成の形・窓検査の置き方に構造的な余地は見えない**(0276 の結論と同じ向き: 直 wasm の計算カーネルは 0.3〜0.5)。

### 9.3 測れなかった物とその理由(1 行ずつ)

- **N1 の新しい CPU 時間(`CLOCK_THREAD_CPUTIME_ID`)の run**: N1 のバイナリを 0291 の後始末で消した。再 build(生成 C の clang -O2、188 MB)は他の build と重なり約 1 時間以上の見込みで、既存の 2 ms CPU 時間標本が同じ量(thread の実 CPU)なので並べ直しにした。
- **実 x86 の native(Wine 上の FL Studio)の thread 別 CPU**: この機械に Wine 10.0 はあるが FL Studio の prefix が無い(インストーラ `flstudio_win64_26.1.7.5653.exe` は `~/ダウンロード` にある)。実行には Xvfb・無音でない実時間の音声 device(PulseAudio の null sink 等)・FL のライセンス/起動の確認が要り、thread 別の CPU は `/proc/<pid>/task/<tid>/stat` で取れるが、**今回の枠(1 時間)では着手していない**(PM が必要なら別の担当に出す)。`perf` は `kernel.perf_event_paranoid = 4` で使えない。

### 12.2 Wine による実 x86 の thread 別 CPU の測定の方法メモ(PM 15:40 の依頼、5 行。**未検証のメモ**で、私は走らせていない)

1. 準備: `~/ダウンロード/flstudio_win64_26.1.7.5653.exe` を `WINEPREFIX=/tmp/…/wineprefix wine <exe> /S`(NSIS の silent。インストール先は `/D=` で指定)で入れる。参照プロジェクト `serina1-serum2.zip` を展開し、欠ける Serum 2 は入れない(lift の run と同じく『欠けたプラグインの窓』を Enter で閉じる)。

3. 音声: FL のミキサー thread は音声 device の消費で進むので**実時間で消費する device が要る**。`pipewire` と `pw-cli` が入っている(pulseaudio は無い)ので、PipeWire の `support.null-audio-sink` を既定の sink にして Wine の winepulse(または winealsa + pulse plugin)で出す。ALSA の `type null` は実時間で消費しない(CPU の速さで捨てる)ので不可。
4. 計測: `wine FL64.exe <flp>` の PID の `/proc/<pid>/task/<tid>/stat` の utime+stime(14・15 番目、CLK_TCK = 100)を 60 s の再生の前後で読み、thread ごとの CPU 秒を出す。ミキサー thread は最大の CPU の task。1 ブロック = 4096 フレーム ÷ 44100 = 92.88 ms なので、音声の再生時間 ÷ 92.88 ms がブロック数。(`perf` は `kernel.perf_event_paranoid=4` で不可。)
5. 注意: 1 コアに固定(`taskset -c N`)・nice・他の Chrome 測定との重なりは許容、起動の最初の 20 s は除く。Wine の `Sleep(1)` の周期とミキサーの待ちで CPU が 100% にならないので、CPU 秒 ÷ ブロックで読む(wasm の 45.1 ms/ブロックと同じ定義)。
