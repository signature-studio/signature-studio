## (b'') の定義(出典なしの選択 S-p2-steady)

(b') は「ダイアログ無しの安定アイドル」(決定 0129。新しい関数入口が出ない)で、計装が要る。ここで使う **(b'')** = 次をすべて満たす走行の部分:

1. **フレームが周期的に回る**: 5 秒ごとのサンプルで、フレーム数(ゲストの `timeGetTime` の呼び出し数。フレームの数え方は下の S-p2-frame)が毎区間 > 0 で、仮想時計がフレームあたり 16 ms ずつ進む(`fps_virtual` = 62.5)。
2. **面が収束する**: 生きている全ウィンドウの面の SHA-256(RGBA、A=255)が、**連続 20 サンプル(100 秒)以上**同一。
3. **窓表が収束する**: `fle_win_table_report` の全文の SHA-256 が同じ区間で同一。
4. **メモリが増えない**: wasm は `memory.grow` が起動後に 0 回(線形メモリ一定)、native は RSS が収束後に増えない(実測: 収束後の RSS は収束時の値以下)。
5. 名前付きの停止が無い(時間切れは停止に数えない)。

「何も起きない」(エンジンが止まる = 従来の idle 停止)は別の状態で、**(b-idle)** と呼ぶ(スレッド 0 が WaitMessage で空キュー、かつ時計を動かさない)。F1 の wasm の idle は (b-idle) で、(b'') ではない。**撤回条件**: 面や窓表が「周期 N のくり返し」(アニメーション)になる走行が見つかったら、2・3 を「周期 N の列」に直す。今回の実測は周期 1(定数)だった。

## wasm -Oz のスレッド C スタック(新しい停止。実測。G3 担当の実測と PM の追記を受けて 8 MiB を測り直した)

**事実(実測)**: wasm -Oz(SEH 有り)を idle フック無しで走らせると、スレッド 2 の最初の重い描画フレームで次のメッセージで停止する(`fle_thread_wasm.c`):

`fle: scheduler: the canary at the low end of the shadow stack of thread 2 was overwritten (at a switch away from the thread): the C frames of the thread are deeper than 1048576 bytes`

| スレッドの C スタック領域(`FLE_THREAD_WASM_CSTACK_BYTES`) | wasm -Oz の結果(Chrome、runtime -O2 または -O0) | wasm -O2 |
|---|---|---|
| **1 MiB(既定)** | **停止**。サンプル #5、壁 34 s、フレーム 72(3 走行で同じ: rt -O2、rt -O0、1 MiB の対照)。メッセージ上の深さは 1,048,576 B | 706 s 走る(停止なし) |
| 2 MiB | **停止**(サンプル #6、壁 38.8 s、フレーム 77) | 未測定 |
| **3 MiB** | 200 s 走る(停止なし、収束まで) | 未測定 |
| 4 MiB | 330 s 走る(収束) | 未測定 |
| **8 MiB**(G3 担当が使った値) | 260 s 走る(停止なし、`jserrors` 空、収束前後とも。この走行は別の Chrome と同時だったので fps は 0.93〜0.95 と低い) | 未測定 |

- **どの深さか**: Oz のスレッド 2 の最大の C フレームの深さは **2 MiB より大きく 3 MiB 以内**(上の閾値から。**実測の範囲**)。-O2 は 1 MiB 未満。つまり同じ呼び出しで -Oz のフレームは -O2 の 2 倍以上深い(Oz は inlining と stack slot の統合が少ないという読み。コンパイラの出力は見ていない)。
- **どの関数か**: **特定できていない**。canary は「スレッドを切り替えるとき」に検査されるので、壊した関数は分からない。停止は**スレッド 2 の最初の重い描画フレーム**で起きる(フレーム差分の記録で call 72 = スレッド 2 の呼び出しに初めて大きな変化が出る所。サンプル #5 のフレーム 72)。その描画は IPP の Warp(`ippiWarpAffineQuad_8u_C4R` → `f_351b5a0`、前の節)なので、その経路が深い(読み)。
- **native との違い**(読み + ヘッダの定数): native のゲストのスレッドは**ホストの C スタック `FLE_THREAD_CSTACK_BYTES` = 16 MiB**(`fle_thread.h` 44 行)で走る。wasm は JSPI の別のスタックに載せ、C フレームは malloc した**シャドウスタック領域 `FLE_THREAD_WASM_CSTACK_BYTES` = 1 MiB**(決定 0124 の W1。出典なしの選択)に置く。native -O2 が 1,180 秒問題なく走ったのは 16 倍の余裕による(native の深さ自体は測っていない)。
- **JSPI のスタックとの関係(決定 0124)**: 2 つは**別の上限**。(a) シャドウスタック領域(スレッドごと 1 MiB。超過は切り替え時の canary 検査 = 今回の停止)。(b) JSPI の中断スタック(スレッドごと。984 kB で toy のフレーム 8,042 段。超えたスレッドだけが `RangeError` でスレッド番号つきで失敗)。**今回の停止は (a)**。(b) の `RangeError` は、-Oz 8 MiB(260 s)・-Oz 4 MiB(330 s)・-O2(706 s)のどの走行でも出ていない(ページの `jserrors` が空)。実エンジンの JSPI スタックの深さは**未測定**のまま(wasm の呼び出し段数は測っていない)。
- F1(決定 0137)の -Oz バンドルは idle フック(`fruity_idle.c`)が仮想時計を凍結するので、スレッド 2 が描画のフレームに入る前に止まっていて、**この停止にまだ当たっていない**(私の stock の -Oz 走行も idle まで行って 15〜20 秒保持して終了、停止なし)。入力(G3)や時計の駆動で idle の先に進むと当たる(G3 担当の実測でも落ちた)。
- **線形メモリ(最終)**: 1 MiB 975,110,144 B、3 MiB 969,867,264 B、4 MiB 1,078,263,808 B、8 MiB 1,082,195,968 B(260 s 時点)。領域の数と malloc の配置で決まるため、サイズに比例しない(読み。領域の数は確認していない)。8 MiB でも 2 GiB の上限に対して約 53%。
- **既定の変更(PM が許した 1 行)**: 定数は `lift/runtime/fle_thread_wasm.h` の `#define FLE_THREAD_WASM_CSTACK_BYTES (1u << 20)`(`fle_thread.c` ではない。`#ifndef` で守られていて `-D…` でも上書きできる)。8 MiB にするなら `(8u << 20)`。**私は変更していない**: wasm 専用の定数で native のオブジェクトは変わらない(`fle_thread_wasm.c` は native では空。Rust のテストに参照は無い = grep)が、通しのテストを走らせる時間が無く、G3 担当が `RT_EXTRA_CFLAGS` で同じ効果を得ているため。入れるなら、wasm のビルド(-Oz と -O2)で 600 秒走ることを確認する。
- 対処の候補: (a) 8 MiB(上)、(b) -Oz をやめて -O2(1 MiB で走る)、(c) スレッドごとの量の見直し(thread 0 は別のスタック、他のスレッドの深さは未測定)。

## PM の未決の点

1. **速い経路を採るか**: native -O2・計装なしを壁探しの標準にする案。ビルド約 28 分(1 回)。壁の修正は runtime のリンクし直しで 1〜2 分。ただし**入口数が使えない**ので、a4 の 942/942・895/895 の確認と gencmp は従来の計装ありで行う。生成 C を変える壁(`imports_table.rs` の行)は、変わった単位だけの再コンパイルを足す必要がある(今回は実行していない)。
2. **(b'') の定義の採否**(上)。決定 0129 の (b') は計装が要るので、最適化版では (b'') を使う提案。
3. **wasm の idle の方針(G3)**: 今の idle フックは時計を凍結するので画面が動かない(idle の面 `721b792e`)。時計を進めると、**スレッド 6 の 16 ms ティック**ごとにスレッド 2 が IPP の描画を 1 フレーム計算するが、wasm -O2 で **1.6 フレーム/秒**(実時間の 1/38)しか出ない。UI をアニメーションさせるには、(i) 描画を速くする(収束後の CPU の 67.6% は `fle_mx_*` の浮動小数点のソフトウェア実装(上)。実機の浮動小数点 / SIMD128 への置き換えが最大の梃子。IPP のホスト側の置き換えは「偽りが増える」(seh2 の (D)))、(ii) 時計を実時間より遅く進める(UI が 1/25〜1/38 の速さで動く)、(iii) 描画を間引く(ゲストの挙動に手を入れる)の選択がある。**推奨は決めない**(PM)。
4. **-Oz を使うか**: -Oz は wasm が半分(321.6 MB / brotli q11 16.3 MB)で、最初の画素が -O2 より 3 秒遅く(14.5 vs 11.4 s)、フレームが 1.4 倍遅く(893 vs 640 ms)、**C スタック 1 MiB では停止する**。-O2 は 675.8 MB / q11 26.8 MB(Workers Static Assets の 25 MiB を超える。R2 前提)。-Oz を使うなら `FLE_THREAD_WASM_CSTACK_BYTES` を 3 MiB 以上(実測の下限は 2 MiB 超、G3 担当は 8 MiB)に(`fle_thread_wasm.h` の既定値の変更。上の節)。
5. **収束した面の異常(P2)**: 調べるか。窓の重なりのクリップ(兄弟ウィンドウ、`WS_CLIPSIBLINGS`)か、再描画の順序か(読み)。調べるなら新しい調査(window model)として。
6. **決定 0132 の「次の SEH 作業」**: 壁 16 の先で SEH の送出は 2 回だけ(決定 0132)。今回 `FLE_SEH_TRACE=1` つきの native -O2 の 240 秒(669 フレーム、仮想 +9 秒)でも**送出 2 回・着地 2 回**(壁 16 の分だけ)。それ以後に走る着地を持つ関数は無い(`logs/p2/native-seh-trace-240s.err.gz`)。QFC・ILTools の着地やハードウェア例外は、今の仮想 +57 秒の範囲では必要になっていない(読み)。
