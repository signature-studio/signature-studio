## 背景

- 決定 0079 の事実（実バイト列の確認。再掲）: スタブの直前 16 バイトは `call rel32`（選択値の変数の初期化。4 通り）と 11 バイトの nop。表の添字 −1 のスロットは、434 個すべてで再配置され、値は「そのスタブの 16 バイト手前」。選択値が −1 のとき、ハードウェアは初期化の `call` に入り、nop を経てスタブに落ち、初期化された変数をもう一度読む。
- 生成 C の `switch`（`Select::Slot`）は、スロットの実効アドレス `r10 + rax*8` の値で case を選ぶ。添字 −1 のスロットが case に無いと `fle_jumptab_miss` で止まる。今回の停止の「selector 0x3363df0」はこのスロットの番地（`r10 − 8`）。

## 決定（仮）

| # | 項目 | 決定 | 区分 |
|---|---|---|---|
| 1 | 添字 −1 のスロットを case にする | 上の 4 条件がすべて成り立つときだけ、`(table − 8, スタブの先頭 − 16)` を表の最初の case として足す。case の先は他の case と同じく関数（`fn_queue`）として閉包に入る。`S − 16` の関数は `call <init>; nop` と、スタブへの fall-through（スタブの入口への尾呼び）になる | 実バイトの確認（434 スタブと 3 スタブの native 対 lifted） |
| 2 | 受理しない形 | 4 条件のどれかが欠けたら足さない。例: 前の表の最後のエントリ（別の番地）、再配置されていない値、`E9`、nop が違う、call の先が code の外。**既存の拒否の挙動は変えない**（合成 PE の S1 は slot −1 が再配置された code ポインタだが main を指すので入らない） | 設計 |

## 解釈が分かれた点

1. **認識器を変えるか、止まって報告するか**。指示は「認識器を変えるのは最後の手段。設計が大きくなりそうなら止めて報告」。判断: 変更は 1 ファイル・約 40 行、受理条件は実バイトの 4 点に限り、実行（native 対 lifted）で証明でき、既存の拒否テストは全部通る、と見て進めた。別の読み（種や注釈で −1 のスロットを与える）は、434 スタブの全部に注釈が要るので採らなかった。
2. **条件 (3) の厳しさ**: nop の 11 バイトまで固定した。434 すべてで成り立った（**実測**）ので緩める理由は無い。他のビルドの DLL では成り立たないかもしれない（その場合は従来どおり −1 で停止）。
3. **`S − 16` を「関数」にしたこと**: スタブの直前 16 バイト（`call; nop`）は元のコードでは直前の関数の後ろの詰め物の位置にある。fe-lift はそこを 1 つの関数として生成する（スタブへ fall-through）。ハードウェアの動き（スロットの値へ jmp し、nop を通ってスタブに落ちる）と同じ。

## PM の判断が要る点

1. この変更（認識器）を入れてよいか。入れない場合、6 モジュール構成の連鎖は QFC → dsp の最初の `ipps*` 呼びで止まる（実測）。
2. 他の 3 つの選択値の変数（0x4541000 以外）の初期化の `call`（`0x37e08c0` など）の中身は、この決定では読んでいない。連鎖の実行では通過した（停止なし）が、CPUID 等の応答に依存した選択（IPP の CPU 振り分け）が仮の応答に支えられているかどうかは未確認。
