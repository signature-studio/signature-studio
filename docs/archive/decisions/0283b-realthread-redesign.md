## 3. (c) FL 自身の CS での UI の待ち(0234p / 0234s)を、k=4 の校正と E9 のミキサー速度で見直した予想

**事実(0234p、非ハイブリッド、Chrome、実時間)**: CS 0x16b6aa8 は**ミキサー自身が 1 回 150〜215 ms、約 5 回/s 保持**(10 秒あたり 4〜7.7 s)。保持の 94〜95% はゲストコードの時間。**協調 1 Worker では UI がこの CS を再生中に待った回数は 0**(起動時の 5 回、合計 100 ms だけ)。実スレッド E(0234s)では **UI の CS 待ちが 85 s で 3.8〜6.1 s(366〜562 回、1 回 7〜16 ms、最長 65〜70 ms)**で、主に CS 0x16b6b20 と 0x1344e938。

**E9 の速度への見直し(読み)**: ミキサーの 1 ブロックの CPU は E5 で 78.5 ms(0276、V8 プロファイル付き)、E7b で −19%、E10(Elastique の hyb +4)と梃子(0276 の 3 つで 1.15〜1.24 倍)の後で約 52〜64 ms。保持はこの CPU の 94% がゲストコードなので、**1 回の保持 ≈ 50〜60 ms**(0234p の 150〜215 ms の約 0.3〜0.4 倍)。
- 保持の占有率 = 保持 ÷ 1 ブロックの周期(92.88 ms)= 54〜65%(r = 1 のとき)。
- UI が CS を取りに行く回数が 0234s の E と同じ 4〜7 回/s なら、1 回の待ちは『保持の残り』= 0〜60 ms の一様に近い分布 × 占有率 → **平均 15〜20 ms/回**、**待ちの合計 60〜140 ms/s**(UI Worker の 6〜14%)、**最長 50〜60 ms**。0234s の E の実測(平均 7〜16 ms、合計 45〜72 ms/s、最長 65〜70 ms)に近いか**やや悪い**(r = 1 になると占有率が上がるため。0234s の腕は r = 0.24〜0.66 だった)。
- = **120 fps(8.3 ms)を超える停止が毎秒 2〜4 回**の見込み(待ちが 8.3 ms を超える確率 = 占有率 p × (1 − 8.3 ÷ 保持) ≈ 0.6 × (1 − 8.3/55) ≈ 0.5、× 4〜7 回/s)。**再生中の UI は 120 fps を保てない**可能性が高い(読み、未測定)。
- 緩和の道: (i) UI がこの CS を取る理由(描画のロック。0234 系は『mixer の描画ロック』と呼ぶ)をゲストコードの読みで特定し、**取る頻度を減らす**(ゲストは変えられない。取る側の API〔`EnterCriticalSection` の返し方〕を変える余地は無い)。(ii) ミキサーの保持を短くする = ミキサーのゲストコードを速くする(0276 の梃子)。(iii) 実機の Windows の挙動(CS は優先度継承が無い)は同じなので、**実機の FL も同じ構造で UI が待つはず**(読み。FL 自身の設計)— つまり**実機でも起きていて、FL が許容している**可能性がある。
