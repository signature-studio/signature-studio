## 1. 方法(何をどう測ったか)

**基準 N1(native)**: HEAD 050fa43 の `git archive` から、配信中の既定の入口と同じ構成(`SHIP_PRESET=F2xH2`: prune S+M、Blend2D 置換 + b2d3 パッチ、HLE dsp、`LOWREGS_BASE=0x1000`、ship2-imports)の生成 C を `app/scripts/build-engine-bundle.sh gen resplit`(40 秒)で作った。生成 C の sha256 は配信中の SHIP2 を作った memfs1 の gen と全 7 ファイルで一致(`logs/generated-c-sha256.txt`)。これを `clang -O2 -fPIE`(計装なし、`-fno-builtin-fprintf/fputs`、runtime も `-O2`、FRUITY ハーネス、上流 Blend2D〔`b2d3-compop.patch`〕を native でビルドしたアダプタ込み)でビルドし(44 単位、5 並列で約 20 分、`native-build.sh`)、148 MB の実行ファイルを得た。**N1fc** = 同じ N1 に `-DFLE_R_FAST_COPY=1`(決定 0203)を足した物。

**基準 N2(実物の FL64.exe を Wine 10.0 + Xvfb で)**: **測れなかった**。インストーラ(`flstudio_win64_26.1.7.5653.exe`)は `/S` で Wine のプレフィックスに入った(`FLEngine_x64.dll` の sha256 が `binaries/win64/` の物と一致)が、`FL64.exe` は起動直後に「The validity of the program could not be verified. Please reinstall it and try again.」のダイアログで止まる(自己署名の検証。画面は `tables/n2-wiz0.png`)。プログラム自身の検証の偽装は禁止なので回避していない。試した時間は 約 25 分(枠は 60 分)。再生ドライバ `wine-run.py`(XTest で同じ G3 スクリプトを実時間で再生し、プレフィックスの全プロセスの CPU を取る)は作ったが、FL が起動しないので数字は無い。

**W(wasm)**: (a) HEAD 050fa43 から同じ F2xH2 で作った wasm(**V0**: 既定のビルド変数、wasm-opt -Oz、関数名つき〔`--profiling-funcs` と `wasm-opt -g`。名前の節だけが違う〕、非混成)、(b) **V1** = V0 + runtime を `-O2`(`RT_OPT=O2`)+ `-DFLE_R_FAST_COPY=1`、(c) **V2** = V1 + dsp の m1-04 ほか 4 単位を `FLE_ALWAYS_INLINE`(`AI_UNITS`)、(d) **V3** = V1 + 最も熱い 6 単位(m1-04, fle-06, fle-03, fle-02, fle-01, m3-01)をユニットの最適化を -Oz でなく -O2 で、(e) **V1H** = V1 + 混成(fe-wasmgen の直接 wasm 977 関数、ship2 の手順 `hyb.sh`)、(f) **配信中の SHIP2**(混成、runtime は HEAD より古い)。実行は node 24 の JSPI(`node-bundle-run.mjs` の写し)と、隔離 Chrome 156 の Worker。

**入力列**: `lift/harness/parity/ops.tsv`(65 操作、11 セッション)。座標は `lift/out-ia2/scripts/ops*.tsv`(1920x1080、Basic.flp を開いた状態)から借りた。G3 スクリプト(仮想時計、決定 0147/0170)で native と node に**同じ入力**を入れる。Chrome は同じ操作を CDP の実時間の入力(連続操作は 16 ms 周期 = 62.5 イベント/s)で入れる。**入力はすべてハーネスの模擬であり、依頼者の操作ではない**。Chrome の既定プロジェクトは空(Basic.flp を開く経路が無い)。
**指標**: 操作の前後の `snap` の間の CPU 秒(native = `getrusage` の user+sys、wasm = node の主スレッドの `threadCpuUsage`〔wasm が走るスレッド〕)。`snap` の末尾(16 面の SHA-256 など)も両側に入る(`cal_snap` = 33〜58 ms が目安)。仮想 1 秒あたりに直して壁時計に依存しない形にした。ゲストの進捗カウンタ(間接呼び出し数)と、16 面の面 SHA を毎回比べる。Chrome は `/proc/<pid>/task/*/stat` の Worker スレッドと rendererMain の CPU、ページが見た `putImageData` の回数のうち画素が変わった物(画面更新/s)。
**負荷**: この機械(16 論理コア)の load は 9〜60(他の担当の作業と重なった)。**壁時計の速度は主張しない**。CPU 秒でも load が高いとキャッシュ競合で 1〜2 割動く。表は load 11〜25 の間に取った物が大半(各 run の `load.txt` に開始・終了の load)。

## 4. 順位の上位の根本原因(証拠つき)

### 4.1 BitBlt の画素ごとの経路(`fle_r_blit`)が -O0 のまま wasm になっていた
- Chrome の Worker の V8 CPU プロファイル(1 ms、V0 = 名前つき、`tables/chrome-*.txt`): 中ボタンドラッグ 3 秒で `fle_r_blit` の自己時間が **2,786 ms / 5,360 ms = 52%**、ホイール 60 Hz で **1,888 / 4,450 ms = 42.5%**。ほかの関数は 10% 未満(`f_2a337c0` 9%、`f_863f60` 4%、…)。JS は 1〜4%、`(program)` 4〜5%、GC ほぼ 0。Worker は wasm の中でほぼ飽和している(1 コアの 85〜100%)。
- 原因: `lift/runtime/fle_raster.c` の `fle_r_blit` は、窓の面(BGRX、`keep_x` を持たない)への SRCCOPY では `memmove` の近道に入れず、**1 画素ごとに** `src_color → fle_r_get → fle_r_rop3(8 回のループ)→ fle_r_put` を呼ぶ。wasm の runtime は `RT_OPT` の既定 **O0**(決定 0161: fle_hle.c だけ -O2)なので、これらは inline されず、`wasm-opt -Oz` も整えきれない。native -O2 のプロファイルでも `fle_r_blit` 22.8% + `src_color` 10.7% + `fle_i2_psubusb` 3.5%(`tables/prof-native-N1-midbutton3s.txt`)。
- 量(`parity_wrap.c` で `fle_r_blit` の戻り値〔書いた画素数〕を数えた): 中ボタンドラッグ 3.4 仮想秒で 600 回・**1.40 億画素**(1 回 約 23 万画素 = Playlist の表示領域)、ホイール 60 Hz 2.4 秒で 514 回・1.02 億画素(`tables/blitvol-ui-pl-N1.txt`)。**画素量は native と wasm で同じ**(同じゲストの描画)なので、差は 1 画素あたりの命令数。
- 先行調査との関係: draw1(決定 0203)は F8 でこの関数を 34% と同定し、`FLE_R_FAST_COPY` を opt-in で入れた(HEAD に入っている、既定 0)。本作業はそれが F8 以外の全操作(Playlist ホイール・ドラッグ・Settings・ミキサー…)でも最大の項目であることと、**runtime 全体の -O0 が根本**であることを示した。

### 4.2 runtime が -O0 のまま(`RT_OPT`)
- `lift/harness/two/build_nmod_wasm.sh`: `CFLAGS_RT="-std=gnu11 -${RT_OPT:-O0} ..."`。runtime の約 80 ファイル(`fle_gdi.c`、`fle_raster.c`、`fle_sse_more.c`、`fle_win.c` …)は全部 -O0(`RT_O2_FILES` で名指しした `fle_hle` だけ -O2)。画素ループ・SSE の補助関数(`fle_satu8`、`fle_packuswb`)・Win32 の呼び出し(`fle_imp_*`)が全部ここ。
- 実測(.o の合計): -O0 5,770,362 B → -O2 5,251,957 B(**縮む**)。wasm 全体(名前を剥がした大きさ)は V0 130,240,067 B → V1 130,219,985 B(−20 KB)。S1 への影響は無い。

### 4.3 ほぼ残る物: ゲストの lift した C の重さと、wasm のコードの質
- N1 自体が重い: アイドル(Basic)0.10、Sampler アイドル 0.33、Sampler 再生 0.43、Playlist ホイール 0.80、中ボタン 0.77、**F8 を開く 2.46** CPU 秒/仮想秒(native -O2)。これは lift した C がレジスタファイル(メモリ)・フラグ計算つきで、実機の x86 より遅いため。実機 FL(N2)の数字が無いので、実機との比は言えない。
- 熱い単位の helper 呼び出し: V1 の Chrome プロファイルで `f_2a337c0`(dsp の IPP の葉関数、unit m1-04)が 12〜15%、さらに m1-04 から呼ぶ非 inline の `fle_ld`/`fle_op_sub`/`fle_cc`/`fle_st` が 650 ms(m1-04 の時間の 29%)。`AI_UNITS`(always_inline)で m1-04 ほか 4 単位を inline する V2 は node で連続操作の合計 −1%(Playlist ドラッグ −16%)、**wasm +7.9 MB(+6%)**で割に合わない。熱い 6 単位(m1-04, fle-06, fle-03, fle-02, fle-01, m3-01)の最適化を -Oz から -O2 にする V3 は、連続操作の合計 **−13%、wasm +4.6 MB(+3.5%)**(混成の無い V1 に対して。混成と重ねた測定は無い)。
- 混成(fe-wasmgen の直接 wasm)は、ゲストの熱い 977 関数を C 経由でなく直接 wasm にする。**V1H が N1(native -O2 の C)と同程度〔持続する負荷では 0.75 倍前後〕まで下がるのは、直接 wasm の翻訳が、レジスタファイル(メモリ)・フラグ計算つきの C より、wasm のローカル変数に載せやすいからと読む**(読み。確かめていない。N2 = 実機の FL との比ではない)。V1 に重ねると連続操作の合計 0.61 倍、中央 0.62 倍(V1H 対 V1)。

## 11. PM の判断点
1. **V1(`RT_OPT=O2 RT_DEFS=-DFLE_R_FAST_COPY=1`。名前つきのプリセットは足さない)を ship3 の既定にするか。anim1 の `F1xH3|F2xH3`〔runtime のうち -O2 にするのは `fle_raster` `fle_sse_more` だけ〕との違いは §5.1 3.**: サイズ中立、画素同一、CPU 合計 −33%(非混成。2.1 の表と Chrome の画面更新/s: Playlist 中ボタンドラッグ 4.7 → 20.4。同条件の node の gate は load が高い間に走ったので未確定)。リスクは runtime -O2 の未定義動作(今回の範囲では不変)。**推奨: 採る**。混成と重ねる手順は ship2 のまま(V1H は V1 に対し CPU 合計 −39%、V0 に対し −59%〔別々の時刻の表〕、V0 に対し −55%〔同じ session で続けて測った gate: 2.26 → 1.02〕、面 SHA 一致を確認)。
