## 3. 実 CPU に要る削減の式 — 『2.9 倍』を読み替える

- **2.9 倍の出どころ**(0274): 仮想時計のモデルは『間接呼び 4096 回 = 仮想 1 ms』(244 ns / 回)。最悪区間のミックスは 1.085 M 回 = 仮想 265 ms で、ブロック 92.88 ms の 2.85 倍。これは**モデルの数で、実 CPU を速くしても変わらない**(実 CPU が速いと idle が増えるだけ。opt1 §1c)。
- **実側の予算**(1 コア、r = 1.0 = 全ブロックを書く): ミキサー `m1 = 44100/4096 [10.77 ブロック/s] × (ms/ブロック)/1000`。E5: 78.5 → **0.845 コア**。E7b: 係数 f を掛ける。f は 2 通りに読める: 関数別の合計 0.91〜0.94(opt1 E5 の 15,116 ms から E7b で直になった 2,121 ms の 40〜65% を引く)、opt1 の x13 対 ff の交互 A/B(書き込み率 0.309 → 0.362、Worker CPU / 音声秒 2.97 → 2.41 s。UI の費用は壁時計に比例し u = 0.40〜0.46 として音声秒あたり u/r を引くと、ミキサー 1.48〜1.68 → 1.14〜1.31 s / 音声秒 = 0.77〜0.78 倍。UI の f_e95750 の減りも含む上限側の読み)。**f = 0.78〜0.92(中央 0.85)** → E7b のミキサーは 0.66〜0.78 コア(中央 0.72)、1 ブロック 61〜72 ms。
- UI 側(再生 30〜50 s、プロファイラ付き): UI+ループ 0.361 + (program) 0.048 = **u = 0.41 コア**(opt1 は窓ごとに 0.40〜0.49)。
- **r = 1.0 で 1 コアに収まる条件**: `m1/k + u ≤ 1`。k = m1 / (1 − u − 余裕)。余裕 0: k ≥ 0.66…0.78 / 0.59 = **1.12〜1.32**(中央 1.22)。余裕 10%: k ≥ 0.66…0.78 / 0.49 = **1.35〜1.6**(中央 1.47)。E5 のままなら k ≥ 1.43 / 1.72。
- **3 つの梃子の合計 12.8〜19.3%(中央 16%)** → ミキサー 0.53〜0.68 コア(中央 0.61)+ u 0.41 = **0.94〜1.09 コア(中央 1.02)**。= r = 1.0 の縁で、余裕は無い。
- 『2.9 倍を覆うか』= **覆わない**(3 つの梃子で 1.15〜1.24 倍。2.9 倍は仮想側の数で、実 CPU の必要量は 1.1〜1.6 倍)。**不足の埋め方**: (a)UI 側 u = 0.41 の 25〜50%(0.1〜0.2 コア)の削減(0263 の UI スレッドの内訳が入口。ただし P2 の 120 fps を目指すと u は逆に増える: opt1 §1d の見積りで 120 Hz なら u ≈ 0.8)、(b)ミキサーを別コアに(mt3 0275 の並列化の評価。そのときミキサー単体は 0.53〜0.78 コアで 1 コアに収まり、UI と足さなくてよい)、(c)両方。

仮想側の校正(mt3 0275 の領分、参考): 最悪区間のモデルの課金 265 ms ÷ wasm の実ミキサー 78.5 ms(E5)= **3.4 倍**、E7b なら 3.7〜4.3 倍で『仮想 = 実』になる(mt3 の sweep: ×4 で書き込み率 0.998)。
