## 0. 事実(依頼者の問いへの答え)

1. **既存 OSS の調査は、この調査まで 1 件も無かった。** `docs/` に CheerpX、v86、remill、McSema、rev.ng、Box64、QEMU、RetDec、wasm2c、Rosetta の語は 0 件(Wine は ctype の値の参照用だけ)。最初のコミット a7791f8(2026-10-20)が既に「FLEngine を Rust で lift して C、wasm」で、方式の比較評価は一度もされなかった。受け入れ条件が増えた(性能 P1〜P3、大きさ S1/S2)のに方式を見直さなかったのは、PM の落ち度である。
2. **Windows 版を lift する決定の経緯。** 本リポジトリに比較の記録は無い。旧プロジェクト(`~/work/signature-studio-dev-handover/`、2026-10-18 に中止)の引き継ぎ資料に、依頼者の最終定義「実物バイナリを lift(x86-64 機械語 → C → WebAssembly)」、対象は Win64 build 5653 と macOS build 5419 の両方、判断 D5(自作の 1:1 recompiler `x64c` を主力、RetDec ベースを並行。x64c 895/942、RetDec 路線 101/942、測り方は別)がある。D5 の比較の中身は旧リポジトリの削除で残っていない。Windows 版を選んだ理由の記録は無い。macOS 版は本リポジトリで一度も分析されていなかった。
3. **旧 `x64c` は「レジスタ=ローカル変数、フラグ=ローカル変数」だった。** 現行 `fe-lift` の `R[]`/`FL` グローバルは、`M1-remaining-work.md` §2.2 の「性能は本段階の目標ではない」から来ており、そこから後退している。

## 1. 調査の結論(作業者の実測と文献。PM 未再測定)

- x86-64 の Windows アプリをブラウザで実用速度で動かした既存品は 0 件。CheerpX と v86 は 32 ビットのみ、QEMU-wasm は遅く、Boxedwine64 は JIT 無し(10 倍超遅い)、McSema は 2022 年にアーカイブ、rev.ng は ELF 向け、RetDec は逆コンパイラ。remill(Apache-2.0)と Ghidra の SLEIGH(Apache-2.0)は命令意味の参照元になる。
- **同じ機械語(K1〜K3)での倍率(CPU 秒、ネイティブ比)**: 現行 lifter は packed 145〜160、scalar 17〜20、整数 5.5〜6.2 倍。公開の変換器 `wwt` の fast mode(明示のメモリ検査なし)は 2.4 / 1.9 / 1.1 倍、既定は 3.9〜5.8 / 約 2 / 1.3〜1.8 倍(出力は Wine とビット一致)。C から `emcc -O2 -msimd128` で作った wasm(天井)は 2.06 / 1.53 / 1.97 倍。`wwt` は MXCSR を持たず x87 を f64 にするなど、忠実度を割り切っている。
- **大きさ**: 全体を事前に変換する方式は、生の大きさでネイティブの 2 倍以内に届かない。`wwt` は freetype 607,032 B を 4.41〜9.2 倍、FLEngine 22.2 MB を 197 MB(8.9 倍)にした。本プロジェクトの現行 `-Oz` は freetype 4.87 倍、size1(決定 0155)の積み重ねで 3.27 倍。brotli 後の転送量は現行でも既に基準内(ネイティブ 6 モジュールの brotli 合計 17.6 MB に対し 0.87〜0.95 倍)。
- macOS 版は、エンジンが FPC 3.2.3 製(Windows 版は Delphi)。システム import 337(Windows 版は 738 名/24 DLL)で面は狭いが、ObjC ランタイムの模倣が要り、AArch64 の lifter を新しく作る費用が大きい。**切り替える強い根拠は出なかった**(CPU 性能は入力の OS でなく lifter の設計で決まる)。

## 2. 決定(仮)

| # | 項目 | 決定 |
|---|---|---|
| 1 | 方式の系統 | **静的 AOT(lift)を維持する。CPU 状態の持ち方を変える。** 現行の `R[]`/`FL`/`X[]` グローバル+遅延フラグ+レーンごとの厳密な浮動小数処理のままでは、P2/P3 に届かない(実測)。変更の担当は、(a) C 経路の改善(決定 0151 hle1、0154 fplow1、0155 size1)と、(b) 直接 wasm 生成(決定 0157 wasmgen1)。 |
| 2 | Windows 版の lift | **条件つきで維持する。** 条件(下の #3)が 2 つの経路のどちらでも満たされなかったときだけ、macOS 版(M6)の保険調査(1〜2 日)を割り当てる。今は割り当てない。 |
| 3 | go/no-go の指標 | 熱い関数と合成カーネルで、wasm -O2 の倍率を測る。**合格線: 整数 ≤ 2、scalar double ≤ 4、packed ≤ 6 倍。** 参照水準: `wwt` fast mode 1.1 / 1.9 / 2.4、天井 2.0 / 1.5 / 2.1。**呼び出し中心(fib 型)とストア中心(挿入ソート型)のカーネルを同じ harness に足す**(`docs/investigations/oss-survey/tools/bench2.c`)。C 経路の改善版と直接 wasm 生成は、**同じ指標**(K1〜K3 + bench2 + 同じ熱い関数)で比べ、担当に表で出させる。 |
| 4 | 忠実度の方針 | **`wwt` の割り切り(MXCSR なし、x87 を f64 にする)は採らない。** 決定 0143/0154 の方針を保つ: ゲストから見える結果(戻り値、書き込むメモリ、フラグ、MXCSR)がビット同一になるときだけ高速経路を使う(窓の内側は同一であることを差分テストで証明)。結果が変わるものは、HLE の定義(AGENTS.md と決定 0151)で禁止のまま。メモリ検査の省略(検査なしの wasm32 の折り返し)は、「黙って意味が変わる」ので本番には使わない(検証ビルド専用)。memory64 の境界トラップに任せる案は、ブラウザの対応を一次資料で確認してから判断する(wasmgen1 に依頼済み)。 |
| 5 | S1 の読み方 | **依頼者の S1(配布する wasm がネイティブの 2 倍以内。目標 1.2 倍)は書いてあるとおりに保ち、再定義しない。** 生の大きさと brotli 後の転送量の**両方を毎回測って並べる**。生の大きさは**現状 未達**(現行 -Oz 4.5 倍、size1 の積み重ねの外挿で約 2.8 倍、呼び出し規約込みの昇格で約 2.0 倍が下限)。全体を事前に変換する方式では、どれも原理的に 2 倍を割りにくいという実測がある。「実行された関数だけを遅延取得する」「元の x86 を配って実行部分だけ翻訳する(混成 M8)」は、**S1 を満たしうる設計として評価対象に入れる**(評価であり、S1 の再定義ではない)。判断は結果を見て、依頼者への報告に実測値で書く。 |
| 6 | 到達しない場合の報告 | P2/P3 が指標を満たさないと測定で出たら、依頼者に**測った予算(1 フレーム 8.3 ms の内訳、プラグインの CPU 負荷の上限)**を根拠に報告する。「WebAssembly の制約」のような説明で済ませない。 |
| 7 | 既存の動的変換 | **今は対象外。** CheerpX が x86-64 を出荷した時(ブログの予定)に再評価する。 |
| 8 | ライセンスの無い OSS | `wwt` など**無ライセンスの OSS は設計の参考だけ**にし、コードを流用しない。Apache-2.0 の remill、Ghidra の SLEIGH、Theseus の Worker 設計は、表示つきで参考にできる。 |

## 3. 訂正(PM が依頼者に先に述べた内容のうち、後で誤りと分かったもの)

- 「DLL ごとの置き換えを評価した記録は 1 件も無い」: **Blend2D については誤り。** `docs/investigations/blend2d-jit-and-drawing-path.md` §8.2 に、上流をビルドし直して Agg2D の 130 スロットを再実装する案 B・案 C がある(wasm の大きさ・速さ・忠実度の定量は無い)。決定 0159(swap1)が定量する。
- freetype は「MSVC 2012」ではなく、MSVC 2005(リンカ 8.0)のビルド(PE の時刻が 2012-09-20)。dsp_ippv2 の export は 449 個でなく 446 個。
- oss1 の報告 1 の「arm64 スライスで S1 の分母が下がる」は誤り(S1 は比であり、IPP を除けば分子も分母も下がる)。報告 2 で訂正済み。
