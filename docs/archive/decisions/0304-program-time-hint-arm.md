### A.1 製品のコード(`app/src/engine/hz.ts`、決定 0182・0268、5 行)

1. ページは `requestAnimationFrame` の間隔の**中央値**を 500 ms の窓(最初の 5 間隔は捨てる、20 間隔以上、4 s で諦めて既定 60)で測り、`1000/中央値` を `measuredHz` とする。
2. `roundToStandardHz`: 標準の値 `STANDARD_HZ = [60, 75, 90, 120]` のうち、**比(|ln(hz/s)|)で最も近い値**に丸める。境界は隣り合う値の幾何平均: **67.1 Hz(60|75)、82.2 Hz(75|90)、103.9 Hz(90|120)**。60 以下(50 Hz も)は 60、120 以上(144・165・240・360 Hz を含む)は 120(0268: 上端を 240 から 120 に下げた)。
3. 100 Hz のパネルは 90、144 Hz のパネルは 120、75 Hz は 75、59.94 Hz は 60。
4. 同じ値を `FLE_DWM_HZ` と `FLE_DISPLAYSETTINGS_FREQUENCY` の**両方**に渡す(`hzEnv`)。測るまでエンジンは既定の 60 で動く。runtime の許容は 24〜1000。
5. 結果: 依頼者のモニタが **67 Hz 以上なら FL の刻みが 75/90/120 に増える**(60 Hz の画面は 60 のまま)。0299 のとおり、刻みの量は `dmDisplayFrequency` に追従する。

### A.2 κ(Hz)の曲線(node、E11 のテスト用 wasm、`tables/0304-hz-curve.tsv`)

| Hz(DWM = SET) | 間接呼び出し/仮想 s(アイドル) | κ(間接呼び出し) | UI のアイドル CPU(core、プロファイラ無し、60 仮想 s の差) | **κ(CPU)** | 再生中の CPU(UI + ミキサー + 他、core)|
|---|---|---|---|---|---|
| 60 | 10.31 M | 1.00 | 0.197 | **1.00** | 1.175 |
| 75 | 12.67 M | 1.23 | 0.260 | **1.32** | 1.187 |
| 90 | 14.94 M | 1.45 | 0.285 | **1.45** | 1.189 |
| 120 | 20.48 M | 1.99 | 0.377 | **1.92** | 1.462 |
| 144 | 27.27 M | 2.65 | 0.434 | **2.21** | 1.518 |

読み: (i)間接呼び出し(決定的)は Hz にほぼ比例(75 → 1.23、90 → 1.45、120 → 1.99)、**144 だけ 2.65 倍と比より大きい**(2.4 倍のはずが 2.65: タイマの間隔をフレーム時間〔ms の整数丸め〕に量子化するため、144 Hz は 6.94 ms の丸めが効くと読む。未検証)。(ii)CPU の κ は 1.32 / 1.45 / 1.92 / 2.21(各 2 本、揺れ ±10%)。(iii)**再生中の CPU は揺れが大きく(同条件で ±10%)、75・90 Hz の +0.01 core は揺れの内**。信頼できるのはアイドルの κ と、120・144 Hz の再生の差(+0.29、+0.34 core)。

### A.3 1 Worker で P3 を保てる Hz の上限(0296 の式、`tables/0304-hz-limit.tsv`)

D(Hz) = A + U60 × κ(Hz)(A = 0.622 core = ミキサー + 他、r = 1。予算 = 1 − s = 0.735 @ v = 1)、必要な全 CPU の削減 ρ = 1 − 0.735 / D。U60(60 Hz、v 1 の UI)は 0299 の 4 通り(0.30 / 0.31〔node 再生〕/ 0.39 / 0.52)。

| U60 | 60 Hz | 75 Hz | 90 Hz | 120 Hz | 144 Hz | ρ ≤ 27%(梃子の高)で収まる最大 Hz |
|---|---|---|---|---|---|---|
| 0.30(一定) | 20% | 28% | 30% | 39% | 43% | **73 Hz** |
| 0.31(node 再生) | 21% | 29% | 31% | 40% | 44% | **71 Hz** |
| 0.39(E7b) | 27% | 35% | 38% | 46% | 50% | 60 Hz でも不可 |
| 0.52(∝ v) | 36% | 44% | 47% | 55% | 59% | 60 Hz でも不可 |

- **梃子が低(3%)・中(13%)の場合は 60 Hz でも収まらない**(最良の U60 = 0.30 でも 60 Hz で 20%)。**梃子が高(27%)で全部出ても、収まるのは 60 Hz と 73 Hz 以下**(75 Hz 以上は不可)。= **67 Hz 以上の画面(75/90/120 に丸められる)では 1 Worker で P3 は成立しない**。
- **現状(E11、v = 0.575、r = 0.89 で CPU 律速)での r の落ち(推定、実測なし)**: Hz を上げても稼働の割合 0.856 が一定、UI の増分が丸ごとミキサーから取られる、と置くと r(Hz) = (0.856 − U(Hz)) / 0.622、U(Hz) = 0.236 κ + 0.064(FL main + JS が κ 倍、(program) は不変): **60 Hz 0.89、75 Hz 0.77、90 Hz 0.72、120 Hz 0.55、144 Hz 0.43**(v の自己調整〔r が下がると idle が増え v が上がる〕を無視した上限の悪化)。**E7b の頃の 0268 の実測(60 → 120 で r −0.037)は課金が重く CPU 律速でなかった領域**なので当てはまらない。E11 以降の CPU 律速の領域での実測は 0(**Chrome で Hz を変えた run 4 本が要る**)。

### A.4 選択肢の整理(実装しない)

| 案 | 内容 | 忠実性 | 性能・P3 | 備考 |
|---|---|---|---|---|
| (a)現状 | rAF の実 Hz を 60/75/90/120 に丸めて渡す(0268) | 契約どおり(上限 120 の丸めは選択) | 67 Hz 以上の画面で P3 が悪化する恐れ(A.3) | 依頼者の機械の Hz は 0 件。GTX 980 の機械は 60 か 144 などが多い |
| (b)上限を 60 に固定 | モニタの Hz を無視して常に 60 を返す | **契約に反する選択**(dmDisplayFrequency は『現在のモードの Hz』)。FL は 60 で動くが、実 Windows の 144 Hz では 144 | P3 は保てる(60 Hz の需要) | 『P2 の 120 fps』と衝突(刻みが 60 のまま) |
| (c)上限を 75 または 90 に固定 | 丸めの標準の値を [60, 75] 等にする | 同上(選択) | 75 でも 1 Worker では不可(A.3) | 中間の案は効果が小さい |
| (d)UI 専用コア(実スレッド版)が入った後は 120 を許す | UI Worker 0.57〜0.99 core、ミキサー Worker 0.71〜0.98 core(0299) | 契約どおり | P3 を保てる見込み(各 Worker ≤ 1 core) | 3 コア以上が前提。2 コア以下の機械は協調 1 Worker に落とす実行時の判断(0289 §8) |
| (e)v の目標を下げる | v = 0.75 を許す(0296: 必要な削減 13〜21%) | 契約どおり | 120 Hz の UI は実時間あたり 0.75 倍の tick | P2/P3 のどちらを優先するかの PM 判断 |

**勧め(推定)**: 実スレッド版が入る前は (a) を維持し、**Chrome で Hz = 60/75/90/120 を変えた run(E12 の本番 bundle、各 5 分 4 本)で r・v の実測を取ってから**、(b)〜(c) のような契約に反する固定はしない。実測の前に固定すると『P2 の 120 fps』を先に捨てることになる。


## PM の決定と取り込み(2026-11-06 18:20、docs のみ。製品の差分なし)

取り込み: alpha1 の最終(訂正の明記つき、18:17)の文書・表・道具を `docs/investigations/alpha19/` に置いた(4 run の生ログ 1.4 MB は入れない。原本は `lift/out-git/alpha19-results/logs/`)。実行は Chrome 156 headless で mt3 の 0293 bundle(plain / hint 27,570 箇所)を ci1 の `page-9fdc492f` で再生した 8 本(腕あたり 4 本、窓 30〜50 s、開始 load 1.7〜12.2〔8 超の 2 本は参考〕)。**依頼者の機械は 0 件**。

事実として受け取る:
1. 『hint の腕の (program) が 2 倍』は再現しなかった。順序を入れ替えた 4 本は腕の差なし(r 0.957〜0.971、(program) 7.0〜8.8 ms/ブロック)。悪化は前の組の hint 2 本だけ(hint 4 本中 2 本、plain 4 本中 0 本、正確確率 0.21)。原因は未特定(環境または run の状態)。
2. hint の局所の効き(A = f_b34aca0 + f_b34eaf0)は plain 10.18 対 hint 9.76 ms/ブロック(−4%、標準偏差の内)で区別できない。0290 付録2 の『A/other −17%』は、悪化した run で分母が膨らんだための見かけ(0290 を訂正済み)。
3. 付録 A(Hz): rAF の中央値を {60, 75, 90, 120} に丸める(境界 67.1 / 82.2 / 103.9。144 以上は 120)。UI の idle CPU は 60 Hz 0.197、75 Hz 0.260、90 Hz 0.285、120 Hz 0.377、144 Hz 0.434 core/仮想 s(κ = 1.00 / 1.32 / 1.45 / 1.92 / 2.21)。1 Worker の P3 は、忠実な梃子の高側(27%)でも約 71〜73 Hz まで。**利用者の画面が 67 Hz 以上だと、1 Worker では P3 に不利になる**(オーナーの画面の Hz は 0 件の測定)。

判断:
1. **H1(branch hint)は E12・E13 とも見送りで閉じる**。再開の条件は V8 の版・実機での別の証拠。トレース 2 本は取らない。(program) の分解(0296 の L7)は gpu1 の 0297 の (c)・設計課題に統合する。
2. **display Hz は契約どおり実際の Hz を返す(固定の 60 にしない)**。この方針は、実スレッド版で UI 専用コアを得た後に、75/90/120 を渡せるかを再評価する(決定 0306、0308 の後)。docs には『利用者の画面が 67 Hz 以上だと P3 に不利(未測定)』と明記する。
3. 未確認: 悪化した 2 本の原因、スレッド別 CPU の比較(その 2 本には採取が無い)、(program) の分解。後片付け(alpha1 の rig など)は PM が許可する。
