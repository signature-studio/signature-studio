## 3. エンジンに載せる方式(実装・実測)

同梱 5 DLL と同じ「実モジュール」方式(決定 0080〜0082)を 6 つ目・7 つ目に拡張した。
1. **lift**: `fe-lift lift FILE --pdata [--hook-points …] [--seeds …] --extra-imports ROWS`(**fe-lift のソースは無変更**)。応答表は全モジュールで同一でなければならない(`merge_tables_n.py` が検査する)ので、ROWS は FLEngine と全モジュールに同じ物を渡す(`FLE_EXTRA_IMPORTS`)。
2. **rebase**: `fe-pe rebase`(ラッパー 0x7000000、Serum2.vst3 0x8000000。他は dsp 0x2000000・QFC 0x1d00000・Blend2D 0x4700000・FreeType 0x4b00000・ILTools 0x6000000)→ `gen_two.sh`(`rebase gen split merge`)→ 単位ごとに `clang -O0 -finstrument-functions`(内容アドレスのキャッシュ `cache/`。生成 C の関数本体が変わらない単位は再コンパイルしない)→ リンク時生成の `fle_realmod_table`。
3. **パス付き `LoadLibraryW`(新規・opt-in)**: エンジンは `LoadLibraryW(絶対パス)` を呼ぶ(従来の runtime は『パス付きの名前は未対応』で停止)。`fle_realmod_path_table`(リンクが渡す『パスの末尾 → 実モジュール名』の表。既定は空の weak 定義)で実モジュールに結ぶ。末尾の比較は ASCII の大文字小文字と `/` を畳み、末尾の直前が区切りか先頭のときだけ一致する。**そのパスが仮想ボリュームにファイルとして存在すること**も要る(無ければ NULL + 126。Learn: パスを指定した LoadLibrary はそのパスだけを探す)。実装: `fle_realmod.c`(`fle_realmod_find_path`)、`fle_load.c`(`load_by_path`)、`fle_vfs.c`(`fle_vfs_guest_is_file`)。
4. **仮想ボリュームの種**(`tables/vfs-seed-wrp1-*.tsv`): ラッパー DLL(エンジンは `GetFileAttributesW` で存在を見て選ぶ)、参照プロジェクトの 49 ファイル、利用者のプラグインデータベース(`.Plugins.ini`・`VerifiedIDs.nfo`。**利用者の機械の供給物**)、Serum2.vst3 とその moduleinfo.json。

## 9. ブラウザ側の設計と wasm 化の見通し(設計だけ。何も実装・実行していない。値は『読み』または既存の決定の実測の引用)

前提(実測): 今回の native 構成は 7 イメージ(FLEngine + 実モジュール 6〔dsp、Blend2D、QFC、FreeType、ILTools、ラッパー〕+ Serum2.vst3 で 8 イメージ)を 1 プロセスに載せ、`fle_dispatch` の結合表でモジュール間の間接呼び出しを解決する。ブラウザでも同じ C を emcc で 1 本の wasm にする(決定 0128/0134 の 6 モジュール構成の延長。`app/scripts/build-engine-bundle.sh` の `mods` に 2 行足し、`REALMOD_C` に path 表を足す)。

1. **サイズの外挿**(推測。ラッパーと Serum2 の wasm はまだ作っていない):
   - ラッパー m6: 生成 C 56.4 MB(58.1 MB)。同じ Delphi のプラグインの plug1 の外挿(C 57 MB → wasm -Oz 約 21 MB、brotli 約 2.5 MB)と、srm1 の wasm/C 比(Serum 2: -Oz 69 MB / C 258 MB = 0.27、-O2 173 MB = 0.67)から、**-Oz で 15〜21 MB、-O2 で約 38 MB**、brotli 約 2.5 MB。Effects 用のラッパー(別イメージ、5,997,056 B)をもう 1 本足すと倍。
   - 重複(plug1 の関数単位の測定、`docs/investigations/plugins-distribution/tables/dup-per-dll.tsv` の引用): Generators ラッパーのコード 2,634,837 B のうち **2,021,764 B(76.7%)は FLEngine の関数と同一**(Delphi の RTL/VCL の複製)、2,620,103 B(99.4%)は他の 1 本以上の DLL と同一(この DLL だけのコードは 14,734 B)。Effects 側も同じ(コード 2,636,073 B、この DLL だけ 16,003 B)。FLEngine が既に載っている前提の plug1 の『B-FLE』(共有ライブラリとして再利用)の見積もりは『Delphi 前面 7 本で native の 0.54 倍』なので、**重複を畳めるビルドなら 2 本のラッパーを足す増分は上の外挿よりずっと小さい**(推測。今回のビルドは畳んでいない: ラッパーの C 58 MB は FLEngine の C と別物として全部出ている)。
   - Serum2 m7: 決定 0177 の実測 = -O2 173 MB(ネイティブ 19.2 MB の 9.0 倍、brotli 9.63 MB)、-Oz 69 MB(3.6 倍、brotli 5.96 MB)。
   - 現在の出荷構成 F2xn(決定 0176)は wasm 136.6 MB(ネイティブ 70.57 MB の 1.94 倍、brotli 10.85 MB)。ラッパーを足すと約 152〜158 MB(+12〜16%、S1〔2 倍〕の余裕 3.2% を超える)、Serum2 も足すと -Oz で約 220〜230 MB、brotli で約 +9〜11 MB。**S1 は、ラッパーだけでも『はい』でなくなる**(読み)。
2. **起動 P1 への影響**: wasm のインスタンス化はサイズにほぼ比例する(決定 0161: A→D の測定)。**FLP がラッパー系のプラグインを持つときだけ**ラッパー(と QFC の VST3 経路)を読む設計が要る。選択肢: (a) 1 本の wasm に静的に入れる(最も単純。S1 と P1 に直撃)、(b) 決定 0096 の遅延モジュールのように関数本体を初回呼び出しまで取得しない(wasm-split 相当。未測定)、(c) ラッパーを別の wasm インスタンスにする — **不可**: `CreatePlugInstance` はエンジンの linear memory にあるホストオブジェクトを受け取るので、同じメモリに載せる必要がある。推奨は (b)。
3. **Serum 2 をどこで動かすか**: 決定 0177 の実測で、Serum 2 は 1 インスタンスあたり Worker +約 530 MB、参照プロジェクトの 6 インスタンスを 1 つの wasm メモリに載せると最大 RSS 3.36 GB(ピアノ込み)= エンジン本体の 931 MiB と合わせると wasm32 の 4 GiB を超える。ゆえに **Serum 2 をエンジンの wasm に静的に入れる案は採れず**、決定 0173 の『1 インスタンス = 1 Worker』になる。すると境界は今回の実測の『QFC の `CreateVST3Instance` → `LoadLibraryW`/`GetProcAddress`/`GetPluginFactory`/IPluginFactory/IComponent の各 vtable 呼び出し』の途中に来る: 実測で、VST3 の読み込みと COM 呼び出しは QFC の lift 済み Delphi コード(エンジンの wasm の中)が行い、プラグインの COM オブジェクトを vtable 越しに呼ぶ。この境界を Worker 間の RPC にするには (i) `LoadLibraryW(Serum2.vst3)` が『遠隔モジュール』のハンドルを返し、(ii) `GetProcAddress` が RPC スタブの擬似 VA を返し、(iii) プラグインが返す COM オブジェクト(IPluginFactory、IComponent、IAudioProcessor、IEditController)の vtable の各スロットを RPC スタブにし、(iv) ホスト側の COM オブジェクト(QFC が作る IHostApplication、IComponentHandler、IParameterChanges、IEventList、IBStream など)をプラグインの Worker にプロキシで見せる、が要る。引数のポインタ(ProcessData の音声バッファ、文字列、構造体)の越境が仕事の大部分で、process の 1 ブロックあたりの呼び出し数は十数回(決定 0173 の往復 10〜200 µs の測定に収まる見込み。推測)。**設計の候補**: 『QFC の VST3 経路(`VST3Instance` のユニット)ごとプラグインの Worker に載せ、ラッパー↔QFC の境界(TVST3Instance のメソッド)だけを RPC にする』は境界の呼び出しが粗い(process、setState、getParameter…)ので現実的、と読むが未検討。
