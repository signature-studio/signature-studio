# 0312i: B-FLE(方式 B)の生成器の変更の設計の読み — 差分の単位・順序・テスト(file:line)と、手で `va_lit` を適用する 2 関数の候補(mt3。PM 指示 23:10。仮。**コードを読んだだけ。cargo build・wasm・Chrome は 0。数は python(nice 19)の出力か『読み』と書く**)

## 0. 冒頭の四点

1. **PM の判断(23:10)**: 方式 **B** = FLEngine の今の形は保ち、**plugin 用に表経由の共有本体を 1 組追加**する。A(FLEngine 自身を表経由にして約 5 MB 縮める)は、ホット経路の間接化が P2/P3 に響く危険があるため S1 の比が実測で 2 に近づくまで保留。区分は『S1 を満たすためのサイズ削減の生成器変更』(FL の挙動の代行ではない、新しい旗・分岐なし)。MB は読みで、alpha1 の 0310(Balance の実 wasm)の値に置き換える。
2. **0312h §3 の訂正(重要)**: 0312h の表の『Balance 共有(B-FLE)1 つ目 約 4.5 MB、Delphi 7 つで約 11 MB』は **A 案(FLEngine の本体を使い回す)の値**だった。**方式 B では共有本体は plugin 用に別に 1 組作る**ので、FLEngine と共通の RTL/VCL 本体(Balance の h0 共有の異なる本体 C 18.95 MB)も**その 1 組に入る**。方式 B の見積り(読み。最終 wasm = C × 0.311): 共通の RTL/VCL 本体 **5.9 MB** + プラグイン共通の枠組み(Flanger と共通の固有 C 11.35 MB)**3.5 MB** = 一度だけ **9.4 MB**。プラグインごとの固有 C 0.42 MB = **0.13 MB** + 表と wrapper 約 **0.4 MB** + 固有データ約 **0.5 MB** = **約 1.0 MB**。= **1 つ目 約 10.4 MB(共有なし約 12.3 MB と大差ない)、2 つ目以降 約 1.0 MB ずつ、Delphi 7 つで約 16.4 MB**。(A なら 1 つ目 約 4.7 MB・7 つで約 11 MB、FLEngine の重複除去 −約 5 MB が別に付く。)**方式 B の利得は 2 つ目の plugin から**。
3. **表の設計を小さくできる発見**: 共有本体のデータ参照リテラル 39,396 のうち **27,373(69.5%)は『call が積む戻りアドレス』**(`R[4] -= 8; fle_st(R[4], 8, UINT64_C(<call の次の命令の VA>))`)。戻りアドレスは**関数の先頭 VA + 関数内の定数**(39,119 のうち 39,114 が関数の先頭以後 1 MB 以内)なので、**どのモジュールでも定数のオフセットは同じ**。表は『その関数自身の VA(1 つ)』だけでよく、戻りアドレスは `T[0] + <offset>`。**表に載る本物のデータ/コードの参照は 12,023(30.5%)**。表は 1 モジュールあたり 参照 12,023 + 呼び先 23,729 + 関数自身 10,310 = 46,062 エントリ × 4 B ≒ **0.18 MB**。
4. **候補の 2 関数(§4)**: 最も実行された物 = Balance `0x4076b0`(FLEngine `0x409c80`、steady で 6,008 万命令、C 11,976 B、call 1・参照 5)、最も大きい物 = Balance `0x5a3d00`(FLEngine `0x653f40`、C 282,507 B、call 426・参照 1,276、実行 3,019 命令=フォームの構築と読む)。**手で書くより、C のテキストを機械的に書き換える小さな script で『表経由』を作る**ことを提案(手の誤りを避け、そのまま生成器の原型になる)。

選び方(PM の指示): **plugin 側で共有される本体(h0)のうち**、(1) 実行された命令が最も多い物、(2) 最も大きい物を各 1 つ。実行回数は『FLEngine の steady + start-up の記録』(`lift/out-hyb1/tables/rank-steady-startup.txt`、関数ごとの命令数)で、**Balance の本体と同じ本体を持つ FLEngine の関数の合計**(Balance 自身の実行記録は無いので代用)。a4 には関数ごとの回数表が無い(合計だけ)ため、この表を使った。

## 5. 区分と No-options の自己点検

- 区分: **『S1 を満たすためのサイズ削減の生成器変更』**(PM の分類)。FL の挙動の補正・代行ではない。値(VA)を表で渡し直すだけで、**表の値は常にそのモジュールの実際の値**なので意味は変わらない(T1 が証明)。
- 新しい旗・環境変数: **製品に無し**。`fe-lift` の `--shared-bodies`・`--shared-index` は生成器(ビルド時)の入力で、`--prune-list` などと同じ種類。FLEngine の既定の出力は不変。class/アドレスの分岐: 無し(共有の選択は本体の hash だけ)。

## 6. 未確認・リスク

- C 側の共有の割合は FLEngine の基準が『製品の C』(direct wasm の 2,758 関数が無い)なので過小評価の可能性。素の lift での再実行(`tools/bfle_plain.sh`)は窓の後。
- 表経由の本体は call が `call_indirect`、データ参照が 1 段間接になる。**plugin の DSP の本体(Balance のパン/ボリューム)は共有されない固有部分**のはずだが、RTL の `Move`・`@GetMem` 等が DSP のループから呼ばれる場合の時間は G9 の実測が要る。
- 共有本体の ID(hash)の安定性(生成器のバージョンで変わる)。`IDX` を bundle と一緒に保存する必要。
- plugin 間でデータ(`.data` の初期化値)も共有できるか(0.5 MB/plugin の見積りは粗い)。
- ジャンプ表を持つ関数は第 1 版では共有しない(Balance で 9 個)。割合は他の plugin で未計測。
- 工数: **見積もっていない**(U0 は約 30 か所の機械的なリファクタ、U1・U2 が本体。plug1 も未見積)。

## 7. 書き換え script の試作(U0/U1 の原型。Balance の生成 C のコピーに適用。23:25〜23:33、nice 19、emcc -c を 6 回だけ)— 実測

`tools/va_lit_rewrite.py GEN.c HEXVA OUTDIR`: 1 関数を取り出し、(i) ラベル `L_<va>` を関数先頭からの相対 `L_<off>` に、コメントの VA を消す、(ii) call の戻りアドレスの push `fle_st(R[4], 8, UINT64_C(<va>))` を `(uint64_t)T[0] + UINT64_C(<off>)` に、(iii) 範囲内の `UINT64_C(0x…)` を `(uint64_t)T[k]` に(同じ値は同じ k)、(iv) 呼び先 `f_<va>` を `((fle_fn_t)T[n])` に書き換える。出力は `S_<hash>(const uintptr_t *T)`(`noinline`・外部リンク = 呼び側の表が畳み込まれない)と、そのモジュールの表 `T_<va>[]`・wrapper `f_<va>(void){ S_<hash>(T_<va>); }`。

- **T1(展開テスト)を python で実施**: 表で展開し戻すと元の本体と一致するか(コメントの VA を除き行単位) — **3 関数とも一致 True**(`tables/0312i/rewrite-prototype.txt`)。
- **変換**(実測): `0x40e800`: 本体 2,548 → 2,227 B、表 2 エントリ(自身 1・呼び先 1)、戻りアドレス 1 を `T[0]+off`。`0x4076b0`: 11,998 → 10,018 B、表 5 エントリ(自身 1・参照 3・呼び先 1)。`0x5a3d00`: 282,529 → 251,670 B、表 847 エントリ(自身 1・参照 842・呼び先 4)、**戻りアドレス 426 を `T[0]+off`**。
- **emcc -c -Oz(`-DFLE_GIL -DFLE_TLS_MORE -pthread`)で原型も共有形もエラー 0 でコンパイル**。wasm object の section の大きさ(code = section 10、data = section 11。.o にはヘッダ由来の分が共通に入る): `0x40e800` code +28 B(+0.1%)・data +15 B、`0x4076b0` code +21 B(+0.1%)・data +27 B、**`0x5a3d00` code +7,388 B(+9.2%)・data +3,396 B(表 847 × 4 B)**。= **表経由にする費用は参照の数に比例し(1 参照あたり code 約 +6 B + 表 4 B)、小さい関数ではほぼ 0、参照が 1,000 を超える巨大関数で +10%強**。共有で一度だけ払うので、plugin ごとの重複(§0)に比べて小さい。
- **注意(発見)**: 最初の版は表と本体を同じ TU・`static` にしたら、**LLVM が S_ を inline して定数の表を畳み込み、原型と同じ大きさ(1 バイトも違わない)になった**。= 共有形の費用は、表と本体が別の module になって初めて現れる(上の 3 つは本体を外部リンク・noinline にして測った)。**共有本体を呼ぶ側(各 plugin の wrapper)は最適化で特殊化されない**ので、呼び出しのコスト(間接の 1 段)は避けられない。
- **未測定**: 呼び出し時間(2 つ目の候補 `0x40e800` は実行 4,497 万命令の本体)。guest の状態(`R[]`・メモリ)を作る harness が要る — 窓の後の ② で。
