## 1. 依頼と、この決定が従う方針

依頼者(原文): 「Unity WebGL ビルドは wasm↔JS/DOM のシリアライズ/デシリアライズ回数を減らして非常に軽量。…少なくとも wasm→worker→メインフレーム→canvas のようなバケツリレーは避けること」「ページが窓ごとの canvas を並べ、もしそれが軽量化の目的を持っているなら、それ自体は合っている。ただ、手段は全く間違っている。行うべきは wasm↔JS シリアライズ/デシリアライズ削減、worker↔メインフレーム通信削減によるパフォーマンス改善であって、場当たり的な軽量化は今回のような不具合を誘発させる。バグなく動いている FL Studio を lift すればバグのないプロダクトが完成する。バグがある場合、余計なことをしているか、API の拡充が不十分であり、そちらに注力するべき。余計なロジックは見つけ次第抹消する」「FL ウインドウを管理するウインドウマネージャーは(Detached モードを除き)FL Studio に備わっており、我々が介入する必要はなく、不具合が発生した場合は外部 API の拡充によってのみ対処する」「Unity WebGL のケースを踏襲し、Worker から draw / bindTexture を実行するコードを我々が作成することも選択肢の一つだと思っていた」。

## 3. 設計

### 3.1 データの流れ

```
エンジン(wasm)                                   Worker                          ページ(メイン)
 窓の面(窓ごと、BGRX) ──┐
 窓表(Z 順・位置・可視)  ├─ fle_desk_compose() ─→ 1 枚の面(R,G,B,A、画面と同じ大きさ、wasm メモリ内)
 レイヤード状態           ┘     (C、-O2)           │ 変更矩形 ≤32(画素が実際に変わった所だけ)
                                                    ├─ putImageData(ImageData〔面のビュー〕, 0,0, 矩形)──→ OffscreenCanvas(1 枚)
 fle_av_poll(カーソル・アクティブ窓の題・画面の大きさ)→ osstate(変化時のみ)──────────────→ CSS cursor / document.title / 画面の大きさ
                                                    └─ desk(≤10 回/秒:計数・提示時刻)──→ 計測
 入力 ←─ idle ごとに SAB リングを読む ←──────────────────────────────── ポインタ・キー・表示変更(リングへ書く。Worker が停止中のときだけ wake)
```

ページに届くピクセルは 0。ページは窓を知らない(窓ごとの canvas・配置・Z 順・可視・レイヤード・主窓の選択・画素の重複排除・窓更新の間引きは D では使わない)。

### 3.2 ランタイムの合成器 `lift/runtime/fle_desk.c`(新規、`.h` 付き)

**何をするか**: 窓表(`fle_win_input_toplevels` = 生存する最上位窓の Z 順〔上が先〕、`fle_win_input_view` = 可視・原点・lid)、窓ごとの面(`fle_raster_surface_peek`)、レイヤード状態(`fle_layered_query`)を**読み**、仮想画面(`fle_screen_w()` × `fle_screen_h()`。screen1 の値で、表示変更で変わる)と同じ大きさの 1 枚の面(R,G,B,A の順、A=255、wasm メモリ内で移動しない)へ、下の窓から上の窓の順に描く。窓の重なりの判定・Z 順・可視の決定は**しない**(窓表のとおり)。FL のクラス名・窓の種類・位置による分岐は無い。

**契約(出典。`docs/investigations/lay1/learn/` の Learn のコピー)**:
- Z 順(Window Features / Z-Order): 「The window at the top of the z-order overlaps all other windows. The window at the bottom of the z-order is overlapped by all other windows.」→ 窓表の順に下から描く。
- レイヤード窓(Window Features / Layered Windows): 「the layered window will not become visible until the SetLayeredWindowAttributes or UpdateLayeredWindow function has been called for this window」→ `fle_layered_query` が `FLE_LAYER_NONE` の窓は描かない。「The system automatically composes and repaints layered windows and the windows of underlying applications」→ 合成はシステム(ここではランタイム)の仕事。
- SetLayeredWindowAttributes: `LWA_COLORKEY`「All pixels painted by the window in this color will be transparent」→ 鍵と同じ色の画素は描かない。`LWA_ALPHA`「bAlpha … Similar to the SourceConstantAlpha member of the BLENDFUNCTION structure. When bAlpha is 0, the window is completely transparent. When bAlpha is 255, the window is opaque.」→ Dst = Src·a/255 + Dst·(1 − a/255)(BLENDFUNCTION の表)。
- UpdateLayeredWindow(BLENDFUNCTION): 「the APIs use premultiplied alpha, which means that the red, green and blue channel values in the bitmap must be premultiplied with the alpha channel value」→ 面の 4 バイト目は premultiplied の α。Src = Src·SCA/255(4 チャネルとも)、Dst = Src + (1 − Src.A)·Dst。**1 回の丸め**で評価する: `(R·SCA·255 + Dst·(255·255 − A·SCA) + 32512) / 65025`。
- 通常の窓の面は BGRX(4 バイト目は α ではない: 決定 0126)→ 不透明にコピー(A=255)。

**損傷領域(何を描き直すか)**: 前回の合成の窓の一覧(lid・原点・大きさ・レイヤード語・面)と今回のを比べ、(1) 新しい窓 → その矩形、(2) 位置・大きさ・レイヤード・面が変わった窓 → 旧と新の矩形、(3) 消えた窓 → 旧矩形、(4) Z 順が最初に違う場所から上の窓 → その矩形(旧と新)、(5) 面への書き込み(`fle_raster_wrote` → `fle_desk_wrote`) → その矩形を窓の原点でずらしたもの。矩形の一覧は最大 32 で、含まれる矩形は捨て、近く(合併しても面積が 1.25 倍以内)の矩形は合併し、満杯のときは増えが最小の組を合併する。描き直しは損傷矩形ごとに『背景で塗り、下の窓から重ねる』(窓の重なりを自分で判断せず、順に塗る)。

**報告の絞り込み(S-desk-trim。PM が承認した条件つき)**: 描き直した矩形は、いったん別の矩形(scratch)に描いて面と比べ、**画素が実際に違う所の外接矩形**だけを報告し、面へ写す(違う画素が無ければ何も報告しない)。

- **原因は残す(PM の条件 d)**: エンジンはアイドルでも毎フレーム、主窓の幅 1 画素の帯を同じ内容で描き直す。これは決定 0187 が記録した、エンジン側の機能(`DwmIsCompositionEnabled` が TRUE を返す行で有効になる。FL が DWM の合成を前提に毎フレームの再描画を要求する)。**我々はこの再描画を止めない・書き換えない**(止めるのは『FL の挙動を補う』ことになる)。実 Windows の DWM は、同一内容の GDI の再描画を合成の段で吸収する(窓の面の内容が変わらなければ画面は更新されない)。したがって**提示側で『変わっていない画素を出さない』ことは、DWM の外部契約に沿った実装**であり、局所的な近道ではない(原因の側ではなく、DWM に相当する合成器の出口でやる)。
- 理由(実測): trim が無いと D は 48〜57 回/s の提示(ブラウザへの putImageData)を続け、Firefox 158 ではそれだけで Worker +0.23 core・全プロセス +0.6 core(§2.3 の D アイドル)。trim 後は 0.6 回/s(アイドル)、11.6 回/s(再生)。
- 点検表の『局所的な近道(重複排除)』に近いので、(a) ランタイムの中の 1 か所(合成器の出口)に集め、ページ・Worker には無い、(b) 最初の呼び出し・画面の大きさの変更・`fle_desk_resync()`(canvas を失ったとき)は絞り込まずに全面を報告する、(c) ビルド時に **`-DFLE_DESK_NO_TRIM` で外せる**(既定は ON、MERGE-NOTES にも書いた)、の形にした。代替: 絞り込まず、ブラウザ側で提示を間引く(窓・内容を知らないが、変化を捨てる危険がある)。
- **条件の確認(PM の条件 b, c, e)**: (b) 費用: §3.2 の下の表と §2.2。(c) 画素同一性: §4.1 の trim ON と trim OFF(全面報告)の比較。(e) 遅延の定義: §4.4。

### 3.3 提示(Worker が 1 枚の canvas へ直接)

`desk.ts` の `DeskPresenter`: `fle_desk_compose()` を呼び、状態(`fle_desk.h` の `fle_desk_state`)を読み、変更矩形ごとに `putImageData(ImageData, 0, 0, x, y, w, h)` を呼ぶ。`ImageData` は wasm メモリ上の面への `Uint8ClampedArray` のビュー(メモリが伸びて `ArrayBuffer` が替わったときだけ作り直す)。**JS でのピクセルのコピー・変換は無い**(BGRX→RGBA は合成器が窓から面へ写すときに済む)。ページは起動時に 1 枚の canvas を `transferControlToOffscreen()` して Worker に渡すだけ。**メインスレッドへピクセルは 1 つも送らない**。画面の大きさが変わったとき(screen1 の表示変更)は、canvas を新しい大きさにして全面を出す。

**提示の時機(rAF に合わせる + 補い)**: Worker の `requestAnimationFrame`(ページの表示更新に同期。**提示の周期は表示の周期に従う**)で提示する。ただし (a) エンジンが Worker を占有し続ける間(起動後、仮想時計が壁時計に追いつくまで)、Worker の rAF がほとんど配られないことを実測した(§4.2: 起動後 12 秒で rAF 132 回に対し、エンジンの idle からの補い 81 回)。さらに、変化のない間は rAF の配達も減る(アイドルで 27 回/s)。そこで『最後の提示から 20 ms 以上たっていれば、エンジンの idle から提示する』補いを入れた(**S-desk-fallback**)。代替: rAF のみ(起動直後の絵が出ない・遅れる)、MessageChannel のターンで周期を作る(rAF の vsync 同期を失い、表示の周期と無関係な頻度で動く)。(b) 入力の結果は、rAF を待たずに**入力を処理し終えた idle で直ちに**提示する(**S-desk-input-present**。コンポジタはどちらでも次の表示更新まで保持する。入力→絵の遅延を、次の rAF までの待ち 0〜16.7 ms だけ縮める)。

### 3.4 入力(SAB リング)

`input/ring.ts`: 1,024 レコード(32 バイト)の SharedArrayBuffer のリング。メイン(生産者)がレコード(マウス・キー・表示変更〔決定 0212〕)を書き、`head` を Atomics で進める。Worker(消費者)はエンジンの idle のたびに読む(`drainRing`)。Worker が止まっている(エンジンが idle で、メッセージかタイマーしか Worker のコードを走らせない)ときだけ、メインが `wake` を 1 つ送る(Worker が `parked` を立て、その後でリングを見直す Dekker の順)。リングが満杯ならそのイベントだけ従来どおりの postMessage。present2 の注意(エンジンの idle は 1,050〜2,000/s なので、リングで縮められるのは 1 ms 未満)のとおり、遅延の主因はリングではない。目的は**通信の削減**(イベントごとの postMessage と構造化複製をやめる)。実測: D の 4 run(各 約 60 入力 + 起動時の入力。計 256 イベント)で、リングから読んだ回数 229、Worker が停止中で `wake` のメッセージが要った回数 69(**イベント 256 個に対し postMessage は 69 個**。従来は 1 イベント 1 postMessage)、リング満杯でメッセージに戻った回数 0。`wake` が要るのは、Worker が停止していて(エンジンが idle でタイマー待ち)、リングを読む機会が無い間に入力が届いたときだけ。

### 3.5 低頻度の状態

`osstate`(カーソルの形・前面窓のタイトル・画面の大きさが変わったときだけ)と `desk`(計数と提示時刻、最大 100 ms ごと、入力の直後は直ちに)。カーソルは『SetCursor が選んだハンドル』(`fle_av_poll` の `cursor`/`cursor_idc`)を CSS の cursor に写す(Learn About Cursors の標準 ID。`ui/cursor.ts` は窓を知らない)。タイトルは『アクティブ窓(`fle_av_poll` の ACTIVE フラグ)のタイトルのうち空でない最後の物』= OS 一般の概念で、FL のクラス名を使わない(旧: `main-window.ts` がクラス名 TFruityLoopsMainForm で主窓を選んでいた)。画面の大きさは screen1 が `fle_av_poll` の見出しに足した値(`screenW`/`screenH`)をそのまま運ぶ。

### 3.7 マルチウィンドウ・ポップアップ・ツールチップ・カーソル

ポップアップ・メニュー・ツールチップは FL(lift 済みコード)が作る最上位窓で、窓表の Z 順に従って同じ規則で重なる。特別扱いは無い(§4.1: FILE メニュー、サブメニュー、F8 のピッカー、パネルのドラッグ中の画素が旧経路と同一)。カーソルの重ね描きはしない(ブラウザの CSS cursor がカーソルを描く。現行どおり)。

### 3.8 提示の周期: rAF と 120 fps / 240 Hz の見込み

Worker の rAF はページの表示更新(vsync)に同期して配られる。提示 1 回の費用 c = 合成(0.18〜0.32 ms) + put(Chrome 0.1〜0.9 ms、Firefox 1〜1.8 ms)なので、周期 T の rAF で毎フレーム提示すると Worker の提示の負荷は c/T。Chrome(c = 0.3〜1.2 ms): 60 Hz で 2〜7%、240 Hz で 7〜29% の 1 コア。Firefox(c = 1.2〜2.1 ms): 60 Hz で 7〜13%、**240 Hz で 29〜50%**(**推測**: 式による外挿。この機械の headless は rAF が 60 Hz〔実測 p50 16.7 ms〕で、240 Hz は未測定)。そこで S-desk-trim(変わった時だけ提示)が効く: 提示するのは『画素が変わったフレーム』だけで、アイドルは 0.6〜4.5 回/s。再生中の提示は変更矩形の数・大きさに比例する。120 fps の UI(P2)を満たすには、(a) rAF の周期に合わせる(本設計)、(b) エンジンが 1 フレームの描画を 8.3 ms 以内に終えること(エンジンの仕事。提示の費用 c は Chrome で 8.3 ms の 10〜30%、Firefox で 20〜40%)が条件。

### 3.9 contextlost の復帰

`watchContextLoss`(決定 0201 の `ctx-resync.ts`)を Worker の 1 枚の canvas に付ける。`contextlost`/`contextrestored` のどちらでも `fle_desk_resync()` を呼び、次の合成が面の全体を報告する(絞り込まない)。窓ごとの再送・dedupe の影の消去は要らなくなる(1 枚だから)。**実機での復帰は未確認**(決定 0201 と同じく `Browser.crashGpuProcess` の確認は今回しなかった)。

### 3.10 Detached モードの境界(今回は触らない)

Detached(窓を OS の窓として切り離す)は、窓ごとの面をそのまま別の OS 窓へ出す機能なので、ページに窓ごとの canvas が要る。将来足すときの境界: (1) ランタイムは窓の面を今と同じに保つ(合成器は面を読むだけで、面を壊さない)。(2) 切り離す窓の lid を合成器に伝える API(`fle_desk_exclude(lid)`: その窓を 1 枚の面から外す)を足す。(3) 切り離された窓の面だけを、そのときだけ従来の方式(A)で別の canvas へ送る。D の経路は変えずに足せる。

cbeacon2 の定義: DOM イベントの時刻から、その入力に答える最初のフレームの時刻まで(`eventToRaf` はその次の rAF の開始まで)。『答えるフレーム』は決定 0205 の定義で、**入力の注入からエンジンの次の idle(+1 ms)までに Worker が投稿したフレーム**。ここで言う入力は、移動 20 + F9 10 + F6 10 とそれぞれの key-up など計 60 前後(`tools/lat-d.mjs`)。

**(e) trim が定義を壊さないか — 測った結果**:

1. **D は構造上、決定 0205 の窓に入りにくい**: 方式 B はエンジンが `present` を呼んだ瞬間(処理の最中、idle より前)にフレームを投稿するが、D は『エンジンが idle になった後に』Worker が窓表から面を作る。提示の時刻は idle + 合成 + put になり、窓の末尾(idle + 1 ms)を超えることがある。これは **trim と無関係に起きる**: trim なしの D2 でも、修正前は 60 入力のうち 11〜19 が『遅れ』(窓の外)になった(下表の『D 修正前』)。trim ありの D3 は 24・17(2 ラウンド)で、D2 の 11・19 と比べて 2 ラウンドでは揺れの範囲を出ない(trim の比較で提示が遅れたかどうかは、この数では言えない)。
2. **測定側の修正**(PM の指示どおり、アプリの計測の側): Worker は『入力を処理したターンの中で』直ちに提示し(S-desk-input-present)、画素が変わって提示したときだけ、その提示が答える入力の `seq` を `desk` メッセージの `answers` に載せる。ページは `LatencyTracker.answer(seqs, lid, at)` でそれらを『答えた』とする(決定 0205 の窓による推定を、Worker が知っている事実に置き換えた。単体テスト 3 件 + mutation 4 件)。画素が変わらず提示が無い入力は答え無し(B の dedupe と同じ。D では trim が出口なのでそうなる)。
