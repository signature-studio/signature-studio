## 2. 定義(`src/ui/latency.ts` の冒頭にも同じ文)

- **eventToRaf(新・P2 の判定)** = `event.timeStamp`(ブラウザが DOM イベントを作った時刻)→ **応答のフレームの `putImageData` の後の最初の `requestAnimationFrame` コールバックの開始**(`performance.timeOrigin + performance.now()`、lat1 の `pRaf` と同じ取り方)。
- **listenerToPut(旧・版 2 の値)** = ページの listener の中(`tPage`)→ 同じフレームの `putImageData` が戻った時刻。lat1(決定 0194)が CDP の外から測ったところ、利用者が感じる遅れより 10〜25 ms 小さかった(起点が S0 を含まず、終点が S4a を含まない)。
- **応答のフレーム** = 注入(`tInject`)の後に Worker が `postedAt` を付けて送った最初のフレーム(決定 0170、不変)。**ページはそのフレームが画素を変えたかを知らない**(§4.1)。
- **7 段階**(足すと eventToRaf に一致。単体テストで確認): `s0` = timeStamp → listener の開始、`s0b` = listener → 入力の記録を作る(`postMessage` の直前)、`toWorker` = `tPage` → エンジンが受け取った `tInject`(Worker のキュー待ちを含む。2 つの時計をまたぐ)、`worker` = `tInject` → 応答フレームの `postedAt`(ゲストの処理と面の取り込み。Worker の時計だけ)、`fromWorker` = `postedAt` → ページの受信(時計をまたぐ)、`put` = 受信 → `putImageData` が戻る、`raf` = `putImageData` → 次の rAF の開始。lat1 の S0 / S0b / S1+S1b / S2 / S3a / S3b / S4a に対応(S1 と S1b は Worker の受信時刻を protocol に足さないと分けられないので、足していない)。
- **起点が使えないとき**: `event.timeStamp` が listener より後、または送信の 10 秒以上前なら、その記録に `tEvent` を付けない(新しい値なし、旧い値だけ)。
- **画面の測定(バースト)の定義**: 『バースト』= 2 秒間(`BURST_MS`)だけ rAF を要求し続ける。始まりは、測定器の開始時、エンジンの最初の idle(バースト中なら、その時刻から 2 秒に延ばす)、以後 60 秒ごと(`BURST_PERIOD_MS`、最初の idle から数える)。バースト外は rAF を要求しない。バーストの途中でタブが隠れたら、そのバーストは中断(間隔は数えない)。`raf.sinceIdle`/`total` は全バーストの累計、`raf.recent10s` と `canvas.recent10s` の rAF の部分は『直近のバースト』、`canvas.recent10s` の描画時間は直近の 10 秒。**入力の応答の rAF(eventToRaf 用の 1 本)は、バーストと重なっても定義を変えない**(別の要求。Chrome は同じフレームで両方のコールバックを呼ぶ)。

## 4. 見つかったこと(合わなかった所と、その原因)

### 4.1 応答のフレームが『見える変化』でない入力がある(ノブの最初の押下)。直していない

app の値は、決定 0170 のとおり『注入の後に Worker が送った最初のフレーム』で閉じる。既定の入口(SHIPH)は待機中に**変化のない同一矩形を 62.4 回/秒**送る(決定 0187)ので、ゲストの答えが**エンジンの最初の idle より後**に来る入力では、その最初の無変化の再描画が『答え』になる。ノブの最初の押下では、エンジンの最初の idle は注入の 1.3〜5 ms 後(`s2b_inject_to_idle`)、見える変化(最初の**変化した**描画)は 42〜47 ms 後に Worker が送る。app の値は 26.8 ms(`worker` 段 1.4 ms の再描画で閉じる)、同じイベントへの外側の測定(最初の変化する描画の次の rAF)は 61.9 ms だった(**SHIPH 48/48 回**、表の『ノブの最初の押下』)。`?dedupe=1`(変化のない矩形を送らない)にすると app 60.5・外側 60.5 で一致する(23/24 回が 2 ms 以内)。= **原因は、ページが『フレームが画素を変えたか』を知らないこと**で、`LatencyTracker` の対応づけの欠陥ではない。ほかの入力(クリック、ホバー、ドラッグの 1 移動 ×2、ホイール、Space、メニュー)は、app と外側が 1 イベントごとに(中央値)0.1 ms 以内で一致した(§3.2)。

PM の指示(02:00)で**直さない**: 解消するのは『`?dedupe=1` を既定にする(無変化のフレームが来なくなる)』か『入力を待っている間だけ、ページが受け取ったフレームの画素を前の同じ矩形と比べる(`client.ts` に手が入る。CPU を使う)』のどちらか。

### 4.2 画面の測定(rAF の連続ループ)が `?dedupe=1` の利点を消していた。バーストに変えて直した

lat1(決定 0194)は、`?dedupe=1` でホバー 30.0 → 15.5 ms、クリック 18.1 → 10.2 ms と報告した。その測定の木(f2dded6)は、ビーコン版 2 の画面の測定(決定 0192)より前の物だった。HEAD 7f024d7 は、ビーコンが有効なら**待機中も 1 フレームごとに `requestAnimationFrame` を回し続ける**(`DisplayMonitor`)。ページがフレームを作り続けるとき、Chrome はポインタ移動の配信を次のフレームまで持つ(lat1 §4: S0 が 10〜14 ms)。§3.1 の表: HEAD で `?dedupe=1` を付けても(ビーコン ON)クリック・ホバーが 25〜30 ms のままで、`&beacon=0`(画面の測定なし)にすると lat1 の値(10.2 / 15.5)に戻った。**P2 の遅延を測るための測定器が、測っている物を 10〜20 ms 悪くしていた**。

直し方(PM の指示): rAF を『バースト』にした(起動時・最初の idle・以後 60 秒ごとに 2 秒。バースト外は rAF を要求しない)。§3.1 の表: バースト版は `?dedupe=1` のビーコン ON でも OFF と同じ値(クリック・ホバーが lat1 の値の近く)になった。cbeacon2 の入力の測定(待っている間だけ rAF を 1 本)は、HEAD との差が run 間の揺れの内だった(§3.3)。ただし、**バーストの間(2 秒)に入った入力は、連続のときと同じく遅くなる**: §3.4 に別の値を出した。

### 4.3 `?dedupe=1` を既定にする前に直す物: 見える変化のない入力が『次の無関係なフレーム』で閉じる

決定 0170 の対応づけ(注入の後に Worker が送った最初のフレーム、5 秒まで)は、変化のないフレームが 62 回/秒来る既定の入口では、見える変化のない入力(ボタンを放す、反応しない場所への移動)を 16 ms 以内の次の再描画で閉じるので目立たない。`?dedupe=1` では無変化のフレームが来ないので、**そうした入力は次の無関係なフレーム(0.1〜0.4 秒後)で閉じる**。実エンジンの `?dedupe=1` で 78 回の入力(移動 52・押下 13・放す 13)を送ったページの記録(`runs/panel-dedupe2/panel-check.json`): 『放す』13 回の eventToRaf は p50 **359.5 ms**(11/13 回が 100 ms 超)、移動は p50 12.9 ms・最大 31.4 ms、押下は p50 6.2 ms。その結果、そのページが送ったビーコンの P2 は p95 **363.5 ms**(p50 9.2 ms)だった。同じ入力を既定の入口(SHIPH)で送ると p95 34 ms(放す 13 回は p50 28.1 ms)。= **dedupe を既定にすると、ビーコンの P2 の p95 が『反応しない入力』の数に支配される**。cbeacon2 は 0170 の対応づけの維持を指示されたので直していない。直し方の候補: eventToRaf の応答を『`tIdle + 1 ms` までに Worker が投函したフレーム』に絞る(lat1 の再結合と同じ規則。応答のないものは値なしになる。0170 の単体テストの一部が変わる)。**PM の判断点**(§5 の 2)。

## 5. PM の判断点

1. **P2 の遅延の判定を版 3 の `input.eventToRaf`(p95 ≤ 17 ms、閾値は不変)にする**と、**画面の測定をバーストにする**(app/ の変更を取り込む)。5173 の配信フロントエンドの差し替えは PM の作業。版 2 の記録の `input.p95Ms` は旧定義なので、17 ms と比べない(summary は別の列に出す)。
2. **`?dedupe=1` を既定にする前の条件**(dd1): (a) §4.3 — 見える変化のない入力が次の無関係なフレームで閉じ、ビーコンの P2 の p95 が 364 ms になる(実測)。eventToRaf の応答を『`tIdle + 1 ms` までに投函されたフレーム』に絞る 数行の変更が要る(0170 の対応づけの絞り込み。今回は指示により直していない)。(b) §4.1 — ノブの最初の押下のように、答えが遅れて来る入力は、最初の無変化の再描画で閉じる。dedupe 既定化で解消する(`?dedupe=1` では app 60.5 / 外側 60.5)。
3. **バーストの値**(2 秒・60 秒ごと・起動時と最初の idle に各 1 回)は根拠のない選択(S-cb2-13、14)。**バーストの間に入った入力は、連続のときと同じく遅くなる**(§3.4: ホバー p50 29.5 → 13.8 ms)。バースト中の入力は 約 3%(2 秒/60 秒)。バーストを短く・まれにするか、入力があったらバーストを延ばさない(今回の実装は入力と無関係)かは PM の判断。
4. `docs/milestones/performance-targets.md` の P2 に『入力→画面』の定義を足す文案は MERGE-NOTES.md。

## 6. 未確認・限界

- **依頼者の機械・実ディスプレイ・実マウスの値は 0 件**。実マウスの `event.timeStamp`(OS のイベント時刻をブラウザが換算した値)が CDP の注入と同じ意味で S0 を含むかは**推測**で、測っていない。この機械の rAF は 60 Hz 固定のヘッドレス(120 Hz の画面では S4a が半分になるはず〔読み〕)。
- **終点は rAF の開始まで**。合成器の出力・VSync・スキャンアウト・ディスプレイの遅れは、ページからは測れない。eventToRaf は『利用者が感じる遅れ』の**下限に近い値**であって、画面に出た時刻ではない。
- 待機中の入力だけを測った。**再生中・F8・メニューの連続・所定のプロジェクト・プラグインは測っていない**(lat1 の play の相は走らせていない)。
- load ≤ 8 の静かな機械では取り直していない。n は 1 セル 12(ホバーは 24)× 2 ラウンド以下で、p95 は粗い。
- Chrome 以外(Firefox は `event.timeStamp` を丸める設定がある、Safari)は未確認。起点が使えない timeStamp は記録ごとに捨てる(§2)ので、新しい値が出ないだけで旧い値は残る。
- 隠れたタブでは rAF が止まる: 2 秒以内に来なかった rAF は『次のフレーム』と数えず、その記録に eventToRaf を付けない(単体テストあり)。実ブラウザの隠れたタブでは試していない。
- ホイールは `WheelAccumulator` が数個のイベントを 1 つの入力にまとめる。起点はそれを送らせた最後のイベントの timeStamp。
- dd1(dedupe の再同期)・obs1(`document.title`)との結合は未確認(この木は 7f024d7。`client.ts`・`dedupe.ts` は変えていない)。
- 計測のコスト(§3.5)は『待機』と『ポインタ移動の流れ』の 2 つだけ。
- **バーストの長さ・間隔(2 秒・60 秒)の妥当性**、バースト中の入力が実機の画面(60〜120 Hz)でどれだけ遅くなるか(この機械のヘッドレスは 60 Hz 固定で、ホバー p50 +16 ms)は未確認。バーストで『画面の測定』が薄くなった分(`raf.total.n` が数百)、依頼者の機械の rAF の分布(p95、遅いフレーム)の精度が下がる。
- §4.3 の修正案(`tIdle + 1 ms` までのフレームに絞る)は試していない。

## PM の判断と取り込み(2026-11-04)

取り込み: `cbeacon2.diff` は HEAD 48cec69+dd1(24b4be0)に `patch -p1 --dry-run` が当たる(app/ の 22 ファイル、offset のみ)。`-` の行 112 本はすべて読んだ(ビーコン版・要約スクリプトの型・`LatencyTracker` の対応づけ・`DisplayMonitor` の連続ループの除去・パネルの P2 行・古い期待値の更新で、意図した書き換え)。PM の測定: typecheck 通過、vitest 1,287 passed + 7 skipped、Worker 43/43、e2e 1109/1109。lift/ には触れていない。

判断:

1. **P2 の遅延の判定は版 3 の `input.eventToRaf`(p95 ≤ 17 ms、閾値は不変)にする。** 定義と注意を `docs/milestones/performance-targets.md` §6 に追記した。版 2 の記録の `input.p95Ms` は旧定義で、17 ms と比べない。

3. **ノブの最初の押下の食い違い(app 26.8 に対し外側 61.9 ms)は直さない。** 既定の入口で無変化の再描画が毎秒 62 回あるのが原因で、`?dedupe` を既定にすると解消する。
4. **`?dedupe=1` を既定にする前の条件**: 見える変化のない入力が次の無関係なフレームで閉じる件(§4.3、ビーコンの p95 が 364 ms)を、eventToRaf の応答を「`tIdle + 1 ms` までに投函されたフレーム」に絞って直す。0170 の対応づけの絞り込みなので、別の作業(dd2)で実装し、単体テストと実エンジンで確かめる。それが済むまで `dd1-default.diff` は当てない。
