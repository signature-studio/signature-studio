## 2. 原因 1: XMM の素通り(`xabi.rs`)

混成では、C 経路は XMM を配列 `X[]` に持ち、直接部の関数は v128 のローカルに持って境界で `X[]` と交換する(決定 0164)。呼びの前に、呼び先が読む(要約 `xin`)レジスタのうち、その関数が自分で書いた物(`own`)を `X[]` に書き戻す(`flush = (xi | reload) & own`)。要約 `xin` は、各関数の逆向きデータフローの『関数の入口で live な XMM』。

`df` の呼びの処理は `live |= flush` で、呼び先の読み `xi` のうち**自分が書かないレジスタ(`xi & !own`)は live に入らない**。0x6649c0 は `sub rsp,0x28; call 0x4764c0; add rsp,0x28; ret` で、自分は xmm を書かず、呼び先 0x4764c0(`cvtss2sd xmm0,xmm0` で xmm0 を読む)の読みを素通しする。その `xin` が空になるので、呼び元の直接版 0x721280 が `call 0x6649c0` の前に xmm0(最終角度)を `X[0]` に書き戻さず、C 側の sincos は `X[0]` の古い値(直前の `call 0x4762e0`(atan2)の戻り値)で計算する。生成した wasm に `X[0]` の store が無いことを確認した(`call 0x6649c0` の前は R[] の store だけ)。

**実測(シャドウ、480 呼び)**: 修正前は 480/480 で出力の点 `[rdx]`・`[rdx+8]` とフレームの sincos 出力 `[rbp+0x28]`・`[rbp+0x2c]` が C 版と違う(atan2 の引数 dx,dy は一致)。例(call #1): 入力点 (794.386, 304.192)、原点 (960.97, 540.97)、`[obj+0x10c]` = −0.000376。C 版の (cos, sin) = (−0.5751, 0.8181) で出力 (794.475, 304.130)(入力とほぼ同じ回転)。直接版は (−0.8179, −0.5754) で出力 (724.19, 707.56)。修正後は 480/480 が**完全一致**(R[0..15]、X[0..15]、スタックの窓、出力メモリ、MXCSR 語)。0x721280 だけを lower した混成は修正後 82 行一致(hyb1 では不一致)。表 `tables/shadow-0x721280.txt`。

**修正**(`xabi.rs`): `df` に、呼びと tail の素通りの読み(`xi`、`Tail(g)` は `xin(g)`、`TailImport` は `IMP_IN`、`TailIndirect` は `IND_IN`)を含む第 3 の集合(`pass_in`)を足し、**要約 `xin` にだけ使う**(計画の入口読み込み `entry` と `flush` は従来のまま。生成物の差は素通り関数を呼ぶ箇所の `X[]` への store が増えるだけ。N=50 は +36 B)。`PASS_THROUGH_FLAG`(既定 ON)、`--no-pass-through` で従来の動作(単体テストの対照用)。素通りは flow-sensitive な kill をしない保守的な集合(必要な store が増えても足りなくならない)。

**単体テスト** `tests/xabi_passthrough.rs`: PE 3 関数(A: `addss xmm0,xmm1; call T; movups xmm0,[rcx]; ret`、T: `call g` 形と `jmp g` 形、g: `cvtss2sd xmm0,xmm0`)を混成で A だけ lower、T+g は C 経路の関数として JS で模す(`X[0]` を読んで 0x20000 に double で書く)。ホスト CPU(`_mm_add_ss`)と 300 入力で比較して一致、**`--no-pass-through` 相当では call 形・jmp 形とも 300/300 が不一致で落ちる**(テスト内で両方向を確認する)。(A が xmm0 を call の後で読むと、旧要約でも `reload` のために flush されて隠れる。そのため A は call の後で xmm0 を書き直す。)

## 3. 原因 2: 進捗カウンタ

- **カウンタが何に効くか**(コードを読んで確認): `fle_progress_count` は `fle_dispatch`(`lift/runtime/fle_dispatch.h` 221 行)で `++` され、`fle_progress_limit`(最初の CreateThread で arm、4096 個先)に達すると `fle_progress_slice()`(`fle_thread.c`)が呼ばれ、**仮想時計を `FLE_PREEMPT_SLICE_TICKS`(10000 tick = 1 ms)進め**、待ちの時刻が来たスレッドを起こし、次の ready なスレッドに切り替える(決定 0147、`S-vclock-slice-*`、出典なしの選択)。つまり**診断ではなく、ゲストの時間列とスレッドの順序を決める**。
- **なぜ C 経路の静的 jmp は数えず、実行時探索は数えるか**: fe-lift は fe-decode が解決した間接 call/jmp(IAT/RIP table/レジスタ定数)を静的な `f_X()`/goto にし、`fle_dispatch` を通るのは未解決の間接分岐だけ。`fle_dispatch` の `++` はその中にある(決定 0147 の『見つかった間接 call は 1 単位』の実装は、静的に解決された物を数えない)。直接部は、解決先が opaque(`flags::analyze` が失敗する、継続入口など。呼びの効果の要約が無いので関数として呼べない)な jmp を `TailIndirect`(実行時のスロット値の探索)に戻し(`lib.rs` の demote)、混成ではそれが `fle_hyb_dispatch` = `fle_dispatch` なので数えられる。
- **実測**: ディスパッチ列を D と『全部』(`--static-calls --sync-saved`、`--hybrid-progress` 無し)で比べると、D は wiz0 まで 10,881,831 回、混成は 10,881,833 回(g3-progress と同じ。+2)。最初の差は 10,803,323 番目で、混成にだけ `0x329fb00`(dsp の大きな関数、opaque。objdump のシンボル名は最寄りの物で当てにならないので書かない)の dispatch が 2 回(`0x3056160`(`jmp [r10+8*rax]` の表)→ `0x3058e20`(`mov rax,[0x454c808]; jmp rax`)の jmp rax)。2 つ挿入した後は列が一致(比較した 78,508 のうち対象の不一致は 2)。以後の g3-progress は +34〜+38、a3000 だけ −152(snapshot の時刻が slice の境界で動いた)。
- **修正**: `--hybrid-progress ADDR`(ADDR = C 部の `fle_progress_count` のアドレス、`link.map`)。demote された jmp(`Fun::demoted` に記録)の前に `*(u64*)ADDR -= 1` を入れる(dispatch が +1 するので正味 0。`count < limit` が保たれているので slice も起きない)。単体テスト `tests/hybrid_progress.rs`(アドレス無しは +1、有りは ±0)。代替(C 側に数えない dispatch 関数を足す)は C 部の再リンクが要るので採らなかった(S-hyb3-3)。

## 4. 原因の切り分け(C 経路の誤りか、直接部の誤りか、未定義挙動か)

| 差 | 原因 | 区分 | 根拠 |
|---|---|---|---|
| 0x721280 の角度 | 素通り関数の xin が空 | **直接部の誤り** | シャドウ 480/480(修正前不一致、後一致)、生成 wasm に store が無い |
| hyb1 2 段目の別の 148 関数(`set-sceT2d`、fle) | 同じ素通り | **直接部の誤り** | `--no-pass-through` で不一致、修正で一致(82 行) |
| progress +2/+34 | demote した jmp が数えられる | **直接部と C 経路の数え方の違い**(どちらの誤りでもない) | ディスパッチ列(上) |
| `--static-calls` の要否 | 解決済み間接 call を C は数えず直接部は数える | 同上 | v3 の run で wiz0 の `clock_ms` が 3602165 対 3601776(D)= **+389 ms**(余分に数えた約 160 万回 ÷ 4096)。D と同じ数え方にしないと時間列が変わる |

**『C 経路の静的化は実行時のスロット値と違うか』(決定 0169 §12.1 の PM 判断点)**: `--static-calls` 無しの run(v3)のディスパッチ列を D と比べ、D に無い余分な dispatch(wiz0 より少し先までの先頭 12,000,000 回の中に 1,629,226 回、異なる (対象, 戻り番地) 88 組)について、戻り番地の `call` の D の静的な呼び先 `f_X` と実行時の対象を突き合わせた: **1,623,169 回(99.6%)で一致、反例なし**。残り 6,057 回は `[rsp]` が戻り番地でない値(tail dispatch。D にも同じ対象が出る)で突合できない。つまりこの経路で C 経路の静的化は実行時の値と同じ先を呼んでいる(違いは数え方だけ)。**C 経路の誤りは見つからなかった**。ただし範囲は『この run で実行された呼び』で、スロットがゲストに書き換えられる別の経路は未確認。

## 10. 未決の点(PM)

1. `--no-pass-through` の既定: 修正を既定 ON にした(不具合の修正)。
2. `--hybrid-progress` `--static-calls` `--sync-saved` の製品型での扱い: 『全部』では 3 つとも必須。N=50 は無しで一致、N=200・1000 は 3 つ付きで確認(個別の要否は N=1000 で未測定)。付けると速度は落ちる(`--sync-saved` は呼びごとに最大 8 store)が、N=1000 の steady は −45% まで下がっている。**N=1000 の製品型は 3 つ付きを標準にする案**。
3. 非原子 RMW(xadd/cmpxchg/xchg のメモリ形)は、SharedArrayBuffer のスレッドを入れない間は許容(hyb1 の PM 判断をそのまま引き継ぐ。本作業では触っていない)。
4. 数え方を D に合わせる(S-hyb3-4)ことが仕様。決定 0147 の字句と違う点を認めるか。
5. **製品型の候補は N≈1000**(node steady −45%、wasm +1.2%〜1.4%)。ただし Chrome では最初の idle は D と同じで Chrome 全体の CPU は idle までに +23%、steady のエンジン Worker は −13% にとどまり、node の RSS が +1 GB。N=1000 を標準にするかは、RSS の原因調査と fin1 の束の上での一致確認の後に決める案。N=200 の製品型と、『全部』の製品型は作っていない。

取り込み: `hyb3.diff`(fe-wasmgen の 7 ファイル、587 行。HEAD 4933389 に `patch -p1 --dry-run` が offset・fuzz・reject なしで当たる)。`-` 行 14 本(`Fun {…}` の構造体初期化、`Config {…}`/`Ctx {…}` の初期化に新しい項目を足した置換、`df` の旧版の関数本体)を読み、意図した置換だけで他の決定の変更の巻き戻しは無いことを確認した。fe-lift・runtime には触れていない。全体テスト **164 results / 2,194 passed / 0 failed**(基準 162/2,192 に新規 2 実行ファイル〔xabi_passthrough、hybrid_progress〕と +2 テスト=担当の予想 163/2,166 より +1 実行ファイル分多いが、新規テストファイルの数と一致)。FLEngine の生成 C は fe-lift を変えていないので不変。PM は 82 行の一致・速度・Chrome を再測定していない(担当の実測)。進捗(G 段階)には数えない。

1. **xabi の素通りの修正は既定 ON**(`--no-pass-through` で従来動作)。N=50 の出力差は +36 B。修正を切ると 300/300 不一致で落とすテストがある。採用。

3. **『全部』(90,418 関数)は採らない**(起動 +25%、wasm 313 MB、steady の利点なし)。
4. **進捗カウンタは仮想時計に効く**(4096 回ごとに 1 ms 進めスレッドを切り替える。決定 0147)。直接生成の数え方は『D と同じ数え方』が仕様。3 フラグ(`--static-calls`、`--sync-saved`、`--hybrid-progress`)は『全部』では全て必須、N=50 は不要。出荷構成にするときは全て付ける。
