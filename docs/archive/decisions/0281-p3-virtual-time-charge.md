## 結論

1. **P3 の書き込みが『1 ブロック周期 → 3 ブロック周期(ちょうど 1/3)』に落ちる原因は、ブラウザの IdleDriver(setTimeout の下限・遅れの切り・bounce・Sleep(1) の粒度)ではなく、エンジン内の仮想時間の課金(決定 0147: 間接呼び出し 4096 回 = 仮想 1 ms)**。根拠(実測): (a) 本番 60 s で仮想時計は実時間と 1:1(1.000〜1.023)、再生中の lagCuts 0、bounce は idle() の 1%、timer の待ちは 1 回 5〜22 ms(§2)。(b) ミキサーの 1 周(Unlock → 次の Unlock)を仮想 ms で見ると、1 ブロック(92.88 ms)に対して 1.0 → 約 2 → 約 3 で、native N1 と同じ形(§3)。(c) **課金の定数だけを変えると 1 周が単調に変わる**: 4096 回で約 3 ブロック、8192 回で約 1.6、16384 回で約 0.8(§3)。
2. **課金を軽くすると、律速は『仮想時間の課金』から『この機械の CPU』に移り、実時間の書き込み率は約 0.5 で頭打ち**: 30〜60 s の平均が 4096 回 0.29〜0.37、8192 回 0.41、16384 回 0.50。16384 回では仮想 s / 実 s が 0.41〜0.49(仮想時計が実時間に追いつけない)、Worker 稼働 86〜88%。ミキサー(Worker の 64〜68%)+ UI(28〜31%)で CPU の天井 ≈ 0.5(この機械・この load・Chrome 156)。**P3(≥ 0.95)は課金の見直しだけでは届かず、ミキサーと UI の CPU の削減が別に要る**(読み)。
3. **直し方の選択肢**は §4 の表(PM が選ぶ。mt3 の『複数の仮想 CPU』の行は mt3 が足す)。実機の FL が見る時間に最も近いのは (b)『ブラウザでは実 CPU 時間で課金する』で、決定性(node の行・a4)を別の道で守る必要がある。(a) の定数変更は出典なしの選択のまま。(d) は契約違反。
4. **決定 0147 §4.3 と `fle_thread.h` のコメントの『環境変数 `FLE_PREEMPT_DISPATCHES` / `FLE_PREEMPT_TICKS` で数を替えられる』は、d6926b4d の `lift/` に実装がない**(`git grep` でコメントと `wall_fr20.rs` の `env_remove` だけ)。測定のために 1 行の定数を変えて増分ビルドした(約 15 分)。測定用に環境変数を実装すれば、再ビルドなしで課金を替えて測れる(提案。実装していない)。

## 4. 忠実な直し方の選択肢(PM が選ぶ。実装はしていない。mt3 が『複数の仮想 CPU』の行を足す形にしてある)

前提(§3 の測定。読み): 実時間あたりの書き込み率は **r ≈ min(1, (仮想 s / 実 s) ÷ (1 周 / 1 ブロック))**。1 周 / 1 ブロックは課金が決める(仮想時間の量)。仮想 s / 実 s は、CPU に余裕があれば IdleDriver が 1.0 に保ち、CPU が足りなければ 1 未満になる(CPU の天井 r ≲ (1 − u) / m。u ≈ 0.3 = UI の CPU 割合、m ≈ 1.3 = 音 1 s あたりのミキサーの CPU 秒、いずれも 16384 回の run からの読み)。いまの本番(4096 回)は前者が効いている(1 周 3 ブロック × 仮想 s / 実 s 1.0 → r ≈ 0.33)。16384 回は後者(1 周 0.85 ブロック × 仮想 s / 実 s 0.45 → r ≈ 0.5)。

## 6. S-gpu7-N(出典なしの選択)と自己申告

- **S-gpu7-13**: テストの定数 8192 / 16384(4096 の 2 倍・4 倍)。出典なし(単調性が見えれば足りる)。
- **S-gpu7-14**: 1 周の仮想時間は、pulse(2 Hz)の `virt` を Unlock のページ時刻で線形補間して出した(読み。pulse の間隔 0.5 s の内側は直線と仮定)。

**自己申告**:
1. **run ごとの load が揃っていない**(16384 回 5.3、対照 5.8〜12.7、8192 回 11.2、本番 6.6→2.6)。実時間の量(書き込み率、Worker 稼働、仮想 s / 実 s)は load の違いを含む。仮想時間の量を主な証拠にした。load の高い他の担当のビルドが走る時間帯で、揃えられなかった。

5. **未解明の 2 点を残した**: (a) CPU 律速でも Worker の event-loop idle が 12〜14%(1 回 12〜15 ms を約 10 回/s)ある。(b) 4096 回でも、試作 bundle は本番より Worker 稼働が高く(90% 対 76%)仮想 s / 実 s が低い(0.82〜0.87 対 1.0)。bundle の違い(HEAD b00932ec 対 d1697a30 の木 + L1)と load の違いのどちらかは分けていない。

## PM の決定と取り込み(2026-11-06 10:55、docs のみ)

取り込み: gpu1 の因果テスト(測定専用 bundle: 間接呼び 4096 → 8192 / 16384 回 = 仮想 1 ms)の結果の文書・表・道具を `docs/investigations/gpu7/` に置いた。測定専用 bundle は製品ではなく、差分に入っていない。測定は実 Chrome 156 で実エンジン、run ごとの load は 5.3〜12.7 で揃っていない(実時間の書き込み率は参考、仮想時間の量を主な証拠にした)。**依頼者の機械は 0 件**。
判断:
1. **3 ブロック周期の原因は『エンジン内の仮想時間の課金』と確定として扱う**(ブラウザの 4096 回は native N1 と同じ形で、IdleDriver・実 CPU の速さに依らない。16384 回でミキサーの 1 周が 0.7〜1.0 ブロックに戻る)。native の側の裏づけは決定 0274(alpha1)、DirectSound の契約の監査は決定 0273(mt3)、課金の較正の設計と選択は決定 0275 / 0279(mt3)。

3. 未確認: CPU 律速でも Worker の event-loop idle が 12〜14% ある理由。試作 bundle(4096 回)が本番より Worker 稼働が高い(90% 対 76%)理由。
