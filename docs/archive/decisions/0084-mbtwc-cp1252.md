# 0084: MultiByteToWideChar — cp1252 の 0x80〜0xFF を、Microsoft が公開するコードページデータファイルに従って変換する（0016 の範囲の拡張。仮の決定）

状態: PM の決定（2026-10-24）を、作業者（サブエージェント）が記録し、実装した。**仮の決定**（実機の Windows 10 22H2 で未確認。撤回条件は下）。事実の出典は `docs/investigations/mbtwc-high-bytes.md`（以下「調査」。節番号はその文書のもの）。この記録は調査に無い主張を足さない。決定 0016（ロケール。「表がページに無ければ停止」）を、cp1252 の MB→WC に限って改める。

## 背景（事実。調査の節番号）

- DllMain(ATTACH) の CRT のロケール初期化（`0x17d674c`）は、cp = 1252、dwFlags = 1、cbMultiByte = 256 で、`buf[0] = 0x20`、`buf[1..255] = 0x01〜0xFF` の 256 バイトを MultiByteToWideChar に渡す。0x80〜0xFF の 128 バイトが入る（調査 §2.5。読み。引数は既存ログの実測と一致）。
- 決定 0016 の限界の項は「MultiByteToWideChar、WideCharToMultiByte は UTF-8 と、ANSI/OEM の ASCII（0x80 未満）だけ。0x80 以上は 1252、437 の表が MSDN のページにないので abort」と書いていた（調査 §3.3）。調査 §3.1 の掃引では、cp ∈ {0, 1, 3, 1252, 437} × dwFlags ∈ {0, 1, 8, 9} の 20 通りすべてで 0x80〜0xFF の 128 バイトが停止し、256 バイトの呼び出しはサイズ問い合わせ（cch = 0）でも停止した（実測）。
- Win32 の Learn のページ（MultiByteToWideChar、GetCPInfo、CPINFO、Code Page Identifiers、Code Pages）に、1252 の 0x80〜0xFF の Unicode 値は無い（調査 §4.1〜§4.3）。表は、Microsoft が公開するデータファイル（`CodpageFiles/1252.txt` の `MBTABLE 256`）にある（調査 §4.4 の 2）。
- 1252 の表の自由度は 0x80〜0x9F の 32 件だけ。0x00〜0x7F と 0xA0〜0xFF は恒等（調査 §5.1）。

## 出典（調査 §4.4 の 2 が 2026-10-24 に再取得して機械的に確認した引用に限る）

- [MS-UCODEREF] 2.2.2「Supported Codepage Data Files」: 「The data files of supported system codepages are published as specified in [CODEPAGEFILES], [UNICODE], and [UNICODE-BESTFIT]. … bestfit1252.txt contains the data for codepage 1252.」
- [MS-UCODEREF] 1.2.1「Normative References」: 「[CODEPAGEFILES] Microsoft Corporation, "Windows Supported Code Page Data Files.zip", 2009」。
- [MS-UCODEREF] 3.1.5.1.1.3「Pseudocode for Mapping a Codepage String to a UTF-16 String」: 「OPEN SECTION SingleByteMapping where section name is MBTABLE from file with the name of CodePageFileName」。SBCS では MBTABLE の第 1 欄の一致する行の第 2 欄を出力する。
- [MS-UCODEREF] 2.2.2.1.2「MBTABLE」: 「The MBTABLE tag marks the start of the mapping from single-byte bytes to Unicode UTF-16.」
- Learn の MultiByteToWideChar のページ（ms.date 2024-02-05）: 「Fail if an invalid input character is encountered.」（MB_ERR_INVALID_CHARS）。無効な文字の定義は「A character that is not the default character in the source string, but translates to the default character when MB_ERR_INVALID_CHARS is not set.」と DBCS の先頭バイトだけの文字。1252 に対する dwFlags の制限は書かれていない（調査 §4.1）。
- unicode.org が公開する `bestfit1252.txt`（37057 バイト、SHA-256 `72ea23c939c5b26fae7aded0207b327e2f3902d7d3c168d7087f5cfc38ee76a9`）は zip の `1252.txt` と同一（調査 §4.4 の 3。再取得で確認）。

## 範囲と実装した動作

- cp が 1252（`CP_ACP` = 0、`CP_THREAD_ACP` = 3（emulated のスレッドロケールのとき）を含む。cp の解決は既存の `fle_cp_resolve`。変更なし）の MB→WC で、バイトが 0x80 以上でも停止せず、次の表で UTF-16 の 1 単位に写す:

  | バイト | 値 |
  |---|---|
  | 0x80〜0x9F | 80=U+20AC 81=U+0081 82=U+201A 83=U+0192 84=U+201E 85=U+2026 86=U+2020 87=U+2021 88=U+02C6 89=U+2030 8A=U+0160 8B=U+2039 8C=U+0152 8D=U+008D 8E=U+017D 8F=U+008F 90=U+0090 91=U+2018 92=U+2019 93=U+201C 94=U+201D 95=U+2022 96=U+2013 97=U+2014 98=U+02DC 99=U+2122 9A=U+0161 9B=U+203A 9C=U+0153 9D=U+009D 9E=U+017E 9F=U+0178 |
  | 0xA0〜0xFF | バイト = 単位（恒等） |

  この 32 件は、zip の `CodpageFiles/1252.txt` の MBTABLE から機械的に取り出し、調査 §5.1 の表と一致することを実装時に確かめた（32 件、不一致 0。恒等でない 27 件、恒等の 5 件 = 0x81、0x8D、0x8F、0x90、0x9D）。
- dwFlags 0、1、8、9 は同じ結果。MB_ERR_INVALID_CHARS（8）が付いても、0x80 以上のバイトは無効扱いにしない（5 つの未定義バイトを含む）。単一バイトのコードページでの 1 と 2 の同時指定（3、7）、0x10 以上のビットは従来どおり 0 と ERROR_INVALID_FLAGS。
- MB_COMPOSITE（2）、MB_USEGLYPHCHARS（4）を含む dwFlags は、従来どおり名前付き停止（バイトが 0x80 未満でも。0016 のまま）。
- 個数の問い合わせ（cchWideChar = 0、出力 NULL）は、他の cp と同様に全バイトを走査して個数を返す。256 バイトで 256。
- 変わらないもの: cp437（`CP_OEMCP` = 1 を含む）と他のコードページの 0x80 以上（従来どおり名前付き停止）。WideCharToMultiByte、GetStringTypeW、LCMapStringW、CompareStringW。UTF-8 の変換。（**0087 の注記（2026-10-24）**: このうち WideCharToMultiByte（cp1252）、GetStringTypeW（CT_CTYPE1）、LCMapStringW（0x100／0x200 と Locale = 0）は 0087 で範囲 D に限り変わった。CompareStringW、UTF-8、cp437 は変わらない。）

## 仮の点

- **未定義の 5 バイト（0x81、0x8D、0x8F、0x90、0x9D）**: 同じ数値の C1 制御に写し、MB_ERR_INVALID_CHARS でも無効にしない。Learn のページはこの場合を定めない（ページの「無効な文字」の定義は、既定文字に変換されるもの、と DBCS の先頭バイトだけの文字）。MBTABLE にはこの 5 件の行がある（調査 §4.1、§5.1）。これは読みで、実機の動作ではない。
- **0x80、0x8E、0x9E**: 旧版（Learn のアーカイブ `cc195054`、ms.date 2008-02-06、本文は画像のみ）は NOT USED（FFFE）とし、現行のデータファイルは U+20AC、U+017D、U+017E を持つ。**この食い違いは未確認の差**。どちらが Windows 10 22H2（決定 0014）の実際の動作かは確認できていない（調査 §5.1 の末尾。現行のデータファイルの方が自然に思える、は推測）。この決定は現行のデータファイルを採る。旧版の画像は、0x82〜0x8C、0x91〜0x9C、0x9F の 24 件がデータファイルと一致した（目で転記した値。0xA0〜0xFF は照合していない。調査 §4.4 の 1）。
- データファイルが「MultiByteToWideChar の仕様」として Win32 のページからリンクされているわけではない（MS-UCODEREF 3.1.5.1.1.3 は旧来の動作を表す疑似コードで、MultiByteToWideChar は名指ししない。調査 §4.4 の末尾。読み）。dwFlags（MB_PRECOMPOSED、MB_COMPOSITE）の効果、MB_ERR_INVALID_CHARS の判定は疑似コードに無い（調査 §8）。
- データファイルの知財: MS-UCODEREF の概要ページの知財の通知（「…you can make copies of it in order to develop implementations of the technologies that are described in this documentation … This permission also applies to any documents that are referenced in the Open Specifications documentation.」。調査 §4.4 の 2）が、zip のデータの再利用に及ぶかの法的な解釈は、この決定では行わない。zip のファイル自体にライセンス文は無い（調査 §4.4 の 2）。

## 撤回条件

- (a) 実機の Windows 10 22H2 で、バイト 0x80、0x8E、0x9E、または 5 つの未定義バイトの結果が上の表と違うと確認されたとき。
- (b) 知財上の異議があったとき（撤回して従来の名前付き停止に戻す）。

## 実装した場所

- `lift/runtime/fle_locale.c`: `fle_cp1252_hi[32]`（`static const uint16_t`。出典のコメント付き）、`fle_mb_to_wide` の単一バイトの経路（cp1252 のとき表を引く。引数に `cp1252` を追加）、`fle_imp_MultiByteToWideChar`（`cp == 1252` を渡す。cp は `fle_cp_resolve` の結果）。cp437 の停止のメッセージは「byte of 0x80 or above in a single-byte code page other than 1252: table not adopted (decision 0084 covers 1252 only)」に変えた。新しい .c、.h は作っていない。
- `lift/runtime/test/gen_cp1252_expect.py`（zip の `1252.txt` から期待の 256 行を書くスクリプト。標準ライブラリのみ。zip と 1252.txt の SHA-256 を先に検査する。出力先が既にあれば書かない）と、その出力 `lift/runtime/test/cp1252_expect.txt`（テストが読む）。

## テスト（`lift/crates/fe-lift/tests/locale.rs`）

期待の表は `cp1252_expect.txt`（上のスクリプトが zip から作った 256 行）から読み、runtime の配列のコピーは使わない。テストの実行に zip は要らない（zip は gitignore された作業物にしかない）。

- `mbtwc_cp1252_every_byte_one_by_one`: cp1252 の全 256 バイトを 1 バイトずつ、dwFlags 0、1、8、9 のすべてで、期待表と一致。
- `mbtwc_cp1252_all_256_bytes_at_once_and_the_size_query`: 256 バイト一括、dwFlags 0、1、8、9 のすべてで期待表と一致。個数の問い合わせ（cchWideChar = 0、出力 NULL）は明示長でも -1 でも 256。バッファが 256 単位ちょうどで通り、255 単位で ERROR_INSUFFICIENT_BUFFER。
- `mbtwc_cp_acp_and_thread_acp_are_1252`: CP_ACP（0）と CP_THREAD_ACP（3）が cp1252 と同じ結果。
- `mbtwc_cp1252_composite_and_glyph_flags_still_stop_on_a_high_byte`: dwFlags 2、4、5、6、0xa、0xc が 0x80 以上のバイトに対して名前付き停止（SIGABRT、メッセージに `MB_COMPOSITE or MB_USEGLYPHCHARS`）。cp1252 の 256 バイト一括、CP_ACP でも。
- `mbtwc_cp437_high_byte_still_stops`: cp437 と CP_OEMCP（1）の 0x80 以上が従来どおり名前付き停止（dwFlags 0、1、8、9、256 バイトのサイズ問い合わせを含む）。
- 既存の `undefined_cases_abort` の行 `mbtwc-high-byte-1252`（cp1252 の 0x80 で停止を表明）を、cp437 の行 `mbtwc-high-byte-437` に直した（cp1252 の新しい挙動に合わせた）。

## 限界

- **実機の Windows では未確認**。ホストは Linux。表は Microsoft のデータファイル（Microsoft が公開した表）であって、実機の動作そのものではない（調査 §8）。
- この決定で動くのは cp1252 の MB→WC だけ。ATTACH が MultiByteToWideChar の先で通る GetStringTypeW（C1 の文字分類）、LCMapStringW（lcid = 0 と 0x80 以上）、WideCharToMultiByte（1252）は、決定していない（調査 §5.3、§6）。実測した次の停止は `docs/investigations/two-module-after-0084.md`。（**0087 の注記（2026-10-24）**: この 3 つは 0087 で範囲 D に限り実装した。決定 0087 の後の実測は `docs/investigations/two-module-after-0087.md`。）
- **ATTACH は完走しない見込み**。調査 §5.3 は、MBTWC を通した先に別の 3 つの表（GetStringTypeW、LCMapStringW、WideCharToMultiByte）が要ると書く。この決定の実装で DllMain が戻るかは、`two-module-after-0084.md` のとおり、次の停止（GetStringTypeW）で止まるので、未達。
- cp437 の 0x80 以上、CP_OEMCP の変換は、必要になった時点で別の決定で扱う（ATTACH は 437 を使わない。調査 §3.2、§5.2）。
