## 1. 現状の読み(コードと既存の決定)

(読み。`lift/runtime/fle_thread.c` 1,460 行、`fle_thread_wasm.c` 141 行、`fle_sys.c`、`fle_event.c`、`fle_win.c`、決定 0050・0056・0092・0122・0124・0147・0173・0196 を読んだ。)

- **スレッドの仕組み**: ゲストの全スレッドは**1 本の JS スレッド(エンジンの Worker)の中の協調スレッド**(スレッド表 最大 256、1 本 = JSPI の 1 本の `WebAssembly.promising` スタック + 1 MiB の C シャドウスタック + 1 MiB のゲストスタック)。切り替えは待ち・譲りの API(`Sleep`、`SwitchToThread`、`WaitFor*`、`MsgWait*`、`GetMessageW`〔空〕、`WaitMessage`、競合した CS、`DwmFlush`、終了)と、**擬似プリエンプション**(決定 0147: 間接呼び出し 4,096 回ごとに仮想時計を 1 ms 進めて切り替える)。切り替えのたびに文脈(`R[16]`、`X[16]`、`YH[16]`、`FL`、MM、x87、MXCSR、`landing`、`seh`、コールバック深さ、トレース深さ、TEB・TLS ポインタ。約 1.6 kB)を**値でコピー**する。
- **仮想時計**: 全スレッドが待っているとき、最小の期限まで仮想時計を進める(`schedule()` → `next_deadline()` → `fle_sys_clock_advance_to`)。さらに擬似プリエンプションで『実行した間接呼び出しの数』が仮想時間を進める(= **仮想時計は仕事の量で進む**)。音声再生中はブラウザの AudioWorklet が実時間で消費するので、`fle_audio_paced` が『期限が実時間で来るまで進めない』(決定 0139)。ゆえに**エンジンが実時間より遅いと、仮想時間が実時間に追いつかず、リングが空になる**(= P3 の失敗の機構)。
- **決定性**: ゲストの動作は仮想時計と協調スケジューリングで決まり、同じ入力なら同じ出力(G3 の 16 スナップ 84 行、parity の 10 セッション)。
- **ゲストが使う同期の API**(静的、`docs/investigations/thread-model.md` §2): CS の Enter の呼び出し点(FLEngine 699、QFC 35、ILTools 24)、Interlocked* / SList、`WaitForSingleObject`(16 点)、`WaitForMultipleObjects(Ex)`、`MsgWaitForMultipleObjects(Ex)`、`SignalObjectAndWait`、`Sleep`(33 点)、`CreateEventW`/`SetEvent`/`ResetEvent`、セマフォ、SRW ロックと条件変数(Blend2D のみ)、TLS/FLS、`PostMessageW`/`SendMessageW`/`GetMessageW`/`PeekMessageW`。**LOCK 接頭辞付きの命令**は FLEngine 257、QFC/ILTools 各 113、Blend2D 201、freetype 21。
- **既存の決定との関係**(読んだもの): 0050(イベント: 表で持つ。T2 以前は『待てない非信号』を停止)と 0092(SRW ロック・条件変数: アドレスをキーにした表。競合は停止)は、**協調スレッドの下では競合しない前提**で書かれている(0122 が待ちに置き換えた)。実スレッドでは両方に本当のアトミックな待ち(`Atomics.wait` / `memory.atomic.wait32`)が要るが、再生中の呼び出しは SRW・条件変数・イベントの待ちとも **0 回**(§2.3)で、SRW は Blend2D(lifted)だけが使う(出荷構成は upstream Blend2D に差し替え済み)。0056(ゲストに見せるスレッド ID = 仮想値。2 本目以降は連番)は実スレッドでもそのまま使える(ID の割り当てをアトミックにするだけ)。0124 の JSPI の切り替えは Chrome で 1.0〜1.9 M 回/秒で、1 Worker の中の協調スレッドとして B′ の Worker 1 の中身にそのまま残る。0173(mt1)と 0186(pw1)は**プラグインを別 Worker に**出す設計(B/C。プラグインごとの別アドレス空間)で、本書の『ゲストスレッドを同じ共有メモリの別 Worker に』とは別。0224 は Cloudflare の Workers の話で、本書の Web Worker とは無関係。

### 2.4 UI とミキサーが共有するオブジェクトと CS の保持時間(実測 + 計算)

**共有する同期オブジェクトは CS の 4 個だけ**(UI とミキサーの両方が Enter する。アドレスは実行ごとに 0x20000 ずれることがある):

| CS | UI の Enter/s | ミキサーの Enter/s | UI の保持(平均 / p99 / 最大) | ミキサーの保持(平均 / p99 / 最大) |
|---|---|---|---|---|
| A(0x1bfce938 / 0x1bfee938) | 2,504 | 1,405 | 12 µs / 50 µs / 3.9 ms | 14 µs / 62 µs / 3.1 ms |
| B(0x16b6b20) | 1,129 | 1,191 | 49 µs / 219 µs / 4.1 ms | 19 µs / 80 µs / 10.3 ms |
| C(0x1c7637f0 / 0x1c7837f0) | 5.5 | 5.5 | 16 µs | 39 µs |
| D(0x16b6b48) | 1 | 5.5 | 15 µs | 7 µs |

保持 = 外側の Enter の終わりから Leave の始めまでの、そのスレッド自身の実行時間(run-clock)+ 保持中の `Sleep` 等の仮想時間。窓は再生中の 1 仮想秒を 10 秒おきに 3 回(3,994 仮想 ms)、`tools/mt2-hold.py`。**ミキサー専用**の CS で保持が長いものがある(`0x16b6aa8`: 1,190 回、平均 2.6 ms、p99 31.6 ms、最大 407 ms〔保持中に Sleep が入る〕)が、UI は再生中の 3 つの窓でこれを取っていない(= ミキサーのブロック処理用のロックと読む。**ユーザーがノブを回すなどして UI がこれを取る場合の UI の停止は未測定**)。

**衝突の見込み(読み。独立の位相の仮定)**: 保持の割合 u = 保持時間の合計 /(窓の仮想時間)(実時間 = 仮想時間の速度で動くとして)。相手の試行が保持中に当たる確率 = u、当たったときの待ち = 保持の残り時間 E[h²]/(2E[h])(長さ偏り)。窓だけで計算した値と、30 仮想秒全体の保持の合計〔`MT2C obj` の hold_ms〕から u を取った値の両方:

| 待たされる側 | 窓 3 回の計算 | 30 仮想秒全体の u を使った計算 |
|---|---|---|
| UI(ミキサーの保持に当たる) | 33.4 ms/仮想 s(3.3%) | 約 18 ms/仮想 s(1.8%) |
| ミキサー(UI の保持に当たる) | 22.3 ms/仮想 s(2.2%) | 約 8.5 ms/仮想 s(0.9%) |

= **試行の約 1〜4% が相手の保持に当たり、待ちは平均して数十〜数百 µs、まれに 4〜10 ms**。この値は**非混成のコードの速さ**での保持時間。混成で UI のコードが約 5 倍(0.19 倍の CPU)、ミキサーが約 3 倍(0.34 倍)になれば、保持時間が同じ比で縮み、待ちの割合は **約 0.2〜0.6%** になる(読み。保持時間が CPU 時間に比例するという仮定)。実スレッドでは CS の操作が共有メモリへのアトミックな RMW になるが、毎秒 1.2 万回 × 約 100 ns(キャッシュラインの往復)≒ 1.2 ms/s = 0.12% で小さい(読み)。

**待ちの分布(読み。同じ仮定で、x ms より長く待つ回数/仮想秒。共有する CS の A〜D の合計。`tools/mt2-hold.py` の末尾の表)**:

| 待たされる側 ← 保持する側 | 待ちが生じる | > 0.1 ms | > 0.5 ms | > 1 ms | > 2 ms | > 4 ms | > 8 ms |
|---|---|---|---|---|---|---|---|
| UI ← ミキサー(非混成の速さ) | 57 | 14.4 | 11.5 | 9.3 | 5.7 | 2.5 | 0.7 |
| ミキサー ← UI(同) | 82 | 17.3 | 11.5 | 8.7 | 3.9 | 0.03 | 0 |
| UI ← ミキサー(保持を混成最良の比 0.34 倍に) | 19 | 4.3 | 2.6 | 1.2 | 0.5 | 0 | 0 |
| ミキサー ← UI(保持を 0.19 倍に) | 16 | 2.1 | 0.4 | 0 | 0 | 0 | 0 |

= UI は最悪で 8 ms 超の待ちが毎秒 0.7 回(非混成)。フレームの予算 16.7 ms(60 fps)に対し 1 回の待ちは収まるが、まれにフレームが 1 つ落ちる。ミキサーは 4 ms 超の待ちがほぼ無く、余裕 約 50 ms(§8.3)に対し無視できる。**この分布は『UI が再生中に入力を受けない』場合**で、入力がミキサーの長い CS を取る場合は未測定(§13)。

### 2.4b 再生中にユーザー入力がある場合(実測 + 読み。**§2.4 の見積りを補正する**。`tables/cs-hold-times-uiplay*.txt`、`g3/ref1-ui-during-play.g3`)

PM の第 1 報への返信 1 が挙げた未測定の場合。操作列は、参照プロジェクトを開き、Space で再生し、再生中に**プレイリストのホイールズーム 20 回、中ボタンのドラッグ、左ボタンのドラッグ**(`ref1-ui-wasm.g3` の操作列を再生中に入れ替えた。窓は再生中の 7 仮想秒、同じ計数コード)。

- **UI が再生中にミキサー専用の CS(§2.4 で『UI は取らない』と書いた 0x16b6aa8)を取る**: 7 仮想秒に 31 回(約 4.4 回/s)。入力の無い再生では 0 回だった。= **ミキサーの『描画ロック』**。
- ミキサーはこの CS を**ブロック 1 つの描画の間ずっと保持**する: 保持の開始は 93 ms おき(= 4096 フレームの周期 92.88 ms)、50 回の保持(5 ms 超)の CPU 時間は**中央値 123 ms、p90 313 ms、最大 433 ms**(非混成・wasm-opt 前のこの木の値で、実時間より遅い構成〔ミキサー 1.1〜1.4 CPU 秒/仮想秒〕。保持の前後に QPC、小さな CS、SList の Push/Pop、`Elastique` の呼び出しが入っている)。保持の合計は仮想時間を超える(u = 1.08)= この構成は実時間に間に合っていない。
- **協調モードでは UI は待たされなかった**(31 回とも `b=0`)。保持は『間接呼び出しの数』で進む仮想時間では短く(Elastique の長い計算は間接呼び出しが少ない)、UI の試行と重ならない。= **協調モードの測定は、この競合を隠す**。実スレッドでは**壁時間**で重なる。
- **実時間の速さ(混成最良の比: ミキサー 0.34 倍、UI 0.19 倍)に縮めた見積り(読み)**: 描画ロックの保持 u = 0.37(ミキサーが 1 ブロックに約 42 ms〔= 123 × 0.34〕、周期 92.88 ms)、残り時間の平均 48 ms、UI の試行 4/s のうち約 37% が保持に当たる = **UI の待ち 約 79 ms/仮想秒(約 8%)、1.6 回/s、うち 8 ms 超が 1.4 回/s、最長は約 150 ms(433 × 0.34)**。ミキサー側が UI の保持に当たることはほぼ無い(UI の保持 平均 55 µs)。他の共有 CS(§2.4 の A〜D)の待ちは 1.2 ms/仮想秒以下。
- **含意(読み)**: 音(P3)は止まらない — ミキサーの待ちは µs 級。**ただしユーザーが再生中にプレイリストをズーム・ドラッグすると、UI が毎秒 1〜2 回、数十 ms(まれに約 150 ms)止まりうる**(60 fps で 1〜9 フレーム分)。これは FL が自分の設計で持つ競合で(ネイティブの FL でも UI はこのロックを待つはず。推測)、我々が足した物ではない。P2(UI の応答)の観点では、『再生中の UI 操作』が実スレッド化の合格線に要る(§9.1 の S3 に追加)。分割の効果(音が途切れない)と UI の滑らかさは別の指標。
- 以前の §2.4 の『衝突は 1〜4%、待ちは 1〜3%』は**入力の無い再生**の値。入力のある再生では UI の待ちが約 8% に上がる(上の見積り)。

### 4.5 混成(fe-wasmgen の直接 wasm)と共有メモリ(実測)

**構成**: 出荷の混成(`HYBRID_SETS=sse2-F2x` = HEAD の `F2xH5` の 1,009 関数、6 モジュール)を、同じ 8 イメージの木に(`tools/mt2-varh.sh` / `mt2-varh2.sh`。oggio・elastique は C 経路のまま)。`hp` = 非共有、`hs` = 共有(`HYBRID_FLAGS` に `--mem-shared`、C 部分に `MT2_SHARED=1`)。参照プロジェクトを開くための dec1 の wrap(`--wrap=fle_imp_GetFileType` ほか)は付けていない(混成の wasm-merge の名前の付け替え〔hyb6 の `HYB_RENAME`〕が要るため)ので、**この 2 つは参照プロジェクトを開けない**。起動 16 スナップと first idle だけを測った。

**見つけた問題と直し方(3 つ。すべて opt-in の差分に入れた)**:

1. **直接 wasm の memory import が共有でない型**(`1`)で、共有メモリの C 部分と合わない → `fe-wasmgen` に `--mem-shared`(import を `1 32768 shared` に)。既定の出力はバイト単位で不変(oggio 431 関数で `cmp` 一致)。`cargo test -p fe-wasmgen -p fe-decode`: 36 results / 187 passed / 0 failed。
2. **`hyb/strip_glue_stubs.py` の正規表現が `-pthread` の glue に合わない**(インデント無し、二重引用符、`/** @export */`)。『glue に missing function のスタブが残る』で停止 → 両方の形を受け付ける 2 行に。旧形式の glue は不変。
3. **wasm-merge は同じ `env.memory` の 2 つの import を統合せず、memory が 2 つになる**(最初の試行 `hs-v1`: コード部 156.1 MB 対 `hp` の 143.5 MB = **+12.7 MB**、memory 添字が全 load/store に付く読み。`wasm-opt` は『multiple memories require multimemory』で拒否。node では起動して 84 行が一致、起動 CPU は `hp` と同じ〔14.14 対 14.16 s〕)。→ C 部分に `-Wl,--export-memory`(import した memory を `memory` として再 export)を足し、直接部分は従来どおり `c.memory`(共有の型)を import すると、wasm-merge が 1 つに束ねる。

## 5. 第 2 Worker の最小の試作(mp1。**実エンジンではない**。同じ `WebAssembly.Module` + 同じ共有メモリを 2 つ目の Worker が instantiate)

- 比較用に `-DGLOBAL_R`(R/X が通常の大域変数 = 今の生成 C の形)。

### 5.2 試作中に直した誤り(自己申告)

最初の版では 2 つ目の Worker が 1 つ目の約 2 倍遅く見えた。原因は**カーネルが `helper_loop` にインライン化され、wasm には OSR(実行中の関数の置き換え)が無い**ため、1 回の呼び出しで走り続ける長いループが Liftoff(基本コンパイル)のままだったこと。`noinline` にすると 2 つ目の Worker も 1 回目の後に TurboFan へ上がり、同じ速さになった(2 本目 66 → 63 ms)。node と Chrome の両方で再現した。実エンジンでは `TMixerThread_DS.Execute` も長い `while` だが、その中の呼び出しは別の関数なので tier-up する(読み)。

### 5.3 『実 Worker の Sleep』の費用(実測。`tables/sleepcost-node.json`)

ゲストの `Sleep(1)` を実 Worker の `Atomics.wait(…, 1 ms)` にすると、1 回あたり **22 µs の CPU**(user 14.6 + sys 7.4)、壁 1.09 ms(node 24、load 38)。協調スレッドの切り替えは約 1 µs(決定 0124: 1.0〜1.9 M 回/s)。再生中の Sleep 系は MIDI 991 + ミキサー 195 + タイマー 62 = **約 1,250 回/s → Worker 1 の約 2.7%**(読み)。MIDI の 1 kHz ポーリング(`TMIDIThread`)が 8 割を占める。B′ では Worker 1 の中が協調スケジューラなので、全スレッドが待つときだけ 1 回の `Atomics.wait`(次の期限まで)で足りる(= 実際は 1 回/ms を下回る)。

## 6. 再現性(G3 の決定的なテストをどう保つか)

- **協調モードを残す**: 同じバイナリが `FLE_THREADS=coop`(既定。今の動作そのもの)と `real`(B′/A)を持ち、G3 の 84 行・parity 10 セッション・全体テスト・a4 は**協調モードで今のまま走らせる**。共有メモリ版が協調モードで今と同一であることは §4.2 で実測した(16 スナップ 6/6、参照プロジェクトの再生 55 行も一致)。
- **実スレッドの run は非決定**: 2 本の Worker の相互作用(CS の取り合い、`Sleep` の起床、メッセージ)の順序が実行ごとに変わる。**ゲートが比べるもの**(案):
  1. 起動〜ウィザード〜idle の安定した画面(UI スレッドだけが走り、他は待機): 協調モードと**画素・窓表が同一**(スナップ行のうち clock を除く部分)。
  2. 再生の**音声 PCM**(AudioWorklet のリングに書かれた最初の N ブロックのハッシュ): ミキサーはブロック単位(4096 フレーム)で決まった入力から描画するので、ブロックの境界が時間でなくサンプル数で決まる限り、協調モードと一致するはず(**読み。未確認**。UI の入力が無い再生セッションで比べる)。
  3. 不変条件: 停止行 0、スレッドの数・開始関数の一致、デッドロックの監視の発火 0、`GetExitCodeThread` の整合。
  4. 繰り返し(例: 20 回)で 1・2 の結果のばらつきを数え、**ばらつき 0 を合格線**とする(違いが出たら競合の兆候)。
  5. ネイティブの生成 C(clang)を `pthread` + `-fsanitize=thread` でビルドし、ランタイムの競合を機械で探す(wasm には TSan が無いので、ネイティブで同じソースを使う)。
- **Worker 内の規則は今のまま、ただし時計は実時間**: B′ では Worker 1 の中が協調スケジューラなので、スレッドの選び方の規則(作成順の巡回、優先度無視)は今と同じ。ただし実スレッドのモードの時計は実時計なので、`Sleep` の起床の順序は時間で変わる(決定的でない)。非決定の源は Worker 0 ↔ Worker 1 の間(§2.4 の共有 CS 4 個とメッセージ)と、この実時計の揺れ。ゲートの『20 回の繰り返しでばらつき 0』は、PCM のように時間に依らない出力に対して置く。

## 7. COOP / COEP の要件(c)

§1 のとおり**すでに満たしている**(`app/shared/headers.ts`、`app/worker/index.ts:160`、`app/tools/assets-middleware.ts`)。本番の Worker は全応答に COOP / COEP / CORP を付ける。ページは `crossOriginIsolated === true` で、共有メモリの `WebAssembly.Memory` が作れること、入れ子の Worker が動くこと(`worker-src 'self' blob:`)を Chrome 156・Firefox 158 の実ページ(§4.3)と mp1(§5)で確認した。Worker のスクリプトの応答にも COEP が付く(同一オリジンの配信)。新しいヘッダー・設定・ユーザー操作は要らない。

### 8.1 計算の前提

- 『P3 = Song Mode の再生で音が途切れない』は、**ミキサースレッドが 4096 フレーム(44.1 kHz で 92.88 ms)の締め切りまでに次のブロックを出す**ことで決まる。現在は UI とミキサーが 1 本の JS スレッドを分け合い(合計が 1 CPU 秒/仮想秒を超えると、仮想時間が実時間に追いつけず AudioWorklet のリングが空になる)、B′ ではミキサーが自分の CPU を持つ。

### 8.3 ミキサーの余裕(最適構成、読み)

- 1 ブロック 92.88 ms の締め切りに対し、ミキサーの CPU 0.48 s/仮想 s は 1 ブロック約 **43 ms**(= 0.48 × 92.88)。余裕は約 **50 ms**。
- UI とのロックの待ち(§2.4、§2.4b): ミキサーが UI の保持に当たる確率は約 1〜2.5%(入力の無い再生)で、待ちは数十〜数百 µs(まれに 4 ms)。**余裕 50 ms に対し無視できる**。再生中にユーザーが UI を操作しても、UI の保持は平均 55 µs と短く、ミキサーの待ちはほぼ変わらない。**逆に UI は、ミキサーの描画ロックを取るとき毎秒 1〜2 回、数十 ms(まれに約 150 ms)待つ**(§2.4b。音ではなく UI の応答の問題)。
- 起床の遅れ(§5.1): `Sleep(1)` + 再生位置のポーリング(1 ブロックあたり約 18 回)の 1 回 22 µs の CPU と数十 µs の遅れ。余裕に対し小さい。
- **DirectSound の再生カーソル**: 現在は仮想時計が進める(決定 0139)。実スレッドでは**実時間の AudioWorklet の消費位置**(リングの read インデックス)を `GetCurrentPosition` に返すのが Windows の契約に忠実で、音切れの検出(アンダーラン)もそのまま実時間になる(読み。未実装)。

## 10. 『lift の忠実性の方針』との関係(PM の第 1 報への返信 2 に答える)

方針: 新しい処理は (b) 外部 API の契約の実装 / (a) 余計な処理の除去 / 変換・通信の削減 のどれかでなければならない。

| 追加するもの | 分類 | 理由 |
|---|---|---|
| ゲストの文脈(`R`、`X`、`YH`、`FL`、MM、x87、MXCSR、TEB、TLS、`landing`、`seh`)を `_Thread_local` に | **(b) スレッドの契約の実装** | x86 の CPU 文脈はスレッドに属する(Windows のスレッドは自分のレジスタ・FPU/SSE 状態を持つ)。今は単一スレッドの前提で大域変数にしており、協調スケジューラは切り替えのたびに値でコピーしている(= **余計な処理の除去**でもある: 切り替えごとの約 1.6 kB のコピーが消える)。FL のクラス名・アドレスによる分岐は無い。**生成 C の形が変わる**(マクロ `R` などの定義だけ。生成物のテキストの変更はほぼ無い)ので opt-in(`FLE_THREAD_LOCAL_REGS`)にし、既定は変えない |

## 11. PM の判断点

1. B′ を段階導入の目標にするか(S1 から。S1 だけでも opt-in で単独に価値がある: 生成 C の LOCK の欠落の修正)。

5. 実スレッドのモードの音声ゲート(PCM のハッシュ)を合格線にするか(§6)。
6. プロセッサ数の応答(現行 1、決定 0017)を、実スレッドが動いた後で上げて FL 自身のスレッドバンク(`TSTBThread`)を使わせるか(別の決定)。

## 14. 付随して見つけた物(担当外。方針『余計な処理は見つけ次第報告』による)

1. **`fle_ld` / `fle_st` の可変サイズ `memcpy` が wasm の `memory.copy` になる**。`lift/runtime/fle_runtime.h` の `fle_ld(a, n)` / `fle_st(a, n, v)` は `memcpy(&v, ptr, n)` で、`n` が定数でない(インライン化されない)呼び出しでは emcc 6.0.12 が `memory.copy` を出す(`-matomics` の有無によらない。小さな C で確認)。非混成の参照プロジェクトの再生のプロファイルで `fle_ld` の自己時間は 7.7〜7.8%、`fle_st` は 1.7%(層『x86 命令の模倣』28.6% の中)。n ∈ {1,2,4,8} の単独の測定(node 24、2 億回)で、可変 n の `memcpy` は **4.4〜5.0 ns/回**、`switch (n)` + 定数サイズの `memcpy` は **0.9〜1.5 ns/回**(約 4 倍。`tables/memcpy-var-vs-switch.txt`、`lift/harness/mt2/mp1/ldbench.c`)。`FLE_ALWAYS_INLINE` の単位では `n` が定数になって問題にならない。**`fle_ld`/`fle_st` を n の switch にすると、非混成の再生の約 7% が取れる見込み(読み。混成の直接 wasm はこの関数を使わない)**。これは `lift/runtime` の変更になるので、この担当では差分を作っていない(変更するなら 84 行の同一性・全体テスト・a4・生成 C の sha の確認が要る)。
2. **共有メモリ版のリンクの警告**: `-pthread + ALLOW_MEMORY_GROWTH may run non-wasm code slowly, consider -sGROWABLE_ARRAYBUFFERS=2`(emscripten 6.0.12)。成長する共有メモリの上の JS の typed array(ページ側の `new Uint8Array(memory.buffer)` など)が遅くなりうる、という警告。wasm の側ではない。ページの JS の経路(表面のコピー・文字列の読み出し)への影響は**未測定**。
3. **wasm-merge は共有メモリの import を統合しない**(§4.5): 同じ `env.memory` を import する 2 つのモジュールを足すと memory が 2 つになり、コード部が約 9% 増える。C 部分に `-Wl,--export-memory` を足して直接部分が `c.memory` を import する形にすると 1 つになる。
