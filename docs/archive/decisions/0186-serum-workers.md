## 1. 結果

遅れ = そのブロックの**全員の応答**が (b+1)×92.879 ms(ブロックの予定の開始 + 1 周期)を過ぎた回数(A1。**/650 ブロック**)。『自身で周期超え』= 渡してから全員の応答までが 1 周期を超えたブロック(前のブロックの遅れの持ち越しを除く)。A2 = (b+2)×92.879 ms を過ぎた回数(出力に 1 ブロック = 92.88 ms の余裕がある場合)。最大の遅れ = 最も遅れた応答の予定の期限からの ms(**この値以上の出力余裕があれば、その run の遅れは 0**。ただし余裕を持たせると走り方が変わるので近似)。必要コア = Chrome 全スレッドの CPU 秒 ÷ 窓の実時間(約 60.6 s)。『他プロセスの CPU』= 許可した CPU の全プロセスの busy から Chrome を引いた値(窓の 1 秒ごとの 平均/p90/最大。`*` を付けた古い run は窓全体の平均だけ)。load は `/proc/loadavg` の 1 分値の窓の前→後。**CPU の HC は `taskset` で包んだ Chrome の `navigator.hardwareConcurrency`**(0-3 → 4、0-7 → 8、制限なし → 16)。**この機械の CPU は 8 物理コア × SMT の 16 論理で、`0-3` は物理 2 コア、`0-7` は物理 4 コア**。

## 2. 何をしたか(方法)

### 2.1 混成 wasm の再現(決定 0181 の手順を HEAD 996bd2d で再実行)
`git archive HEAD` を `lift/out-pw1/src/` に展開し、`cargo build --release -p fe-lift -p fe-decode -p fe-wasmgen`(HEAD のまま)。rebase 済み Serum2.vst3(srm1 の `Serum2.2000000.vst3`、SHA-256 a71adcda…)と種 `fix-s2w.txt`(`docs/investigations/hyb2/inputs/`)から `gen_vst3a.sh` で生成 C を作った(SHA-256 **c90fd52c38650436…**、43,918 関数 = 決定 0181 と同じ)。`hyb2.sh`(hyb2 の道具の写し。パスと `--rel-sites` の入力だけ変更)の `prep select strip n0 build gen merge` で、census の上位 N=123(全 process 候補)を直接 wasm にした混成を作った(`--mx-window --trap-vex --no-elide --lazy-ext --hybrid-merge --mx-packed --mx-rc --unbal-stub --opaque-stub --tail-all --rel-sites`)。直接部 4,440,378 B、全体 173,552,713 B。
HEAD の runtime には決定 0178 の `fle_filedlg.c` があり、`fle_imp_SHGetKnownFolderPath` が vst3a の `vst3a_imp.c` と二重定義になってリンクが落ちた。リンクに `-Wl,--allow-multiple-definition` を足した(リンク順で先頭の `h/*.o`=vst3a の定義が勝つ)。この選択は出力ハッシュで確かめた(下)。

### 2.2 Chrome の Worker ホスト(新規 `lift/harness/web/pw1/`)
- **1 インスタンス = 1 Worker**。同じ `WebAssembly.Module` を全 Worker で共有(Serum 用 1 つ、OTT 用 1 つ)。プラグイン本体・VFS の seed・音色データ(1.1 MB)・状態ファイルは SharedArrayBuffer で 1 つだけ持つ(mt1 の共有 VFS)。
- **ハーネスは無改造**。Serum のハーネスは process の前後で CPU クロックを 1 回ずつ読む(`srm1_thread_cpu_s`、Worker では `performance.now()`)。`RESULT init_cpu_ms`(DllMain→状態の設定→setActive が済んだ印)の後は、**1 回目の呼び出しで SAB スロットの要求を `Atomics.wait` し(32 KiB の入力をコピー)、2 回目の呼び出しで応答を書いて(32 KiB の出力をコピー)エンジン Worker を起こす**(mt1 の `pipe-plugin.js` と同じ方式)。OTT は mt1 の `vst-host.js` の `clock_time_get(3)` で同じ。入力の 32 KiB は代役(楽器に音声入力は無い。OTT は自分のハーネスの合成信号を処理する)。本物は process() と、受け渡し・起床・スケジューラの費用。
- **エンジン Worker** が T0 + b×92.879 ms(=4096/44100 s)に全インスタンスへ同時にブロック b を渡し(扇形)、全員の応答を待つ。遅れたブロックは飛ばさず、次をすぐ始める(混ぜる側が全員の出力を要するため。遅れは後続に波及する=閉ループ)。ブロックごとに、予定時刻・渡した時刻・各プラグインの「起きた/処理開始/処理終了」を記録する。
- **暖機**(`warm=1`): 本番のインスタンスより先に、**状態(の組)ごとに 1 個の捨てインスタンス(OTT は 1 個)**が同じ Module で自由走行する。最初のプロトコルは 150 ブロック、以後の既定は**実時間 25 秒 + 3 秒の静置**(`warmms=25000 settle=3000`。§4)。V8 の lazy compile と tier-up はコードが Module に属するので、本番インスタンスは暖まったコードで始まる(mt1 の設計)。`warm=0` は冷間(暖機なし)。
- **音**: 状態 s で 1 音(C4、ノート番号 60)をブロック 0 で押して 650 ブロック(60.6 秒)保持。`c` = 4 音和音(60,64,67,72)、`s` = 無音(音なし)。node の 650 ブロックの run で保持音の process 時間は減衰しないことを確かめた(状態 3 の中央値 24.0 ms、最小 23.0 ms)。

### 2.3 測定

### 2.4 位相をずらした独立リング(PM の依頼 1。`ring.html`・`ring-plugin-worker.js`・`ring-engine-worker.js`・`run-ring.mjs`)
ロックステップ(§2.2)の代わりに、**各インスタンスが自分の周期で自走し、出力を 4 スロットのリングに積む**。インスタンス k は T0 + b×92.879 ms + φ_k にブロック b を始める(遅れていればすぐ始める。先行はしない `ahead=0`)。その位相 φ_k は周期の黄金比列(φ_k = frac(k × 0.618034) × 92.879 ms。重い Serum を先に並べているので、重いものが周期の中で離れる)。**エンジン側(読み手)は何も渡さず待たず**、T0 + (b + 1 + lead) × 92.879 ms に各インスタンスのカウンタ(作ったブロック数)を見て、ブロック b が出来ていなければ『欠け』と数え、出来ていればリングから 32 KiB を読む(`lead=1` = 出力に 1 周期の遅延。ロックステップの A2 と同じ総遅延)。同じハーネス・同じ Module・同じ暖機(25 秒)。測るもの: 読み手の欠け(インスタンス × ブロック)と欠けのあるブロック数(/650)、他の読む時刻(lead 0・0.5・1・2)で数え直した欠けのあるブロック数、各インスタンスが自分の期限(自分の開始 + 1 周期)を過ぎた数、CPU・他プロセスの CPU・load。**P3 は Song Mode の再生(ライブ入力ではない)なので、1 周期の出力遅延は、再生開始が 93 ms 遅れ、ライブ演奏の応答が 93 ms 遅れるだけで、再生中の音の欠けには影響しない**(読み。FL 自身が PDC〔プラグイン遅延補正〕でミキサートラックごとに遅延を揃える〔決定 0173 の読み〕種類の遅延。実機の FL が何ブロック先行して process するか、ASIO バッファの大きさとの関係は未確認)。

## 6. P3 に向けた読み(**読み**。確かめていない解釈を含む)

**実測の骨格**(§1・§5): (a) 混成 Serum 2 は Chrome の Worker 1 本ずつに分けても、空いていれば process の最小が node の CPU 時間とほぼ同じで(状態 3: 最小 22.9 ms、p50 23.3〜23.8 ms 対 node の最小 23.0・中央値 24.0 ms)、K が増えても伸びない(HC=16 で K=6)。(b) 必要コア(CPU 秒/実秒)は決定 0181 の式にほぼ一致(Serum 6 個で +1〜8%、参照風で +0〜14%)。(c) 遅れは **CPU の総量ではなく** 次の 3 つで決まった: ① 状態 5 の 1 インスタンスの尾(遅れた回の最後に答えたのは、状態 5 を含む構成で 98% 以上が状態 5。process p50 62〜68 ms = 周期の 67〜73%、p99 103〜119 ms。状態 5 を 1 個だけ HC=16 で走らせても 44/650 遅れた〔`k1s5-hc16-r0`〕。遅れた区間でその Worker の CPU 時間の合計は process の wall 時間の和とほぼ同じ〔43.1 s 対 43.0 s〕=CPU を待たされたのではなく、同じ CPU 時間で約 1.7 倍遅く走った。他のプロセスが 4〜7 コア分走っていたので、SMT の兄弟スレッドを他のプロセスが使っていた間の遅さと読む。**他のプロセスが 1 コアほどの run でも起きる**: `heavy-hc8-r6`〔ロックステップ、物理 4 コア × SMT〕では、状態 5 の process が 200〜350 ブロック目の約 150 ブロックだけ 146〜162 ms(通常 70 ms)と 2.2 倍になり、遅れが 10 秒まで積もった。状態 5 の Worker の CPU は 55.9 s〔通常 約 43 s〕。他のプロセスは 1.0 コア。**自分の 18 本の Worker 同士が SMT の兄弟を取り合った**と読む)、② HC の小さい機械で全員を同じ瞬間に起こす扇形が起こす CPU の取り合い、③ 他のプロセス(この機械では 0.5〜13 コア分。`nice` が効かない autogroup 環境)による途切れ。

1. **CPU の量**: ピアノを除く 6 個の Serum がすべて鳴るとき 2.05〜2.19 コア。これに OTT 12 個(1 ブロック CPU 約 11.8 ms)を足した参照プロジェクトに近い構成で 3.5〜3.9 コア(式 3.4〜3.5)。『軽い 4 個が鳴り 2 個が無音、他は OTT 並み』は 2.6〜2.8 コア(決定 0181 の見積りは他 14 個で 2.82、式を今回の OTT 12 個・約 10.5 ms で直すと 2.5)。**見積りは CPU の量として当たっている(+0〜14%)**。外れていたのは、その先の『周期内に収まるか』。
2. **HC=4(この機械では物理 2 コアの 4 スレッド)は収まらない**。軽い構成(必要 2.6〜2.8)で 296/11/1、Serum 6 個(2.1)で 28〜75/650(A2 は 0〜2)、参照風(3.2)は 650/650/650 で遅れが増え続ける(最大 5.7〜9.0 秒)。物理 4 コアを 1 スレッドずつ(`0,2,4,6`)にしても、参照風は 650/650/650、軽い構成は 12/344/49。SMT の 4 スレッドは計算(§5.3)で理想の約 3 コア相当に見えるが、**扇形のリリースが平均需要より多い並列度を要する**ので、平均需要 3.2 コアの参照風は、理想の専有 4 コアでも遅れ続ける(計算)。
3. **HC=8(物理 4 コアの 8 スレッド)**: 軽い構成(2.7)は 0/0/209/0/2(209 は他プロセスの途切れ)で収まる。参照風(3.5)は 69/35/18/231/10(A2 27/1/0/167/0。231 は途切れ)で、他のプロセスが 1 コア以下の run でも 10〜69/650(1.5〜11%)遅れる。つまり **HC=8 で軽い構成は収まり、参照風はぎりぎり**。
4. **HC=16(物理 8 コア)**: 軽い構成は 0/0/31/2/86、参照風は 34/36/53/64/7(A2 は 12 の 1 回以外 0)。他のプロセスが 4〜8 コア分走る中での値。
5. **途切れ(他のプロセスの負荷の急な上昇)**: 他のプロセスが 1 秒ごとの最大で許可した CPU のほぼ全部(HC=8 で 7 コア分、HC=16 で 12〜14 コア分)に達した時、Worker が 6〜29 秒 CPU を待たされ、最大の遅れが 0.6・1.3・10.9・14・18 秒の run が出た(20 回中 4 回、K=6 の 1 回)。リングを 4 ブロック(372 ms)にしても吸収できない。**遅れ 0(P3 の字義)は、機械の空き具合が保証されなければ保証できない**。ブラウザは CPU の優先度を選べない(`taskset` はこの測定の道具で、製品では使えない)。
6. **余裕(先行レンダー)**: 暖機 25 秒の HC=8/16 の run 20 回のうち、最大の遅れが 1 ブロック(93 ms)以内に収まったのは 14 回、2 ブロック(186 ms)以内は 15 回、4 ブロック以内は 16 回(§1.8)。決定 0173 の S-mt1-lead(2〜4 ブロック)の方向を支持する: **2 ブロック(186 ms)あれば通常の run はほぼ吸収できる**が、上の 4 回は吸収できない。再生開始に 186〜372 ms の先行時間が要る代わりに、Song Mode の再生中の遅延は増えない。ライブ演奏(MIDI 入力)には使えない。
6b. **状態 5 は何が重いか(PM の依頼 2。`tables/state5-top10.md`、決定 0165 の native lift の命令数の統計)**: 状態 5 の process は 1 ブロックで x86 命令 51.3 M(状態 3 は 26.1 M の 2.0 倍。時間は 64 対 24 ms の 2.7 倍)、scalar SSE が 31%・packed SSE が 21%。上位 10 関数で命令の 49.9%、どれも**1 ブロック 4096〜24576 回(1〜6 回/サンプル)**呼ばれる小さい関数で、うち 4 個(命令の約 22%)は状態 3 では 0% = 状態 5 の音色が使う別の発振・フィルタの経路。6 個は N=123 の直接版に入っている(残り 4 個はアドレスが関数の途中=switch の case 継続で、親の wasm 関数に統合されている可能性が高い。未確認)。**読み・対策の候補**(どれも未実施): (i) 直接版の SIMD 化の拡大(srm1 の C 経路で `-msimd128` が 3〜22%)、(ii) 1 サンプルごとの小さい関数の呼び出しのインライン化(wasm の関数呼び出しのコスト)、(iii) 状態 5 だけ 2 ブロック先行して走らせる(リングの深さを個別に)、(iv) フリーズ(事前レンダリング)、(v) 位相を状態 5 に有利に置く(他の重いインスタンスと重ならない位相。計算では黄金比の位相でも状態 5 の尾は残る)。
7. **Serum の何を直すか**: 遅れの出所が状態 5(と、無い構成では状態 0・1)なので、状態 5 の process 時間を下げる。計算(§5.3 と `tables/sim-s6-state5-scale.tsv`、測った需要の再生)では、状態 5 を 20% 下げると理想の 4 コア以上で遅れが 3〜11/650 から 0〜7 に減る。0/1/3/4 は p99 が周期の 1/3 程度で余裕がある。4 音和音(状態 3)は node の中央値で 92 ms = 周期の 99% で、1 インスタンスでも 145/119/24 遅れる。
8. **位相をずらした独立リング(PM の依頼 1。§1.0b。Chrome で実装して測った)**: 各インスタンスが自分の周期で自走して 4 スロットのリングに積み、読み手が 1 周期後に読む(出力遅延 1 周期 = ロックステップの A2 と同じ総遅延)。**効いた所**: ① Worker の run-queue 待ちの最大が 6〜19 秒から 0.0〜0.4 秒に(18 本が一斉に runnable にならない)、② HC=8(物理 4 コア × SMT)の参照風で欠けが 0/644/1/0/2/0(644 は load 22 の途切れ。それ以外の 5 回は 0〜2)。ロックステップの A2 は 27/1/0/167/0/457/8/0(同じ分に交互に走らせた 3 組では 457/8/0 対 0/2/0)、③ HC=4(物理 2 コア × SMT)の参照風が『650/650/650 で遅れ続ける』から 131/145(約 21%)に。**効かなかった所**: ① HC=16 でも他のプロセスが 6 コア以上走る時(345/68)は 1 インスタンスの尾が残り、ロックステップの A2(0/0/0/12/0)と同程度かそれより悪かった、② HC=4 の参照風は必要 3.5 コアが 2 物理コアに収まらず欠けが残る、③ 他のプロセスが許可した CPU のほぼ全部を使う時間帯はどの方式も破綻する。計算(§5.3.1)の『専有 4 コアで足りる』は、HC=8 の測定(0〜2/650)と矛盾しない。実機の FL が全インスタンスの出力を同じ境界で要する構造か(ミキサーのグラフ、音源が同じ段にあるか)、何ブロック先行して process するかは未確認(読み)。
9. **プラグイン遅延補正(PDC)**: PDC は各プラグインが報告する遅延を揃える仕組みで、実行時間の揺らぎは吸収しない。揺らぎの吸収は先行レンダー(リングの深さ)で、PDC は『先行した分だけミキサーが出力を揃える』役に回る(読み。FL がプラグインの `getLatencySamples` を PDC に使うかは未確認、決定 0173)。
10. **ピアノ**(除外): どの構成でも 1 インスタンスが周期の 1.9 倍以上(決定 0181)。これを含めると HC がいくつでも **P3 は未達**(1 インスタンス = 1 スレッドで周期を超える)。フリーズ(事前レンダリング)か 1 インスタンスの並列化が要る(決定 0181 の PM 追記)。
11. **エンジンと GUI の分**: 今回の Chrome は何も描かず、エンジンの本体(約 1.0〜1.2 コア、決定 0166)も走っていない。それを足すと、参照風は 4.7〜5.1 コア、軽い構成は 3.8〜4.0 コア。物理 4 コア(HC=8)では参照風は収まらず、軽い構成が際どい。**HC=4 の機械では、ピアノを除いても、軽い構成も収まらない**(読み)。

## 9. 出典のない選択(S-pw1-…)

- **S-pw1-1 遅れの定義**: 全員の応答が (b+1)×92.879 ms(ブロックの予定の開始 + 1 周期)を過ぎたブロックの数(A1)。A2 は +1 周期。理由: 依頼の定義『処理完了が次の期限(開始 + k×92.88 ms)を過ぎた回数』。代替: 期限に余裕(余分な出力バッファ)を持たせる深さ A=2,3、遅れた ms の閾値(5 ms、20 ms も併記)。
- **S-pw1-2 閉ループ**: 遅れたブロックを飛ばさず次をすぐ始める。理由: ミキサーが全員の出力を要する。代替: 期限で捨てる(音が欠ける回数を直接数える)。
- **S-pw1-3 扇形のリリース**: 全インスタンスに同じ瞬間にブロックを渡す(HC が小さいと、ここで 1 周期あたりの CPU 仕事が一斉に起きる)。代替: インスタンスごとに位相をずらす(未実施)。
- **S-pw1-4 暖機**: 状態(の組)ごとに 1 個の捨てインスタンス(OTT は 1 個)が同じ Module で自由走行してから本番。2 つの方式を測った: (A) 150 ブロック(Serum で 4〜14 秒相当、OTT で約 1.6 秒。最初の測定のプロトコル。`results-w150/`)、(B) **実時間 25 秒**走らせ、さらに 3 秒置く(以後の既定。`results/`)。理由: 暖機 40 ブロックだと本番のブロック 59〜69 で山(66〜246 ms)、150 ブロックでも負荷の高い run で本番の最初の約 80 ブロックが約 2 倍遅かった(§4)。代替: 650(全部)、なし(冷間。測った)、tier-up 完了の検出(未実装)。
- **S-pw1-5 音**: 1 音 C4 を保持(状態 0/1/3/4/5)、和音 4 音(状態 3)、無音(音なし)。保持音は 650 ブロックで process 時間が減衰しない(node)ので、1 ブロックあたりの仕事は一定。実際の曲の音の入り・切り・音色変化は含まない。
- **S-pw1-6 32 KiB の受け渡しは代役**(上記)。
- **S-pw1-7 K=6 の構成**: 参照プロジェクトの 6 個は状態 0,1,2,3,4,5 に対応するが、ピアノ(状態 2)は JSPI のスレッドビルドが Chrome の Worker ホストに無いため除外し、6 個目は状態 3 を重ねた(`0,1,3,4,5,3`)。軽い 4 個 = `0,1,3,4`。『軽い 4 個が鳴り、2 個が無音』= `0,1,3,4` + 無音 2 個(状態 0,1 で音なし)。
- **S-pw1-8 OTT = mt1 の C 経路 wasm**(`ott-c.wasm`、process 約 10.5 ms/ブロック)。決定 0181 の見積りの『他の約 12 個は OTT 並み 11.3 ms』に近い。実際の『他の約 12 個』(Vital、Kilohearts …)ではない。mx9(混成、約 3.4 ms)は使っていない。
- **S-pw1-9 nice 5**: 依頼のとおり。他の担当は nice 15 が多いが、そうでないものもあり、この機械は共有。HC の制限は Chrome 全体を `taskset` で包み、その CPU に他のプロセスも載りうる。
- **S-pw1-10 リンクの `--allow-multiple-definition`**: 上記。代替: runtime の `fle_filedlg.o` を外す。
- **S-pw1-11 N=123 のみ**: N=200/1000 は作っていない(決定 0181 で N=123 と定常が同じ)。
- **S-pw1-12 他プロセスの CPU**: 窓の 1 秒ごとに『許可した CPU の全プロセスの busy(`/proc/stat`)− Chrome 全スレッドの CPU(schedstat)』を測り、平均・p90・最大を併記する。古い run〔暖機 150 ブロック〕は窓全体の平均だけ(`*`)。理由: 遅れの原因が自分の構成か他のプロセスかを区別する。代替: 実行中のプロセス名を記録する(上位だけ `others` に記録)。
- **S-pw1-13 計算(§5.3)**: 処理共有(n 本の runnable が c コアで各 min(1, c/n) の速さ)、理想のコア、閉ループのエンジン、各インスタンスは 650 ブロックの系列の別の位相(乱数 20 回)。理由: この機械の SMT・他のプロセス・起床を除いた下限を、測った CPU 時間の需要から出す。代替: 離散イベントで FIFO のコア割り当て、SMT の係数。**測定ではない**。
- **S-pw1-14 HC=4/8 の物理コアでの読み**: `taskset -c 0-3` は物理 2 コア × SMT、`0-7` は物理 4 コア × SMT(この機械の兄弟は cpu0-1、2-3 …)。依頼は 0-3 / 0-7 なのでそのまま測り、物理コアを 1 スレッドずつ使う `0,2,4,6` を補足した。依頼者の機械の HC=4 が『2C/4T』か『4C/4T』かで結論が変わる。
