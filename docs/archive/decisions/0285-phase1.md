# 0285 工程 1(診断と実測): 型付きの間接呼び出しの『適合数・φ・s・c_new』(mt3w)

状態: **仮**(設計 0285 の続き。コードの変更は fe-wasmgen の診断 +82 行だけで、生成物の wasm は変えていない)。作業者 mt3w、2026-11-06 JST。基準: e9-wip `b0fe2c11` + 0286(= E10 の hyb-U リスト、`tmp/regen/out-NEW4`)。区分: **実測**=出力を見た値(出どころ付き)/**読み**=推論/**未確認**。

## 0. 冒頭の三点(正直さ)

1. **実エンジンが実行されたか**: (a) **native の N1**(alpha1 の道具で、C 経路のまま -O2 で native 化した実エンジン。FLEngine と実モジュール 7 つの lift した C)を、参照プロジェクトの再生(`a12-play.g3`、ハーネスの模擬入力で、ユーザーの操作ではない)で走らせ、`fle_dispatch` のフック経由で間接呼びを数えた。(b) fe-wasmgen の診断を hyb-U の 4,046 関数に当てた。(c) 合成の micro-benchmark(node 24 の V8)。**ブラウザ・wasm の実エンジンの走行は 0 件**(wasm 側の ms は 0276 の E5 のプロファイルの値を借りた)。代役・再生・画像の物はない。
2. **主な結果**: 適合する関数は 4,046 中 **608(15.0%)**しかないが、**動的な間接呼びの 68.9% は『caller が hyb-U かつ target が同じ module の適合する関数』**(UI 側のスレッド 59.5%、ミキサーのスレッド 97.8%)。理由は、呼ばれる関数が小さな葉の関数に偏るから。micro-benchmark の 1 呼びの差は **約 4.4〜5.1 ns**。⇒ ミキサー(worker 全体)の CPU の **約 4.1〜7.5%(典型 6.1%)**(見積り)。サイズの増加は **約 +140 KB**(+0.1%)で、first idle の費用は node の実測比で **+2〜8 ms**、悲観の読みで +74 ms。
3. **未確認**: ブラウザでの実際の効果(V8 のプロファイルの self 時間)。micro-benchmark は合成で、熱いループ・分岐予測が当たる(実コードより有利)。native の数は『間接呼びの回数は native・wasm で同じ』という設計(決定 0147/0179)に頼る。caller の特定は戻りアドレスの走査で、`jmp` の tail 呼びが混ざると caller がずれる(静的には FLEngine の間接呼びの site 44,180 のうち tail は 140 = 0.3%)。

## 1. (1) 述語の真の数(実測。`tables/p1-fit-by-module.tsv`、`0285-phase1-fe-wasmgen-diagnostic.diff`)

| module | lowered | **適合** | 不適合 | うち xmm だけが理由 | xmm を許せば適合 | adapter の code bytes(適合分、標準の形)| 間接呼びの site(hyb-U 内)|
|---|---|---|---|---|---|---|---|
| fle | 2,927 | **429** | 2,498 | 678 | 1,107 | 6,932 | 1,939 |
| dsp | 159 | 4 | 155 | 66 | 70 | 88 | 0 |
| b2d | 75 | 12 | 63 | 8 | 20 | 139 | 26 |
| qfc | 359 | 82 | 277 | 119 | 201 | 1,186 | 283 |

- **不適合の理由は xmm が支配的**: 不適合 3,438 のうち、xmm を触る物が 3,346(97%)。xmm 以外の理由だけの物は 92(r10/r11 の live-in だけ 26、他のレジスタの read 65、callee-saved の非保存 1)。`does not preserve` を含む物は xmm との併発を含めて 198。`tables/p1-fe-wasmgen-diag-output.txt` に module 別の理由。⇒ 設計 0285 の『Phase 1 は xmm を触る関数を対象外』は、**関数の数では 85% を落とす**。
- **サイズ(実測 + 読み)**: 適合 608 の標準 adapter は合計 **9,792 B**(平均 16 B。私の設計時の見積り 40 B × 4,046 = 160 KB は大きすぎた)。設計の adapter は key 確認と進捗の加算が付くので +約 30 B ずつ ≒ +18 KB。site は 2,760 で、共有の補助関数を使う形なら 1 site あたり約 40 B ≒ **+110 KB**(補助関数を使わない inline は約 85 B ≒ +235 KB。micro-benchmark では速さが同じ〔§3〕なので共有の形を推す)。表は module あたり数 KB。**合計 約 +140 KB**(engine wasm 142.6 MB の +0.1%)。
- **生成物の wasm が変わっていないことの実測**: 診断あり/なしの fe-wasmgen(`b0fe2c11` のソース)で、8 module の wasm の sha256 が**全て一致**(`tables/wasm-sha256-patched-and-unpatched.txt`、同じ引数〔onez.sh〕)。

## 2. (2) φ の native 測定(実測。`tools/p85hook.c`、`tables/phi-windows-*.txt`、`tables/p85-counts-a12-play.tsv.gz`)

**方法**: alpha1 の N1(`out-alpha3` の gen3 をそのまま、runtime は 0275 の木)に、`fle_dispatch_hook`(census 用の弱いポインタ。本番は NULL)を使う使い捨ての 1 ファイル `p85hook.c` を足してリンクした。hook は (戻りアドレス `*R[4]`, target VA, ゲストのスレッド番号 `fle_thread_current()`, 10 仮想秒の窓)ごとに数えて `fn()` を呼ぶ。**生成 C・runtime は変更なし**。`a12-play.g3`(参照プロジェクトを開く → 閉じる → 再生、100 仮想秒、`FLE_G3_*` の模擬入力)を 1 回(**約 2 分、仮想 130 秒、間接呼び 16 億回**)。分類は E10 の hyb-U リストと §1 の適合表で、caller = 戻りアドレスを含む関数。

**結果**(窓 5〜6 = 仮想 3650〜3670 s = 0274 の『最悪区間』と同じ。1 ブロック = 4096 サンプル = 92.88 ms、20 仮想秒 = 215.3 ブロック):

| ゲストのスレッド | 間接呼び/ブロック | target の module | caller が hyb-U かつ target が同 module の適合 = **φ** | その回数/ブロック |
|---|---|---|---|---|
| **0**(FL の main スレッド、target の 99.6% が FLEngine)| 1.054 M | fle 99.6% | **59.5%** | 0.628 M |
| **18**(ミキサー、target の 98.1% が Elastique)| 0.343 M | elastique 98.1% | **97.8%** | 0.336 M |
| 全スレッド | **1.397 M** | | **68.9%** | **0.963 M** |

(窓 4〜11 でも φ はスレッド 0: 59.7%、スレッド 18: 97.1%。窓 0〜12 全体: 61.5% / 96.6%。窓 0〜12 でのスレッド 0 の残りは、target が適合しない同 module の U が 30%、xmm だけの理由で 6〜7%、他 module の U 0.3〜0.5%、C 経路の関数 0.04%。『xmm を許せば』φ はスレッド 0 で 68.0%、スレッド 18 で 98.0% = +0.09 M/ブロックにすぎない。)

- **N は 0274 の 1.085 M/ブロック(モデルの入力)でなく 1.397 M/ブロック**(同じ窓)。差は私の窓の切り方か、モデルが数えない呼びがあるかで、**原因は未確認**。以降の式は私の測定値 1.397 M を使う。0276 の測れている部分(dispatch 1.23 + 小 adapter 3.60 = 4.83 ms/ブロック)を割ると **3.46 ns/呼び**(0276 の 4.45 は N=1.085 M で割った値)。
- 残りのスレッド(2、7、4 ほか)は合計 0.02% 未満で無視できる。
- **caveat**: (i) native の間接呼びの回数が wasm と同じであることは設計に頼った(progress の count が同一、決定 0147/0179)。(ii) caller の特定は『戻りアドレスの走査』で、`jmp` の tail 呼びだと一つ外側の caller になる。静的な site は FLEngine で 44,180 中 tail が 140(0.3%)。動的な割合は未確認。(iii) スレッド 0 を『UI』と呼んだのは、target が FLEngine に 99.6% のため(読み)。ブラウザの main スレッド(キャンバス描画、P2 の 120 fps)とは別物。wasm では全ゲストスレッドが同じ worker で協調動作する(読み)ので、この梃子が効くのは worker の CPU(P3 側)。

## 3. (3) s と c_new(実測 + 合成)

**caller 側の spill/reload(静的に数えた)**: 熱い caller `f_b2f3650`。**全 100 仮想秒の走行で `f_b2c16b0`/`f_b2c16c0`(`lea eax,[rcx*2+1]; ret` の 2 つの葉)への間接呼びは 3.63 億回 = 全間接呼び 16.1 億の 22.5%**で、スレッド 18(ミキサー)が 3.13 億、スレッド 0 が 0.50 億。caller は 30 の site(戻りアドレス 0xb2f3c96〜0xb2f41b2、全て `f_b2f3650` の中。最多の 6 site が各 3,582 万回)。その `f_b2f3650` の本体(wasm の 17,017 行、`tools/sites.py`)の `fle_hyb_dispatch` の呼び 28 site すべてが同じ形: **呼びの前に i64.store 15 + v128.store 3、呼びの後に i64.load 1 + v128.load 0〜1 + i32.load 2**(mx guard の更新)。型付きの経路ではこの store 18 個と load 1〜2 個が不要になる(戻りアドレスの 1 store は残る)。

**micro-benchmark**(`tools/bench/`、node 24.19.0 = V8 13.6.233、`taskset -c 15`、5000 万回 × 5 の最小値、他の job が走っている load 6〜8): 3 つの wasm module(共有メモリ/表、C 側の `dispatch`、生成コード側)で、**現行の経路の構造を再現**(上の store 18 + 戻りアドレス + `dispatch` の import 呼び〔landing・cache 検索・progress・hook・C 側の表の呼び〕+ page-ABI wrapper の約 10 load / 9 store + 戻りの reload)と、**型付きの経路**(landing/hook/pseudo-VA の確認 + 乗算 hash + `call_indirect` で adapter に key 確認と progress → body)を比べた:

| 経路 | 1 呼びあたり(直接呼びの 0.2 ns を含む)|
|---|---|
| 直接呼び(inline) | 0.20 ns |
| **現行**(spill + dispatch + wrapper) | **7.6〜8.3 ns**(3 回: 7.59 / 7.70 / 8.06 / 8.34)|
| **型付き(inline の確認)** | **3.1〜3.4 ns** |
| 型付き(確認を共有の補助関数に) | 3.2〜3.4 ns(inline と同じ。サイズが小さい形を推す) |
| **差(現行 − 型付き)** | **4.4〜5.1 ns** |

- **交差検証**: 現行の合計 7.6〜8.3 ns ≒ 0276 の測れている部分(3.46 ns、E5 の実プロファイルと私の native の回数から)+ caller 側の spill/reload(約 4 ns、micro-benchmark 上)。**一致する**(読み)。
- 限界: 合成で、ループが熱く分岐予測が当たる。実コードでは cache・BTB の影響が入る。V8 のバージョンは本番の Chrome 156(V8 15.6)でなく node 24 の V8 13.6。**c_new = 3.0 ns(型付き − 直接)**は 設計 0285 の仮置き(1〜3 ns)の上限に当たった。

## 4. (4) 結論

**実装した場合のミキサー(worker)の CPU の減り**(見積り。1 ブロックあたり、φ・N は実測、1 呼びの差 Δ は合成):

| | 対象の回数/ブロック | Δ=3.0 ns(下限)| Δ=4.5 ns(典型)| Δ=5.5 ns |
|---|---|---|---|---|
| スレッド 18(ミキサー)| 0.336 M | 1.01 ms(1.4%)| **1.51 ms(2.1%)** | 1.85 ms(2.6%)|
| スレッド 0(FL の main)| 0.628 M | 1.88 ms(2.7%)| **2.82 ms(4.0%)** | 3.45 ms(4.9%)|
| **合計(worker)**| **0.963 M** | **2.89 ms(4.1%)** | **4.33 ms(6.1%)** | **5.30 ms(7.5%)** |

(% は 0276 の『E7b のミキサー 70.65 ms/ブロック〔= E5 の 78.5 × 0.90〕』に対する割合で、**この分母は 0276 の仮定**。0276 の見積り 4.8〜5.8% と重なる。)

**first idle の費用**: 追加 約 +140 KB。0276/0264 の悲観の読み(0.53 ms/KB)で +74 ms。node の Liftoff 実測(0264: 読みの 1/9〜1/40)で +2〜8 ms(推定)。E7b の ci1 の実測(Chrome −1,432 ms、Firefox −376 ms)は『バイトが増えても first idle が速くなった』差し引きの値で、1 KB あたりの費用の下限も上限も与えないが、悲観値の +74 ms は余裕の内。**ブラウザの first idle の実測は無い**。

**GO/NO-GO の推奨: GO(実装して opt1 が実エンジンで測る。撤回条件つき)**。理由: (i) 利得の根拠が 3 つとも実測に変わった(φ 68.9% = 回数、Δ ≒ 4.4〜5.1 ns = 合成だが現行の 7.6〜8.3 ns が実プロファイル + 静的な spill 数と整合、サイズ +140 KB)。(ii) 利得の下限(Δ=3 ns)でも worker の約 4%。(iii) 変更は設計 0285 のとおり『同じ順序・同じ契約・slow path は今の経路』で、新しい分岐やオプションを足さない。**撤回条件**: opt1 の V8 プロファイルで `fle_hyb_dispatch` と小 adapter の self 時間の合計が 4.83 ms/ブロックから 30% 以上減らない、または first idle が +100 ms を超える、または progress/slices/snap の clock_ms の行が E10 と一致しない。

**設計への反映(工程 2 で)**: (1) xmm を触る関数の対象化は、動的な回数で +0.09 M/ブロックしか増えない(関数の数は +970)ので Phase 1 では不要。(2) `jmp` の tail は静的に 0.3% なので Phase 1 の対象外のままでよい。(3) サイズは共有の補助関数の形(約 40 B/site)。(4) 設計の表の大きさ 2^k ≥ 8N は、適合が 608 なので module あたり最大 fle の 429 → 4,096 slot で足りる。
