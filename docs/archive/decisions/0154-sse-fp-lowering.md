## 原因の確定(K1 が 80〜108 倍だった理由)

**遅い経路に落ちていたのではない。**

| 測定 | 結果(実測) |
|---|---|
| K1 の高速経路の通過(`FLE_MX_STATS`、20000 回走行) | addss(レーン)10,240,000 件 fast / slow **0**、mulss 同、入力は 0.01×(i%97)(ゼロと正規数だけ。非正規数・NaN なし) |
| K2 の高速経路の通過 | addsd・subsd・mulsd 計 92,160,000 件 fast / slow **0** |
| 実エンジンの高速経路の通過(決定 0143 の計数、`docs/investigations/fp1/logs/engine/mx-stats-engine-O0.txt`) | addsd 463,743,812 fast / 110,575 slow ほか、99.9% 以上 |
| 実エンジンのこの決定の経路の通過(新規、`logs/engine/engine-vstats-table.txt`、native -O0 の計数ビルド、FRUITY 有効、`stat.g3` = idle・3 s・ウィザード 5 s・Enter・4 s の仮想時間) | SSE 浮動小数の命令 **1,748,558,351 件のうち 99.9845% が新しい経路**、ガード(PE 未設定・RC・PM)で外れた命令 0.0009%、窓の外 0.0146%。**packed 命令は 3.17%、scalar が 96.83%**(addsd 24%、cvtsi2sd32 21%、subsd 17.5%、mulsd 16%、cvttsd2si32 7%、addss 4%) |

したがって K1 の過大評価は、(1) 分母の native 機械語が packed 1 命令 = 4 レーンを約 1 サイクルで流す極端に速い物で、(2) 実エンジンの FP の 97% は K2・K4 型の scalar double なので K1 は実エンジンの代表ではない、の 2 点による。合成カーネルの値の分布による過大評価ではない(窓の外・遅い経路に落ちる入力は K1 に無く、実エンジンでも 0.015% 未満)。

高速経路の内側(K1 の `mulps` 1 命令、clang -O2 のアセンブリ): 4 レーンの各ガード(オペランド 2 つの指数部の検査、約 12 命令)、`cvtss2sd`→`mulsd`→`cvtsd2ss`、結果の検査、旗を 4×4 バイトで一時領域へ書いて 8 バイトで読む、X[] への 8 バイト 2 回の書き込み直後の 16 バイト読み出し(store-forwarding 失敗)、`fle_mxcsr` の読みと PE の判定の省略条件。1 レーンあたり約 12 サイクル(5.2 ns/標本 × 4 標本 ÷ 8 レーン演算 ÷ 約 5 GHz)。K2 は 1 つの FP 演算あたり約 3.5 ns。

決定 0143 の候補だった `FLE_MX_OP2` の `always_inline` は効かなかった(K1 5.1→5.0、K2 35.7→35.5 ns/標本、誤差内)。呼び出しの寄与は小さい。

## 設計(実装は `lift/runtime/fle_mxcsr_vec.h`、`fle_mxcsr_cvt.h`、`fle_mxcsr_flags.h` のラッパー)

命令 1 つ(使うレーンのすべて)を一度に判定する。次の 2 つがともに成り立つときだけホストの演算 1 回に置き換える。

1. **ガード**(結果が不正確になり得る命令だけ): `(MXCSR & 0x7020) == 0x1020` = RC = 0(最近接偶数)、PE(bit 5)が立っている、PM(bit 12)がマスクされている。決定 0143 の S-fp1-sticky(PE が立ち済みでマスクされていれば PE の判定を省く)と同じ前提で、`fle_mx_fin` が MXCSR に OR する値はこのとき必ず変わらない。FTZ・DAZ・他のマスクはガードに入れない(窓が非正規数と tiny な結果を除くので結果にも旗にも効かない)。
2. **窓**(使うレーンのすべてのオペランド):

| 命令 | 窓(binary32 / binary64) | 窓の中で成り立つこと |
|---|---|---|
| ADD SUB MUL | ゼロ、または 2^-62 ≤ \|x\| ≤ 2^62 / 2^-510 ≤ \|x\| ≤ 2^510 | 結果は 0 か正規数(和は 2^-85 の整数倍なので 0 か ≥ 2^-85、積は 0 か 2^-124〜2^124)。IE・DE・ZE・OE・UE は起こらず、FTZ・DAZ は無関係。結果は最近接偶数の IEEE 結果 = 従来の整数実装の結果 |
| DIV | 被除数は上と同じ、除数は 0 でない窓の中 | 商は 0 か 2^-124〜2^124。ZE・IE(0/0)は除数 0 が要るので起こらない |
| SQRT | 被除数は ±0 または 2^-62 ≤ x ≤ 2^62(負は窓の外) | ±0 はそのまま、他は 2^-31〜2^31 の正規数 |
| MIN MAX | ゼロ・正規数・無限大(NaN と非正規数は窓の外) | 旗は立たない。結果は `a < b ? a : b`(`a > b`)で、等しいとき(+0/-0)は第 2 オペランド。**RC・PE・マスクのガードは要らない** |
| CMPSS CMPSD CMPPS CMPPD(8 述語すべて) | MIN MAX と同じ | 旗は立たない(IE は NaN、DE は非正規数が要る)。述語 3 と 7 は定数。**ガードは要らない** |
| CVTSS2SD CVTPS2PD | ゼロ・正規数・無限大 | 厳密。**ガードは要らない** |
| CVTSI2SD(32 ビット整数)、CVTDQ2PD | 全部 | 厳密。**ガードは要らない** |
| CVTSI2SS CVTDQ2PS CVTSI2SD(64 ビット) | \|i\| ≤ 2^24 / 2^53 なら厳密(ガード不要)。それ以上はガードを要する(丸めて PE) | |
| CVTSD2SS CVTPD2PS | ゼロ、または 2^-100 ≤ \|x\| < 2^101(指数部 923〜1123。結果は binary32 の正規数)。ガードを要する | |
| CVTTSS2SI CVTTSD2SI CVTTPS2DQ CVTTPD2DQ(切り捨て) | ゼロ、または窓の下限以上で \|x\| < 2^31(64 ビット結果は < 2^51、packed binary32 は ≤ 2^30)。ガードを要する | |
| CVTSS2SI CVTSD2SI CVTPS2DQ CVTPD2DQ(丸め) | 同、上限 \|x\| < 2^31-1(scalar)/ ≤ 2^22(packed binary32、`(x + 1.5·2^23) - 1.5·2^23` で最近接偶数)。ガードを要する | |

窓の外、ガードを満たさない、レーンが 1 つでも窓の外 — いずれも**決定 0143 のコードへそのまま落ちる**(レーンごとの高速経路、次に整数実装。関数本体は 1 行も変えていない。外に出した `FLE_MX_SLOW` 関数 `fle_mx_do2_slow_p`、`fle_mx_cmp_slow`、`*_slow` から呼ぶだけ)。したがって新しい経路の正しさは『窓の中で結果と旗が従来と同じ』だけで決まり、窓の外の挙動は従来のコードが決める。

**NaN**: NaN は窓のどの比較(`>=`、`<=`、`==`)にも偽になるので、NaN を含む命令は必ず従来のコードへ落ちる。ホスト(x86 の clang 結果、wasm)の NaN の伝搬規則・ペイロードの非決定は、**この経路では NaN が演算に入らないので観測されない**。SSE の NaN 規則(第 1 オペランドの QNaN、既定 NaN `0xFFC00000`)は従来の整数実装だけが決める。

**旗**: この経路は MXCSR を書かない(ガードのために `fle_mxcsr` を読むだけ)。PE を立てる必要のある命令(PE が未設定)は窓に入っていても従来のコードへ落ちる。旗の更新を省く変更(PE が未設定のまま省く、など)は**していない**(下の『(b)』)。

## ホストへの要求

決定 0143 と同じ(最近接偶数、`FLT_EVAL_METHOD == 0`、fast-math なし、融合なし)に加え、ベクトル拡張(`__attribute__((vector_size(16)))`)の比較と四則が IEEE。x86-64(SSE2)と wasm(`-msimd128` あり: v128、なし: LLVM がレーンごとに展開)で確かめた。`__builtin_elementwise_sqrt` がないコンパイラ(gcc)では packed の SQRT だけ従来のコードへ落ちる。wasm で `-msimd128` なしの場合はベクトル型ではなくレーンごとのビット列の窓(1 回の引き算と 1 回の符号なし比較)を使う(`FLE_MXV_LANES`)。

## (c) NaN

NaN を含む命令は窓の外(比較が偽)なので必ず従来のコードへ落ちる。ホストの NaN 伝搬(x86 の SSE と wasm で規則が違い、wasm は仕様上ペイロードが非決定)は、この経路の結果には現れない。NaN を含む結果が観測される箇所(`movmskps`、比較の結果、`ucomiss` の PF)も、NaN を含む命令は従来の整数実装が計算するので従来と同一。**NaN ペイロードの差を『保証しない』と書く必要が生じない**(差が無い)。

## 出典なしの選択(撤回条件つき)

| 名前 | 内容 | 理由 | 撤回条件 |

## 次の候補(届かないものは届かないと書く)

本決定でエンジン全体は約 10% 速くなっただけで、**P1〜P3 には届かない**(約束しない)。浮動小数の MXCSR 厳密処理は、実エンジンの時間のうち 1 割前後まで下がった。残りは別の要因:

1. **窓の検査**(K1 の残りの約半分): 1 命令あたり packed で約 20 ベクトル命令。(a) `-msse4.1`/AVX2 のホストで約 8〜17% 減(上)。(b) fe-lift が基本ブロック単位で『このレジスタは直前の窓の検査を通った値から作られた』を持てば検査を省ける(範囲外、別の決定)。(c) 指数部の整数の引き算と符号なし比較にして 2 つのオペランドをまとめる案は、ゼロ(窓に入るが指数部 0)の扱いが要るので、命令を数えた限り今の浮動小数の比較(オペランドあたり 6 命令)と同じで、実装していない(未測定)。
2. **X[]/R[] のメモリ経由と遅延 flags**(K1 の約 35%): 生成 C の形(`X[1] = fle_mx_mulps(X[1], X[0])` の毎回のメモリ読み書き、`fle_op_add` が 6 つの旗を `FL` へ 1 バイトずつ書く)。これは fe-lift の出力を関数単位でレジスタに載せる大規模な変更(範囲外)。部分幅の書き込み(8 バイト 2 回)のあとに 16 バイトで読む store-forwarding 失敗も同じ根。
3. **DAZ・FTZ のベクトル再現**: 窓の外は実エンジンで 0.0146% だが、プラグインの DSP(減衰する尾の非正規数)では多いかもしれない。`|x| < MIN` を 0 にする bitselect と結果の同じ検査で足せる。旗〔DE・UE・PE〕の扱いを従来のコードと揃える必要があり、差分テストの範囲が増える。vst1 の次の段階(プラグインの実行)の実測を待つ。
4. **`FLE_MXV_SLOWBYVAL` と wasm の `-msimd128`**: packed は大きく速くなる(K1 が数倍)が、scalar の部分 16 バイト化(8 バイトを書いて 16 バイトで読む)が V8 で重く、K2 は -O2 で +26%(34 → 43 ns/標本)、-Oz で +7% 遅くなる。`fle_xmm` を 2 つの `uint64_t` の構造体にして scalar を 8 バイトのままにする案は、生成 C が `X[i].u64[k]` で触るので、union の形のまま `-msimd128` のコンパイラが 16 バイトにまとめるのを防ぐ必要がある(未着手)。
5. **ラッパーの強制インライン**(wasm -Oz): K2 −45% だがユニットが +9〜16% 大きくなり、コンパイル時間が 2 倍(サイズ条件 S1/S2 との兼ね合い)。scalar double の 4 命令(addsd subsd mulsd cvtsi2sd)だけを強制する選択肢は未測定。
6. **シャッフル**(`shufps`・`unpck*`・`movhlps` ほか。dsp_ippv2 の m1 に 29,809 箇所): ベクトル化されていない整数/レーンのコード(`fle_sse_shuf.h`)。FP の厳密性とは別だが packed コードの時間に効く。本決定では未着手。
7. **IPP の HLE**(決定 0151、hle1): エンジンの SSE 浮動小数の大半は dsp_ippv2 の Warp の内側のループ(scalar double)なので、関数単位の置き換えの方が大きい。

## 限界(確認できなかったこと)

- **実機 Windows との照合は 0 件**。『従来の実装と同一』を示すもので、ゲストの正しさを示すものではない。
- **実プラグイン(Serum 2 ほか)の命令の実行は無い**。実プラグインの窓に入る割合は未測定(vst1 の census は静的な命令数だけ)。静的な割合は Serum 2 で fp_scalar 1.9%・fp_packed 0.4%(`instruction_mix.tsv`)。
- 実エンジンの通過率 99.9845% は、1 つの走行(idle→3 s→ウィザード 5 s→Enter→4 s の仮想時間、native -O0)の値。曲を再生している状態・プロジェクトを開いた状態・マスターの VST3 が動く状態は無い。
- native -O2 のエンジンの速度は、この共有機械(load average 8〜25)の CPU 時間(`/usr/bin/time` の user+sys)の中央値。範囲(最小〜最大)を併記した。**壁時計は load average 8 以下の走行でだけ意味がある**ので採らなかった。
- wasm のエンジン全体(92 ユニット)・Chrome・実ブラウザは未測定。wasm の数字は合成カーネル(node)だけ。
- 重要な構成の 1 つ(遅い経路の呼び出し規約を `__wasm_simd128__` で切り替える)は、ビルド済みの native オブジェクトがバイト一致する(ユニット 5 本、ランタイム 60 本)ことで再ビルドを避けた。全 92 ユニットの比較はしていない。
- gcc では packed SQRT が新しい経路に入らない(コンパイラの組み込み関数がない)。
- 『計数ビルドでの通過率』は -O0 の計数ビルドの値(命令の種類ごとに数えた)で、-O2 の最終ビルドそのものの計数ではない(計数は最適化に依らない)。

## PM の判断点

1. **ガードと窓の設計**(S-fplow-window、S-fplow-guard、S-fplow-noguard)の採否。撤回は `-DFLE_MX_NOVEC` の 1 マクロ。
2. **wasm の `-msimd128`**: packed(K1)は -O2 で約 9 倍、-Oz で約 2.4 倍速いが scalar double(K2)が -O2 で +26% 遅い。出荷は『なし』のままを提案(S-fplow-wasm-nosimd)。
3. **wasm -Oz のラッパーの強制インライン**: K2 −45%、ユニット +9〜16%。サイズ条件 S1/S2 を見て判断。
4. **旗の更新の省略**: 行わなかった(S-fplow-nopeskip)。dsp_ippv2 の IPP 関数が旗を読んで消すので、呼び出し元の解析の担当を付けるなら効果は『PE 未設定のときの判定』0.0009% だけで小さい。
5. **決定 0151(hle1)との合流**: 重なるファイルは無いと読むが、hle1 が `lift/runtime/` を編集していれば `fle_mxcsr_flags.h` のラッパー部分で衝突し得る。
