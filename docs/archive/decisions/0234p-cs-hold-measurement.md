## 1. 何を測ったか(作業木だけの計測。納品物には入れない)
- `FLE_CS_HOLD_STATS`: クリティカルセクション(CS)ごとに、Enter で取ってから Leave で手放すまでの実時間(`performance.timeOrigin + performance.now()`: どの Worker でも同じ時刻軸)を、保持者の内訳に分けて数える。
  - off: 保持者のスレッドが走っていなかった時間(`schedule_ex` の中: ほかのスレッドが走った / Worker が待った)。
  - imp: 保持者が呼んだ runtime の import の自分の時間(入れ子の import・コールバック・off を除いた self 時間)。GIL 版のラッパー(`gen_wrap.py`)で測る。
  - cb: ゲストのコールバック(ウィンドウプロシージャ)の自分のゲストコードの時間(`fle_call_guest` の前後)。
  - その他: 残り = 直接のゲストコードの時間 **+ GIL の待ち + OS に割り当てられなかった時間**(GIL の待ちは import の自分の時間に入れていない)。
  - 保持 1 回の長さの分布、保持の呼び出し元(Enter の戻り先)、最長の保持 10 件、監視 CS の中で呼ばれた import の上位。
- 待ち(`cs wait`): 待ち手のスレッド、保持者のスレッド、回数、ms、最長。
- 道具: `tools/hold-sum.py`(エンジンのログから 10 秒ごとの差分の表を作る)、`tools/holdstat_port.py`(作業木 t3 → h6 への移植)。表: `tables/cs-hold-hold{2,3,4}.txt`。

## 2. 結果(Chrome 156、非ハイブリッド GIL、最適化 wasm、参照プロジェクト、負荷 16〜22)

|---|---|---|---|---|---|---|---|
| hold2 | 再生 3 区間(3651-3671) | 5,667 / 9,076 / 8,678 | 5,419 / 8,695 / 8,289 | 228 / 353 / 374 | 181 ms(ミキサー) | 0 回 | 0.81 / 0.70 / 0.70 |
| hold3 | 再生 3 区間(3661-3681) | 8,526 / 8,411 / 6,850 | 8,114 / 8,040 / 6,552 | 375 / 342 / 288 | 243 ms(ミキサー) | 0 回(1 回 UI→ミキサー 65 ms) | 0.50 / 0.60 / 0.68 |

- 保持は**ミキサー自身**: Enter の戻り先 0x12aefcd、1 回 150〜240 ms、約 5 回/秒。その時間の 94〜95% がゲストコード(+ GIL の待ち + OS の割り当て待ち)、runtime の import が 3.5〜5%、off はほぼ 0。
- UI(thread 0)がこの CS を長く握るのは『プロジェクトを開く』区間だけ(3 回: 1.4 s、1.5 s、7.2〜11.3 s。Enter の戻り先 0x1253b60)。その間ミキサーは待つ(17→0: 1.3 s + 7〜11 s)。再生中の区間にミキサーが UI を待った回数は、3 回 × 3 区間でほぼ 0(多くて 1 回、78 ms 以下)。
- 各 Worker: CPU は UI 73〜75%、ミキサー 48〜61%(1 コアに対して。負荷 17)。UI スレッドは再生中 WaitMessage にほとんどいない(10 秒に 30〜65 ms)= **UI も詰まっている**。ミキサーの Sleep(1) の待ちは 10 秒に 1.0〜1.5 s(10〜15%)。
- GIL(再生中の 10 秒あたり): W0(UI)の保持 約 1.0〜1.2 s、待ち 1.6〜2.1 s(16〜21%)。W1(ミキサー)の保持 約 0.5 s、待ち 0.76〜1.2 s(8〜12%)。GIL の合計の保持率は 15〜18%。
## 3. 読み
- 『UI の描画が長く CS を握ってミキサーを待たせる』は再生中の区間では起きていない。前回の『7.7 s / 309 回 = 約 25 ms』は 1 回の 6.4 s(プロジェクトを開く区間)を含む合計の平均で誤り(残り 308 回は合計約 1.3 s)。
- 非ハイブリッドでは UI もミキサーもほぼ飽和している(ゲストコード主体)。ミキサーの書き込み率が 0.4〜0.85 なのは、(i) ゲストコードの実行時間(SSE エミュレーション)、(ii) GIL の待ち(8〜12%)、(iii) 負荷 17 の機械での OS の割り当て、の合わせ。分けては測っていない(OS の割り当て待ちは、同じ区間のワーカーの CPU 時間 / 実時間で見るしかない)。
- → ゲストコードを速くする手(ハイブリッド = 直 wasm)が先。ハイブリッド + GIL の測定(§5)で、ミキサーの CS 保持の長さ(150〜240 ms が何 ms になるか)と書き込み率を見る。

## 4. 本番に近い協調 1 Worker(非ハイブリッド、MT2_SHARED + TLS_REGS、GIL なし)で同じ測定(PM 指示 2(2))
- 同じ計測を協調版にも入れた(`schedule_ex` の中の時間を off とする)。import / コールバックの内訳は GIL のラッパーが無いので取れない(imp = cb = 0、ゲストコードと runtime の区別なし)。負荷 20〜28。表: `tables/cs-hold-nc1.txt`、`cs-hold-ncm1.txt`。
- 構造は実スレッド版と同じ: 再生中、CS 0x16b6aa8 をミキサー(thread 18)が 1 回 150〜215 ms(Enter の戻り先 0x12aefcd)で保持し続ける(10 秒あたり 4〜7.7 s)。off(その保持中に協調スケジューラが他のスレッドを走らせた時間)は 10 秒あたり 0.1〜1.0 s。
- **UI(thread 0)がこの CS を待ったのは、起動時の 5 回、合計 100 ms、最長 29 ms だけ**(保持者は thread 7 = 起動時のワーカー)。再生中の区間には 0 回。UI がこの CS を待たない限り、ミキサーの 150〜240 ms の保持は UI の応答に影響しない。
- マウスを動かしながら再生(`tools/scn-ref3-tempo-mouse.json`: 再生の直後に 90 回、100 ms おきに移動): 同じく UI の待ちは 0 回(`tables/cs-hold-ncm1.txt`)。UI の入力が CS を要求する頻度はこの操作では 0。**ただしこれは『マウス移動』だけで、クリック・ドラッグ・メニューは測っていない。**
- エンジンの Worker は 1 本で 93% / 1 コア(UI とミキサーが同じスレッド)。PCM のテンポ当てはめは 0.60(nc1)と 0.70(ncm1)(残差 0.09〜0.15 s、負荷 20〜28)。実スレッド版(非ハイブリッド)の 0.15〜0.41 より高い。**理由の仮説(未検証)**: 協調版は仮想時計で、UI の更新・タイマーは仮想時間で進むので、機械が遅いと UI の仕事も減る(UI は WaitMessage に 30% いる)。実スレッド版は実時計なので、UI は再生中ほぼ 100% 忙しい(WaitMessage 0.3〜0.7%)。実スレッド版の UI の仕事量(約 75% / コア)が、同じ機械のミキサーの CPU を削っている可能性がある(負荷 17〜22 の下では OS の割り当てが効く)。
- 起動の 1 回(nc2)は最初の idle に到達せず、シナリオが捕捉なしで終わった(原因は調べていない)。
