## 2. 原因(ui1 の読みを、同じコードの `?pace=timer` で再現して確認した)

- 旧 `IdleDriver.arm()` はエンジンが idle に入るたびに、次の期限(1 仮想 ms 先が多い)に `setTimeout((next − now) / 10,000)` を張った。ワーカーの timer は、timer の callback の中から(エンジンの再開は microtask なので同じタスクの中)次の timer を張る連鎖になるため、ブラウザの『入れ子 5 段を超えた setTimeout は 4 ms 未満を 4 ms にする』規則(HTML の timer の仕様)に掛かる(**読み**。仕様の文面。Chrome 156 で確かめたのは次の観測)。
- **実測(変更前 = `?pace=timer`)**: 主窓アイドルの 60 実秒で仮想 12.9 秒(仮想/実 = 0.2147、idle 226/s)。ui1 の 0.217 を再現した。ゲストの定常の仕事は『仮想 16 ms ごとの重いサイクル + その間の軽いサイクル 15 回』なので、1 周期が実時間で 16/0.215 ≈ 74 ms かかり、ゲストのタイマー(UI の更新周期など)は実時間の約 1/4.6 でしか進まなかった。
- **ui1 の実測(PM 経由で受領。この決定では再測していない)**: Chrome 156 の Worker で、入れ子の `setTimeout(f, 1)` は 4.12 ms、`setTimeout(0)` も 4.13 ms、`MessageChannel` の往復は 0.015 ms(`lift/out-ui1/tables/timer-clamp-test.json`)。1 ms の期限を `setTimeout` で待つ設計は 4 ms 刻みになる。
- **実測(診断。この決定で取った)**: 同じ Chrome のワーカーで、`MessageChannel` の往復を挟む timer の連鎖(入れ子にならない)は 4 ms に丸められない(`hidden-timers.mjs` の A の worker で `setTimeout(10)` の連鎖が 85〜96 回/s、`MessageChannel`+`setTimeout(0)` の往復が 15〜25 万回/s)。**読み**: 入れ子の連鎖が丸めの原因で、ターンを `MessageChannel` で返せば避けられる。
- エンジンの CPU は余っていた(主窓アイドルで Worker の CPU は 0.066 コア = 実時間の 6.6%)ので、問題は CPU ではなく**起こし方**だった。

## 4. 設計

状態: アンカー `(wall, ticks)` — 最初の idle で `(host.now(), nowTicks)`。目標 `raw(w) = anchor.ticks + (w − anchor.wall) × 10,000 × rate` ticks。

| 場面 | 動作 |
|---|---|
| idle(期限 `next`、仮想 `now`) | `t = clamp(raw(w), now − maxLead, now + maxLag)`(切ったらアンカーを `(w, t)` に動かす)。`next ≤ t`(実時間が期限に追いついた): ターン予算(`w − turnStart < 4 ms`)が残っていれば**その場で** `deliver(next)`(エンジンは microtask で再開し、次の idle もすぐ戻る)。予算切れなら `yieldTurn(...)`(`MessageChannel`)で次のターンに回す。`next > t`: `setTimeout((next − t) / 10,000 / rate)` 1 回 |
| 入力が来た(idle 中) | 従来どおり**その場で**渡す。時計は `min(next, max(now, raw))` まで動かす(遅れていれば期限まで。期限は越えない)。入力は遅れの解消を待たない(S-clk-input) |
| 遅れ > `maxLagMs`(1 s) | 超えた分をアンカーの移動で捨てる(仮想時間は飛ばさない。仮想時計が実時間より遅れたままになる)。`lagCut` フックで警告(Worker は 5 秒に 1 回ログ) |
| 進み > `maxLeadMs`(100 ms) | 同様にアンカーで捨てる。100 ms 以内の進み(エンジン自身の計算が決定 0147 のスライスで時計を進めた分)は残し、次の待ちをその分伸ばす(長期の速さが 1.000 になる) |
| `end()` | `deliver(-1)`。保留中のターンは何もしない(idle 番号が違う) |

ページへの報告(`ReportThrottle`): idle は最初と 40 ms に 1 回、resume は『ページが idle と思っている』ときと入力・終了のときだけ。報告は**ドライバーの判断の前**に出す(ターンを返さず再開するとき、ページが『idle の後に resume』の順で受け取るため)。

## 6. ゲストが経験する時刻の列は変わらない

**読み(コードの構造)**: ドライバーがエンジンに渡すのは (1) 『期限 `next` までクロックを動かせ』(`deliver(next)`、エンジン側で `fle_thread.c` が `min(adv, next)` に切り詰める)、(2) 入力のときの `clockTo(min(next, 目標))`(期限を越えない)、(3) 終了だけ。どれも**エンジン自身が報告した期限**で、ホストの実時間は『いつ渡すか』にしか効かない。従って、入力が無ければ、ゲストが見る (idle 番号, 仮想時刻, 次の期限) の列は駆動に依らない。native のハーネスの 16 スナップ(`FLE_G3_SCRIPT` でエンジン内の `g3_script_idle` が駆動する)は、そもそもページのドライバーを通らない(`fle_idle_wait` を呼ばない)ので、この変更では変わりようがない。`lift/` を 1 バイトも変えていないことは `clk1.diff` の一覧で確認できる。

**実測**(ブラウザ、実エンジン): `IdleTrace` — 全 idle の (番号, 仮想時計, 次の期限) を畳み込んだ FNV-1a ハッシュの 500 idle ごとのチェックポイントを、pace=timer と pace=catchup の実行で比べる(最初の入力 = Enter の前まで)。結果は §8.2。

**取り込んだ範囲**: `app/` の 29 ファイル(`clk1.diff`)。wasm・生成 C・ゲストは無変更。PM の検証: `patch -p1 --dry-run` は HEAD 846427a で fuzz・offset・reject なし、適用後に `tsc` クリーン、vitest 793 passed(41 ファイル)、Worker 43/43、e2e(スタンドイン)の結果は取り込みコミットの本文に書く。

**決めたこと**:
1. 既定の駆動は追いつき方式(catchup)。パラメータ(遅れの上限 1000 ms、先行の上限 100 ms、ターン予算 4 ms、報告の間引き 40 ms)は承認済み。旧方式は `?pace=timer` で残る。

3. **入力→次の更新(P2)の測定に欠陥があった**。決定 0161 後に PM が書いた `docs/milestones/performance-targets.md` §4a の「p50 175 ms、最大 298 ms(8 回)」と `docs/investigations/b1/pm-default-entry-D-run1.txt` の同じ値は、この欠陥(答えの更新を数えず、数百 ms 後の無関係な更新を数える)を含む可能性がある。訂正は §4a に書いた。直した測定器による再測定は、load ≤ 8 の静かな機械で行う(未実施)。
