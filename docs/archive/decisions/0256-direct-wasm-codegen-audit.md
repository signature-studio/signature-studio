## 結論

1. **直 wasm は x86 1 命令あたり wasm 約 9 命令(FLEngine・dsp・QFC)、Elastique は約 34**(静的、census 重み付き。Elastique は遅い経路を含み過大)。構造は『アダプタ(60〜110 命令)+ 型付き本体』。-Oz で −18%、**wasm-opt の水準(-O2/-O3/-Os)は ±1% で梃子にならない**(§2)。
2. **取り除ける最大の物は 64 bit アドレスの 4 GiB 検査**: 命令数の 11〜22%(FLEngine 14.7%、dsp 11.4%、QFC 22.1%、Elastique 5.2%。重み付き、静的、§3)。残りは locals/定数/制御/幅変換というスタックマシンの構造そのもので、TurboFan では畳まれる。
3. **だが命令数は時間の律速ではない**: 検査を**全部**外した非忠実な版(L1、命令 −15.4%)でも、scene b の書き込み率は +4.6%±4.9%、CPU/ブロックは **−2%±1.5%** で有意でない(往復間の揺れ — ciQ だけで CPU 35.8〜39.8 s — が差より大きい)。= **直 wasm の時間は命令数では決まらない**(メモリ・分岐・呼び・遅い経路の C 呼びが律速、という読み。TurboFan/Liftoff の別は未確認)。忠実な P1 の時間効果はこれ以下(§5)。
4. **試作 2 件**(忠実、小さい、試験つき): **P1** = 同じ基底レジスタの直線コードで 4 GiB 検査を 1 回にする(+92 行 + 試験 +202 行)、FLEngine の直命令 **−7.6%**、直コード −5.7%、wasm **−0.30%**。**P2** = アダプタの callee-saved 保存を『C スタブに届かない閉包』だけ省く(+22 行 + 健全性の試験)、アダプタ −12%(fle)〜−30%(dsp)。fe-wasmgen の試験は全通過、**node の 84/55/87 行は ciQ と P1+P2 で差 0**(試験用ビルド)、2ca825ff に dry-run が通る(§6、§9)。**時間: 交互測定(2 往復)では P1・PC とも ciQ より良くならない**(CPU/ブロック P1 +0.002、PC +0.008 s、標準誤差の内)。サイズは wasm −0.30%(P1)/−0.37%(PC)。
5. **P1/P2 の採否(PM の方針)**: **単独では出荷しない**(時間の効果が測れない)。差分は保管し、opt1 の fe-wasmgen の差分(E 系)が CI の冷間ビルドに入るときの相乗り候補にする(全面ビルドの費用は 1 回で済む)。相乗りの条件(PC の CPU/ブロックが ciQ より悪くないこと)は、測定(2 往復)で PC が +0.008 s/ブロック(+4%、標準誤差 3%)と『悪くない』と言い切れず、時間の利得も無いので、**採るなら理由はサイズ(wasm −0.37%、直コード −5.7%)だけ**。PM の判断に委ねる。
6. **L2 の教訓**: アダプタの callee-saved 保存/復元は必須(外すと起動で停止)。P2 は『届かない閉包』の形でしか成り立たず、その閉包の健全性は試験(5 ケース + 変異で殺す確認)で固定した。
7. **0251 の set-U の 4 関数は直 wasm として実行されていた**(f_e95750 の本体 自己 447 ms・inclusive 1,769 ms、4 関数の自己の和 908 → 511 ms)。CPU 時間の A/B が −0.02 s だったのは、ミキサーが CPU 律速で節約分が書き込みに回るためと読める(0251 の同じ run の書き込み率 +6.7%、n=4 で有意でない)。0251 の結論(+139 KB は入れない)は変えない。以後の効果判定は Worker の CPU でなく『書き込み率と CPU/ブロック』で行う。

## 6. 試作(fe-wasmgen。どちらも小さい 1 項目。PM の木には書いていない)

**P1: 同じ基底レジスタの直線コードで 4 GiB 検査を 1 回にする**(`gpu4-p1.diff`: `wasm.rs` +32、`lower.rs` +60、`tests/addr_facts.rs` +202)
- `Code`(wasm.rs)に、local ごとの `local.set/tee` の回数と、`loop`/`else`/`end` で増える epoch を持たせる。`mem_addr` は、最初の `[reg+d0]`(0≤d0<2^31、rsp 以外)で従来の検査(`reg+d0` を専用ローカル S0 に tee、`>>32` が 0 でなければ trap)をして、**事実** (S0 のローカル, d0, reg のローカルと書き込み回数, epoch) を残す。同じ reg の後続 `[reg+d]`(0≤d<2^31)は、事実が有効(reg のローカルが同じ・書き込み回数が同じ・epoch が同じ)なら検査せず、S0 を i32 に落とした値を基底にして、d≥d0 は memarg offset(d−d0)、d<d0 は `i32.const (d−d0); i32.add` で使う。
- **なぜ旧規則と同じになるか**: S0 < 2^32 は検査済み。d≥d0 の和 S0+(d−d0) は 64 bit で折り返さず、memarg の offset は符号なし 33 bit の和なので、旧規則が 4 GiB 検査で落とす場合(和 ≥ 2^32)は新しい形でもアドレス ≥ 2^32 で OOB の trap。d<d0 で S0<d0−d の借りが出る場合は i32 の折り返しでアドレスが ≥ 2^31 になり、メモリ ≤ 2 GiB なので OOB の trap。借りが出ない場合・和が 2^32 未満の場合は同じアドレス。『負の基底 + 正の disp が 4 GiB 内に折り返す』場合も、最初の検査が和 S0 を使うので旧規則と同じに扱う(§6 の試験の 2^64−n の入力)。
- **前提と固定**: 『wasm のメモリ ≤ 2 GiB』(link-web.sh 23 行の `-sMAXIMUM_MEMORY=2147483648`)。試験 `the_linked_memory_is_at_most_2_gib` がその行を読んで ≤ 2^31 を assert する(4 GiB にすると試験が落ちる)。
- **trap の種類**(PM (b)): 旧は `unreachable` の RuntimeError、新は `memory access out of bounds` の RuntimeError。ページ側(`app/src/engine/fruity.ts`)は実行中の trap をどちらも `kind:'trap'` + message で扱い、`classifyEngineError`(起動時の分類)の OOM 判定は `memory access out of bounds.*grow` を含む場合だけなので、違うのは表示の文言だけ。
- **試験**(`tests/addr_facts.rs`、node。2 本): 6 本の小関数 × 439 入力(メモリ内、メモリ末尾、2 GiB、4 GiB−8、4 GiB、2^64−n で base+disp が折り返してメモリ内に入る値、負、乱数 400)を、アーキテクチャの規則 (base+disp) mod 2^64 ≥ 2^32 かメモリ(1 MiB)の外なら trap、そうでなければ 8 バイトを読む、と比較(trap 前に書かれた出力も)。関数: 昇順の disp、降順、基底レジスタへの書き込みが途中にある、同じ disp の繰り返しとそれより小さい disp、**前方 jz で飛ばされる腕の後で合流(合流後は再検査される)**、**ループ本体が基底を書く**(PM (c))。**6 本とも相違 0**。同じ試験を**旧実装(ciQ)も通る**(試験の規則 = 旧規則の確認)。呼び出しを挟む形は、呼び元の reg のローカルは結果の `local.set` でだけ変わり、それは書き込み回数に数えられるので同じ機構(add rcx で代用して試験)。
- **効果**(静的): FLEngine の直モジュール(-Oz 後)2,279,549 → **2,105,923(−7.6%)**、直コードのバイト 5,203,937 → 4,908,229(−5.7%)、wasm 141,803,207 → **141,380,524 B(−0.30%)**。L1(全部外す)の命令数 −15.4% の約半分。
- **node の行**: 下の P2 と合わせて確認(§6 末)。

**P2: アダプタの callee-saved 保存を『C スタブに届かない閉包』だけ省く**(`gpu4-p2.diff`: `lib.rs` +22 −3)
