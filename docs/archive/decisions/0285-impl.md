## 2. 契約と同一性(設計 0285 §5 の確認。実装で分かった点)

- 補助関数が `done = 0` を返す条件は 4 つ: `fle_landing_top != 0`、`fle_dispatch_hook != 0`、target の上位 32 bit が非 0(pseudo-VA)、表に無い/key が合わない。いずれも**何も変えずに**今の経路へ行く(戻りアドレスの store は同じ値の二重書き込み)。
- adapter に入ったとき(= 検索が hit した後)に `count += 1`、`count >= limit` なら `fle_hyb_slice`、それから typed body。`fle_dispatch` の順序と同じで、miss では数えない(今の経路が数える)ので二重に数えない。
- **適合する関数は『呼び出しを含まない葉に近い関数』に限られる**(実装で分かった): 間接呼び・import・C 経路の関数への呼びを含む関数は、xmm の summary が ALLX/`IND_*`/`IMP_*` になるので適合しない。テストの caller F(`call rax` を含む)も不適合になった。工程 1 の φ(68.9%)は、まさにこの述語で測った値。
- 型付きの経路で省くのは、R[] への spill 18 store と、戻りの reload(rax の 1 load、xmm0 の reload、`xflush`)。`mx_guard_refresh` は**残した**(callee の下で LDMXCSR が実行される可能性を排除できないため)。
- 工程 1 の述語に『stack を pop しない』を足した(`ret n` の callee は Win64 の間接呼びの契約に合わない)。実測: 適合は工程 1 の 608 から **607**(`0xb0345a2` が『pops the stack』だけを理由に外れた)。そのうち **603 が adapter を持つ**(dsp の 4 は、dsp の hyb-U に間接呼びが無いので、module に補助関数も表も足さない〔`dsp` の wasm は渡す/渡さないで同一〕)。PM の依頼の『608 個』より 5 少ない: 1 は上の条件、4 は dsp。

## 4. hybrid の段階のスクリプトの変更と、広げなかったガード

`hyb_guard cpart` は C 部のコードに `i32.const <address>` が出るかで『link map がこの C 部のものか』を確かめる(4 つの address)。新しい 3 つのデータ(`fle_progress_limit`・`fle_landing_top`・`fle_dispatch_hook`)は、C 部では `fle_dispatch` の inline からの `i32.load offset=<address>` の形で現れうるので、`i32.const` の数え方では 0 になって**誤って段階を落とす可能性**があり、C 部のビルドが無いと確かめられないため、ガードは広げなかった。代わりに `hyb_guard map`(link map の sha256 が C 部を作った link のものか)が引き続き全アドレスの正しさを守る(新しい 3 つも同じ link map から読む)。**C 部を含む冷間ビルドは PM の CI で初めて通る**(未確認)。link map の行の形は既存の 4 つの正規表現と同じ(列: アドレス・サイズ・alignment・名前)で、alignment を `[0-9]+` にしたので 4 でも 8 でも合う。

## 5. 方針との適合(必須の記載)

- **lift の忠実性**: 追加する処理は (c) 通信/変換の削減 — wasm↔C の境界の往復と R[]/X[] への spill/reload を、callee が読まない物については省く。`fle_dispatch` の契約(landing・検索・進捗の加算と slice・hook・未知の target の停止)は**変えず、同じ順序で行う**。FL の挙動を補う・代行する処理、class/窓の種類/アドレスによる分岐は無い(site ごとの target の特別扱いも無い)。
- **no-options**: 環境変数・実行時のフラグ・切り替えは無い。`--hybrid-dispatch` は fe-wasmgen のアドレスの引数(`--hybrid-progress` と同じ種類で、生成の入力)で、段階のスクリプトが常に渡す。渡さない呼び出し(テストなど)の生成物は従来と同一。
- **進捗の誠実性**: 実エンジンで確認していない物を、確認したとは書いていない。

**式**: worker(ゲストのスレッド群が協調で走る 1 本のスレッド)の 1 仮想秒あたりの CPU 需要を D [core·s/仮想 s]、使える CPU を C(≤ 1 core)とすると、仮想時計の進み r = C / D。この梃子で減る需要を δ とすると **r' = r × D / (D − δ)**(= r / (1 − δ/D))。
- δ = (1 ブロックの減り [ms]) × 44100/4096 [ブロック/仮想 s] / 1000 [core]。工程 1 の減り(対象 0.963 M 呼び/ブロック × 差 Δ)は Δ = 3.0 / 4.5 / 5.5 ns で 2.89 / 4.33 / 5.30 ms/ブロック → **δ = 0.031 / 0.047 / 0.057 core**。内訳(Δ=4.5): ミキサー(guest 18)0.016 core、FL の main(guest 0)0.030 core。
- D は 2 通りに置く: (i) 0276 の profile から 1.17〜1.26 core(ミキサー 0.76〜0.85 core〔E7b/E5〕+ UI 0.41 core)、(ii) E9 の実測 r = 0.55 から逆算した 1/r = 1.82(C = 1 core とすると)。

| D | δ = 0.031(Δ=3.0 ns)| 0.047(4.5 ns)| 0.057(5.5 ns)|
|---|---|---|---|
| 1.17(profile、E7b)| r' = 0.565 | **0.573** | 0.578 |
| 1.26(profile、E5)| 0.564 | 0.571 | 0.576 |
| 1.82(r = 0.55 から逆算)| 0.560 | **0.564** | 0.568 |

**結論(見積り)**: E9 の 0.55 は **0.56〜0.58 に戻る**(+0.01〜+0.03。0.45 の遅れのうち 2〜7%)。0285 だけでは 1.0 に遠く、型付き直呼びは『D を 4% 前後減らす』梃子で、r を 1.0 に戻すには D を r = 0.55 のとき約 45% 減らす必要がある(D' = 0.55 D)。= 他の梃子(0287 の D3、実スレッドのミキサー〔別コア〕)と合わせる前提。**未確認**: この式は『worker が C を使い切っている』前提。E9 の worker は 0.46〜0.5 core しか使っていない回があり(PM 12:50 の『Worker CPU/音声秒 −35%』)、その場合 r は CPU で決まらず δ の効きはさらに小さい(r' − r < 上の値)。また ms/ブロックの根拠は工程 1 の合成 micro-benchmark の差 Δ と native の呼び回数で、ブラウザの実測ではない。
