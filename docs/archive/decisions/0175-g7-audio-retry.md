## 測り方

- **運転手** `app/test/e2e/audio-g7.mjs`(判定はしない): ページを開き、エンジンの first idle を待ち、Enter でウィザードを閉じ、エンジンが静かになるのを待ち、さらに 30〜90 秒待ってから測定窓を始める(S-ur-settle)。窓は ① quiet(トランスポート停止)② メトロノームのボタン (750,21) をクリック → Space で再生(play)。窓の始めと終わりの AudioWorklet のカウンタの差が欠け。同時に: 1 秒ごとのカウンタ、worklet の 50 ms サンプル、エンジンの `audio-pulse`(仮想時計・消費 frame・スレッドごとのスライス)、Worker の報告(Unlock の時刻)、**全 idle**(typed array: 仮想時計、idle から idle までの時間 = 連続計算の長さ)、窓の更新(lid、矩形)、**Worker スレッドの `/proc/<pid>/task/<tid>/schedstat`(CPU に乗った ns と run queue 待ちの ns)を 5 ms ごと**。
- **欠けの数え方**(`fle-out.worklet.js`、単体テストで固定、S-ur-def): デバイスが PLAYING の間、1 quantum のうちエンジンが公開した frame が 128 に足りなければ 1 欠け quantum、足りない frame 数も数える。連続した欠け quantum = 1 episode、最長の連続も数える。非ゼロ出力が 1 つでもある quantum = 非無音。
- **連続計算(stretch)の CPU 時間**: エンジンが idle から次の idle まで(ページに報告される idle の `busyMs`)を壁時計で測り、同じ区間の Worker スレッドの CPU 時間(`schedstat` の実行 ns、5 ms の標本から補間)と run queue 待ち(同)を切り出した。**負荷の高い機械では壁時計の連続計算 ≈ CPU 時間 + 待ち**で、待ちは機械の負荷、CPU 時間はエンジンの仕事。

## 結果 2: 原因の切り分け

### 2.1 欠けの原因は『ミキサーの 1 ブロックより長い連続計算』で、壁時計では負荷が足し、CPU 時間ではメモリ拡張だけが残る
- **ミキサー自体は軽い**: ミキサーのスライスが始まってからブロックを Unlock するまでの時間は平均 3.4〜6.3 ms(n4・n5 が 3.4、n3 が 6.3、n1 が 5.9)、最大 28.7 ms(n1)・33.1 ms(n3)・67.8 ms(n4・n5)。78 ms(ブロック周期 92.9 − リード 15)を超えたもの 0(`unlockCompute.over78`)。
- **定常の連続計算(idle から idle まで)の CPU 時間**: 20 ms 以上の連続計算の CPU 時間は中央 11〜15 ms、p95 14〜24 ms(t6・n1・n3・n4・n5)。**壁時計**は同じ窓で p95 45〜85 ms、最大 55〜235 ms(待ちが足される。Wait/Run 12〜185%)。

| 走行 | 連続計算(≥ 20 ms 壁)の数 | CPU 中央 / p95 / **最大**(ms) | 壁 中央 / p95 / 最大(ms) | CPU > 60 ms | 壁 > 60 ms |
|---|---:|---|---|---:|---:|

- **静かな機械(q1)では 375 秒に 20 ms 以上の連続計算が 10 回だけで、うち CPU が大きい 4 回は 90 ms・49 ms〔どちらもメモリ拡張〕、44 ms〔t=152.7 s〕、31 ms〔t=320.5 s〕で、後ろ 2 つの原因は調べていない。ほかは 20 ms 台以下**。q1 のメモリ拡張は 1,028.1 → 1,226.9 MB(t=212.0 s、CPU 49.1 ms、欠けなし)と 1,226.9 → 1,472.4 MB(t=330.5 s、CPU **89.5 ms**、欠け 9 quanta)。混んだ機械の同じ拡張は CPU 60〜68 ms と 123〜131 ms で、**拡張の停止の CPU 時間も負荷で伸びる**(キャッシュ・メモリ帯域の取り合い、読み)。

- **定常の『7 秒おきに 156 ms』(PM の問い)**: t3(nice 15、load 22)の窓にあった壁 155 ms の 2 件(7 秒間隔)は、CPU 時間の分解ができていない走行(t3)のもの。CPU 時間で分けられる走行(t6・n1・n3・n4・n5)には **7 秒周期の CPU 停止は無い**。長い壁時計の連続計算は、いずれも**主窓(lid 14)の 1〜3 枚の再描画(0.33〜1.1 Mpx)の周期**で終わる(`stretch-frames.tsv`。ui1 の『heavy cycle』= 1 仮想秒に 76〜84 回、VCL の木の走査)で、その CPU 時間は p95 14〜24 ms。壁 156 ms は『その 1 サイクル(CPU 約 40 ms)+ run queue 待ち』と読める。**関数の同定(ゲストのどの処理か)は、名前つきビルド(ui1 の D')が無く未実施**。

### 2.2 リードのモデルと較正(壁時計の連続計算 → 欠け)
- モデル: 連続計算 s(ms)がエンジンの許容 T を超えると、超えた分 `(s − T) / 2.9 ms` の quanta が欠ける。T を『リード 60 ms』とすると**過大に予測する**(t3: 予測 74・実測 59、t5: 155・57、t6: 400・194)。較正した T は **約 70〜80 ms**(t6: 70、n4: 80)。リード 60 に約 10〜20 ms の余りが乗る(ゲストが既にコミット済みの先、ミキサーの周期)。
- **較正した T を CPU 時間に当てると**(負荷のない機械での予測): n1・n3・t6(メモリ拡張の前)は **欠け 0**。メモリ拡張の 60〜131 ms は T を超える。`tables/*/stretch-calibration.tsv`。予測 1(13:35、nice 5 で quiet/play 60 s 欠け 0)は的中(n3)、300 秒は**外れ**(n4。メモリ拡張を予測に入れていなかった)。予測 2(delay 100 の 300 秒でメモリ拡張由来の episode 0)は的中(n5)。**予測 3**(静かな機械の nice 15、14:36:40 に記録〔走行の 14 秒後〕): R1(quiet 60 s で 0)は的中(q1)、R2『メモリ拡張の 2 回だけが欠ける、合計 20〜30 quanta』は**仕組みは的中、量は 3 倍過大**(q1: 拡張 2 回目だけで 9 quanta、1 回目は吸収。静かな機械では拡張の CPU 停止が 49・90 ms で、混んだ機械の 60〜131 ms より短い)、R3(load が 8 を超えたら…)は発動せず(走行中 load 4.6〜7.1)。

### 2.5 その他の経路(task 4 の項目)
- **ブロック長 4096 frame(92.9 ms)とブロックの間隔**: エンジンの Unlock の間隔は中央 94.1〜94.7 ms、p95 101〜106 ms、p99 117〜144 ms(最大 1.5〜2.8 秒は起動直後)。公称 92.88 ms との差は AudioContext の消費/実時間と、ミキサーのポーリングの粒度。書き込みの先行(Unlock から worklet が最初の frame を読むまで)は中央 114 ms、p5 87〜91 ms、p1 66〜71 ms(上限。worklet の投稿が最大 50 ms 遅れる)。`tables/*/unlock-intervals.tsv`・`unlock-ahead.tsv`。
- **Space → 最初の非無音の遅れ**(上限、worklet の 50 ms 投稿と入力経路の揺れを含む): 静かな機械の q1 で 165 ms、混んだ機械で 198〜568 ms(delay 0)。
- **メトロノームのボタンのクリックそのもの**が 95 ms の連続計算(CPU 95 ms 前後、主窓の再描画)を起こし、q1 では 5 quanta 欠けた(t=116.8 s。測定窓の外〔play 窓は Space の直前から〕)。
- **ミキサーのスライス長 vs idle 周期**: ミキサーのポーリング(`Sleep(1)` + `GetCurrentPosition`)は 1 仮想 ms ごとの期限で、idle は 1 秒に約 1,000〜1,100 回(ページへの報告は 40 ms に 1 回に間引かれる〈決定 0170〉)。報告された idle の間隔 p50 42 ms は間引きのためで、エンジンの停止ではない。
- **ページのメインスレッドと Worker の postMessage/SAB**: 音声のデータは**エンジンの EM_JS が Worker から SAB へ同期的に書き**、worklet が SAB を直接読む。ページのメインスレッドも `postMessage` も経路に無い(構造から)。ページ側の負荷は 0.03〜0.04 コア(決定 0170)。
- **GC**: 単独では測っていない。Worker の連続計算の CPU 時間(p95 14〜24 ms)に含まれる。JS の GC が 60 ms を超える停止を出した証拠は、CPU 時間の最大(メモリ拡張を除き 32〜42 ms)には無い。
- **タブの抑制(hidden)**: `Target.activateTarget` で別タブを前に出し `document.visibilityState` が `hidden` になった 39.0 秒(h1。nice 15、load 18〜21、トランスポート停止): AudioContext は `running` のまま ctx 38.91 s / 壁 39.0 s、欠け 0 quanta、エンジンの idle は続いた(Worker のタイマーが抑制されないのは決定 0170 の測定と同じ)。**再生中の hidden、実機のウィンドウの最小化・遮蔽・タブの切替は未測定**。同じ走行で hidden から戻して再生した 40 秒は 1,605 quanta / 78 episode だったが、Wait/Run 148% の負荷の窓で、hidden との因果は示せていない(同じ負荷の d60・d120・l30 が 127 / 0 / 1,073)。

## 設計案(測定値を根拠に。実装は小さい opt-in の `audiodelay=` だけ)

### 1. 仮想時計を音声の消費に合わせる必要はあるか
測定(上の表、ドリフト): 仮想時計/実時間 = 1.0000(0170 の追従。60 秒以上の窓)。AudioContext の消費/実時間 = 0.9998(nice 5、300 秒)〜0.991(nice 15・load 35)(headless Chrome。実機未確認)。ミキサーは**音声の消費位置(AudioWorklet が読んだ frame 数 = RD)**を `GetCurrentPosition` で見て書くので、仮想時計が音声と何 ms ずれても**音の連続性には効かない**(仮想時計はミキサーが「いつ位置を見に来るか」を決めるだけ)。ずれは(a)ゲストのタイマー(UI の更新)が音声より最大 0.02〜0.1%(nice 5 の 300 秒で 63〜66 ms) だけ速く進む、(b)ゲストが再生位置を時計から作る箇所があれば、その箇所だけ音声より進む、の 2 点に出る。(b) は未確認(FL の再生位置の表示が `GetCurrentPosition` 由来か、`GetTickCount` 由来かは読んでいない)。
- 案 A(採る): 何もしない。G7(連続性)には不要。
- 案 B(P3 の本番で聞こえ方に問題が出たら): idle-driver のアンカー(仮想時刻 ↔ 実時刻の対応)を、`(仮想 − 消費)` の誤差に比例して**最大 ±0.5%** だけ傾ける(スルー)。仮想時間は飛ばさない。`idle-driver.ts`(0170)の変更になるので、clk1/PM の合意が要る。
- 案 C(採らない): 仮想時計を AudioContext の時計から作る。音声が止まる(タブの抑制、デバイスの切替)とゲストの全タイマーが止まる。

## PM の判断点

1. **G7 の記録**: 『G7 の字義の基準(アンダーランを一定時間 0)を、条件 X(`audiodelay=100`、headless、空プロジェクト、load 30〜40、Chrome nice 5)で 300 秒観測した』。既定(delay 0)は 60 秒で観測、300 秒は観測できなかった。数値条件(P3)を満たすまで『達成』と数えない(PM が判定して記録する)。
2. **`audiodelay` を既定にするか**: 既定は 0 のまま。代償は、設計上、音が delay 分遅れること(**測定では分解できなかった**: Space → 最初の非無音の遅れ〈上限値、worklet の 50 ms 投稿と入力経路の揺れを含む〉は delay 0 の 5 走行で 198〜568 ms〈240、254、198、214、568〉、delay 60 が 338 ms、delay 100 が 320 ms、delay 120 が 754 ms で、負荷による揺れ ±200 ms 以上が delay 分 60〜120 ms を隠す。予測 2 の Q3『約 340 ms』は値は合ったが、基準が 198〜568 ms で動くので的中とは言えない)と、ゲストの画面の再生位置が音より delay 分先に動くこと。ライブ演奏のモニターには向かない。**聞こえ方・実機での遅れは未確認**(依頼者の確認後に PM が決める)。
3. **P3 の窓の定義**(S-ur-window): パネルの P3 は『first idle 以後の欠け quanta』、注に直近 60 秒・最初の音以後・デバイスの状態別。ゲストのトランスポート(再生中か)をページから読めるようにするか(appview に項目を足す。`lift/` の変更)。
4. **取り付け方**(S-ur-hook): `window.Worker` を包んでいる。`EngineClient` に Worker の getter を 1 つ足せば包みは要らない(`client.ts` の変更。この作業では指示により触らなかった)。
5. **メモリ拡張の停止(CPU 60〜131 ms)**: 決定 0174(leak1)で増加自体が止まれば消える見込み。止まらない場合の front-end だけの手は『起動の無音の間に wasm メモリを先に伸ばす』(エンジンの malloc/free を呼ぶ。グルーの HEAP ビューの更新が絡むので未実装・未検討の読み)。runtime の手は『ミキサーの先読み』(ゲストがコミット済みの範囲の終わりまで公開。D の再ビルド約 1 時間強)。**どちらも未実装**。
6. **音声データを書き換える補正は一つも入れていない**(リサンプルも補間も位置の微調整も)。ドリフト(消費/実時間 0.9998〜0.9992、300 秒で 60〜110 ms)は音の連続性に効かないので補正の必要を示す測定は得られなかった。入れるなら PM の判断(既定にしない)。
7. **リードの上限**: 1〜1000 ms を受け付けるが、ゲストのバッファの半分(92.9 ms)を超えると成立しない(0139 の検査)。PM の例の 120/250 ms は試していない(試すと波形が壊れる見込み。未測定)。
8. **起動直後の欠け(PLAYING から約 15 秒、270〜5,500 quanta)**: ウィザード/ロゴの描画の 110〜340 ms の連続計算。音は無い。放置か、ゲストの再生を始めるまで worklet を OPEN のままにする(runtime の変更)か。
