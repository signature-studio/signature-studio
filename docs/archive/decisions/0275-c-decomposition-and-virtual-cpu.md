## 冒頭の 3 点

1. **測ったこと(実エンジンの実行)**: lift した実エンジン(`FLEngine_x64.dll` と同梱 DLL を C にしたもの)を **native -O2** で、alpha1 の台本 `a12-play.g3`(**ハーネスの入力の模擬**: プロジェクトを開く → ダイアログを閉じる → Space → 100 仮想秒の再生)で **7 本**走らせた(base、`FLE_PREEMPT_DISPATCHES` = 8192 / 16384 / 32768、`FLE_PREEMPT_TICKS` = 2500 / 1250。ほかに alpha1 の既存の x2/x3/x4 の trace 3 本を再集計)。**base の G/L/U 行(G/L/U の 33,378 行)は alpha1 の trace と全行一致**(再現)。ブラウザは**測っていない**(gpu1 の既存表を引用)。実機 Windows は 0 件。命令数は**測れていない**(`perf_event_paranoid` = 4、valgrind・qemu なし)。
   - **C の中身**(§1): 再生中の C(最後のポーリング → Lock)は、**ミキサー自身の課金 165〜267 スライス = 仮想 165〜267 ms が全部**。ほかのスレッドが C の間に課金されるのは 1 サイクル最大 9 ms、中央値 0。UI スレッド(th0)は C の間も走る(450〜736 スライス = 1.8〜3.0 M 回の間接呼び)が、**窓プロシージャの中(深さ 2〜3)なので課金 0**。**スキップされたスライス 321,112 本の 100% が th0 で、ミキサー(th18)のスキップは 0**(alpha1 の「終わりの 73% は callback の中で飛ばされる」は mix 本体ではなく UI の分。訂正)。
   - **30 s 付近で変わった物**(§1): ミキサーの 1 ブロックの課金が **3 ms(間接呼び 1.27 万回)→ 165 ms(0.68 M 回)→ 264〜267 ms(1.08 M 回)→ 190〜207 ms**(54〜88 倍)。UI の課金は 10 s に 4〜27 ms(変化なし)、UI のスキップは 25,238 → 27,699 本/10 s(+10%)。曲の位置で決まる(alpha1: 再生を 20 s 遅らせても押してから同じ 4.9 s 後)。
   - **校正**(§2。**10:19 の訂正を反映**: alpha1 のプロファイルの標本間隔は 2 ms〔`A4_PROF_US=2000`〕で、20,246 標本 = **40.49 CPU s**。私は最初 20.246 s と読んで半分にしていた): ミキサーの 354 M 回(課金 86,421 ms)に対し CPU 40.49 s ⇒ **114.4 ns/回**(この Zen 5、cpuinfo 5.1 GHz、約 584 cycle)。モデルは 244 ns/回 = **2.13 倍遅い**(0.885 仮想 s/s ÷ 0.413 CPU s/s でも同じ)。ミキサーの実 CPU は 1 ブロックあたり平均 92 ms = **m ≈ 0.99 CPU s / 音声 s**(40.49 s ÷ 40.87 音声 s)で、ブラウザの m ≈ 1.0(opt1)と同じ。
   - **sweep**(§3、native): 30 s 以降の書き込み率 base 0.419(C 中央値 180 ms)→ ×2(DISPATCHES 8192)0.722(108 ms)→ ×4(16384 または TICKS 2500)**0.998**(53 ms)→ ×8 **1.000**(26〜27 ms)。DISPATCHES と TICKS は同じ k で同じ結果。
2. **結論**:
   - 3 ブロック周期の原因は **「ミキサー自身の mix 区間の仮想時間 C が 2 ブロック(186 ms)を超えること」で、C を決めているのは決定 0147 の `S-vclock-slice-time`(4096 回 = 1 ms)の校正**。UI でも DirectSound でもブラウザの pacing でもない。この定数は**出典なしの選択**(根拠は「初期化が 1.78 s になる」だけ)で、今回初めて実測の足場ができた(57 ns/回)。
   - **(b) 仮想 CPU の並列化は C を縮めない**(C の全部がミキサー自身の課金。UI は既に課金 0)。のみならず実機の契約(プロセッサ数 1 を答える `S-sysinfo-1cpu`)と食い違う(§4)。
   - **(e) 校正(k ≥ 3.4。この機械の lift したコードと同じ速さは k = 2.13)は仮想軸を解くが、実 CPU の軸は解かない**(k > 2.13 は『この機械で lift したコードが実際に出せる速さより速い仮想 CPU』なので、実 CPU が追いつかない)。gpu1 のブラウザの腕がそのまま示している: L16384(×4)でも書き込み率 **0.553(30〜60 s は 0.502)**、virtual s / real s = 0.43〜0.50、Worker busy 86〜88%(`p3-arms.md`)。native では ×4 で 1.0 になるのに、ブラウザでは 0.5 で止まる = **u + m·r ≤ 1(r ≲ 0.53)の実 CPU が律速**。P3 は (e) 単独では直らない。(a) 単独でも直らない(読み: 仮想の課金は呼び回数で決まり実 CPU に依らない。ブラウザの現状は virtual s / real s = 1.0・event-loop の待ち 13〜33% で、仮想軸が先に縛っている。(a) 単独のブラウザの腕は無い)。**(e) と (a)/(c) の両方が要る**。
   - 推奨・順序・リスクは §7。
3. **未確認**: (i) 実 Windows の FL の C(実機の値は 0 件。§2 の 39〜105 ms は『lift のコードより遅くない』という前提の**上限の見積り**で読み)。(ii) 命令数。(iii) ブラウザでの (e) 後の UI 遅延(gpu1 の腕は UI のスライスが 36〜42% → 29〜31% に減り、virtual s / real s が 0.43〜0.50 になった = P2 の悪化の疑い)。(iv) 30 s 付近でミキサーの課金が 54 倍になる理由(曲のどの要素か)。alpha1 の標本では Elastique が自己時間の 70.3% で、時間伸縮のクリップが始まる形と読むが、プロジェクトの中身は見ていない。

## 1. C の分解 — 何が C を作っているか(native、実測)

C = 最後の `GetCurrentPosition`(半分が変わったと見たポーリング)→ 次の `Lock`。課金 = 仮想 CPU の 1 ms スライス(`Q` 行)を使ったスレッド。スキップ = スライスが callback の中(深さ > 1)で終わり、時計も切り替えも動かなかったもの(`D` 行)。mix = ミキサー(th18)。出力: `tables/c-split-per-10s-base.tsv`、`tools/c_split.py`。

- **C の中の間接呼びの内訳**(C の全呼び = 課金スライス + スキップ スライス、各 4096 回): 30〜40 s の 1 サイクルで 2.52 M 回 = ミキサー 0.68 M(165 スライス)+ UI 1.84 M(450 スライス、課金 0)。ミキサーの 1 ブロックの間接呼び: 10〜30 s は **1.27 万回**(3 スライス)、30〜50 s は **0.68 M**、50〜70 s は **1.08 M**、70〜120 s は **0.77〜0.85 M**。
- **30 s 付近で何が変わるか**: UI ではない(UI の課金は 10 s に 4〜27 ms、スキップは +10%)。**ミキサーの mix 本体が 54〜88 倍重くなる**。alpha1 の標本(仮想 3630〜3728 s、スレッド 18、2 ms ごと)の自己時間は Elastique 70.3%・FLEngine 14.1%・runtime/libc 12.5%・dsp_ippv2 3.1%(`alpha12-results/tables/native-mixer-cpu-by-module.tsv`)。

## 2. 校正 — 4096 回 = 仮想 1 ms は何に対して何倍遅い CPU を仮定しているか

### 2.1 定数の出典(決定 0147 §4.3・§7、読み直し)

| 名前 | 値 | 出典 | 判定 |
|---|---|---|---|
| S-vclock-slice-progress | 4096 回 | 2 のべき | 出典なしの選択 |
| S-vclock-slice-time | 10,000 ticks = 1 ms ⇒ 0.244 µs/回 | 『初期化の間接呼び 1,049 万回が仮想 1.78 秒になる』≒『FL の起動は数秒程度』という一般的な認識(**読み・未確認**)の下限。0147 §0 の 1 番が自分で『実機の確認 0 件。出典なしの選択』と書いている | **出典なしの選択(測定でも Learn でもない)**。Learn に値は無い |
| S-vclock-depth | 深さ > 1 のスライスは時計も切り替えも動かさない | 窓プロシージャ等の下に、runtime の表を走査中の関数があるかもしれない(再入の安全) | 実装上の制約。**UI を課金 0 にする効果**が本来の校正に隠れている(下) |

0147 の決定時に分かっていなかった物: **ミキサーが 1 ブロックに実行する間接呼びの量**(0.68〜1.08 M)。これで初めて『C が 2 ブロックを超える』ことが定数から読める。

### 2.2 実測の足場(native、この機械)

| 量 | 値 | 出典 |
|---|---|---|
| ミキサー(th18)の間接呼び(仮想 3630〜3728 s) | 354.0 M(課金 86,421 スライス × 4096) | 私の base の Q 行 |
| 同じ窓のミキサーの CPU(native -O2) | **40.49 s** = 20,246 標本 × **2 ms**(SIGPROF を 2 ms の CPU ごと、`A4_PROF_US=2000`、`alpha1_rec.c:513`)⇒ 0.413 CPU s / 仮想 s | alpha1 `native-mixer-profile-top-functions.txt` の 1 行目の『20.246 CPU s』は 1 ms 仮定で半分(ファイル先頭の NOTE)。`native-mixer-cpu-by-module.tsv` は『2 ms each』 |
| 1 回あたり | **114.4 ns** ≒ 584 cycle(cpuinfo 5,106 MHz。VM の表示で実際の周波数は未確認) | 上の 2 つの商 |
| モデルの課金 | 244.1 ns/回 = **2.13 倍遅い**(= 0.885 仮想 s/s ÷ 0.413 CPU s/s と同じ) | 定数 |
| 1 ブロックの CPU(窓の平均) | 40.49 s ÷ 440 サイクル = **92 ms** | 同上 |
| m(ミキサーの CPU s / 音声 s) | 40.49 s ÷ (440 × 4096 / 44,100 = 40.87 s) = **0.99** | 同上 |

**m ≈ 0.99 は『native -O2 でも lift したミキサーは、この Zen 5 の 1 コアをほぼ丸ごと使って実時間』**を意味する(ブラウザの m ≈ 1.0 と同じ)。プロファイルは SIGPROF 付きの run で、標本の負荷は小さい(読み)。

### 2.3 実機の C はどれくらいのはずか(**見積り・読み**。実機 0 件)

前提: (1) 実機の FL も同じ数の間接呼びを実行する(lift は命令を保存する)。(2) 元の x86 のコードが lift した -O2 の C より速い倍率 **f_l ≥ 1 は不明**(lift は普通遅くなる側。測れない)。(3) 同じ IPC。下の表は f_l = 1 の値 = 『実機の C の上限』。f_l で割る。

| 区間 | ミキサーの間接呼び/ブロック | このホスト(5.1 GHz)で 114.4 ns/回 | 4 GHz 換算 | 3 GHz 換算 | 3 GHz・f_l = 2 | モデルの C |
|---|---|---|---|---|---|---|
| 30〜50 s | 0.68 M | 77 ms | 99 ms | 132 ms | 66 ms | 165 ms |
| 50〜70 s | 1.08 M | 124 ms | 158 ms | 210 ms | 105 ms | 265 ms |
| 70〜120 s | 0.77〜0.85 M | 88〜97 ms | 112〜124 ms | 150〜165 ms | 75〜83 ms | 190〜207 ms |

- モデルの C は f_l = 1 の上限の **2.13 倍(このホスト)・1.67 倍(4 GHz)・1.25 倍(3 GHz)**。**『モデルが実機より何倍遅い』は f_l 次第で、f_l が分からない限り言えない**(最初の版の『2.5〜4.3 倍』は標本間隔の読み違いで撤回)。f_l ≥ 1.6 なら、同じホストで C ≲ 78 ms(k = 3.4 の C と同じ)になる = **k ≥ 3.4 は『元のコードが lift のコードより 1.6 倍速い CPU』の仮定と同じ**(未確認)。
- 3 ブロックの崖は C ≥ 186 ms(0273)、1 ブロック周期を保つ C の目安は ≲ 85 ms(sweep で x3 の p90 = 91 ms が境)。**f_l = 1 の 3 GHz では 50〜70 s の 210 ms が崖を超える** = lift のコードがそのまま実機に載れば 3 GHz 級では実機も崩れる(f_l が 1.3 以上なら 160 ms 以下で崖の手前に収まる、読み)。
- 命令数は**測れていない**。584 cycle/回 × IPC 1〜3 ⇒ 約 580〜1,750 命令/回は読み(ホストの周波数が未確認なので幅は広い)。

### 2.4 UI を課金しないことが校正を隠している(読み・数は実測)

UI は 11.2 M 回/s の間接呼びを実行する(1,095 M ÷ 98 s)。仮に全部を課金すると、仮想 CPU の消費(UI の ns/回が未測定なので『ミキサーと同じ ns/回』と仮定した上限)は k = 1(244 ns)で **2.73 仮想 s/s**(破綻)、k = 2.13(114 ns)で **1.28**、k = 4(61 ns)で **0.68**、k = 8 で 0.34。深さ > 1 を課金 0 にする `S-vclock-depth` があるので UI は問題にならなかった。= (e) の k = 4 以上は『UI を課金しない特別扱い』を外す道も開くが、k = 2.13 では UI だけで 1 CPU を超える(外せるかは再入の安全の問題で別。UI の ns/回の実測が要る)。

## 4. (b) 仮想 CPU の並列化の評価

| 観点 | 評価 | 根拠 |
|---|---|---|
| C を縮めるか | **縮めない** | C の全部がミキサー自身の課金(§1)。他スレッドの課金は C の間に中央値 0 ms、最大 9 ms。UI の 1,095 M 回は既に 128 ms しか課金されていない(0.13%) |
| 実機の契約と合うか | **合わない** | `GetSystemInfo`・`GetLogicalProcessorInformation` はプロセッサ数 1・mask 1 を答える(`fle_sys.c`、`S-…`『ホストのコア数を答えると出力が機械で変わる』、決定 0122『プロセッサ数は 1 のまま。偽らない』、決定 0234c『マルチプロセッサ(1 プロセッサの契約)』)。1 CPU と答えて 2 本の仮想 CPU に課金するのは矛盾。N > 1 を答えると FL の側のスレッド構成(現在ミキサー 2 本 t7・t18、両方 TIME_CRITICAL)が変わる可能性があり、新しい未確認の経路になる |

| 実 Windows に近いか | 近づく物は無い | 実機のマルチコアの並列は『ミキサーの C = 自分の CPU 時間』であり、今のモデルでも C は自分の課金だけ。差が出るのは校正(1 回の速さ)で、並列度ではない |

**(b) は成立しない**(C に効かず、1 CPU の契約と矛盾し、規則を足す)。軸は (e)。

### 実 Windows の FL が見る時間との関係
ゲストは仮想時計(`GetTickCount`・QPC・`timeGetTime`)で時間を見る。実機では FL のミキサーの C は『実 CPU の時間』で、モデルではそれが『呼び回数 × 244 ns』。(e) は後者の傾き(ns/回)を実機の傾きに近づける。FL が自分の CPU メーターや underrun を QPC の差から出すなら、現在のモデルではそれがf_l = 1 の上限の 1.25〜2.13 倍(f_l が大きければもっと)に見える(**未確認**: FL の CPU メーターの値を 30 s 付近で読んだわけではない)。

## 7. 推奨(PM の判断材料。実装はしていない)

1. **(b) は採らない、(f) も採らない**(§4、§5)。
2. **(e) は仮想軸の必要条件**。k は `S-vclock-slice-time` の定数 1 つの変更で、新しい分岐・特別扱いを足さない(lift-fidelity の「定数の見直し」。出典は無いまま、足場が実測になる。k = 2.13 を超える部分は『元のコードが速い』という f_l の仮定で、未確認)。k の下限は 3.4(ミキサーの C の p90 の最大 290 ms ÷ 1 ブロック内に収める目安 85 ms)、ホストの lift したコードと同じ速さが 2.13(k = 2.13 では C = 78〜125 ms で、重い区間はまだ 1 ブロックを超える。native の x2 の実測 0.72〜0.79 に近い)。k > 2.13 は実 CPU が出せない速さなので、必ず (a) とセットにする。**TICKS で変える方(10000 → 2500 または 2300)を推奨**: 4096 回のスライスの境界(= スレッドの切り替え点)が変わらないので、窓表が 17 中 16 で base と一致し(DISPATCHES は 0)、Sleep(1) の起床も細かくなる。DirectSound の結果(C・書き込み率)は DISPATCHES でも同じ。
3. **(e) 単独でブラウザに出さない**: gpu1 の L16384 は書き込み率 0.55 にしか届かず、virtual s / real s が 0.43〜0.50、UI の割合が減る。(e) は (a)(0270 の直 wasm 化と m・u の実測)と同じ冷間ビルドで、**P2(UI の遅延・120 fps)と P3(書き込み率・途切れ)の両方を測って**出す。
4. **(a) の目標値**: u + m·r ≤ 1 で r = 1 に届くには、u ≈ 0.46 のままなら m ≈ 1.0 ⇒ ≤ 0.54(例。u も下がれば緩む)。m の現在値は native でも 0.99、ブラウザで 1.0。0270 の見積り(約 660 ms)は実測ではないので、E8 の実エンジンの測定で m と u を取り直す。**(c) 実スレッドでも足りない**(読み): ミキサーに 1 コアを渡しても m = 0.99 ⇒ C = 77〜124 ms(このホスト、f_l = 1)で、50〜70 s の重い区間は 1 ブロックを超える。(c) も m を下げる (a) とセットで効く。
5. (d) は利用者の設定として説明する物で、モデルの修正ではない。置き場が未特定。

## 8. 限界・自己申告

- **実測 = native の仮想時間の実エンジン**(7 本 + 既存 3 本の再集計)。ブラウザ・実機は 0 件。gpu1 の表は引用。
- 台本は alpha1 の `a12-play.g3`(**ハーネスの模擬**)。k の sweep の 1 本目の base が alpha1 の trace と全行一致なので、私のビルド(alpha1 の t12h の runtime + 診断 2 点、`out-alpha3/gen3` の生成 C、`obj-b/h/realmod_table.o`)は同じ挙動。**ただし alpha1 が最後に入れた `f_425500` の `SetWindowPlacement` の差し替え(`wrap-f425500.c`)は入れていない**(その行が t12h の runtime に無く、リンクできない)。0275 の量(DirectSound の列・間接呼び)に影響しないと読む。
- **標本間隔の読み違い(自己申告)**: alpha1 の top-functions の 1 行目『20.246 CPU s』を 1 標本 = 1 ms と読み、ミキサーの CPU を半分にした(by-module の表に『2 ms of process CPU each』とあったのに確認しなかった)。10:19 に PM 経由で alpha1 から指摘され、40.49 s に直した。第 1 報の『57.2 ns/回・4.27 倍・実機の C の上限 39〜105 ms・2.5〜4.3 倍』は撤回し、『114.4 ns/回・2.13 倍・77〜210 ms』に差し替えた(sweep と仮想軸の結論は CPU 秒を使わないので不変)。
- ns/回の分母は『課金スライス × 4096』(スライスの境界の端数は ±4096 回)。ミキサーの CPU は alpha1 の標本(仮想 3630〜3728 s、スレッド 18 のみ)で、私の base と同じ窓。UI の ns/回は測っていない。
- 『実機の C の上限』は f_l ≥ 1・同 IPC の仮定の読み。命令数は測れていない。
- 私の診断(`0275-diag-not-for-merge.diff`、`fle_thread.c` に D 行と `FLE_PREEMPT_DISPATCHES/TICKS` の環境変数、`fle_callback.c` に E 行)は**マージしない**。alpha1 の t12h の診断(Q・G・L・U・S・P 行)の上に載る差分。
- 規則の逸脱の自己申告(0275 で追加): (a) 存在しない `bash` という名前のツールを 1 回呼んだ(shell として実行された)。(b) 最初のビルドで `lift/out-mt3y` が 489 MB まで増えた(上限 500 MB。直前に cargo の target 3 本と tmp の中間表を消した)。(c) native の実行は 2 本ずつ、`taskset -c 14/15`、`nice -n 15` で回した(負荷は 8〜15 の窓。他の測定の窓を邪魔した可能性は否定できない。E7b のデプロイの前後)。
