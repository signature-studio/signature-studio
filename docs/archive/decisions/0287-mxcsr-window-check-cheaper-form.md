# 0287 パックド add/sub/mul の MXCSR 窓検査を、同じ述語のまま安くする(alpha15)

決定 0287(仮)。対象は fe-wasmgen の SSE lowering(`--mx-packed` / `--mx-rc`)の `mx_pk_ok`(packed add/sub/mul の「全レーンが窓の中」検査)だけ。基準は E9 の `b0fe2c11`(`e9-wip`)。日付 2026-11-06。

**実エンジンの実行について**: 本書の Chrome の測定は、E7b の**本番 wasm**(`fl-engine-ci-d9c160aa`、実エンジンを lift した物)の `Elastique` と `dsp` の窓検査の条件だけをバイト列で書き換えた物を、Chrome(実時間、参照プロジェクト `serina1-serum2.flp`)で 45〜60 秒再生したときの V8 CPU プロファイルです。代役・再生・期待値の貼り付けはありません。書き換えは**試作(使い捨て)**であり、出荷物ではありません。

## 0. 結論(先頭 3 点)

【測ったこと(実測)】
1. **実ミキサーでは、命令数を減らした D3 も、命令を足した案 A も、出荷版より良くならなかった。** 同一実行内の比 A/other(`f_b34aca0`+`f_b34eaf0` / ミキサーのその他): 出荷版 3 回 0.1734 / 0.1875 / 0.2005(平均 0.187)、**D3 0.2135**(予測は 0.145 = −23%)、案 A 0.2376、窓検査の全除去 0.0624(Chrome 156、ミキサースレッド 30〜50 s、load は D3 が 14.6 → 16.4 と高い)。D3 は出荷版の揺れ(±7〜10%)の範囲かそのすぐ外で、**効果は確認できなかった**(1 組)。
2. 微小ベンチ(node/V8、本番ではない)では D3 は現行の検査費を −32〜−35%(1.10〜1.17 → 0.72〜0.78 ns / ベクトル対)に下げ、案 A はゼロが半分を超えると現行より遅い。**微小ベンチは実ミキサーを予測しなかった**(D3 の予測が外れた)。
3. 述語の同値と正しさは確認できた(実 wasm の条件との 900 万件で不一致 0、ホスト CPU との差分テストと変異テスト 9 通り、node の行 84 / 55 / 87 が無改造版と差 0 行)。壊れてはいない。効かないだけ。

【結論】
- **D3 は E12/E10 に載せない(現時点の判断材料: 効果を実測で示せていない)**。差分は小さく(`rcgen.rs` +28 行、`lower.rs` +4 行)、述語は厳密に同値で、wasm は 約 86〜92 KB 小さくなる(−0.06%)ので、害は無いが、載せる価値を示す測定が無い。載せるなら、実ミキサーで出荷版との交互 3 組以上で示してから。
- 窓検査を全部除くと ミキサー全体で −7.6〜−11.5%(保守側。別の正規化で −15.7%)なので、検査の費用そのものは大きい。『演算の命令数を減らす』では取れず、費用は別の所(巨大関数のコード量、`local.get` の再読込、制御フロー)にあるという読み(**未検証の仮説**)。次に試すなら、検査の**コードのバイト数**と**読み出し回数**を減らす形(検査を共通の小関数に出す〔呼び出しの費用とのトレードオフ〕、`local.tee` で一時ローカルに `abs` を 1 回だけ作る)の比較を、同じ交互の測定で。

## 1. 検査の厳密な意味(1 枚)

### 1.1 構造(E7b / E9 の lowering、`lower.rs` `mx_packed`)

`ADDPS/SUBPS/MULPS`(`PD` 版も同じ形、f32 と f64 で窓の幅が違う)は、`--mx-rc` のとき次の形になる。`d` は宛先の v128 ローカル、`sv` は元オペランドを入れた一時ローカル。

```
local.get mx_rcl ; i32.eqz
if                                     ;; ガード: MXCSR の RC=0 かつ PM(精度例外)がマスク済み かつ PE が立っている
  <窓検査 P(d, sv): i32>               ;; ← 本件の対象
  if   d = f32x4.add/sub/mul d sv      ;; 素の wasm SIMD 1 命令
  else mx_slow: d,sv を mx_buf に書く → fle_hyb_mx(kind 40/42/44) を呼ぶ → 結果を d に読む → mx_guard_refresh
  end
else                                   ;; RC が 1〜3(rcl-1 <u 3): rcgen.rs の指向丸めヘルパ(自前の窓つき)。窓の外は mx_slow。rcl=4(ガード偽)は mx_slow
  ...
end
```

- `mx_rcl` はローカル。`ldmxcsr` の後、および C 経路の呼び出しの後ごとに `mx_guard_refresh` が作り直す: `rcl = (PE が立ち PM がマスクなら RC(0〜3)、でなければ 4)`、つまり `rcl == 0 ⇔ (mxcsr & 0x7020) == 0x1020`。FTZ/DAZ(0x8040)は**ガードに入っていない**(窓の中なら結果は FTZ/DAZ に依らないため)。
- ガードが真の割合は 99.8%(0282: `ldmxcsr` 554,968 回のうち偽になる値は 0x9fc0 と 0x1f80 だけ)。値の大半は FTZ/DAZ の切替(0x9fe0 166k、0x1fa0 164k、0x1fb0 81k、0x9ff0 81k、0x9fe1 51k)。MXCSR は ミキサー 1 ブロックあたり約 770 回変わる。**ゆえに検査の結果をレジスタの値以外(MXCSR をまたいで)再利用することはしない**(再利用する案は採らない)。

### 1.2 述語 P(何を検べるか)

`P(a, b) = ∀ レーン x ∈ (a のレーン) ∪ (b のレーン): x が ±0、または 偏りつき指数 e(x) ∈ [lo, hi]`

| 形 | lo..hi(偏りつき指数) | 値の範囲 | 備考 |
|---|---|---|---|
| f32(ADDPS/SUBPS/MULPS) | 65..189 | 2^-62 ≤ \|x\| < 2^63 | `x` の ビット列 A = x & 0x7fffffff が 0 または [65<<23, 190<<23) |
| f64(ADDPD/SUBPD/MULPD) | 513..1533 | 2^-510 ≤ \|x\| < 2^511 | |

ゼロは許す(符号つきゼロも)。**反例(偽になる)**: 非正規数、NaN、無限大、窓の外の大小。符号は見ない。2 つのオペランドの全レーンの AND。現行の命令列は 1 オペランドあたり 12 命令(`x<<1`、`(t - lo<<S) <u n<<S`、`or (t == 0)`)× 2 + `and` + `all_true` = f32 で 26 命令(f64 は 30 命令)。

### 1.3 真のとき何を省くか(なぜ忠実か)

真なら、`fle_hyb_mx` の呼び出し(`mx_buf` へ 32 バイト書き、C 関数、`mx_buf` から読む、`mx_guard_refresh`)を省いて wasm の 1 命令にする。これが忠実である理由:

- 窓の中のオペランド(非正規・NaN・無限大なし)では IE/DE/ZE は立たない。加減は被演算数の 1 ulp が 2^-85 以上なので結果が非正規にならず(UE なし、FTZ にも触れない)、積は 2^-124〜2^126 で正規(UE/OE なし)、和は 2^64 未満(OE なし)。
- 結果が不正確なら PE が立つが、ガードで PE はすでに立っており、PM はマスク済み(例外は起きない)→ MXCSR は変わらない。
- 丸めは RC=0(最近接偶数)で wasm と同じ。ゼロの符号(x − x = +0 など)も同じ。DAZ/FTZ が立っていても、窓の中は非正規が出てこないので結果は同じ。

### 1.4 偽のとき

窓の外(ゼロ以外の極小・極大・NaN・Inf を 1 レーンでも含む)なら `mx_slow` = ホスト側の C 経路(`fle_hyb_mx`)が本物の x86 の意味(MXCSR のフラグ更新を含む)で計算し、結果を `d` に戻して `mx_guard_refresh` する。**この偽の経路の結果が正しさの根拠**なので、条件は「真のときだけ省ける」を満たす限り(真の集合が窓の内側の部分集合であれば)どう作ってもよい。現行は「窓の中(ゼロ含む)」ちょうど。

### 1.5 現行の費用

- `f_b34aca0` と `f_b34eaf0`(Elastique、同じ形の 2 本、それぞれ 106,516 命令・347,923 バイト)は f32 の窓検査を**各 646 箇所**持つ(f64 は 0)。2 本でミキサー(E7b、約 84.4 ms/ブロック)の **14.8〜16.7%**(0282 の 3 回)。
- 窓検査を全部除去した対照(0282、3 組): この 2 本が**−43%〜−65%**、ミキサー全体が**−7.6% / −8.7% / −11.5%**。検査は この 2 本の時間の約 3 分の 2 に当たる。これが**どんな安い検査でも超えられない上限**。
  - 別の正規化での同じ対(A3 対 B2): ミキサーのその他の時間で速さを合わせ、f32 の窓検査を持つ 31 関数(1,778 箇所)だけを見ると 1,705 ms(ミキサーの 26.9%)→ 710 ms(×0.42)で、除去の上限は **15.7%**(= (1,705 − 710) / 6,331、`tables/0287-f64-share.txt`)。上の 7.6〜11.5% は 2 本の関数の A/other 比から出した値で、こちらは保守的。D3 の効果の見積もりは保守側の 7.6〜11.5% を使い、広い側(15.7%)なら 5.2%(= 15.7% × 0.33)になる。
- 全体(Elastique + dsp)の窓検査は f32 2,051 箇所、f64 440 箇所(試作の書き換えが対象にした箇所。条件の形が合わない 281 箇所と、add/sub/mul でない 51 箇所は除く)。

## 2. 候補(3 つ)

記号: R = 検査を全部除去したときのミキサー全体の削減 = 7.6〜11.5%(3 組)。s = その案が検査費を減らす割合。**ミキサー全体への効果の見積もり = R × s**。

| 案 | 命令数(f32 / 箇所) | s(根拠) | 見積もり(ミキサー全体) | 忠実さのリスク |
|---|---|---|---|---|
| **現行** | 26 | 0 | 0 | — |
| **A 指数だけの先行検査**: 2 つのオペランドの上位 16 ビットを 1 回のシャッフルで集め、指数が [lo,hi] かを 16 ビット×8 レーンで見る(10 命令)。真なら 1、偽なら**現行の条件**で決める(`if (result i32) 1 else <現行> end`) | 真のとき約 13(10 + `if`/`else`)、偽のとき 13 + 26 = 39 | z をゼロ/窓外のレーンを含む検査の割合として s = 0.5 − z(命令数)。z=0 で 0.5、z≥0.5 で負 | 命令数だけなら 3.8〜5.8%(z=0)。**実測は負**(§3.5、§4) | 述語は現行と同じ(偽のとき現行が決めるため。快速側が真なら必ず現行も真 = 実 wasm で 300 万件 ×6、不一致 0)。リスクは性能の逆効果だけ |
| **B 窓 OK フラグのローカル**: レジスタごとに「検査済み」フラグを持ち、そのレジスタを書く命令で消し、既に検査済みなら検査を省く | 平均 約 22.5 + フラグ操作 | 静的に、`f_b34aca0` の 646 箇所のオペランド検査 1,292 件のうち 422 件(32.7%)が同じ未変更レジスタの再検査。ただしフラグの設定・消去の費用で純削減は検査命令の約 13% | 1.0〜1.5% | 設計上、`ldmxcsr`・`stmxcsr`・C 経路の呼び出し・`call` でフラグを全部消す(指示どおり、MXCSR に触れる呼び出しをまたいで結果を再利用しない。述語は MXCSR に依らないので消さなくても正しいが、指示に従う。その分、純削減はさらに小さい)。消去漏れ(別経路で書かれたレジスタ、`jmp` の合流)で**偽の「検査済み」**が出ると窓外を素の命令に通す = 非忠実。1,300 個超のローカルを持つ関数にさらにローカルを足す(レジスタ割り当ての悪化)。**採らない** |
| **D3 同じ述語を 1 回で縮約**(下記 §2.1) | 21(`any_true` 形) | 微小ベンチで −32〜−35%(1.10〜1.17 → 0.72〜0.78 ns)。命令数では −19%(26 → 21) | 見積もりは 2.5〜3.8%(= R × 0.33)だったが、**実測では確認できず**(§5) | 述語が**厳密に同じ**(真偽が全入力で現行と一致)。リスクは実装の誤りだけ(= 差分テストと変異テストで確認) |

### 2.1 D3 の式(f32)

A(x) = `f32x4.abs(x)` = 符号を除いたビット列(0 以上の符号つき整数としても同じ順序)。

- 上限違反(悪): `max_s(A(a), A(b)) >s ((hi+1)<<23) − 1`(全レーンの A(a), A(b) の大きい方が U 以上)。
- 下限違反(悪、0 < A < L = lo<<23): f(A) = A + 0x7fffffff(桁あふれあり)とすると、f は A=0 を符号つきで最大に、A=1.. を最小側に、順序を保って写す。よって `min_s(f(A(a)), f(A(b))) <s f(L)`(ゼロのレーンは最大値になり最小値を決めない)。
- 条件 = `not any_true(上限違反 | 下限違反)`。

命令列(21 命令):
```
local.get a; f32x4.abs; v128.const 0x7fffffff; i32x4.add
local.get b; f32x4.abs; v128.const 0x7fffffff; i32x4.add
i32x4.min_s; v128.const f(L); i32x4.lt_s
local.get a; f32x4.abs; local.get b; f32x4.abs
i32x4.max_s; v128.const U-1; i32x4.gt_s
v128.or; v128.any_true; i32.eqz
```
現行は 1 オペランドごとに窓の幅の比較と `==0` の比較をして AND を取り `all_true` していた。D3 は 2 つのオペランドを `min`/`max` で先に 1 本にし、比較を 2 回(符号つき 1 命令ずつ)にし、最後を `any_true`(`all_true` より安い)にした。述語は変えていない。

案 D と D2 は D3 の途中の形(下限を `le_u`、`all_true`)で、微小ベンチだけ(§3.2)。

## 4. 案 A が逆効果になった理由(推定)と、そこから得た条件

## 6c. E9 の『仮想 s/実 s 0.55』をどこまで戻すか(PM の追加依頼、12:50)

仮定と式(**推定**。E9 の bundle での CPU の内訳は測っていない):

- 仮想時計が Worker の CPU に縛られている(E9 の純再生で実時間あたり 0.49〜0.76、窓平均 0.54〜0.56 = r)とき、仮想 1 秒あたりに要る CPU を D(コア秒)とすると r ≈ C / D(C = 使えるコア数)。D3 が D を g_w 割減らすと **r' = r / (1 − g_w)**、戻る量 Δr = r' − r、戻る割合(ギャップ 1 − r のうち)= Δr / (1 − r)。
- g_w = (D3 がミキサースレッドで減らす CPU)/(Worker 全体の CPU)= f_m × g。ここで g = D3 のミキサースレッド全体に対する削減(§2: 2.5〜3.8%、保守側。広い側は 5.2%)、f_m = ミキサースレッドが Worker の CPU に占める割合。E7b の 0282 の値(ミキサー 0.909 コア、UI+ループ 0.398 コア)から f_m ≈ 0.909 / (0.909 + 0.398) = **0.70**(E9 では書き込み率が上がり Worker の CPU/音声秒は −35% なので f_m は変わる可能性がある。未測定)。

| 場合 | g_w | r = 0.55 から r' | Δr | ギャップ 0.45 のうち戻る割合 |
|---|---|---|---|---|
| 保守側 g = 2.5% | 0.70 × 0.025 = 1.75% | 0.5598 | +0.0098 | 2.2% |
| 中央 g = 3.8% | 0.70 × 0.038 = 2.7% | 0.5652 | +0.0152 | 3.4% |
| 広い側 g = 5.2% | 0.70 × 0.052 = 3.6% | 0.5706 | +0.0206 | 4.6% |
| 仮想時計がミキサーの CPU に縛られていて、Worker 全体で割らない(g_w = g) | 2.5〜5.2% | 0.564〜0.580 | +0.014〜+0.030 | 3〜7% |
| 縛っているのが UI スレッドだけ | 0 | 0.55 | 0 | 0% |

**結論(式でよいとの指示): D3 だけでは 0.55 は 0.56〜0.58 までしか戻らない(ギャップの 2〜7%)。** ミキサーの窓検査の除去の上限(保守側 R = 7.6〜11.5%)をそのまま取れたとしても、g_w は 5〜8% で r' は 0.58〜0.60 程度。0.55 を 1 に近づけるには、UI スレッドの削減(0282: UI+ループ 0.398 コアのうち FL の guest が 80%)とミキサーの実スレッド化のほうが桁が違う。**Chrome の D3 の A/B の実測(§5)では g が確認できなかった(A/other が下がっていない)ので、実測に基づく D3 の寄与は 0〜誤差の範囲**。上の表は『微小ベンチどおりに効いたとしたら』の上限の見積もり。
