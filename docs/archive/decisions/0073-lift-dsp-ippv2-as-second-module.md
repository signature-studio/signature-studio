# 0073: dsp_ippv2_x64.dll は「無い」と定義せず、2 つ目のモジュールとして同じ Rust ツールチェーンで lift する（方向の決定）

状態: PM の方針決定（2026-10-23）を、作業者（サブエージェント）が記録した。**方向の決定**であり、「仮の決定」ではない。この決定は値（リベース先のアドレス、CPUID の応答、スレッドの扱い、メモリの上限など）を一つも決めない。それらは未決事項（下）で、この決定の後続作業で決める。実装もこの決定の後続作業で、この決定では何も変更していない。実現性は `docs/investigations/dsp-ippv2-lift-feasibility.md` が調べた（同日。判定はそちらを参照）。

## 状況

`docs/investigations/after-comparestringw.md` の停止点は、ゲスト（`FLEngine_x64.dll`）の `LoadLibraryW("dsp_ippv2_x64.dll")`（呼び出し元 `f_6539e0` ← `f_653f40`）である。この名前は `fle_modules[]`（仮想モジュール 26 名）にも `fle_load_absent[]`（欠けている 9 名、決定 0029）にも無く、`fle_load.c` が名前付きで止めている。A4（DllMain → InitUnits の完走、決定 0046 と 0060）はこの先に進めない。

## 事実（出典は `docs/investigations/external-modules-usage.md`。節番号はその文書のもの）

- `dsp_ippv2_x64.dll` は FL Studio のインストーラ内に実在する（§1.1。EXTRACTFILE のエントリ 56484、`Shared` 配下。実測）。32 ビット版 `dsp_ippv2.dll`（エントリ 56482）も同じ場所にある。
- 39,942,656 B、SHA-256 `497dd4f7…c352`、PE32+ x64、ImageBase 0x180000000、SizeOfImage 0x261f000、446 エクスポート、インポートは KERNEL32.dll の 72 名のみ、`.pdata` 50,529 エントリ（関数開始 30,816）、DYNAMIC_BASE と `.reloc` あり。抽出済みのコピーは `lift/out-ext/dsp_ippv2_x64.dll`（§1.1。実測）。
- ゲストは `LoadLibraryW` が成功すると 423 回（distinct 420 名）`GetProcAddress` を呼び、保存先（`.bss` の 420 個のスロット）に関数ポインタを置く。保存先を読む 424 関数の 977 アクセスは、読み込みの直後に NULL 検査をしない（§1.2。読み）。上位の呼び出し元が別のフラグで守っているかは未確認（§1.2、§7）。
- そのため「この DLL は無い」と答える仮想環境は、実機（実 Windows の FL Studio）で DLL が存在することと異なる主張になる（§1.1 の実測と、ゲストが `SetDllDirectoryW("Shared\\")` を呼ぶ実測の整合）。

## 決定

1. **`dsp_ippv2_x64.dll` を「無い」と定義しない。** `fle_load_absent[]` に加えない。
2. **仮想モジュールの偽の表（ゲストが引く 420 名にだけ偽の関数を答える表）も作らない。** 決定 0055 の msctf.dll のように「ゲストが引く名前だけを応答表に載せる」形は、この DLL には採らない（420 関数の意味を runtime が創作することになるため）。
3. **実在のコードで答える。** `dsp_ippv2_x64.dll` を、`FLEngine_x64.dll` と同じ Rust ツールチェーン（`fe-pe` → `fe-decode` → `fe-lift`）で C に lift し、wasm にして、`LoadLibraryW` / `GetProcAddress` / `FreeLibrary` がそのモジュールの実在する export を返す形にする方向で進める。
4. **実装はこの決定の後続作業**とする。作業の分割案は調査文書 §9 にある（案であって、決定ではない）。
5. この決定は M2 の一部だが、A4 の完走に必要なものとして扱う（PM の方針）。

## 却下した案

- **(a) 停止のままにする。** A4 が進まない。停止は測定結果としては正しいが、DLL が実在する以上、次の停止点（`RegCreateKeyExW`。external-modules-usage.md §5 の仮の NULL の連鎖で実測）以降の測定ができない。
- **(b) `fle_load_absent[]` に加える（NULL と 126 を返す）。** 実機の DLL の有無について偽の主張になる。決定 0055 が msctf.dll について採った基準（「環境の定義と矛盾する場合は、欠いているとは定義しない」）と同じ理由で採らない。ゲストが NULL を許容する読み（§1.2）は、「無い」と答えてよい根拠にならない（許容は、ゲストの設計であって、実機の事実ではない）。
- **(c) 自前の IPP 実装に置換する。** 次の 3 点で採らない。
  1. bit 一致の根拠が無い。IPP の浮動小数点関数（FFT、FIR、リサイズなど 420 名）の丸め、演算順序、CPU ごとに選ばれる実装の違いを、実物のバイト列なしに再現できる根拠がない。決定 0046 の A5（オラクルとの bit 一致）の趣旨に反する。
  2. 規模が大きい。ゲストが引く名前だけで 420 個あり、種別は信号処理（ipps 345）と画像（ippi 71）に及ぶ（§1.2）。
  3. 実機にある実在のコードを、創作で置き換えることになる。本リポジトリの方針（創作しない。仕様から言えないことを事実として書かない）に反する。
  - 旧リポジトリには D20 という決定があり、この案（自前の IPP 実装への置換）だったと PM から伝えられている。**旧リポジトリの D20 の本文は本リポジトリに無く、読めていない**（決定 0035 と 0046 が同じ事情を書いている）。したがって D20 の内容や、そのときの根拠を本書は評価しない。本リポジトリでこの案を採らない理由は上の 3 点で、本リポジトリで確認できる事実（`ipp_names.txt` の名前、PM の方針）だけに基づく。旧リポジトリで置換が成立していた条件（例えば、使う IPP 関数の範囲が絞れていたか）は未確認。

## 未決事項（この決定では決めない。値も決めない）

- **リベース方式**: wasm32 のリニアアドレスは 4 GiB 未満で、ImageBase 0x180000000 に置けない。`.reloc` を適用して低い基底に置く方式を含め、どの方式にするか、基底の値、既存領域（アリーナ、ハンドル領域、`GLOBAL_BASE`）との配置。調査文書 §2 に候補と条件がある（案）。
- **実行時の CPU 振り分け**: DLL は CPUID で実行時に実装系統を選ぶ構造に読める（調査文書 §5。読みと仮説）。現行の CPUID 応答（最大葉 1、葉 1 の ECX = 0。決定 0009、0047）のままにするか、変えるか。変える場合は XGETBV の値（XCR0）の決定が先に要る（決定 0047）。AVX/AVX-512 系の命令を lift の対象にするか、到達しない設計にするか。
- **スレッド**: wasm は単一スレッド前提（決定 0017、0045）。DLL の `ippSetNumThreads` / `ippGetNumThreads`、DllMain の `DLL_THREAD_ATTACH` / `DLL_THREAD_DETACH`、TLS/FLS の扱い。
- **メモリ**: 現行 `flengine.wasm` の最大メモリ（2 GiB）、アリーナ 512 MiB、生成 C の大きさと wasm のサイズ、リンクと実行のメモリ。2 つ目のモジュールを足したときに収まるか。
- **モジュールの境界**: 2 つのモジュールの生成 C の分け方（レジスタ配列 `R[16]`、`FL`、`X[16]`、dispatch 表をモジュール間で共有するか分けるか）。

## 撤回条件

次のどれかが分かったら、この決定を見直す（その場合は PM に報告し、(a) または (c) を改めて比べる）。

- 実現性調査（または後続作業）で、`dsp_ippv2_x64.dll` を同じツールチェーンで lift して wasm で動かすことが**不可能**と分かったとき（例: wasm のメモリ上限、リンクの限界、未対応命令の規模が現実的でない、など。調査文書の判定は「条件付き可能」で、不可能とは判定していない）。
- DLL が実機で使われない（例えば、実機で `LoadLibraryW` がこの DLL に対して失敗する）ことが、一次の根拠で確認されたとき。本書の事実は「インストーラに実在する」までで、実機の実行時の読み込みの成否は未確認（external-modules-usage.md §7 の未確認）。
- PM が方針を変えたとき。

## 確認できていないこと

- 実機で `f_653f40` が何度呼ばれるか、実機で DLL が読み込まれる経路（external-modules-usage.md §7）。
- 旧リポジトリの D20 の本文（上記）。
- この決定の実装後の A4 の到達点。lift が成功しても、DLL の関数がゲストの要求どおりに動くかは、後続作業のテストで確認する。
