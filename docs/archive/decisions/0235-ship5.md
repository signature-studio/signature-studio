## 7. first idle の悪化の原因(PM の依頼 (b))と L5s

**(i) V8 の遅延コンパイル(node の `--trace-wasm-compilation-times`、`tables/v8-liftoff-trace-A-vs-B.txt`、`tools/s5-v8trace.py`)**: 起動 16 スナップで V8 が初回呼び出しで Liftoff コンパイルする関数(wasm の遅延コンパイルは既定)は A 13,791 個・合計 103 ms・本体 22.9 MB・コード 48.5 MB → B 14,482 個・**合計 702 ms**・本体 25.6 MB・コード 67.8 MB。parity boot では A 14,483 個・131 ms → B 15,188 個・817 ms。本体の大きさ別: 10〜50 KB は A 244 個・14 ms → B 312 個・136 ms、**50〜200 KB は A 25 個・38 ms → B 48 個・533 ms**(boot では 62 → 599 ms)。B の最遅は 90〜156 KB の関数で 1 個 90〜113 ms、A の最遅は 649 KB の関数が 16〜19 ms(同じ大きさの C 由来の関数に比べ約 40 倍/バイト)。**node の短い run では TurboFan の tier-up はトレースに出なかった**(`--trace-wasm-compilation-times` に Liftoff の行だけ)。V8 の flag `--wasm-dynamic-tiering` は既定で有効。直接 wasm の関数は局所変数が非常に多い(hyb6 §8 の『上限なしだと本体 1.1 MB・ローカル 14,644 個』)ので、Liftoff のレジスタ割り当て・スタック管理の費用が大きいのだと**読む**(測っていない)。

**(ii) 起動で実行される関数(hyb6 の census `E-all.tsv.gz`、`E-class.tsv.gz` と、今回の hybrid report の `wasm_code_bytes`。`tables/l5-new-big-functions.txt`)**: L5 で新しく入った 12,124 関数(wasm 16.9 MB、wasm-opt 前)のうち、起動(`start`)で実行されるのは **10,139 関数・13.1 MB**(A のリストの起動で実行される 1,007 関数・2.4 MB の 5.5 倍)。起動で実行される x86 命令のうち、A のリストの関数は 6.65 G、L5 の新規関数は 0.77 G(9%)。**起動で実行される関数の集合が A と大差ない、という前提は成り立たない**(L5 は census の和集合を入れているので、起動で一度だけ実行される 1 万関数が直接 wasm になる)。

**(iii) 『起動で実行される関数だけを L5 から除く』案の試算(census)**: L5 の新規関数のうち起動(`start`)でも実行される物が、参照プロジェクトの scene(開く+アイドル+再生)の x86 命令に占める割合は **13.0%**、起動で実行されない新規関数は 1.6%(parity boot では 1.84% と 0.24%)。つまり**再生の利得の大半(新規関数が担う 14.6% のうち 13.0%)は起動でも一度は実行される関数**にあり、『起動で実行される関数を除く』と L5 の利得もほぼ消える。そのため採らず、**大きさだけで除く案**を試算した(census の x86 命令の割合と本体の大きさ):

## 8. PM への判断材料(まとめ)
- **F2xH7 = L5s は既定にする条件のうち (1) first idle の C−A の中央値 ≤ +1.0 s〔Chrome +0.71 s、load ≤9 で +0.50 s〕、(3) 11 場面・ドラッグ・サイズ〔C: Firefox 10/11、Chrome 9/11 + d8 の再実行 2 回 100/100、ドラッグは A・B と同程度、wasm 133,886,854 B〕を満たす**。(2) 同一性は 通った(C も起動 16 スナップ 84 行が A と全行一致、parity 532/532 行一致)。(4) のテンポは ref3 が測る(C の bundle のパスと assets を渡した)。
- **L5 全部(F2xH8)を既定にしない理由**: Chrome の first idle が +2.79 s(24/24 組で遅い)。P1(10 s 以内)の線に近づく(Chrome の B の中央値 9.52 s)。
- **効果の大きさ**: 出荷構成の参照プロジェクトの再生は B が A の 0.70〜0.76 倍(C は未測定。除いた関数の再生の x86 命令は 2.3% なので近い値と**推測**)、UI 操作の parity は 0.89 倍。runner の増分は約 0(同じ構成)、wasm +4.5〜6.3%、タブのメモリ +30 MB 台、node の RSS +14〜20%。
- **残った懸念**: Chrome の C の裾(高 load のときに +3.5〜+6.6 s)、Firefox の C の裾(+3.3〜+6.0 s 3 組、原因未解明)、C の NO_FS=1 の出荷形そのものでの同一性(NO_FS=0 の変種で確認)、C が F2xH7 の最終プリセットからの冷間ビルドではない点。

## 9. 出典のない選択(S-ship5-n)
- **S-ship5-1**: `WASMGEN_MAX_FN_COST` の既定を『混成の段』でなく F2xH7・F2xH8 の preset block に置いた(§1)。代替: 段の中(F2xH5 の意味が変わる)、`CONFIG_VARS` に別の導出を足す。
- **S-ship5-2**: 冷間ビルドを `CI_JOBS=2`(runner 相当)・A と B を同時(負荷の共有を同じにするため)で作った。代替: JOBS=4 の単独実行(時間は短いが runner と違う)。

上の判断 1 に書いた『F2xH5 平均 0.811 / L5s 平均 0.949』は **load が 6〜18 で混在した run の値**で、F2xH5 と L5s の差を示す根拠としては弱かった。ref3 が静かな時間帯(load 3 前後、Chrome、交互、03:00〜03:05)に追加で測った値: load 2.7〜3.0 で L5s X=1.021(ゲストの仮想時計/壁時計 0.47)、F2xH5 X=1.016(同 0.279)、load 3.3 で F2xH5 X=0.980。全 25 run を load 順に見ると、load < 4 は 1.02/1.02/0.98(n=3)、load 5〜8 は F2xH5 0.84〜0.91・L5s 0.99〜1.03、load 9〜15 は F2xH5 0.67〜0.90・L5s 0.71〜1.04、load > 17 は両方 0.60〜0.76。**読み:** 音楽の速さ(P3 の『内容』)は **CPU が空いていれば F2xH5 でも実時間になり、競合があると崩れる**。Worker は 1 スレッドが CPU を約 0.95〜1.0 使い切るので、SMT の相手スレッドが忙しいだけで遅れる。L5s は崩れにくく(load 5〜15 で F2xH5 より高い)、静かな時の差は仮想時計(UI/タイマー側)の速さに出る(0.47 対 0.28、各 n=1〜2)。
