## 2. 背景

- 目的: 『ブラウザ上で FL Studio を動作させる』。G7(音声)・G6(操作感)の律速は速度。決定 0146(perf3)の gdb 実測: 最終構成(FRUITY 有効、SEH 入り)でスレッド 2(lid 18 `TLightweightLayeredControl` のロゴの描画)が CPU の 97〜99%、仮想秒/実秒 0.11〜0.17(native -O2)。ロゴは初期化の最中に作られ、仮想 +7 ms に `HideLogo` され、スレッド 2 の最初のティック(+24 ms)より前なので、フェードの遷移が始まらず t = 1.0・α = 0.00198813 のまま永遠に(無改造では仮想 +148 s まで)描かれる。
- PM の読み: 協調スレッド(決定 0122)は待ち・譲りの API でしか切り替えないため、主スレッドが 1 千万回以上の間接呼び出しの初期化を続ける間に他のスレッドへ順番が回らず、初期化全体が仮想 +7 ms で終わる。実機ではスレッド 2 が並行して走る。= 『見えないロゴを永遠に描く』は実機に無い人工状態の疑いが強い。この疑いを実測で確かめ、是正する。
- PM の方針 A: 主スレッドが走っている間にも決定的な擬似プリエンプション(タイムスライス)を入れる。切り替えの条件の追加は『決定 0122 の例外』として書く。`Sleep(0)`・`SwitchToThread`・WM_TIMER の期限・`DwmFlush`・idle 検出・WM_PAINT の規則を壊さない。
- 『WM_QUIT を渡す改造をしてもスレッド 2 は終わらなかった(未解決)』(perf3 の what-if)の原因も調べる(§8)。

## 4. 設計

### 4.1 候補(評価して選んだ)

| 案 | 内容 | 評価 |
|---|---|---|
| **A(採用)** | 進捗カウンタが閾値を超えるたびにスライスが終わる。仮想時計を一定量進め、期限の来た別スレッドへ切り替える | 決定的(native・wasm・最適化の有無で同じ)。テスト・SHA の再現性を保つ |

### 4.2 進捗カウンタの選択

| 候補 | 判定 |
|---|---|
| 関数入口数 | 計装つきビルドにしか無い。wasm では native より 2 少ない癖。**不可**(依頼文) |
| `fle_ld`/`fle_st` | 依頼文が不可とした(読み: 最適化で数が変わりうる、重い)。**不可** |
| API 呼び出し数(import thunk 経由) | 数え口が中央に無い(`fle_imp_*` の定義が 535 関数、`call [IAT]` と `jmp [IAT]` の 2 形)。全関数に挿入すると差分が巨大。リンク時の `--wrap` は生産のビルドに入れたくない。**不採用**(初期化中の量は上の 160 万で、間隔は十分細かいので、数えられれば足りた) |
| クロックの読み(`GetTickCount` など) | 初期化中 1.6 万回ほど。粗すぎる。**不可** |
| **間接呼び出し(`fle_dispatch` が関数を見つけた回数)** | ゲストの命令の回数であり、native・wasm・-O0・-O2 で同じ。`fle_dispatch`(`fle_dispatch.h` のインライン関数)は未解決の間接呼び出しが必ず通る**1 か所**で、生成 C は 1 行も変わらない。初期化中 1,049 万回(API 呼び出しの約 6.5 倍)。**採用** |

間接呼び出しの数え方の限界: 直接呼び出し(`call f_XXXX`)は数えない。計算だけのループ(`f_6a73a0` の画素ブレンドなど)は進捗 0 とみなされ、切り替わらない。= 実機では速い計算(SIMD)が、lift では遅いことの裏返しで、仮想時間では 0 とみなすのは実機に近い向き(**読み**)。

### 4.3 S-vclock-slice-time の根拠

1 スライス = 間接呼び出し 4096 回 = 仮想 1 ms(10,000 ticks)。1 回あたり 0.244 µs。**根拠(読み・出典なし)**: (1) 初期化(間接呼び出し約 1,050 万回)が仮想 **1.78 秒**程度になる(スキップされるスライスの分を含む。実測 1776 ms)。FL Studio の起動が『数秒程度』という一般的な認識(**読み**、未確認)の下限に近い。(2) 決定 0139 の S0: ゲストは `timeBeginPeriod` を 2 回呼ぶ。1 ms の分解能で動くと読んだので、待っているスレッドは 1 ms の細かさで目を覚ます。(3) 実機のスケジューラの量子(Windows のクライアントで 15.6 ms の倍数)は採らなかった(待ち解除で優先度が上がり、短い時間で走る読み)。**この値を倍にすれば初期化は 3.5 秒、実時間のロゴのティックも倍(約 +14 CPU 秒)になる**。値を替えるには環境変数 `FLE_PREEMPT_DISPATCHES`・`FLE_PREEMPT_TICKS`。

## 8. `PostThreadMessageW` と『WM_QUIT でも終わらなかった』の原因

- 実装は E3。応答行はテーブル末尾の 1 行。公式文書の規則どおり: キューがあるスレッドの待ち行列に積み、取り出す側の `MSG.hwnd` は NULL、キューが無い(そのスレッドが User/GDI 関数をまだ呼んでいない)・ID が無効なら FALSE と 1444、10,000 件で 1816、`DispatchMessage` は hwnd NULL のメッセージを配送しない(0 を返す。決定 0122 の S11)。
- **perf3 の what-if の 3 つの結果の説明**(決定 0146): (1)『TRUE を返すだけ』では対象スレッドのキューに何も入らないので、スレッド 2 の `GetMessageW` のループは続き(スレッド 2 の `Execute`(`f_71da40`)は `PeekMessageW` でキューを作り、`GetMessageW` が 0 を返すまで回る標準のループと読める)、主スレッドはそのスレッドのハンドルを待ち続ける(perf3 が見た『`MsgWaitForMultipleObjects` で待ち続け、仮想 260 秒でも進まない』)。(2)『WM_QUIT を通常の投函メッセージとして渡す』では、`GetMessageW` が 0x12 を通常のメッセージ(戻り値 1)として返すだけでループは続く。(3) 対象スレッドの `q->quit` に立てる方式だけが `GetMessageW` に 0 を返させる。この決定の実装は (3) と同じ経路。
- **WM_QUIT の扱い(実装で確かめた)**: perf3 の what-if で『対象スレッドの `q->quit` に立てる』方式はスレッド 2 を終わらせ、『通常のメッセージとして FIFO に積む』方式(`fle_thread_post(…, 0x12, …)`)は終わらせなかった。**原因は、FIFO に積まれた 0x12 を `GetMessageW` が通常のメッセージ(戻り値 1)として返し、スレッドのループ(`while GetMessageW(...)`)が続くこと**。`GetMessageW` が 0 を返すのは `q->quit` の経路(他の投稿メッセージが無いとき)だけ。この決定は `PostQuitMessage` と同じ経路にした。変異検査 M10(WM_QUIT を FIFO に積む)で `wall_fr20` の 3 件が落ちる。
- 実エンジンでの確認(**実測**、gdb): 仮想 2181.922 ms に `cur=0`(メインスレッド)が `PostThreadMessageW(idThread=0x1003, Msg=0x12, wParam=0, lParam=0)`。スレッド 2 のスレッド関数が戻り(`FLE_FRUITY_THREAD_TRACE`: `exit 2 0 clock=36021819220` = 仮想 2181.9 ms)、窓表は 116 → 114 行(消えるのは lid 8 の `TLightweightLayeredControl` と lid 7 の `TPUtilWindow` の 2 窓。lid 7 は表の上ではスレッド 0 のもので、ロゴの後始末が壊すと読む = 未確認)。`DLL_THREAD_DETACH` は `thread_finish` が実モジュールへ送る(決定 0122 E6 の既存の道。ここでは通知の中身を観察していない = 未観察)。戻り値 R[0] は gdb の `finish` が切り替えで取れず、直接は見ていない(単体テストは 1)。

## 13. 限界・未決の点・規則違反の自己申告

### 13.1 限界(測れなかったこと)

- 実機 Windows との照合は 0 件。実機のロゴのティック数・起動時間は未確認。
- 速度の旧新・ホットスポット・音声は **7b82424 + 差分**の木(native -O2 計装なし)。進捗の一致・面 SHA・Chrome の速度・窓の作成順は cd8c6d9 + 差分、面 SHA の表と a4 と変更したテストは 2b3a2f2 + 差分(§1・§9.7・§10.2・§11.4)。
- Chrome は 1 回(2 回起動した。最初は dist に種の一覧 `vfs-seed-fonts.tsv` が無く Worker が 404 で落ちた)。headless・GPU なし・1 台・loopback だけ。wasm -O2、Firefox、Safari は未測定。**ブラウザの音声(AudioWorklet が位置の源)でのスライスの効果は測っていない**: native は仮想時計が源なので、ミキサーのブロック間隔は公称に一致するが(§9.4)、ブラウザでは実時間のペースと重なる。Chrome の速度(仮想秒/実秒)は、`wall` モードで測っていない(`fixed` モードの 1 回だけ)。
- 『Enter 後 約 7 倍』は native -O2 の値で、同じ機械の他の走行(vis1・g8a1)の負荷が重なる(測定中のロードアベレージ 1〜2、全体テスト中は 10)。wasm の値は計算(未測定)。
- 進捗は間接呼び出しだけ(§4.2)。コールバックの中ではスライスを切らない(S-vclock-depth)ので、UI の長い計算(窓プロシージャの中)の間はミキサーが走らない。= 決定 0139 の『ミキサーが他スレッドのスライスに追いつけない』は定常ではまだ残る。

- 面の SHA の『収束』は定常ではなくなった(キャレットの点滅)。基準として使うときは時刻を固定すること。

### 13.2 未決の点

1. 1 ms / 4096 回(S-vclock-slice-time)でよいか。初期化が仮想 1.78 秒、ロゴのティックが 94 回。実機の起動が数秒(読み)なら、倍の 3.5 秒でも妥当。倍にするとロゴの描画で実時間が約 +14 CPU 秒増える。
2. S-vclock-depth(コールバックの中は切らない)を緩めるか。G7 の本題(ミキサーが UI の計算に追いつく)はここにある。窓の表・DC の表など、コールバックの下で走査中のランタイムの状態の再入安全性を調べる必要がある。
3. 次の HLE は `f_6a73a0`(整数 SSE2 の補間ブレンド): 起動の主スレッド、ロゴ消滅後の再描画、Enter の停止のそれぞれで 65〜79%(§12)。Warp 系の優先度は下がった。
4. 面 SHA の基準の更新(§10)を採るか。`a4-fruity.sh` の注釈の古い SHA の扱い。
5. `FLE_PREEMPT=0` の保険を残すか(Windows の挙動ではない)。
