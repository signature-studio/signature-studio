## 結論

1. **UI スレッドの CPU はほぼ FL 自身のコード**: 根 `f_1375990`(UI)の busy は 17.1 s(実 45.2 s の 38%)で、**(a) FL コード 91.5%**(直 wasm 69.1% + Blend2D/モジュール 0.8%、C 経路 10.4% と、その C 経路が呼ぶ SSE/x87 エミュレーション 6.5%・生成 C のヘルパー 4.9%)、**(b) ランタイム C 6.3%**(1.09 s。`fle_r_blit` 365 ms だけが 1% を超える)、**(c) JS import 0.1%**(提示は別の根で Worker busy の 2.2%)、**(d) libc 2.1%**(0.35 s)。上位 40 の自己時間は UI busy の 72.7%、そのうちランタイムは 3 本(`fle_r_blit` 365、`IntersectRect` 94、`rgn_combine` 77)だけ(§2)。
2. **FL の呼び出し 1 回あたりのランタイムの作業は一定**(増幅なし): `fle_imp_*` の入口の合計は 0.4 s、1 回 5 ns〜13 µs(§3)。UI の仕事量を決めているのは FL 自身の tick(QFC の `Sleep(16)` → `PostMessage 0x8ffc` 62.5 回/仮想秒、決定 0250)で、**1 tick あたり UI は約 16.7 ms の CPU**(FL 15.3、ランタイム 1.06、libc 0.35)。ミキサーは 1 仮想秒あたり 1.17 CPU 秒、UI は 1.04 CPU 秒(書き込み率 0.363 のとき)。
3. **『ランタイムの上乗せ』を全部ゼロにしても高々 Worker CPU の約 3%**(影比較 + 提示 約 0.9 s、libc の qsort/malloc 0.28 s、blit の比較 ≤ 0.04 s): 書き込み率にして高々 +3%。**ランタイムの余計を削って P2/P3 を稼ぐ道は、この測定では閉じている**(§4、§5)。次の梃子は FL 側(C 経路の関数を直 wasm にする。UI の C 経路 + その結果 = 21.7%、ミキサーでは 66%)。
4. **ホットな関数が Liftoff に取り残されている仮説は不成立**: `--wasm-tiering-budget=1`(全関数を直ちに TurboFan)で `fle_r_blit` 365→347 ms、`f_863f60` 4,363→4,277 ms、書き込み率 0.363→0.355、Worker CPU 37.8→37.7 s(1 回ずつ、差なし。§6)。
5. **提示**(§7〜§9): 提示は 4.8 回/秒しかなく、1 回 0.95 Mpx(= playlist の窓ほぼ全面、3.8 MB)をアップロードし、費用は compose 2.3 ms + put 1.0 ms + draw 0.14 ms = **3.4 ms/提示**(16.6 ms/s)。提示が 4.8 回/秒なのは `DESK_FALLBACK_MS`(20 ms = 上限 50 回/秒)のためではなく、**エンジンが Worker のイベントループへ戻る回数が約 10 回/秒**(V8 の `(idle)` 9.6 回/s)だからと読める。ピクセルは wasm の heap から WebGL の `texSubImage2D` へ直接渡っていて(Worker の OffscreenCanvas)、`postMessage` を通る画素は 0。60 回/秒で提示するとこの Worker で約 200 ms/s(コアの 20%)。
6. **影比較**: 外す案は PM の判断で採用の試作にしない(desk_scene.rs の 2 検査に反する)。測定専用に外したビルドで測ると、影比較が省くのは 1 提示あたり 0.33〜0.43 Mpx(26〜34%)で、その代わりに 1 提示 2.2 ms 払っている。書き込み率・Worker CPU の差は雑音の内(§8)。

7. **表示 Hz(§10、PM の追加依頼)**: エンジンに渡す Hz を 60/120/144/240 にすると、idle の UI は 297 → 503 → 642 → 856 ms/s(1 tick ≒ 3 ms)、再生ではミキサーの書き込み率が 0.363 → 0.326 → 0.310 → 0.291(10–45 s は 0.287 → 0.247 → 0.228 → 0.210)。**120 を超える Hz は絵を増やさずミキサーの予算だけを食う**(120 → 240 で −0.035)。= `hz.ts` の上端を 120 にする案は妥当。60 → 120 の −0.037 も P2(120 fps)の代価として同じ向きに出る(n=1、ノイズ ±0.013)。144/165 Hz のディスプレイでは上端 120 だと 1 tick 1.2〜1.4 フレームの不均一(24〜45 回/s の繰り返し)が見える。240 Hz は均一。

## 7. 提示の経路と、再生中に実際に変わる画素

## 9. 提示の設計(通信・変換の削減)と、60 回/秒で提示したときの費用

**(a) rAF が来ない場合の fallback の根拠**(コード `worker.ts:38,139–149,254–290` の読みと、HEAD の実測): 通常は Worker の `requestAnimationFrame` で `deskTick()`(提示)を呼ぶ。コメント(`worker.ts:147`)は『エンジンが Worker を占有している間(= 実時間より遅れているとき)は rAF が届かない(実測)ので、エンジンの idle から最短 `DESK_FALLBACK_MS`(20 ms)おきに提示する』。rAF だけでは画面が止まる、というのが根拠で、この run でも rAF の `ticks` は 4.48/s、idle 経由の試み `idleTicks` が 7.02/s、提示された(画素が変わった)のが 4.83/s。**提示の回数を決めているのは 20 ms の定数(上限 50 回/s)でなく、エンジンが Worker のイベントループへ戻る回数**(V8 の `(idle)` 9.6 回/s、ticks + idleTicks = 11.5 回/s)と読める。rAF を無制限にする旗を付けた run(§10 の `240-raf`)でも提示は 3.94 回/s で増えず(rAF の ticks は 11.9 回/s に増えた)、この読みを支持する。60 回/秒にするには、エンジンが 16 ms ごとにイベントループへ戻る(JSPI の suspend/resume)か、提示を別の Worker に移す必要がある。『エンジンが実時間に追いつくと idle が増え提示が増える』は読み。

1. **idle(プロジェクトを開いて止めたまま)**: UI の根の CPU は 297 → 503 → 642 → 856 ms/s(60 → 120 → 144 → 240 Hz)。Worker 全体の busy は 418 → 607 → 745 → 953 ms/s で、**Hz が 1 上がるごとに約 3.0 ms/s**(= FL の 1 tick が idle で約 3 ms の CPU)。240 Hz では idle だけで Worker の 95% が埋まる。native の alpha1 の値(60→120 Hz で idle CPU +83%)に対し、wasm では UI が +69%、Worker 全体 +45%。
2. **Song Mode 再生**: Worker の busy は 905〜952 ms/s で**飽和したまま**(Hz に依らず)。Hz を上げると UI が増えた分だけミキサーが減る: UI 380 → 505 → 536 → 601 ms/s、ミキサー 416 → 336 → 304 → 267 ms/s。**書き込み率(0–45 s / 10–45 s)は 0.363 / 0.287 → 0.326 / 0.247 → 0.310 / 0.228 → 0.291 / 0.210**。60 → 120 で −10% / −14%、120 → 144 で更に −5% / −8%、120 → 240 で更に −11% / −15%(60 → 240 では −20% / −27%)。ノイズ(±0.013)より大きく、4 点で単調。
3. **答え: 120 を超える Hz を渡すと、画面に出る絵は増えない(FL の tick が増えるだけ)のに、ミキサーの予算を食う**。120 → 240 の差だけで書き込み率 −0.035(0–45 s)/ −0.037(10–45 s)。P3 を満たしていない間は、**60 → 120 の −0.037 も同じ向きの費用**(P2 の 120 fps の代価)。= **`hz.ts` の上端を 120 にする案は妥当**(PM の案)。
4. 提示回数/s は Hz でほぼ変わらない(再生 4.99 → 4.29。提示は rAF(ヘッドレスでは 60 Hz)とエンジンの idle で決まり、Hz は効かない。Hz が上がるほど Worker に idle の隙が減り、わずかに減る)。提示経路の ms/s は 17.6 → 11.3 に減る(提示が減る分)。提示 1 回の費用は Hz に依らない。
5. 再生中の UI は 1 tick あたり 17.4 → 12.9 → 12.0 → 8.6 ms(UI の ms/s ÷ (Hz × 書き込み率))と下がる = tick 数に比例しては増えない(読み: 仕事の一部が tick に依らない、または遅れている間に FL のメッセージが合流する)。idle は比例に近い(3.0 ms/tick)。
6. **限界**: (i) 提示の rAF は 60 Hz のまま(実ディスプレイの高い rAF は未測定)。(ii) n=1。(iii) この機械は load 12〜29 の共有 VM。(iv) Hz はページが渡した値を `FLE_DWM_HZ`/`FLE_DISPLAYSETTINGS_FREQUENCY` に入れただけで、実ディスプレイでの測定ではない。

**上限を 120 にしたときの 144/165/240 Hz の実ディスプレイでの見え方**(コードと算術からの読み。実ディスプレイは未確認):
1. FL の描画の輪は 120 tick/s で止まる = FL のアニメ(再生位置の線、メーター、チャンネルラックのカーソル、時計)は最大 120 回/秒しか更新されない。
2. 提示は『画素が変わった rAF だけ』(`deskTick` が `shown > 0` のとき。変わらなければ canvas は前のフレームを保つ)。ディスプレイが 144 Hz なら rAF は 144 回/s 来るが新しい絵は 120 回/s しか出ないので、**144 Hz では 6 フレームに 1 回、同じ絵が 2 フレーム続く**(周期 1,1,1,1,1,2 = 24 Hz の拍)。一定速度で動く物(再生位置の線)に、24 Hz のうなり(ジャダー)が見える。**165 Hz** は 165/120 = 1.375 で、2 フレーム続く回数が 45 回/s の不規則な並び(1,1,2,1,2,1,1,2…)。**240 Hz** は 1 tick がちょうど 2 フレームで均一(ジャダーなし)。120 Hz 以下のディスプレイは今と同じ。
3. tick は仮想時計(エンジンが遅れている間は実時間より伸びる)で、実の vsync と位相が固定されない。エンジンが実時間に追いつけていない間(書き込み率 < 1)は、渡した Hz の何分の 1 しか実際には回らない(いまの書き込み率 0.36 では、120 を渡しても 120 × 0.36 ≒ 43 tick/実秒)ので、**P3 を満たすまでは 120 でも 144 でも見え方は同じ**。ジャダーは P3 を満たしたあとの話。
4. 代案(`hz.ts` の丸めの規則の小変更。どれも旗なし): (A) 上端 120(PM の案): 144/165 でジャダーを受け入れる、240 は均一。(B) 120 を超える表示には『表示 Hz ÷ 整数』のうち 120 以下で最大の値(144 → 72、165 → 82.5〔整数でない〕、240 → 120): 均一だが FL は 72 fps(144 Hz) — P2 の『120 fps』を満たさない。(C) A に加え、144/165 Hz のときだけ 120 tick を 144/165 の rAF に割り当て直す(提示側で補間)は、FL の挙動を変えない範囲では不可能(絵は 120 種類/s しか無い)。= **(A) が妥当**で、ジャダーは表示側の既知の限界として文書に書く。
