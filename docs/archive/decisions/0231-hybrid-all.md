## 5. 速さ(実測: node の主スレッド CPU 秒/仮想秒、参照プロジェクト、この機械)

**ばらつきについて(重要)**: 他の担当のビルド・測定と共有の機械で、同じ版の同じ操作列の CPU 秒が load で 10〜25% 動く(w2 の再生は 3.79〜4.89)。load が 4 以下の回だけが静かな値で、load 10 を超える回は競合で CPU 秒が増える向きにしか動かない。このため (1) 各行に開始時の load を併記し、(2) 版を交互に繰り返して w2 を毎周回に入れ、(3) 平均・最小・最大と、**同じ周回の w2 に対する比**(競合がほぼ同じ状態で比べる)を書く。壁時計の主張はしない。絶対値は『この機械の値』で、依頼者の機械の値ではない。

## 8. 見つけたこと: 『全部 lower』は V8 のコンパイルメモリを桁違いにする(決定 0185 の規則を掛けないと使えない)

最初に作った hybrid-E の全部入り(`hE5` = 現行 1,009 + b 12,097 + c 37 = 13,143 関数、**サイズの上限なし**)は、出力が完全に一致し(起動 16 スナップ 84 行・参照プロジェクト 55 行・UI 49 行・parity の 10 セッション 552 行のすべて w2 と一致)、再生が 2.14 CPU 秒/仮想秒まで下がったが、**node の最大 RSS が 13.3 GB**(w2 は 1.4 GB、h1009 は 1.4 GB)だった。同じ wasm を V8 の Liftoff だけ(`--liftoff-only`)で走らせても 6.1 GB。起動 16 スナップの user CPU も 16.4 s(w2)→ 22.0 s(hE5)に増えた。E1+E2 だけの `hE2`(3,009 関数、上限なし)でも RSS 4.2 GB。

原因(読み): 最終 wasm に本体 1.10 MB・ローカル 14,644 個の関数と 725 KB・6,088 個の関数(`tools/wasm-funcs.py`)ができていた(w2 の最大は 615 KB・13 個、h1009 は 649 KB・369 個)。V8 のコンパイル Zone は本体バイト数 × ローカル数にほぼ比例する(決定 0185: Liftoff 0.8 B/単位の中央値)。dry-run の見積もり(本体バイト × ローカル数)が 30,000,000 を超える関数は、上限なしで ok だった物のうち 12 個あり(分類の最終版では 10 個が d 類の『over the size limit』、残りは b を『両方の旗で ok』に直したときの 2 個)(`f_7cf9b0` 828 KB・`f_7e5290`・`f_1046a30`・`f_1280530`・`f_7f6f20`・dsp `f_2120cb0` ほか)、決定 0185 が除いた 6 個と同じ顔ぶれ + 6 個。これらは E の命令の 0.4% しか担わない。

**対処は既存の規則**: fe-wasmgen の `WASMGEN_MAX_FN_COST=30000000`(決定 0185、環境変数、既定は無制限)を `few.sh`(リスト作り)と `wasm-var*.sh`(hybn0/hybrid の fe-wasmgen)に掛け、リストから除いた(d 類の『over the size limit』)。ship4 の混成の機構(`HYBRID_SETS`)はこの環境変数を設定しない — **リストを機械的に拡げるときは、リストを作る側とビルドする側で同じ上限を掛けないと、ビルドが『listed but not emitted』で止まるか、RSS が桁違いになる**(MERGE-NOTES)。上限に近い境界の 2 関数(`f_73d5c0`、`f_dd5a80`)は出荷の旗では上限内で `--mx-packed --mx-rc` を足すと超えたので、b 類を『両方の旗で ok』に直した(S-hyb6-b-both)。上限つきの結果は §5 以降。
