| 窓 | r(ff5) | ゲストのスレッド群÷壁 | UI+ループ÷壁(u) | idle÷壁 | program÷壁 | m = スレッド群÷r | r_max = (1−u)÷m |
|---|---|---|---|---|---|---|---|
| 10–20 s | 0.40 | 0.370 | 0.478 | 0.086 | 0.064 | 0.93 | 0.56 |
| 20–30 | 0.41 | 0.374 | 0.492 | 0.089 | 0.044 | 0.91 | 0.56 |
| 30–40 | 0.33 | 0.386 | 0.488 | 0.080 | 0.045 | 1.19 | 0.43 |
| 40–50 | 0.33 | 0.369 | 0.449 | 0.154 | 0.027 | 1.11 | 0.50 |
| 50–60 | 0.36 | 0.359 | 0.453 | 0.134 | 0.053 | 0.99 | 0.55 |
| 全体(60 s) | | 0.343 | 0.464 | 0.115 | 0.077 | | |

(ff4(200 µs)も同じ形: u 0.435〜0.476、スレッド群 0.209(0〜10 s)〜0.388、r_max 0.32〜0.50。)

- **実測**: **u(UI+ループ)は 0.42〜0.49 でほぼ一定**(書き込み率 r が 0.33〜0.41 に動いても動かない)。ゲストのスレッド群は 0.36〜0.39 で、これも r に比例せず(r が下がる窓で m が上がる = 1 音声秒あたりの費用が曲の進みで上がる)。= PM の読み(UI の費用は壁時計に比例し、r に比例しない)と合う。**ただしこれはプロファイラ付きの割合**で、プロファイラ無しの Worker は 0.66〜0.75(ser-ff3)。
- **読み**: プロファイラ無しの割合を同じ比率(スレッド群:UI = 0.44:0.56 前後)で割ると、u ≈ 0.39、m·r ≈ 0.31、m ≈ 0.9(r = 0.33)。**待ちを 0 にしたときの r の上限は、式 `r_max = (1 − u) ÷ m` で 0.6〜0.7 前後**(プロファイラ付きの値そのままだと 0.43〜0.56)。PM の見積り(0.6〜0.75)と同じ桁。**この式は『UI の費用が壁時計に比例する』= 仮想時計が壁時計と同じ速さで進む設計(c = 1)の前提**。c > 1 のまま lead の上限を小さくして仮想時計を先に進めると、UI の tick も仮想時間で刻まれる(読み、未測定)ので UI の費用が c 倍近くまで増え、r の上限は `1 ÷ (u + m·r の CPU 秒/仮想秒)` で約 0.45〜0.5 になる(下の 1e の表の行)。**どの設計を採るかで上限が 0.45 〜 0.7 に分かれる**。
- **P2 と P3 の両立(PM の読みの確認)**: u ≈ 0.4(UI 60 Hz 相当で)+ m·r ≈ 0.9(r = 1)= 1.3 コア。UI を 120 Hz にすれば u は約 0.8 でさらに 1.7 コア。**1 Worker 1 コアでは、待ちを 0 にしても P3 の 1.0 には届かない**(必要な CPU の削減は約 1.3〜1.7 倍、または UI とミキサーを別コアに)。数字はプロファイラ付きの割合から換算した見積りで、プロファイラ無しの直接の分解ではない。
