## 2. 何をしたか

### 2.1 rcgen の lower.rs への接続(依頼 1)
決定 0172 の `rcgen.rs`(RC≠0 のスカラ add/sub/mul の wasm 補助関数 4 つ)は lower.rs に未接続だった。混成の窓(決定 0164/0169)の判定に RC を足した:

- 局所変数 `mx_rcl` = `(MXCSR & 0x1020) == 0x1020`(PE が立ち PM がマスク。守り)なら `(MXCSR >> 13) & 3`、でなければ 4。関数の入口・呼び(C スタブ・直接関数)の後・`ldmxcsr` の後・C 呼び出し(`fle_hyb_mx`)の後に MXCSR から作り直す。C の slow の後に作り直すのは、最初の不正確演算で PE が立つ(Serum 2 は process の頭で MXCSR=0xffc0 にして旗を消す)のに、その関数の残りが遅い経路に居続けないため。
- `mx_rcl == 0` → 従来の窓(ホスト演算そのまま)。`1..3` → rcgen の補助関数(窓判定を中でする。窓外なら (0,0) を返し C へ)。`4` → C(`fle_hyb_mx`)。
- 補助関数を足した: パックド addps/mulps(f32x4)・addpd/mulpd(f64x2)(全レーンの窓判定+TwoSum/Dekker/二重積を SIMD で。subps/subpd は第 2 オペランドの符号反転)、cvtsd2ss、divsd/divss/sqrtsd/sqrtss(決定 0172 の `fle_mxr_div64/sqrt64/div32/sqrt32` と同じ式)。cvttsd2si 等の**切り捨て**変換は RC に依らない(守りは PE 立ち・PM マスクだけ)。
- 足した命令形(窓つき・C への落とし先 `fle_hyb_mx` の種類 40〜58): パックドの add/sub/mul/div/sqrt/max/min(div・sqrt は常に C)、cmpps/cmppd/cmpss、cvttps2dq、roundss/roundsd(即値 bit2=0 のとき)。窓なしの形(`sse_x2`): andnps/pd・pandn、unpck{l,h}{ps,pd}、punpck{l,h}{bw,wd,dq}、movlhps/movhlps、movl/h{ps,pd}(メモリ入出力)、shufps/shufpd、pshufd/pshuflw/pshufhw、pcmpeq/pcmpgt{b,w,d}、psr/psl/psra{w,d}(即値とレジスタのカウント)、packuswb/packsswb/packssdw、pmuludq、movmskps/pd・pmovmskb、pextrw。

### 2.2 網羅率の 4 つの壁を外す(census で見つけ、opt-in で外した)
census(`fe-wasmgen --census`)の process 命令の分類で、直接版にできない理由は順に: (1) パックド算術に窓の規則が無い(混成では関数ごと C のまま)、(2) 足りない命令形(andn・shuf・cmpps・…)、(3) 『RSP が入口の値でない』= switch の親と case 継続関数、(4) 『opaque な呼び先を呼ぶ』(流れ解析が flag の recipe 無しで落ちた関数 `shr r,cl` の CF を後で読む形が呼び先にあると、呼び元ごと C のまま)。

## 4. 見つけた誤り(直接生成部の誤り 1、ビルドの誤り 1)と、見つけ方

**関数単位の二分探索の道具**: C 側に `fc_<va>` の写し(候補 1,000 関数の C 本体を名前だけ変えて残す)を持つビルドを 1 つ作る(`COPIES=1`、約 10 分)と、どの部分集合を直接版にするかは**直接部だけを作り直す**(fe-wasmgen `--hybrid-only SUBSET --c-copies ALL`、wasm-merge、1 回走らせる。約 1 分)ので、候補 123 個の先頭から二分探索すると 6 回(約 6 分)で 1 関数に絞れる(`tools/hbisect.py`、`mkvariant.sh`)。N=50/123/200/1000 はこの 1 つの C 部から作った(未使用の写しは C 部に残る)。

1. **switch の dispatch(TailIndirect)が渡すレジスタが足りなかった**(直接生成部の仮定): fe-lift は image-base 形のジャンプ表(`lea r10,<image base>; mov r9d,[r10+r8*4+T]; add r9,r10; jmp r9`)を解決せず `fle_dispatch(R[9])` にする。fe-wasmgen の TailIndirect(`jmp reg`)は『Win64 の tail call』と仮定し、rcx・rdx・r8・r9・rax と xmm0..3 だけを C の dispatch に渡し、rax だけを受けた。memset(0x2a18f80)のジャンプ表の宛先は r11(埋め値 0x0101…×dl)と xmm0 を読むので、古い r11 で埋めてバッファが壊れ、初期化中に `fle_addr_hi32` で止まった。二分探索で 0x2a18f80 に特定(候補 83 番目)。`--tail-all`(全レジスタ・全 XMM を渡して受ける。liveness も)で解消。**エンジンの混成(hyb3 の 82 行一致)は『TailIndirect の宛先は Win64 の呼び先』という仮定の下で成立している。仮定が崩れる経路(エンジンの image-base 形のジャンプ表を持つ関数が直接版になる)が無いかは未確認**(hyb4 に伝えた)。
2. **`--wrap=fle_mxcsr_load` で C 部が `__wrap_fle_mxcsr_load` としてしか出さない**(ビルドの誤り): `ldmxcsr` を含む関数を直接版にすると wasm-merge の後に `c.fle_mxcsr_load` が未解決の import として残り、WebAssembly.instantiate が失敗する(N=50 には ldmxcsr を含む関数が無かった)。`hybrid_glue.c` に `FLE_HYB_WRAPPED_MXCSR` のときだけ別名の export を足した(エンジンのビルドには影響しない)。

(誤りではないが書く) 最初の混成(N=50、RC 補助関数なし)は cvtsd2ss が RC=3 のため 1,266 万回 C に落ち、状態 3 が 38 ms だった。補助関数を足すと C 呼び出しが 7 回になり 24 ms。**速さのために正しさを緩めた所は無い**(窓外は常に C)。

## 5. switch の親関数と case 継続関数を 1 つの wasm 関数にまとめる(PM の依頼 2。設計・評価・試作)

### 5.1 問題(実測)
Serum 2 のコンパイラは switch を `lea B,[rip+T]; movsxd X,[B+I*4]; add X,B; jmp X` に落とす(表 T は .rdata。各項は『T からの符号つき 32 ビット差』で、RVA ではないので fe-lift の決定 0089/0109 の形ではない)。fe-lift はこれを解決せず `fle_dispatch(R[x]); return;`(動的探索)にし、vst3a の rel_table_seeds.py が各項の宛先 4,142 個を**関数の種**にした(553 サイト)。結果、case の本体は『親の RSP フレームを引き継いで ret する別関数』= RSP が入口の値でない関数になり、fe-wasmgen は親(間接 jmp の時点で RSP が入口と違う)も継続も直接版にできなかった。process 命令のうち『RSP 非釣合い』は 状態0 16.4%、状態1 31.8%、ピアノ 35.6%、状態3 3.4%、状態5 37.5%。

### 5.2 試作(全 530 サイト分を実装した。『最小の試作 1 サイト』より進めた。opt-in)
- fe-decode `jumptab::resolve` の検査を 1 か所緩めた: 表が .text の**外**(読み取り専用データ)にあるとき『表が注釈した関数の範囲にある』検査をしない(.text の中の表は従来どおり)。FLEngine の 4 サイトと ILTools の 1 サイトは .text の中の表なので従来と同じ検査。
- fe-wasmgen `--rel-sites FILE`: rel_table_seeds.py の sites.tsv(jmp_va, table_va, entries)から `Spec`(`Kind::Rel32 { base: T }`)を 1 サイトずつ作る。注釈する関数の範囲は、そのジャンプを含む .pdata 関数の全 piece の範囲。宛先を**種から外す**(親の switch の blocks として親に取り込まれ、独立の関数にならない)。既存の `Term::Switch`(Select::Target)の lowering をそのまま使う。
- 結果: 530 サイトを Spec にし 487 表が通った。落ちた 43: 表が .text の中で範囲外 11、宛先が命令の途中(verify) 約 25、宛先が範囲外 2、他。落ちた親は従来どおり C のまま(`--unbal-stub` で呼び元から C スタブとして呼ぶ)。
- 通した 487 表で直接版にした混成の**出力ハッシュは全 6 ケースで基準と一致**(N=123/200/1000)。N=123 の process 命令のうち直接版で実行される割合 99.7〜100%(§1の表)。

### 5.3 評価項目
(a) **継続関数が親以外から呼ばれるか**: 宛先 4,142 個を種から外した census で、**別の入口(呼び先・.pdata の先頭・別の種)として現れたものは 0 個**。1 つの宛先が複数の表の宛先になることも 0 件。つまり複製もトランポリンも要らない。ただし『この census の関数集合では』であり、関数ポインタ経由の間接 call で飛び込む宛先が無いことの証明ではない(混成の C 部は宛先の C 関数を従来どおり持つので、飛び込まれても従来の C 経路で動く)。
(b) **合成関数の大きさ**: switch の親 361 個のうち直接版にできたのは 317 個(落ちた 44: RSP 非釣合い 19、8/16 ビット回転 12、bsr 7、bsf 2 など)。wasm のコード長は中央値 11 KB、p90 72 KB、p99 281 KB、最大 887 KB(0x22f7510、x86 の 4,765 命令)。128 KB 超 10 個、256 KB 超 5 個、512 KB 超 1 個、1 MB 超 0 個。wasm の x86 バイトあたり 6.4 倍(中央値)。V8 の wasm 関数の上限(約 7.6 MB)には届かない。**V8 が大きい関数で TurboFan を諦める/遅くなる閾値は測っていない**。最大の親を含む N=1000 の実測(node: 起動 init_cpu 1.57 s〔N=123 は 0.70 s〕、定常は N=123 と同じ。Chrome: §6.2 の block0)で見た。

### 5.4 リスクと、決めてもらう点
- **--rel-sites の安全性は、ジャンプ表の形(T からの差)と bound(`cmp`/『by neighbourhood』)が rel_table_seeds.py の判定に依存**する。bound が過大なら表の外を宛先にしうる(verify が命令の途中を棄却するが、命令の先頭なら通る)。487 表で出力ハッシュは一致したが、**状態 0〜5 の process で通った表の分岐だけ**を確かめた(実行されない case の正しさは未確認)。
- 決定: (i) `--rel-sites` を既定にするか(fe-decode を 1 か所緩めている。FLEngine の生成 C には影響しない)、(ii) br_table 化、(iii) エンジンの混成で同じ表を(エンジンには rel 形の表は『手書き注釈』の 4 サイトしか無い)。

## 8. エンジン(FLEngine)の混成・他の担当への影響

- **既定の出力は変わらない(実測)**: HEAD 26478ee の `git archive` から作った fe-wasmgen と、この差分を当てた木の fe-wasmgen に、Serum 2 の候補 123 個で新フラグ無しの同じ命令行を渡すと、出力 wasm(237,842 B)と report がバイト一致した(`logs/default-identity.txt`)。**エンジン(FLEngine)の混成を作り直しての比較は行っていない(未確認)**。
- **`--tail-all`(§4)**: fe-wasmgen の TailIndirect が『Win64 の tail call』(rcx・rdx・r8・r9・rax と xmm0..3 だけが宛先に渡る)と仮定していたのが、switch の dispatch(宛先が同じ関数のブロック)で崩れた。**hyb3 のエンジンの混成の 82 行一致は、この仮定の下で成立している。仮定が崩れる経路(エンジンの image-base 形のジャンプ表を持つ関数が直接版になる)が無いかは未確認**。hyb4(エンジンの N=1000)に、`--tail-all` ありなしで 82 行一致を確かめるよう要点を送った。`--tail-all` は opt-in。
- **`--unbal-stub` / `--opaque-stub`**: 保守的な署名の C スタブ呼び。エンジンでは未適用・未測定。署名が保守的(全レジスタ・全 XMM)なので、エンジンで使うと呼び元の入口のレジスタが増えて遅くなりうる。
- **`--rel-sites`**: Serum 2 専用の入力(rel_table_seeds.py の sites.tsv)。エンジンの rel 形の表は手書き注釈の 4 サイトで、これは .text の中。fe-decode の緩和はエンジンの結果に影響しない(読み)。
- **進捗カウンタ(hyb3 の `--hybrid-progress`)**: 単体のプラグインハーネスには仮想時計の進捗の仕組みが無いので Serum 2 の混成には使っていない。**プラグインがエンジンの中で動くとき(wrp1 の仕事)の数え方は未検討**。
- **hyb3 の xabi.rs の素通りの修正**: Serum 2 の混成でも必要だった(無いと XMM 引数がずれる、との連絡のとおり)。この作業の測定は hyb3 の作業木の xabi.rs で行い、載せ替え後(HEAD 26478ee の xabi.rs)でも N=123 の直接モジュールが同じ大きさ・全 6 ケースのハッシュ一致を確かめた(`logs/hashcheck-s4-123.txt`)。
- **決定 0172(rz1)**: rcgen.rs の『未接続』を接続した(§2.1)。rz1 の C 側(`fle_mxcsr_rc.h`)の式をそのまま wasm に写した補助関数で、ホスト CPU との差分試験(§3)は rz1 の枠組みの延長。決定 0172 の表の『直接 wasm 生成部: lower.rs へは未接続』は、この決定で接続済み(Serum 2 の混成で使用)。
- **決定 0177(srm1)**: srm1 の『C 経路 wasm では P3 に届かない見込み』に対し、混成は 1 インスタンスの定常を 0.35〜0.53 倍にし、ピアノ以外は周期内に入れた。ピアノは残る。

## 9. 出典のない選択

- **S-hyb2-1 窓**: パックド addps/subps/mulps(f32x4)の窓は決定 0154 のスカラの窓を全レーンに(0 か 2^-62..2^62)、addpd/subpd(f64x2)は 0 か 2^-510..2^510(RC=0 の速い経路は mulpd も同じ)、RC≠0 の mulpd の補助関数は決定 0172 の 2^-400..2^400。理由: 結果が正規数になり IE・DE・ZE・OE・UE が起こらない範囲(決定 0154/0172 の証明をレーンごとに当てただけ)。代替: レーンごとの個別判定(窓外のレーンだけ C)。撤回条件: 差分試験の不一致。
- **S-hyb2-2 全レーンの窓判定**: 1 レーンでも窓外ならそのパックド命令全体を C 経路の関数で実行する。理由: 結果の混成(レーンごと)より単純。代替: レーンごとの選択。
- **S-hyb2-3 RC≠0 の守り**: `(MXCSR & 0x1020) == 0x1020`(PE が立ち PM がマスク。決定 0172 と同じ)。C の slow の後と呼び出しの後に MXCSR から再計算する局所変数 `mx_rcl`(RC=0..3、守りが偽なら 4)で分岐する。撤回条件: MXCSR を直接書く命令(fxrstor 等)を直接版にするとき。
- **S-hyb2-4 C の slow の種類 40..58**: hybrid_glue.c の `fle_hyb_mx` に packed 算術(40..52)、cmpps/cmppd/cmpss(53..55)、cvttps2dq(56)、roundss/roundsd(57,58)を足した(C 経路が生成 C から呼ぶのと同じ関数)。
- **S-hyb2-5 --unbal-stub の保守的な署名**: RSP 非釣合いの関数(switch の親)は直接版にせず、直接版の呼び元からは『全レジスタを渡し、要求された結果を全レジスタから返し、何も保存されない、XMM は全部渡して全部返す』C スタブとして呼ぶ。RSP は呼びの後に読み戻さない(C 経路が `R[4] += 8` で戻すのと同じ)。理由: 呼び元から見れば普通の関数。代替: 親ごとに本当の署名を解析(未実装)。撤回条件: 出力ハッシュの不一致(N=50 で全 6 ケース一致を確認)。
- **S-hyb2-6 --opaque-stub**: 流れ解析が『flag read from a definition without recipe』(`shr r,cl` の CF を後で読む)だけで落ちて CFG が無い関数も、呼び元からは同じ保守的な署名の C スタブとして呼ぶ。理由: 通常の ABI に従う葉関数(浮動小数→整数の丸め)。ABI に従わない関数には使えない(確認は出力ハッシュ)。
- **S-hyb2-7 --rel-sites**: fe-decode の 1 行の緩和(表が .text の外なら注釈した関数の範囲の検査を飛ばす)と、宛先を種から外す。表の形(T からの符号つき 32 ビット差)は rel_table_seeds.py の判定(`cmp`/`by neighbourhood`)に依存する。
- **S-hyb2-8 関数の選び方**: process(決定 0165 の 6 状態の実行命令数の割合の和)→ init(状態 0・3 の命令数)→ 静的な大きさの順の最初の N 個、census が ok のものだけ。N=50/200/1000 は依頼の値。代替: 実行回数順、状態 3 だけ。
- **S-hyb2-9 測定**: 1 ブロック = 4096 フレーム、40 ブロックの『最小の 1 ブロック CPU(スレッド CPU 時間)』の、6 回の run の最小と中央値。run は交互。

## PM の判断と取り込み(2026-11-03、追記)

取り込み: `hyb2.diff`(12 ファイル、基準 HEAD 26478ee。fe-wasmgen の rcgen/lower/lib/main/xabi と 5 つの新しいテスト、`fe-decode/src/jumptab.rs` の 1 か所、`lift/harness/hyb1/hybrid_glue.c`)。PM の検証: `patch -p1 --dry-run` は offset・fuzz・reject なしで当たる。`-` 行 20 本を全て読んだ(fe-wasmgen の内部ロジックの置換、`hybrid_glue.c` の配列サイズ 40、`jumptab.rs` の 1 行)。**共有の fe-decode の変更**(`.text` の外のデータ内の表を、注釈された関数の内側でなくても受け入れる。`.text` 内の表は従来どおり)は fe-lift も使うので、**fe-lift を再ビルドして FLEngine の生成 C を作り直し、sha256 が `cd9107ce…`、215,811,678 B で不変なことを確かめた**。全体テスト **169 results / 2,199 passed / 0 failed**(164/2,194 + 新規 5 実行ファイル、担当の値と一致)。a4(FRUITY 無効)942/942・895/895・functions 5,310・entries 1,009,731 で不変。PM は Serum 2 を実行していない(数字は担当の実測)。実行したのは実エンジンではなく、実プラグイン Serum2.vst3 を vst3a の代役の上で動かした測定で、**P3 の達成でも進捗(G 段階)でもない**。
