## 1. 方法

- `lift/harness/fruity_g3.c` に native 専用(`-DFLE_G3_FORKPROBE` と `-Wl,--wrap=syscall`)の命令を足した: `probe NAME`〜`probe-end`(子の標準出力・標準エラーは `$FLE_G3_PROBE_DIR/NAME.out/.err`、CPU 秒の上限は `$FLE_G3_PROBE_CPU`)、`setenv NAME [VALUE]`、環境変数 `FLE_G3_FOLLOW=1`(スクリプトが FIFO で、命令を後から送れる。エンジン 1 本で何十もの操作を試せる)。子の `gettid` が親と違うと runtime の単一スレッド規則が即停止するので、`__wrap_syscall` で親の tid を返す。最初の版はこれを知らず全件が停止し、その回の結果は破棄した。
- 停止の原因は、ハーネスが出す『最内の lifted thunk』の名前、`tools/thunks.py`(PE の import 表と thunk のバイトから VA → `dll!name`。FLEngine の import thunk 890 本、行なしで停止するもの 232 本)、`fle_seh.c` に足した診断(遅延ロードの例外 0xC06D007F の DelayLoadInfo から dll と関数名、`RtlUnwindEx` の登録の連鎖)で特定した。
- 修正の検証は『行を足した生成 C』で行った。`fe-lift lift … --extra-imports FILE`(決定 0156)で行を足す。行の無い API は thunk が `fle_unsupported`、行がある API は `fle_imp_*` を呼ぶ。応答表(GetProcAddress・遅延ロード補助が使う `fle_resp_table`)も同じ行から作られ、**全モジュールで同じでなければならない**(`merge_tables_n.py` が検査)ので、FLEngine と 5 DLL のすべてを同じ行で lift する(`a4-multi.sh` に opt-in `FLE_EXTRA_IMPORTS`、`build-engine-bundle.sh` に `EXTRA_IMPORTS`)。
- 再コンパイルは、関数の本体が変わった単位(FLEngine の import thunk を含む `fle-00`・`fle-01`・`fle-02`〈native の切り方〉、ILTools の `m5-00`・`m5-01`、`common.c`)と変わった runtime のファイルだけにした。他の単位は 24 行の未使用の宣言(`void fle_imp_X(void);`)が増えるだけで、コンパイル結果は同じ(宣言のみの差、`diff` で確認)。
