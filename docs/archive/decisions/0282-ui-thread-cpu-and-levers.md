## 6. 依頼 3 — MXCSR 窓検査の費用

### 6.1 静的な量(E7b の wasm)

- 窓検査は fe-wasmgen の `mx_packed` / `mx_pk_ok`(`lower.rs` 3639〜)が出す: 演算ごとに、**両方のオペランドの全 lane について『0 か、指数が窓の中(f32: 2^-62..2^62)』を整数の SIMD で判定**(`local.get; i32.const 1; i32x4.shl; local.tee T; v128.const K; i32x4.sub; v128.const C; i32x4.lt_u; local.get T; v128.const; i32x4.eq; v128.or` をオペランドごとに 1 回、`v128.and`、`i32x4.all_true`)して `if`、偽なら C 経路の `fle_hyb_mx` を呼ぶ。**1 回の検査 = 約 26 命令(SIMD 約 14、局所の出し入れと定数)、検査される演算 = 1 命令**。ガードの条件は『RC = 0・PE が立っている・PM がマスク』(`mxcsr` の局所 / global)。
- `f_b34aca0`(= `f_b34eaf0` の複製。106,516 命令、locals 4,003)に **packed の窓検査が 646 か所**(`if` の直前が `i32x4.all_true`)、`fle_hyb_mx` の call サイトは 1,938。検査の命令は 646 × 26 = 約 16,800 命令 = **関数の静的な命令数の 15.8%**。Elastique の 133 関数では 1,971 か所(検査の命令 51,200)。
- **FL が MXCSR を触る頻度(測定。『まれ』ではなかった)**: 静的な `ldmxcsr` / `stmxcsr` は FLEngine に 9、Elastique に 199、dsp_ippv2 に 2,323(`objdump`)。**native N1(HEAD の runtime、`fle_mxcsr_load` / `store` に数え上げの診断を入れた変種〔入れない〕)で起動 + プロジェクトを開く + 40 仮想 s の再生(`a12-play40.g3`、約 67 仮想 s)の間に `ldmxcsr` が 554,968 回(うち値を変える物 510,694 回)、`stmxcsr` が 493,608 回**。= 約 8,300 回/仮想 s、**ミキサーの 1 ブロック(92.88 ms)あたり約 770 回**。読み込まれた値は少数で、FTZ(ビット 15)と DAZ(ビット 6)の**切り替え**が大半: `0x9fe0`(FTZ+DAZ、PE のフラグ立ち)166,451、`0x1fa0`(FTZ/DAZ なし、PE 立ち)164,451、`0x1fb0` 81,175、`0x9ff0` 81,174、`0x9fe1` 51,160、`0x1fa1` 9,033、`0x9fc0` 1,334、`0x1f80`(既定、PE なし)4 ほか。= **MXCSR の RC は常に 0、PM はマスクのまま、PE は立っている値が 99% 以上**で、窓のガード(RC = 0・PE 立ち・PM マスク)は実際にほぼ常に真(`0x9fc0` と `0x1f80` だけが偽 = 0.2%)。ただし値は**1 ブロックに 770 回変わる**ので、ガードを関数単位で 1 回に畳むことはできず、基本ブロック内でだけ畳める。呼び出し元(最初の 32 か所のみ記録、256,441 回分)は **dsp_ippv2 の `f_38e6d90`(97,224)・`f_32e9c00`(69,540)** と **Blend2D 系の `f_48b1344` / `f_48b13c0` / `f_48b0abc`(86,000 弱)**で、IPP の関数が呼ばれるたびに FTZ/DAZ を切り替えて戻している形。ブラウザの run の 20 s では `fle_mxcsr_load` の自己時間は 2 ms(ミキサー)。

### 6.3 読み

- 窓検査(packed の add / sub / mul)の費用は、Elastique の SIMD のホットな関数で**その関数の時間の 43〜51%**、ミキサー全体で **7.6〜8.7%**。スカラーの検査・変換・min / max の検査は測っていない(外すと範囲外で壊れるので、この方法では測れない)。
- **MXCSR の側のガードは安いが、畳めない**: 窓検査の『オペランドの窓』(SIMD の部分、B で外した物)と『MXCSR のガード』(RC = 0・PE 立ち・PM マスク)は別。ガードは測った値の 99.8% で真で、判定は局所 / global の比較 1 回に近い。ただし MXCSR は 1 ブロックに約 770 回変わる(IPP の呼び出しごとに FTZ/DAZ を切り替える)ので、関数全体で 1 回に畳む案は使えず、**畳めるのは `ldmxcsr` を挟まない基本ブロックの中**だけ。B は『オペランドの窓』の SIMD 部分(1 回約 26 命令)だけを外した。
- **忠実な削減の形**(検査を外すのではなく、同じ判定をより安く): ①オペランドごとの『shl → sub → lt_u → eq → or』を、abs と整数比較の短い形にする(約 26 → 18 命令の見込み、−30%)、②両オペランドの判定を 1 回にまとめる、③**窓の導出**: 前の演算の結果が窓の中と分かっているとき(窓の幅が演算で広がる量を指数の足し引きで押さえる)、次の演算の検査を省く。①②で検査の費用の 30〜40%(ミキサーの 2〜3%)、③まで行けば半分前後(3〜4.5%)と読む(**未検証。③は固定小数点のように指数の範囲を追える部分に限る**)。
- **ミキサーの梃子として並べると**(0276 の表 3 に追加): ①E8 のフラグ 5.0〜8.5%、②型付きの呼び 4.8〜5.8%、**③窓検査を安く 2.5〜4.5%(忠実な形)**、④x87 3〜5%。

## PM の判断と取り込み(2026-11-06 11:40、docs のみ。差分は製品の木に無い)

取り込み: alpha1(alpha14)の第 1 報(最終は 12:45 まで。変わればこの節を更新する)の文書・表・道具を `docs/investigations/alpha14/` に置いた。入れていない物: `tools/a14-nomx-patch.py`(wasm の窓検査を常に真にする throwaway)、`tables/diag-*-NOT-FOR-MERGE.*`、生の V8 プロファイル(`logs/`、約 1.1 MB)。測定は Chrome 156 headless の本番 E7b bundle `fl-engine-ci-d9c160aa` と native N1。E8 の bundle のブラウザ測定、実 Windows、依頼者の機械は 0 件。プロファイラ付きの値で、run 間の負荷が違う(A1 load 4、A2 load 15〜18、B load 9〜24)ので比で読む。

判断:
1. **UI の CPU は 0.398 コア、guest 関数が 80%、tick は 62.6〜65.2 回/s で 1 回 5.04 ms**(0263 の 16.7 ms は tick の数え違いだった。訂正する)。present は 0.009 コアで、描画の間引きや Hz 上限の引き下げは効かず採らない(FL の挙動でもある)。
2. **1 コアの予算**: ミキサー 0.909 コア(E7b、84.4 ms/ブロック)+ UI 0.398 = **1.31 コア**。0276 の梃子 3 つ(12.8〜19.3%)+ 窓検査の忠実な形(2.5〜4.5%)+ UI の梃子 3 つ(0.055〜0.11 コア)を全部入れて 0.98〜1.11 コアで縁。**ミキサーを別コアに出せば単体 0.69〜0.77 コア**。よって P2(UI 120 fps ≈ u 0.8)+ P3 を 1 Worker 1 コアで両立させるのは設計上できない可能性が高く、**実スレッドのミキサーの再評価(決定 0283 (4)、gpu1)を進める**。
3. **MXCSR の窓検査を外すのは FL の挙動を変えるので採らない**(外し過ぎた版は SIGABRT と memory OOB で壊れた)。同じ判定をより安く行う形を **決定 0287(alpha1)** で設計・試作する(見積り ミキサーの 2.5〜4.5%、未検証)。throwaway で外した版の −7.6〜−8.7% は『この検査の費用の上限』の参考値であって採用値ではない。
4. **復元後の toolbar の 15 px のずれは、最小化の時点で FL 自身の AlignControls(戻り番地 0x825570)が起こし、alpha10 / D の無い HEAD でも出る**。契約の逸脱は見つかっておらず、足すなら FL の配置を補うことになるので**直さない**(lift 忠実性の方針)。実 Windows の FL で同じかは未確認。
5. UI の梃子のうち ①(直 wasm どうしの呼び出しの境界)は決定 0285(mt3、typed direct→direct の call_indirect)と同じ実装。②(f_863f60 の質)③(UI に残る C 経路)は 0285 と 0286 の後で再評価する。
