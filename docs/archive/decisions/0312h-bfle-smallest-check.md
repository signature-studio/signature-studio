## 2. 実験の限界(正直に)

- **FLEngine 側の基準は『製品の C』**(`wsrc/src/fle-*.c`)で、`--pdata` だけの素の lift ではない。製品の C には (i) hybrid で direct wasm に下げた関数 2,758 個が**入っていない**(`hyb/lowered-fle.txt`)、(ii) hook・SEH・site override・prune が掛かる。plugin には無い。**共有の割合は過小評価の可能性**。素の `fe-lift lift FLEngine_x64.dll --pdata` で再実行する(窓の後。1 本、約 20 s・RSS 数 GB〔読み〕)。plug1 のバイナリ側の実測は『Balance のコードの 78.3% が FLEngine と同一』(`code_not_in_FLEngine` 21.7%)で、**C 側の 65.5%(モジュール固有 34.5%)はそれより悲観的**。差の原因は未特定(上の基準の違いと、C 側の正規化が命令単位の違い〔flags の生存解析に依る出力の違いなど〕を拾う可能性)。
- 正規化は**イメージ範囲の全リテラルを `@`** にするので、範囲内の即値同士が違う 2 関数を『同じ』と数える**過大評価**がありうる(逆に flags の出力の差は『違う』と数える)。呼び先は h0 では全部同じ記号に潰す(共有の基準としては、呼び先を表経由にする設計と整合)。
- **同じ本体 = 同じ意味**とは限らない: 範囲内の即値が違う、呼び先が意味的に違う、は表経由にしても本体が同じなら表の値で解決される(正しい)が、**範囲内の即値が『アドレスでない定数』のとき**、表に入れても値はそのモジュールの実際の値なので意味は保たれる(誤分類は効率を落とすだけで正しさは落とさない)。この点は設計の長所。
- Flanger は Balance の『プラグイン間の共有』の確認用で、他のプラグイン(Filter 以降、MSVC の engine)には適用していない。Delphi 以外(FLEX・Frequency Shifter の Engine)では成り立たない(plug1)。

## 4. 生成器の変更の設計(差分は書いていない。cargo build は窓の後)

**VA を出す場所**(`crates/fe-lift/src`、`grep` で数えた): RIP 相対の実効アドレス `ip_rel_memory_address()` が **12 か所**(lib.rs:272、insn_int.rs:177、int_ext.rs、int_more.rs、mmx.rs、sse_int2.rs、sse_more.rs、sse_pack.rs、sse_scalar.rs、sse_shuf.rs、sse_ssse3.rs、vex.rs)、絶対の displacement `memory_displacement64()` が **13 か所**(同じファイル群、lib.rs:286)、直接分岐の目標 `near_branch*()` が 7 か所(flaglive.rs・int_more2.rs・lib.rs)、`f_<va>` を出す indirect.rs、ラベル `L_<va>`(lib.rs 3 か所)、ジャンプ表(jumptab.rs)、即値のアドレス(`lea`・`mov r, imm`、`imm_lit`)。+ **hybrid の direct wasm の生成器 `fe-wasmgen`**(同じ VA を出す。FLEngine は 2,758 関数が direct wasm)。= **約 30 か所 + wasmgen**。

**案(packaging 中立な ABI)**:
1. すべての範囲内の VA リテラルを 1 つの補助関数 `va_lit(va)` を通し、関数ごとの参照リスト `refs[k]` に記録して `T[k]` と出す。呼び先 `f_<va>` も `T[n+j]`(関数表の index)に。**誤分類は効率を落とすだけで意味は保たれる**(表の値は常にそのモジュールの実際の値)。
2. 共有する本体は `void S_<hash>(const uint32_t *T)`(`T` は引数)。各モジュールは**薄い wrapper** `void f_<va>(void){ S_<hash>(T_<va>); }` と表 `static const uint32_t T_<va>[]` を持つ。`T` を引数にするので**現在のモジュールの大域変数も thread-local も要らない**(ミキサーと UI が別モジュールの本体を同時に走らせても競合しない)。
3. 共有しない関数(モジュール固有、ホットな関数)は今の形のまま(表なし)。
4. 共有の単位は『本体の hash が FLEngine に存在する物』(今回の h0)から始め、**呼び先を表経由にするので直接呼びは間接呼び(`call_indirect`)になる**。性能への影響は未測定。

**FLEngine 自身の扱い(2 案、PM の判断)**:
- **A. FLEngine も表経由の本体を使う**(一つの本体を FLEngine と全 plugin が使う)。**FLEngine の重複 24.77 MB の C が畳まれて縮む**(最終で約 −5 MB)。**FLEngine のホットな経路(UI・ミキサー)でデータ参照が `T[k]` の 1 段、呼びが `call_indirect` になる**ので、P2(120 fps)・P3 に響く危険。受け入れ測定が要る。
- **B. FLEngine は今の形を保ち、plugin 用に表経由の本体を 1 組余分に持つ**: 共有された異なる本体 18.95 MB の C ≒ **最終で約 5.9 MB**(一度だけ)。FLEngine に性能の危険は無い。2 つ目の plugin から A より得。
- 中間: **ホットでない物だけ表経由**にする(手がかりは『起動で実行される関数は FLEngine で約 9%』(plug1/performance-targets の値。実行回数は別に測る))。

**最小の次の一歩(窓の後)**:
1. 素の FLEngine の lift(`fe-lift lift binaries/win64/FLEngine_x64.dll FLEngine.c --pdata`)で本実験を再実行 — 基準の違いの分を分ける。
2. 小さな試験: Balance の共有候補の 1 関数に `va_lit` を適用した C を手で作り、wasm の大きさ・呼び出しの時間を測る(約 0.5 日〔読み〕)。
3. 生成器の差分(約 30 か所 + wasmgen)は 1〜2 の結果で A/B を決めてから。工数は見積もっていない(plug1 も未見積)。

## PM の判断と取り込み(2026-11-06 23:10、docs のみ。製品の差分なし)

取り込み: mt3 の 0312h(B-FLE の最小の確かめ)の文書・表・道具を `docs/investigations/mt3w/0312/` に置いた。実行は B1 の CI の fe-lift(Balance と Flanger を各 1.2 s)と python(nice 19)の**読み取りだけ**で、**wasm・Chrome・依頼者の機械は 0 件**。大きさの見積りは係数(B1 の FLEngine の実測: C 1 B あたり pre-opt の wasm 0.407、最終 × 0.765)による**読み**で、Balance の wasm を実際に作った値ではない。

事実として受け取る(mt3 の実測・python の出力): 正規化した本体の一致(h0)で、Balance の 12,549 関数・C 34.1 MB のうち **10,310 関数(82.2%)・C 22.38 MB(65.5%)が FLEngine の製品の C と同じ**(Flanger も ±0.5 ポイント)。呼び先まで同じ(h1/h2)は 51.3%/33.3%(関数)に下がる。モジュール固有 11.77 MB のうち **96.4% は Flanger にも同じ本体がある**(プラグイン共通の枠組み)ので、プラグイン固有は 0.42 MB(3.6%)。FLEngine 自身にも重複があり、59,568 関数のうち 25,762 関数・C 24.77 MB(13.3%)は同一の本体。表なしで共有できる葉は 1,719 関数・1.2 MB(共有の 5.4%)だけで、残りは表(データ参照のリテラルを関数ごとの `T[k]` に)が要る。

判断:
1. **方式は B を採る**: FLEngine の今の形(データ参照が直接、呼びが直接)は保ち、プラグイン用に『表経由の共有本体』を 1 組だけ追加する(共有された異なる本体 C 18.95 MB ≒ 最終 約 5.9 MB を一度、2 つ目以降のプラグインの増分は約 1 MB〔読み〕)。**A(FLEngine 自身を表経由にして約 5 MB 縮める)は保留**: UI・ミキサーのホットな経路でデータ参照が 1 段間接、呼びが間接になり P2/P3 に響く危険があり、受け入れ測定(P2/P3 の ABBA)が要る。S1 の関門に必要になるまで(プラグインが鳴り、実測で比が 2 に近づくまで)やらない。中間(ホットでない物だけ表経由)は A の測定の後。プラグインの共有部分は Delphi の RTL/VCL の枠組みで、オーディオ処理の本体(プラグイン固有 3.6%)ではないので、B はプラグインのホットな経路を間接化しない見込み(読み)。
2. 区分: 生成器の変更は『S1 を満たすためのサイズ削減』で、FL の挙動の代行ではない(表経由は意味を保つ。誤分類は効率を落とすだけ)。新しい旗・環境変数・クラス/アドレスの分岐は足さない。No-options 適合。
