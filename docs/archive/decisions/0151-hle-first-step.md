### F.1 由来と、壊れうるもの(確認した)

- **由来**(読み。出典を探した結果): `git log -S"fno-builtin"` の最初は a7791f8(2026-10-20)の `lift/harness/build.sh`(`-O0 -g -w -fno-builtin -ffp-contract=off -fPIE`)。その後の `build_two_native.sh`・`build_nmod_wasm.sh`・各テストの clang 呼び出しが写した。**決定文書にもコミットメッセージにも理由の記述は無い**。`grep -rn "fno-builtin" docs/decisions`: 0031 は『既存の build.sh と同じフラグ』、0138 は『native -O2 のフラグを wasm の units に揃える』と書くのみ。**0143(fp1)は『生成 C は -fno-builtin なので memcpy は libc の呼び出しになる。最初の高速経路で標本の 30% が libc』と書き、MXCSR のヘッダの中だけ `__builtin_memcpy` に直した**(フラグ自体は疑われなかった)。考えられる理由(読み、確かめていない): 最初の -O0 -g のデバッグビルドで `memcpy` を普通の呼び出しにしておく。
- **効果の原因**(実測): 生成 C は `memcpy` を直接呼ばない(`grep` で 0 件)。呼ぶのは**ヘッダの小さな inline 関数**: `fle_ld`/`fle_st`/`fle_ldx`/`fle_stx`(ゲストのメモリの読み書き)と SSE の補助関数(`fle_runtime.h` 2、`fle_sse.h` 14、`fle_flags.h` 4、`fle_vex.h` 6、`fle_mxcsr_flags.h` 4 の計 30 か所)。`-fno-builtin` では固定長でも libc の `memcpy` 呼び出しになる(f_6a73a0 の中だけで 104 か所)。`nm -u` で数えた『`memcpy` を未定義シンボルに持つ単位』: **92 → 18**(残りは可変長のコピー)。
- **壊れうるもの**:
  1. `--wrap=fprintf --wrap=fputs`(native の `build_native_perf3.sh`・web の `link-web.sh`・wasm のリンク行): 組み込みを有効にすると、clang は**引数の無い** `fprintf(stderr, "…\n")` を `fwrite` にして、ラッパーが見えなくなる(`fle_rd` の『未定義フラグの読み』、`fle_bad_count` のメッセージ)。**実測**(`nm -u`、`logs/flag-nm-u.txt`): `-fno-builtin -fbuiltin` で `fprintf` が `fwrite` に変わる。**→ `-fno-builtin-fprintf -fno-builtin-fputs` を付ける**と変わらない(実測)。
  2. `memcpy` の重なり: 30 か所を読んだ。すべて『ローカル変数 ↔ ゲストのメモリ』『ローカル配列 ↔ ローカル変数(ビット変換)』『TEB のバッファ ↔ ローカル』で、**ゲストのメモリどうしの `memcpy` は無い**。`rep movs` などゲストどうしのコピーはランタイム(`fle_*.c`)にあり、ランタイムは元から `-fno-builtin` 無しでコンパイルされている(native の `build_native_perf3.sh` は `-O2 -Wall -Wextra -fPIE`、wasm の CFLAGS_RT)。
  3. 未アライン: `memcpy` の組み込みは x86-64 で `mov`/`movups`(未アライン可)、wasm で `align=1` の load/store。
  4. NULL: glibc の `string.h` が `memcpy` に `__nonnull((1,2))` を付けているので、`-fno-builtin` でも clang はこの仮定をしていた(変化なし)。
  5. 浮動小数点の組み込み(`sqrt`・`floor` など。置換で意味が変わりうるもの): ヘッダと生成 C に libm の呼び出しは**無い**(`grep`。コメントに `floor(sqrt(x))` の文字があるだけ)。FP の演算はすべて `fle_mx_*`・`fle_*` の自前の関数で、`-ffp-contract=off -fno-fast-math` は残している。
- **将来の最適化の露出**: 16 スナップの一致は、将来の最適化のバグが無いことの証明にならない。変わるのは組み込み関数のインライン化だけで、生成 C の関数本体は 1 バイトも変わっていない、までが確認したこと。**UBSan(`-fsanitize=undefined -fsanitize-trap=undefined`。この機械には UBSan のランタイムライブラリが無いため、最初の未定義動作で SIGILL になる方式)を最終フラグの熱い 5 単位(fle-00・fle-01・fle-03・fle-20・m1-36。検査の箇所 23,098〔`ud1` 命令の数〕)で走らせた(`tools/hle1/ubsan.sh`、`logs/ubsan.txt`): `cmp-short.g3` の 1 回の走行で検査は 1 つも発火せず、84 行は基準とバイト一致、終了コードは基準と同じ 134(終わりの abort)**。対象は 92 単位のうち 5 つと走った経路だけで、証明ではない(残りの単位は未検査)。`GEN_FNO_BUILTIN=1` で旧フラグに戻せる。

### R.1 Chrome が node ほど効かないように見える理由の切り分け(PM の依頼 05:40 (b))

問い: 大きい wasm は Liftoff(基準コンパイラ)で始まり、TurboFan(現在は Turboshaft)への昇格に時間がかかるため、Chrome では効きが小さいのではないか。

一次資料(読み):
- V8 の文書(`v8.dev/docs/wasm-compilation-pipeline`、`v8/docs/wasm/architecture.md`): 関数はまず Liftoff でコンパイルされ、**呼び出しが多い『熱い』関数が Turboshaft に昇格する(動的な階層化)。wasm には OSR が無く、昇格したコードが用意できた後でも、実行中の呼び出しは Liftoff のコードで終わる**。実験用に Liftoff のみ(`--liftoff --no-wasm-tier-up`)・最適化のみ(`--no-liftoff --no-wasm-tier-up`)・遅延コンパイル(`--wasm-lazy-compilation`)のフラグがある。
- compilation hints(関数ごとに階層を指定するカスタムセクション): V8 には非公式の `compilationHints` セクション(関数あたり 1 バイト、function セクションと code セクションの間)があり(WebAssembly/design#1473 の V8 開発者のコメント)、新しい提案 `metadata.code.compilation_priority`(WebAssembly/compilation-hints、フェーズ 2)の対応コード(`kCompilationPrioritySectionCode`)も V8 にある。しかし WebAssembly 公式の機能表(`features.json`)は Chrome を **『フラグが必要: `--js-flags=--experimental-wasm-compilation-hints`』**としている。= 利用者の Chrome ではコマンドラインのフラグ無しには使えない。PM の指示(利用者の環境で使えないものは使わない)に従い、**製品の対策としては採らず、実験もしていない**。

測定(実測):
- ページ側の印(`run-g3-chrome.mjs` の `marks`): wasm のダウンロードの終わりからコンパイルの完了まで 0.3〜0.7 秒(全単位 0.6 秒、hot20 0.4 秒、基準 0.3 秒)、`main` の開始はページを開いてから 2.8〜3.9 秒。= コンパイル(Liftoff)の待ちは小さい。昇格の待ちは、ページ側の印では直接は見えない(階層ごとのカウンタをページに出していない。未実施)。
- **診断(Chrome のフラグを使った隔離 headless Chrome の実験。製品の設定ではない)**。エンジンの実行(`main` の開始から最初の idle まで)の秒、loadavg 13〜20、各 1 回(既定のみ 3 回):

| 変種 | 既定(Liftoff → 昇格) | Liftoff のみ(昇格なし) | 最適化のみ(`--no-liftoff --no-wasm-tier-up`) |
|---|---|---|---|
| 基準 | 18.5 s(15.5〜19.2、3 回) | 14.6 s | 25.2 s |
| hot20 + HLE 入り | 7.8 s(7.4〜11.0、3 回) | 10.0 s | 29.3 s |
| hot20 / 基準 | 0.42 | 0.68 | 1.16 |

  読み: (1) **昇格を止めた Liftoff のみの方が、既定より速い(基準 14.6 対 18.5 s)**: この負荷の機械・この約 20 秒の窓では、昇格(バックグラウンドの Turboshaft コンパイルと、階層化のための計測コード)は得になっていない。hot20 では逆(Liftoff のみ 10.0 s、既定 7.8 s)。各 1 回で負荷が違うので、**差は傾向であって確定ではない**。(2) 最適化のみは遅い(25〜29 s)。`wasm_compiled` の印が 0.2〜0.3 秒なので、実際のコンパイルは遅延(関数の初回の呼び出しの時)に起きて実行時間に入っていると読む(未確認)。= 全関数を最初から最適化する道は使えない。(3) **always_inline の効き(hot20 / 基準)は、既定で 0.42、Liftoff のみで 0.68**: 昇格なしでも効く(Liftoff はインライン化しないので、ソース側のインライン化の効果がそのまま出る)が、既定の方がより効く。
- 結論: 『昇格待ちのせいで Chrome では効かない』という仮説は、この測定では支持されなかった。Chrome でも、エンジンの実行で見れば効いている(基準 18.0 → 7.8 s)。中間報告 4 の『Chrome の V8 は小さな関数を自分でインライン化するらしく効きが小さい』という説明は、根拠が足りなかったので撤回する(§P.3)。『最初の idle』の比が node の CPU の比より小さく見えるのは、固定費(ページの読み込み・ダウンロード・コンパイルの約 3〜4 秒)が Chrome の値に入っているためと、node の値は CPU 秒(Chrome は壁時計)であるため、と読む。

## H. HLE(ゲストの関数のホスト実装)の最初の一歩 — f_6a73a0

### H.1 HLE の定義(この作業の規則)

ゲストの関数と**結果が完全に同一**(戻り値、書くメモリ、レジスタ、フラグ、例外・未定義の扱い)なホストの C/SIMD 実装。**計算結果を事前に生成して貼る・画面を再生する・出力を変えるものは HLE ではなく禁止**。同一性は差分テストで示す。この作業で作った実装は『HLE 入り』と明記する。**この決定の差分には入れていない**(PM の指示。参考のパッチとして `docs/investigations/hle1/tools/hle-reference/` に置いた)。

### H.2 機構(参考実装。`docs/investigations/hle1/tools/hle-reference/hle1-hle-reference.diff`。f_6a73a0 と f_33d6e70 の 2 つの実装を含む)

- `fe-lift lift ... --hle-entries FILE`(新しい `lift/crates/fe-lift/src/hle.rs`、`lib.rs` の `generate_with_hle`、`main.rs`)。FILE の 1 行は `ADDR NAME`(`0x6a73a0 lerp_rows`、`rva:0x...` も可)。決定 0105/0120 の注釈ファイルと同じ形。生成 C は関数の最初の命令のブロックの中に 1 つのガード `{ extern int fle_hle_NAME(void); if (fle_hle_NAME()) return; }` を持つ。ブロックスコープの `extern` なので、`#include` や宣言は 1 バイトも変わらず、変わるのはその関数の単位だけ(実測: 92 単位のうち `fle-03.c` の 1 つ。生成 C で変わるのは 1 行、+73 B)。**オプション無しの出力は従来とバイト一致**(実測: FLEngine の C の SHA-256 `6d39d04f…` が新 fe-lift・オプション無しで同一、common.c も m1〜m5 も同一)。

## W. f_33d6e70(dsp の bilinear な affine ワープ)の HLE — 参考実装(差分には入れない)

### W.1 なぜこの関数か

フラグの変更(§F)の後の native 起動の CPU(標本 914 件 = 4.57 CPU 秒)は **f_33d6e70 が 37.3%(1.71 CPU 秒)**。次は主スレッドの平らな尾(f_127c600 11% of 主スレッド など)。f_33d6e70 は dsp_ippv2 の leaf(229 命令、呼び出し 0)で、起動の間にスレッド 2(ロゴの描画)が毎ティック呼ぶ。

### W.2 読み(capstone、`tools/probe/disasm_pe.py`)

| 項目 | 読み |
|---|---|
| 引数(Win64) | rcx = src、rdx = dst、r8d = src の送り(バイト)、r9d = dst の送り、[rsp+0x28] = y0、[+0x30] = y1、[+0x38] = 行ごとの (xs, xe)(int32 の組)の表、[+0x40] = double 6 個 c0〜c5、[+0x48] = 幅 W、[+0x50] = 高さ H |
| 計算 | 行 r = 0..y1−y0(y1 < y0 なら何もしない): sx0 = c1·y0 + c2、sy0 = y0·c4 + c5(行ごとに +c1, +c4)。画素 x = xs..xe: sx = c0·xs + sx0、sy = xs·c3 + sy0(画素ごとに +c0, +c3)。ix = trunc(sx + 1e-7)、iy = trunc(sy + 1e-7)。fx = sx − ix、fy = sy − iy(ix ≥ W なら fx = 1.0 と ix = W−1、iy も同様)。4 チャネルそれぞれ: top = p00 + (p01 − p00)·fx、bottom = p10 + (p11 − p10)·fx、out = trunc(0.5 + top + (bottom − top)·fy)、バイトで書く。定数 1.0・0.5・1e-7 は 0x440ef50/58/60(rdata)から読む |
| 副作用 | dst のバイト、死んだスタック(r14 r15 rbp の push、xmm11〜15・rbx rsi rdi r12 r13 の退避、行ごとの r9d・r11・rdx の退避)、volatile のレジスタ(rax rcx rdx r8〜r11 xmm0〜5)、フラグ(最後は `add rsp,0xb0`) |
| 浮動小数点 | double の加減乗算、int→double(`cvtsi2sd`)、double→int の切り捨て(`cvttsd2si`)のみ。MXCSR に旗を立てる可能性があるのは不正確(PE)・非正規・範囲外 |

### W.3 実装(`fle_hle.c` の f_33d6e70 の節、`fle_hle_warp_body.inc`)

- **lifted の文そのものを使う**: `tools/hle1/gen_hle_body.py` が生成 C の f_33d6e70 を、レジスタ表 `R[16]`・`X[16]` を**引数**(グローバルを隠す)にした関数 `hle_body_warp` として書き出す(232 行)。ホストは同じ文を同じ順序でローカルのレジスタ表の上で走らせる。メモリ・整数・フラグの操作は lifted と同じ関数(`fle_ld`、`fle_op_*`)のまま。**置き換えるのは 5 つの FP 基本操作だけ**(`fle_mx_addsd/subsd/mulsd/cvtsi2sd32/cvttsd2si32` を素の IEEE の double 演算に。`-ffp-contract=off`)。つまり、この 5 つが『ちょうどそれをする』と証明できれば、全レジスタ・フラグ・メモリが同一になる。
- 証明は**呼び出しの前の計画**(`warp_plan_make`)が行い、満たさなければ何も触らずに lifted が走る(S-hle-refuse と同じ): (1) MXCSR: RC = 0、PE が既に立っている、全例外マスク(これで FP の旗は何も増えない)。(2) 6 つの係数が 0 または 1e-30 ≤ |c| ≤ 1e30、定数 3 つが 1.0・0.5・1e-7(演算が非正規・桁あふれ・無効を作らない)。(3) 行ごとに sx・sy の再帰を同じ演算で追い、丸め誤差込みの境界で、全画素の sx + 1e-7 と sy + 1e-7 が (−1, 1e9) の中(切り捨てが範囲内で、添字が 0 以上)。画素の値はバイトなので、これはデータに依らない。(4) dst の書き込みが、死んだスタック・引数スロット・係数・行表に触れない(関数がそれらをもう一度読むため)。(5) 1 ≤ W, H < 2^20、行数 ≤ 2^16、1 行 ≤ 2^16 画素、スタックの整列。
- `FLE_HLE=check` は lifted 本体とホストを同じ入力で走らせ、R・X・フラグ・書いた全範囲(スタック 200 B と dst の各行)を比べる。

### W.4 同一性(実測)

- 差分テスト(`difftest_warp.c`、lifted の f_33d6e70 を `extract_lifted.sh` で取り出して対比。入力は乱数+境界 17 種: 良い入力、dst が行表・係数・フレームに重なる、src がスタックに重なる、dst が src に重なる、MXCSR の RC ≠ 0・PE なし・マスク解除、係数が巨大・極小・非正規・NaN・Inf、y1 < y0、座標が幅・高さの外(クランプ)、行を飛ばす、座標が負、座標が 32 ビットの外、スタックが整列していない、係数が範囲外、定数が変わっている、行数が 65536 を超える)。ホストが先に走り、**断ったら何も触っていないこと**を確かめ、**引き受けたら**状態を戻して lifted を走らせ、アリーナ(送り元・送り先・表・フレームの窓)・R[16]・X[16]・フラグ・ゲストの MXCSR を比べる。**合計 12,000,000 ケース(seed 301〜303 の 9×10^6 = クラス 0〜14 と、最終版のテストの seed 401 の 3×10^6 = クラス 0〜16)で 4,233,505 件を比較、不一致 0**。断るべき入力(クラス 6・12〜16)を引き受けたことも 0、断った呼び出しが何かを触ったことも 0。
- 実エンジン上のオンライン検査(`FLE_HLE=check`、native -O2、16 スナップの走行): f_33d6e70 の呼び出し **120 回(54,277 行)すべて引き受け、不一致 0**、断った呼び出し 0。16 スナップの 84 行が基準とバイト一致。
- 変異検査 21 件: 18 件を検出(FP 基本操作の取り違え 5、MXCSR のガード 3、座標・係数の範囲 4、定数の検査、整列、行の再帰、本体の 3 件の変更)。**生き残り 3 件はすべて等価な変異**: W12(NaN の係数を通す比較の反転 — 座標の範囲の検査が NaN を断る)、W19(行数の上限 — 巨大な行数は座標の範囲か表の読みで断られる、テストの範囲では同じ)、W20(座標の下限 −0.999 → −1.5 — 添字 −1 は両方が同じバイトを読む)。

## I. 熱い関数と IPP の export の対応(PM の依頼、swap1 報告 1 への答え。読み取りと集計だけで、新しい HLE は実装していない)

依頼の要点: dsp_ippv2 は Intel IPP の静的リンク版(export 446 個)で、perf2/perf3 では `ippiWarpAffineQuad_8u_C4R` 68〜74%、`ippiWarpPerspectiveQuad_8u_C4R` 8.9〜12.4% などと読めた。本作業の熱い関数がどの export の内側かを、export の RVA(`lift/out-swap1/tables/dsp_ippv2-exports.tsv`、読み取りのみ)と照らして、『IPP の export 名』で併記する。

### I.1 方法(実測と読み)

- export の VA = 0x2000000 + RVA。各 export の lifted 関数 `f_<VA>` を生成 C(`gen/v-base/src/m1-*.c`)から読む(`tools/hle1/ipp_exports.py`)。446 行のうち VA が重なるのは 1 組(`ippiResizeCenter_8u_C3R` と `_C4R` が同じ VA 0x17c8310)で、445 個の関数を読んだ、**431 個は IPP の CPU 別ディスパッチ stub**(`movsxd [0x45410a0]`〔CPU 番号〕→ 表 `jmp`)で、表の飛び先に『初期化 thunk(番号 -1)』と『CPU 別の本体 0〜6』が並ぶ。残り 14 個は ippMalloc など単独の関数。全表は `logs/profiles/ipp-export-stubs.tsv`。
- 標本(§3 と同じ `base-prof.prof`、基準フラグ、`cmp-short.g3`、SIGPROF 200 Hz、3,812 標本)の C スタックの各フレームを export に結びつける(`tools/hle1/ipp_chains.py`): スタックのどこかに、ある export の stub・初期化 thunk・CPU 別本体のどれかがあれば、その export の中。stub の末尾呼び出し(tail call)でフレームが消えても、CPU 別本体のフレームが残るので特定できる。
- 限界(正直に): (a) C スタックは 64 フレームで切れる。`ippiFilterBoxBorder_8u_C4R` の内側の `f_27ad5f8 ↔ f_27ad5d6` は相互に深く再帰し、根まで届かない標本が 107 件ある。この 107 件は『関数の VA が、その export の CPU 別本体の開始 VA から 0x10000 以内で、直前にある』ことで export に結びつけた(**アドレスによる推定**。`ipp-exports-base.md` に件数を別記)。(b) 標本は 1 回の走行(基準フラグ)の 3,812 件で、最終フラグの走行の標本は関数名の表(`hot-nb`)しか残っておらず、export への結びつけは基準フラグの標本でだけした。(c) 『CPU 番号』は走行で 0 番(stub の表の最初の本体。`f_33640e0` → `f_3378b20`、`f_33642a0` → `f_3379d00`、`f_2743af0` → `f_27ab5c0`)に入っていた(標本のスタックに現れる本体が 0 番だけ)。
