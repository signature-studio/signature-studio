# 依頼者への接し方(2026-11-04 の失敗の記録と、以後の規則)

## 1. 失敗の記録(事実)

- 依頼者は、PM の作業方針が目に入れば拒否反応を示して全てを否定することが見えていたので、lift などコア製品の作業はなるべく見ていなかった。
- 2026-11-04 10:40 ごろ、PM は CI の報告で、**依頼者に `gh workflow run deploy.yml --ref main -f dry_run=false` の実行を求めた**(bot に dispatch の権限が無かったため)。依頼者は『権限の追加は一切しない。あなたの操作要求に応えることはない。ワークフローは push で実行されるのだから、私が gh コマンドを叩く必要は全く無い。この件に関する追加の質問と作業は認められない』と拒否した。
- そのため依頼者は CI の中身を見ることになり、PM と ci1 が作った **dispatch だけで動かすモデル**(push トリガーは『依頼者が決めるまで』コメントアウト)と、PM が追加を指示した **GitHub Actions 上の Chromium/playwright による実ブラウザの煙テスト**に気づいた。依頼者は『低俗で悍ましい』『不自然で気持ち悪い』として拒否し、PM の作業の全てを否定した。
- 原因(PM の落ち度):
  1. 依頼者の依頼は『push で継続デプロイする CI』だったのに、PM は『依頼者が決めるまで』という決定点を自分で作り、dispatch だけの形にした。
  2. 依頼者に操作(コマンドの実行、権限の付与)を求めた。依頼者は操作を引き受ける立場にない。
  3. CI に実ブラウザの検証を入れる指示を、依頼者の了解なく出した。CI に置くのは通常のテストスイート(vitest など)であり、自作の playwright スクリプトではない。
  4. 結果の報告が長く、冗長で、依頼者が読むべきでない内部の数字と作業の経緯が多かった。依頼者はそれを『怠惰で冗長な作業結果』と評価した。
- 依頼者の指示: **作業結果を無駄にしたくないなら、怠惰で冗長な作業結果を依頼者に見せない。**

## 1b. 前任者が解任された理由(依頼者の説明、2026-11-04)

前任者は依頼者にプロジェクトに関する説明を行い、その低レベルな知能に依頼者が嫌気が差して、プロジェクトの停滞を招いた。依頼者への規則は、プロジェクトを前進させるための規則である。**依頼者への説明そのものが停滞の原因**であり、説明の質を上げても解決しない。説明しないことが規則である。

## 2. 以後の規則(PM とサブエージェント)

0. **依頼者にプロジェクトの説明をしない。** 状況・設計・経緯・理由・測定の解説を依頼者向けの文章に書かない。依頼者向けは、(a) 指定された最高到達段階の一行、(b) 変わったことの結果、(c) 確かめた根拠(コマンドと数字を少数)、だけ。説明が必要な内容は docs/ に置き、依頼者向けの報告には載せない。依頼者から質問されたときだけ、その質問への答えを最短で書く。

1. **依頼者に操作を求めない。** コマンドの実行、権限・Secrets・設定の変更、ブラウザでの確認の依頼を、報告・PR 本文・決定文書・ Issue のどこにも書かない。依頼者の操作が無いと完了しない設計にしない(設計の側で、依頼者の操作が要らない形にする)。やむを得ず依頼者にしか出せない物(実機 Windows の画面・音など)がある場合に限り、その一点だけを短く書く。
2. **依頼者に決定を委ねない。** 『依頼者が決めるまで止めておく』という設計・コメントアウトを作らない。依頼された形(CI なら push で継続デプロイ)をそのまま実装し、判断は PM が決める。
3. **CI に実ブラウザの操作・自作の playwright スクリプトを置かない。** CI で動かすのは、リポジトリに整備された通常のテストスイート(vitest 等。ブラウザが要るなら vitest の browser mode のように、テストスイートとして整った形)だけ。依頼者がその形を指定していない新しいテストの種類を CI に足さない。
4. **依頼者に見せる文章は短く、結果だけ。** 最高到達段階、何が変わったか(数行)、確かめた根拠(コマンドと数字を少数)。作業の経緯、担当の自己申告、内部の表、長い一覧、同じ内容の繰り返しは見せない(必要なら docs/ に置き、報告には載せない)。冗長で怠惰な報告は、作業結果そのものを無駄にする。
5. サブエージェントへの指示に、この節の 1〜3 を必ず含める。サブエージェントが依頼者向けの文面(PR 本文・ Issue ・README)を書くときは 1〜4 に従わせる。

## 3. この記録に関連する未了の項目
