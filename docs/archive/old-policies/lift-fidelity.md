# lift の忠実性の方針(2026-11-04、依頼者の指示)

依頼者の指示(原文要旨): 「バグなく動いている FL Studio を lift すればバグのないプロダクトが完成する。バグがある場合、余計なことをしているか、API の拡充が不十分であり、そちらに注力するべき。余計なロジックは見つけ次第抹消する。」「FL ウインドウを管理するウインドウマネージャーは(Detached モードを除き)FL Studio に備わっており、我々が介入する必要はなく、不具合が発生した場合は外部 API の拡充によってのみ対処する。」「行うべきは wasm↔JS シリアライズ/デシリアライズ削減、worker↔メインフレーム通信削減によるパフォーマンス改善であって、場当たり的な軽量化は今回のような不具合を誘発させる。」

## 1. 原則
1. 不具合の原因は、(a) 我々の余計な処理、(b) 外部 API(Win32 など)の実装の不足・契約違反、のどちらか。対処は (a) の除去と (b) の拡充だけ。
2. 余計なロジックは見つけ次第抹消する(下の点検表で判定)。除去して壊れる物は、API の不足の表れなので API を拡充する。
3. FL の窓管理は FL 自身が持つ(Detached を除く)。ランタイムは Win32 の契約を実装するだけで、FL の窓の挙動を代行・補正・特別扱いしない。ページは窓の挙動を決めない。
4. 性能は、変換と通信の削減(wasm↔JS、Worker↔メイン)で出す。ピクセルのバケツリレーを避ける。

## 2. 点検表(新しい処理を足すとき/既存の処理を見直すとき)
| 問い | 『はい』なら |
|---|---|
| これは外部 API の文書上の契約(戻り値・副作用・メッセージ)の実装か | 残す。出典(Learn など)と Wine 差分の試験を付ける |
| これは FL の観測(診断・ログ・計測)だけか | 製品の経路から切り離す(`?debug=1` やビルドの opt-in) |
| これは FL の lift 済みコードがやるべきことを代行/補正/上書きしているか | **抹消**。必要なら不足している API を拡充する |
| これは FL のクラス名・窓の種類・位置・文言で分岐しているか | **抹消** |
| これは性能のための局所的な近道(重複排除、間引き、窓ごとの特別な描画経路など)か | 抹消の候補。通信・変換の削減(下の 3)で置き換えられるか評価する |
| これは命令の意味(x87・SSE・MXCSR など)を速い近道で実装しているか | 次の 2 つだけ忠実とする: (A) 結果が bit 単位で同じ別実装、(B) 厳密な前条件(制御語が既定、例外なし、f64 で完全に再現できる場合だけ、など)を満たすときだけ近道し、外れたら元の経路に戻る実装。いずれも、ホスト CPU/native との差分試験と変異試験を付ける。前条件のない近似(例: x87 を f64 で近似)は**抹消**(2026-11-06、決定 0296 の PM 節) |
| これは単に動かすための仮の実装(PROVISIONAL)か | 契約に照らして実装し直す。残す間は一覧にして期限を付ける |

## 3. 性能の方針
- 目標の経路: エンジン(wasm)がデスクトップの画素を自分のメモリに持ち、**Worker が直接 OffscreenCanvas に提示する**(メインスレッドにピクセルを送らない)。wasm メモリから canvas/GPU への転送は変換なし(または GPU 側の並べ替え)で、JS でのピクセルのコピー・変換を避ける。入力は生のまま SharedArrayBuffer のリングで Worker に渡す。ログ・計測・状態は低頻度にまとめて送る。
- 窓の合成(位置、Z 順、レイヤードのアルファ)は、OS の部品(DWM / ウィンドウシステム)の実装としてランタイムが行い、ページは合成後の 1 枚のデスクトップ面を表示するだけにする(窓の知識を持たない)。Detached モードは例外(OS の窓として切り離す機能のため)。
