## 1. 現状(コードの事実、file:line)
- ページ: ゲストの画面 = room の **CSS px**(`app/src/ui/screen-fit.ts:3-5`『1 guest pixel = 1 CSS pixel; the browser scales the canvas by the device pixel ratio』、`chooseGuestScreen`)。canvas の backing store は guest の画面の大きさ(`ui/desktop.ts:24-25` `canvas.width/height = this.screen`)、CSS の大きさは `screen × scale`(scale は 1)(`desktop.ts:45-52` `apply`)。**dpr 1.75 では 1 guest px が 1.75 device px に引き伸ばされる**(ブラウザの補間)= ぼやけ(O7 の機構、読み。canvas の `image-rendering` の指定は無い)。`window.matchMedia('(resolution: …dppx)')` の change で `applyDisplay` を呼ぶ(`main.ts:304`)が、ゲストの大きさは変わらない。
- ランタイム: プロセスは **DPI unaware**(`fle_proc.c:392-403` の `GetProcessDpiAwareness`)で、DPI は 96 固定: `shcore!GetDpiForMonitor` は 96/96(`fle_appfile.c:225-245`、S-g8a-dpi『unaware の場合の選択、出典なし』)、`gdi32!GetDeviceCaps(LOGPIXELSX/Y)` は `FLE_GDC_LOGPIXELSX` = `FLE_SCREEN_PX_DPI`(`fle_gdc.h:31-32,69-70`)、`FLE_SCREEN_PX_DPI` は `fle_screen_dpi()` = 96(`fle_screen.h:58-59,71`。コメントに『decision 0212: 96 unless FLE_SCREEN_DPI says another』とあるが、**今は env を読まず常に 96**)。`GetSystemMetrics` のアイコン 32/16・カーソル 32 は 96 DPI の値(`fle_sysmetrics.c:27-44`)。
- ビーコン: `GuestScreenInfo.dpi: null`(`screen-fit.ts:14-25`)= DPI をエンジンへ伝える経路は今ない。
- ネイティブの参照(依頼者の log): 『Main GUI scaling factor: 1.75 (system set to 168PPI)』。製品は『1 (system set to 96PPI)』(O8)。

## 2. 契約(Win32 の DPI)で必要になる物と、census の実測(`tables/0318-dpi-imports-FLEngine.txt`、`tools/census_dpi.py`)
- **実行ファイルの manifest(実測)**: インストール済みの `FL64.exe` の manifest は **`<dpiAware>True/PM</dpiAware>`**(per-monitor aware)、longPathAware true、supportedOS は Win7/8/8.1/10。= 本物の FL は**起動時から per-monitor DPI aware**。`fle_proc.c:392-403` のコメント『nothing says that the host process declares DPI awareness』は、この manifest と**矛盾**する(出典は manifest にある)。runtime は『awareness = `fle_screen_dpi() > 96` なら PER_MONITOR、それ以外は UNAWARE』(`fle_proc.c:409`)で、`fle_screen_dpi()` は常に 96 なので、いつも UNAWARE を答えている。
- **FLEngine_x64.dll の DPI・表示・カーソル関係の import(実測、静的 + delay-load)**: `shcore!GetDpiForMonitor`・`GetProcessDpiAwareness`(delay)、`user32!IsProcessDPIAware`・`GetPhysicalCursorPos`・`SetPhysicalCursorPos`・`LogicalToPhysicalPoint`・`PhysicalToLogicalPoint`・`SetThreadDpiAwarenessContext`・`SetThreadDpiHostingBehavior`(delay)、`gdi32!GetDeviceCaps`、`user32!GetSystemMetrics`・`SystemParametersInfoW`・`AdjustWindowRectEx`・`EnumDisplayMonitors`・`GetMonitorInfoW`・`MonitorFromPoint/Rect/Window`・`EnumDisplaySettingsW`、`dwmapi!DwmIsCompositionEnabled`(delay)、カーソル/アイコン一式(`LoadCursorW`・`SetCursor`・`GetCursor`・`GetCursorInfo`・`CreateIcon*`・`DestroyCursor`・`DestroyIcon`・`DrawIconEx`・`GetIconInfo`・`ShowCursor`)、`GetDC`・`GetDCEx`・`ReleaseDC`・`ScrollDC`・`ScrollWindow`・`ScrollWindowEx`。**`SetThreadDpiAwarenessContext` と `SetThreadDpiHostingBehavior`(スレッド単位の awareness の変更)を FL が呼ぶ**ので、実装は『process の awareness が PM で、スレッドが一時的に別の context にする』を許す形が要る。
- 値を返す物(契約): `GetDeviceCaps(LOGPIXELSX/Y)`(per-monitor aware v1 のプロセスでは**システム DPI** = 起動時のプライマリモニタの DPI。読み、Learn の High DPI の記述)、`GetDpiForMonitor`(MDT_EFFECTIVE = 実 DPI、MDT_RAW/ANGULAR = 物理 DPI)、`GetSystemMetrics(SM_CXSCREEN/CYSCREEN)`(DPI aware なら**物理 px**)、`SM_CXICON/CXSMICON/CXCURSOR`(システム DPI で変わる: Learn『About Icons / About Cursors』)、`SystemParametersInfoW(SPI_GETICONMETRICS/NONCLIENTMETRICS)`(フォントの大きさ、DPI で変わる)、`AdjustWindowRectEx`(DPI 非依存)。
- 状態: `IsProcessDPIAware` = TRUE、`GetProcessDpiAwareness` = 2(PER_MONITOR)。
- FL 自身の設定: Settings → General の『Main GUI scaling』(System / 100%…)。『system set to 168PPI』を読んで 1.75 倍で自分の UI を描く(ネイティブの挙動)。

## 3. 設計(契約どおり。FL のクラス名・窓・位置の分岐は足さない)
1. **ページ(communication の側)**: ゲストの画面 = room を **device px** で数える: `guest = round(room_css × dpr)`(clamp は `SCREEN_MIN/MAX` のまま)。canvas の backing store = guest(物理 px)、CSS の大きさ = `guest / dpr`(= room)。device px と guest px が 1:1 になり、ブラウザは補間しない。dpr が分数(1.75)のとき CSS の大きさが整数 px に丸められないので、`ResizeObserver` の `devicePixelContentBoxSize` で room の device px を取り、guest をそれに合わせる(丸めは device px)。HiDPI の切り替え(ウィンドウを別 dpr の画面へ動かす)は既存の `matchMedia` の change で追従。
2. **ページ → エンジン**: 既存の env の仕組み(`screenEnv`: FLE_MONITOR_W/H)に `FLE_SCREEN_DPI = round(96 × dpr)`(168)を足す。実行中の変更は既存の WM_DISPLAYCHANGE の経路(`FLE_SCREEN_REMAXIMIZE`)に乗せる。ビーコンの `dpi` を埋める。
3. **ランタイム(契約の実装 (b))**: `fle_screen_dpi()` が env を読む(コメントの意図どおり、clamp 96〜384)。**process の awareness は env に依らず PER_MONITOR(manifest の `True/PM` が出典)**にし、DPI 関連の API(§2)を『DPI aware な 1 画面、物理 px の画面、その DPI』として一貫して答える(値の出所を `fle_screen_dpi()` と画面の大きさの 1 か所に一本化)。DPI が 96 のときは今と同じ答えになる。
4. **性能(P2)**: 物理 px の面は dpr² 倍(dpr 1.75 で 3.06 倍、dpr 2 で 4 倍)。この機械の SwiftShader では CPU 時間が Mpx にほぼ比例(0.09〜0.10 コア/Mpx/s、`logs/rt-ptv-*`)なので、物理 px の再生 UI は同じ present 率で CPU を 3〜4 倍使う。実 GPU(依頼者の RTX 5080)では転送と upload の費用だけ(読み、本機で測れない)。present の経路は P(別 Worker)+ V7 で CPU が engine と分かれる。WebAssembly.Memory は面の分だけ増える(3840×2160 dpr 1 で +97 MB を実測、`logs/fb5a`)。物理 4K × dpr 2 は 7680×4320 = `SCREEN_MAX` に当たる。
5. **確認(実装後)**: (i) `canvas.width` = `devicePixelContentBoxSize` の幅、(ii) engine log(Settings → Debug)が『Main GUI scaling factor: 1.75 (system set to 168PPI)』、(iii) 絵の周波数成分(エッジのシャープさ)を dpr 1 の絵の整数倍拡大と比べる。
