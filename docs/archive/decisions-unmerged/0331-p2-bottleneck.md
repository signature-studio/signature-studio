## 2. ボトルネックの切り分け(測定から読める範囲)

1. **E13 A(協調)の中で最も重いのはミキサー側の wasm 計算**。協調 E9 の実測では、全スレッド協調で 1 Worker(1.04〜1.22 コア相当)を共有しており、UI が同じ Worker に乗っている。**フレーム間隔 73 ms のうち、大半はエンジンの 1 フレームの計算**と読める。
2. **P+V7 は present の経路(Present Worker)を変えたことで、present/s が 2 倍に上がった**が、Worker 全体の CPU が +44% 増えた。= 非同期化の代償として、余分な変換(画素のバケツリレー)が増えている。**現状の超過の残る部分(34 ms のうち内訳)は未分離**。
3. **UI tick の不足(73% WaitMessage)は P2 の主因ではない**。UI が仕事を持っていない待ちであり、present 側が飽和した後は効かない(R1 の wasm の one-side 不可用)。この方向に投資する効果は見えない。
4. **実スレッドのミキサーは単独で 1 コアを超えている**(1.07〜1.17)。再生で P3 を満たすには this が先。

## 3. 削減案(3 件まで。通信・変換の削減のみ)

### 案 1: wasm → JS の pixel 変換・再コピー(present 経路)を削る
- **何が重いか(読み)**: P+V7 で presents が増えたが、Worker 全体 CPU が +44%(P の Worker の分)。画素データは wasm 側で生成され、JS 側で再生され、場合によっては中継される。
- **削れる変換**: 1 present の間に画素が wasm → JS → canvas の順に何回コピーされるかを数え、コピーを 1 回に寄せる(Present Worker の内で合成する)。FL が描く量は変わらない。
- **効果の推定**: present/s の増加分に見合う CPU の減少。+44% の半分を削れば、現在 34 ms の frame 内で数 ms 規模(推定。測定なし)。
- **検証方法**: ci1 の pure の手順で present/s と Worker CPU を計測する。before/after の差分を出す。

### 案 2: idle ごとのページへの通知(R1 の序列化)を削る
- **何が重いか(読み)**: Worker は毎 idle で idle メッセージ・input-done・engine-log を postMessage する。engine-log は startup で約 1,600 行を batched で送る(flag 生乾きなら 0.9 コア× 1 スレッドが最大性能で動く)。
- **削れる変換**: idle の通知を VR フローの数に合わせる(flag 生乾き: FFmpeg は 1 本の enqueue に対して 11 のゃに輝。締抽出)。present の通知側を軽くする。
- **効果の推定**: UI Worker の 54〜63% の CPU のうち数 ms の削減(P+V7 の CPU 増加分)。測定なし。
- **検証方法**: Worker スレッド全体の CPU(60 s)を ci1 の pure で計測する。

### 案 3: ミキサー Worker の重複計算(書き直し)を削る(G11 の前提)
- **何が重いか(測定)**: 実スレッド版で、同じ 1 ブロックを 2 回計算する『書き直し』が 14〜20% あり、これが無いと 0.9〜1.0 コアに収まる。= P3 の音の滑らかさに直結する。
- **削れる変換**: 非同期の書き直し。FL の描画・mixing のアルゴリズムは変わらない(exact algorithm は FL の libFB が変える)。
- **効果の推定**: ミキサー側の CPU を 1.07〜1.17 → 0.9〜1.0 コアに収める(0.07〜0.17 コアの削減。推定)。
- **検証方法**: 0289 の `per-unlock-cpu.py` で Unlock あたりの CPU を計測する。

## 4. してはならないことの確認(昭和)

- 描く量(窓の数・サイズ・描画頻度)をページ側で決めない(FL の決定)。ページ側での窓ごとの canvas 並べ替え・可視/Z 決定・画素の重複排除は『場当たりな軽量化』で採らない。
- クラス・窓の種類による分岐を足さない。
