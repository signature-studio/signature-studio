## 1. 何をしたか

fe-wasmgen(x86-64 機械語 → wasm の直接生成部。決定 0157・0164)を、実エンジン(FLEngine_x64.dll と同梱 5 DLL: dsp_ippv2・Blend2D・QFC・FreeType・ILTools、合計 10,348,619 命令・109,157 関数)に適用した。構成は決定 0161 の D(C 経路、起動 20 単位の always_inline + dsp HLE + wasm-opt -Oz)を土台に、**直接生成部が lower できる関数だけを C の単位から外して直接 wasm に差し替えた混成**。C 経路のランタイム(import・間接呼び・SEH・スレッド)は C のまま。既定の挙動は変えていない(すべて opt-in)。

ワークツリーは `lift/out-hyb1/`(HEAD b07659a の `git archive` を `src/` に展開)。成果物は `lift/out-git/hyb1-results/`。`lift/out-websrv/assets/` と既定の入口には何も置いていない。

| v2 − 『特別』(SEH ラッパー 2,816、hook 9、landing 3、HLE 1、site 1 は C のまま) | 82.8%(90,418) | 58.2% |

## 4. 混成のビルドと測定方法

- ビルドは `tools/hyb-build.v2.sh`(select → strip → n0 → build → opt → gen → merge)。lower する関数集合 = census の `ok` − 『特別』を、(定常 60 仮想秒の実行命令数 + 起動の実行命令数)の降順で上位 N 個(N=50/1000/全部)。選んだ関数を C の単位から外し、残りを D と同じ手順で wasm にして wasm-opt -Oz を C 部分だけに掛け、直接生成部の 6 モジュールを `wasm-merge` で C 部分に結ぶ。
- 同一性: D と同じ環境で node 上で実エンジンを走らせ、16 スナップの 82 行(g3-snap 16、g3-surface 34、g3-wintable 16、g3-progress 16)を D の行と全行比較する(`tools/g3cmp.sh`)。
- 速度: node の主スレッド CPU 秒(`process.threadCpuUsage`)の中央値。D と混成を交互に走らせる(`tools/ab.sh`、`ab_sum.py`)。共用機(load 6〜40)で、**壁時計の速度は主張しない**。

### 6.1 見つかった不具合(実エンジンで初めて出た物。単体テストや FreeType の差分テストでは出なかった)

**不具合 1: 解決済みの間接 jmp(delay-load thunk)を実行時探索にしていた(修正済み)。** 「all」が DllMain の初期化中に abort した。delay-load thunk `f_407320` の `jmp [slot]` は、スロットの初期値(ファイル上)が関数入口でない stub `0x407310`(`push rdx; lea rdx,[desc]; jmp 0x4072b0`)を指す。fe-lift(C 経路)はこれを stub への普通の jmp にする。fe-wasmgen は `TailIndirect`(実行時のスロット値を関数入口表で探す)にしていた。`ir.rs` を C 経路と同じ(`Jmp`/`Tail`)に直した(解決先が解析不能な関数の入口なら従来どおり実行時探索。dsp の IPP dispatch stub 61 関数)。単体テスト `tests/jmp_resolved.rs`(修正を外すと失敗)。

**不具合 2: 解決済みの間接 call を、C 経路は静的に直接 call、直接部は実行時のスロット値で呼んでいた(`--static-calls` で C 経路に合わせた。opt-in)。** fe-decode が『ファイル上のスロットの値(または定数レジスタ)が関数入口を指す』と解決した `call [slot]`/`call reg` を、fe-lift は実行時のスロット値に関係なく静的な `f_<target>()` にする。直接部は実行時の値を読んでいた。ゲストがスロットを書き換えると D と違う関数を呼ぶ(本来の x86 の意味は実行時の値で、**C 経路の扱いが潜在的な誤りかどうかは未確認**)。`--static-calls` を付けると、起動中に実行される 5,081 関数を lower した試行で wiz0 の lid 8 サーフェスの sha256 が D と一致した(付けないと 318x446)。単体テスト `tests/jmp_resolved.rs`。

**不具合 3: C 側に入る呼び(C の関数・import・dispatch)の前に、直接部が保持する被保存レジスタ(rbx・rbp・rsi・rdi・r12〜r15)を R[] に書き戻していなかった(`--sync-saved` で直した。opt-in)。** 呼び先の要約が『読む』と言うレジスタしか R[] に出さないため。C ランタイムの SEH の巻き戻し(RaiseException・仮想アンワインド)は呼び先の要約に関係なくレジスタ全体を読むので、`virtual unwind did not move the stack pointer up` で abort した(rbp 枠の関数の RSP が古い rbp から計算される、という読み。確かめたのは『`--sync-saved` で abort が消えた』ことだけ)。これは速度に響く(呼びごとに最大 8 回の store)。

### 6.2 二分探索(PM の質問 2。『最初に分岐する関数』)

道具: C 部分に『実行された lower 可能な関数 E(11,123 関数)の C のコピー `fc_<va>`』を持たせた固定の C 部分(`c.opt_bis*.wasm`)を 1 つ作り、試行ごとに直接部の 6 モジュールだけを作り直す(`tools/bis-trial*.sh`、探索は `tools/bis-search.py`)。試行で lower する関数 = 候補集合 S と、一度も実行されない関数(C の本体を外してあるので lower する)。S に入らない E の関数は C のコピーを呼ぶ。対照: S = 空(E の関数をすべて C のまま)は**全行一致**(`ctrl0`)。

| 試行(生成部は『ir.rs 修正後・フラグなし』) | S の大きさ | 結果 |
|---|---|---|
| ctrl0 | 0 | 一致 |
| early1a / early1b(起動中に実行された 5,081 関数の 1/3 ずつ) | 1,694 | どちらも不一致 |
| early2a / early2b | 565 | 不一致 / **一致** |
| early3a / early3b | 189 | どちらも不一致 |
| onlyV2(新しい命令で初めて lower できた 400 関数のうち起動中に実行された 117) | 117 | **一致** |
| noV2(同 5,081 関数から onlyV2 を除いた 4,964) | 4,964 | 不一致 |

読み: 二つの別の 1/3 の両方が不一致 → 原因が一つの関数ではなく、多くの関数に効く共通の意味の差(不具合 2)だと分かった。新しい命令(cvtsi2ss・cvtsd2si・xadd・cmpxchg・xchg)の関数は原因ではない(onlyV2 が一致)。単体テストに AH 源の 3 形(エンジンの spin lock `lock cmpxchg [rbx],ah` と同じ)、cvtsi2ss/sd のメモリ源 4 形、`xchg reg,reg` の 8 形を追加して通した。

`--static-calls` と `--sync-saved` を付けた生成部での探索(S の初期集合 = 実行された 11,122 関数。『最初に分岐する関数』を探す):

『5 分割・4 本並列』にして、初期集合は `--static-calls --sync-saved` で『最初の 1/3』(3,708 関数、VA 昇順)が不一致だった集合にした。結果(`logs/bis-search-sceT.log`):

| 段 | S の大きさ | 結果 |
|---|---|---|
| 1 | 742 × 4(+残り 740) | 4 つとも一致 → 残りの 740 を取る(相互作用か、残りに原因) |
| 2 | 148 × 4(+残り) | 148 の 2 つ(a と d)が不一致、b と c は一致 → VA の小さい方 a を取る(**原因の部分が 2 つ以上ある**) |
| 3 | 30 × 4 | b が不一致 |
| 4 | 6 × 4 | c が不一致 |
| 5 | 2 × 2 | 一致、一致 → 残りの 2 つ |
| 6 | 1 | 不一致 |
| 確認 | 1 | **`0x721280` だけを lower した版(E の他の関数は全て C のコピー)が不一致** |

**最初に分岐する関数(VA 昇順で最初の不一致)= FLEngine の `0x721280`**(295 バイト、native)。二次元の点を、オブジェクトの原点(`[rbx+0x80]+0x1e4/0x1ec`)に対する極座標で変換し直す float の関数: `[rsi]`・`[rsi+8]` の double から原点を引いて単精度にし(`cvtsd2ss`)、長さ(`call 0x40c650`)、角度(`call 0x4762e0`)、sin/cos(`call 0x6649c0`、出力は `[rbp+0x28]`・`[rbp+0x2c]`)を求めて double に戻して `[rsi]`・`[rsi+8]` に書く。xmm6〜xmm8 を `movdqa` で枠に退避する。これを lower すると D とずれる(progress・サーフェスが違う)。

**原因は特定できていない。** 確かめたこと: (a) MXCSR 窓を `--mx-force-slow`(窓の速い経路を全部 C の遅い経路にする)にしても、窓を外しても、この 1 関数だけで不一致のまま(窓は原因でない); (b) この関数の命令形(REX.W つきの cvtsd2ss/cvtss2sd、xmm8 の dest/src、`subsd xmm,[mem]`)を単体テストでホスト CPU と比べると全て一致(テストを `tests/sse_forms.rs` に追加); (c) これを除いても、2 段目の 148 の別の部分(d)も不一致なので、原因の関数は他にもある。**読み(未確認)**: xmm6〜xmm8 を C の関数(3 つの call)をまたいで v128 ローカルに持つので、C 側が xmm6/xmm7 を破壊する、または X[] との受け渡し(`xabi`)に誤りがある可能性。次にやるなら、この 1 関数の C 版(`D/onat/gen/flengine.c` の `f_721280`)と直接版を、レジスタとメモリを乱数にして関数単位で比べる(FreeType の difftest と同じ道具の FLEngine 版)。

### 6.3 N=50 の同一性は、diff に入れた既定の生成部でも成り立つ(実測)

N=50 の速度・同一性の測定に使った wasm は、`ir.rs` 修正の前の生成部で作った物。diff に入れた最終の生成部(既定のフラグ)で N=50 の直接部 5 モジュール(FLEngine 40 関数、dsp 2、Blend2D 3、QFC 3、FreeType 2。ILTools は N=50 に無い)を作り直し、前の物と `cmp` で比べた: **5 モジュールともバイト列が完全に同じ**(`H/t50/n-<m>.wasm` と `n-<m>_c.wasm`)。したがって N=50 の 82 行一致・速度・大きさは、最終の diff の既定の挙動にそのまま当てはまる。

## FreeType の『配置に依存する不一致』の説明(PM の質問 1 への答え)

**測ったもの**: wasmgen1 の `difftest.cjs`(`docs/investigations/wasmgen1/tools/`)で、FreeType.dll の 1,588 関数(fe-wasmgen が純粋モードで lower した物)を、C 経路の同じ関数(同じ機械語を fe-lift で C にして wasm -O2 にした物)と 1 関数あたり最大 100 回(乱数のレジスタ・スタック・データ領域の初期値、seed 1)実行して比べた。比べる物は、戻りレジスタ(rax・rsp・被保存レジスタ)、書き込み後のスクラッチ領域・スタック引数・データ領域・低位メモリ、import 呼びの記録、停止の有無。**実エンジンの実行ではなく、機械語単位の差分テスト**(エンジン全体の一致は別に 16 スナップの 82 行で見ている)。

**結果**:

| 条件 | 関数 | 反復 | 不一致 | 層依存と判定 | 片側だけ停止 | 備考 |
|---|---|---|---|---|---|---|
| `--c2` なし(C モジュールは 1 つ) | 1,588 | 156,519 | **48**(11 関数) | 0 | new 7 / C 314 | 旧 wasmgen1 のバイナリでも同じ 48 → 退行ではない |
| `--c2` あり(C モジュールをもう 1 つ、別のメモリ配置で用意) | 1,588 | 155,942 | **0** | 197 | new 1 / C 300 | C 側停止 300 のうち 300 は harness の import 代役 `fprintf`(C 経路が代役を呼び、新側が呼ばない形) |

**『層依存』とは何か**: ある反復で C 経路と新経路の結果が違ったとき、**同じ C 経路の関数を別のメモリ配置の C モジュール(`--c2`)で走らせると、C 経路自身の結果が変わる**場合、その反復は『C 経路自身が自分のデータの置き場所に依存している』反復で、新経路の誤りとは言えないので別に数える(`artifacts`)。0 になったのは、不一致 48 の全部がこの型だったから。

**機構**(実測した関数 3 つ。表は `tables/ft-difftest-noc2.tsv`、`tables/ft-difftest-c2.tsv`):

- `0x4b01fb0`(16 回不一致): 乱数のレジスタから決まる配列 `[r10-0x30]` へ、約 170 万回のループで 1 バイトずつ書く。ポインタが小さい値(例: 0x1b)から始まると、書き込みは**低位メモリ 80 MB 全体**を舐め、C モジュール自身のレジスタ配列 `R[]`(C 経路ではメモリ上にある。新経路のレジスタは wasm のローカル変数でメモリに無い)とディスパッチ表を壊す。壊れた C 経路は以後別の結果を出し、新経路は壊れない。
- `0x4b28250`(1 回不一致 + new 側停止 4): 16 バイト要素の配列を線形探索し、個数は乱数の 32 ビット値。個数が大きいと同じく低位メモリ全体を読む。読む内容に C モジュール自身のデータが入るので、結果が配置で変わる。
- `0x4b20870`(8 回不一致): adler32。長さが乱数のとき同様。

**ゲストがこれに依存しうるか**: **依存しない、と読む(推測を含む)**。この 3 つの共通点は、ポインタ・長さが『有効な範囲の値』ではなく乱数の 64 ビット値であること。Windows 上では、アドレス 0x1b や NULL ページ付近は**アクセス違反で停止する範囲**で、正しいゲストはそこを走査しない。エンジンの実行では、これらの関数は有効なバッファ(ヒープ・スタック・ビットマップ)に対して呼ばれ、16 スナップの 82 行が C 経路(D)と一致している(実エンジン、N=50 では FreeType 2 関数を lower)。**許容できる理由**: 不一致は『C 経路もその状態では未定義に近い』入力だけで、壊れ方は C 経路の `R[]` の位置という、ゲストから見えない実装の都合による。**確かめていないこと**: エンジンが実行する全ての FreeType 呼びが有効バッファであること(実行した経路だけが 82 行で確かめられている)。**撤回条件**: 本物の FreeType 呼びの入出力を C 経路と新経路で比べて 1 つでも違ったら、この読みを撤回する(現状は全 FreeType の lower が N=50 の 2 関数だけで、「all」の同一性が通ったときだけ全関数で 82 行が一致した証拠になる)。

## 12. 未決の点(PM)

1. **`--static-calls` を混成ビルドの既定にするか**。C 経路は『ファイル上のスロットの値が関数入口の間接 call』を実行時の値に関係なく静的な直接 call にしている。直接部が実行時の値を読む(本来の x86 の意味)と、ゲストが書き換えるスロット(Delphi のメモリマネージャ表など)で D と違う関数を呼ぶ。同一性を D に合わせるなら opt-in を既定にする。**C 経路のこの扱いが潜在的な誤りかどうか(実機は実行時の値で呼ぶ)は未確認**で、PM が決める点。
2. 混成の目的が速度なら、**N=50 を既定の候補**にしてよいか(同一性が確認できた唯一の構成。定常 CPU −39%)。N=1000/全部は同一性の問題が片づくまで出さない。
3. 非アトミックな RMW のまま進めてよいか(PM 承認済みの継続確認)。

## 14. lift の忠実性の方針(2026-11-04 追加、`docs/policies/lift-fidelity.md`)への適合

この作業で足した処理は、すべて直接生成部(fe-wasmgen)の内部で、ランタイム・ページ・FL のクラス名/窓/位置による分岐は 1 つも足していない。分類(方針の (a) 余計の除去、(b) 外部 API の契約、通信/変換の削減のどれか):

| 追加 | 分類 | 理由 |
|---|---|---|
| `ir.rs`: 解決済み jmp を普通の jmp にする | (a) 生成部が余計なこと(実行時のスロット探索)をして C 経路とずれていたのを除去 | C 経路(fe-lift)の挙動に合わせる |
| `--static-calls` | (a) 同上(実行時のスロット値を読む余計) | C 経路と同じ静的な直接 call |
| `--sync-saved` | C ランタイム(SEH 巻き戻し)の契約への適合: 呼びの前に被保存レジスタを書き戻す。(b) に近い | レジスタ全体を読む C 側の契約 |
| 新しい命令(cvtsi2ss、cvtsd2si、xadd、cmpxchg、xchg) | 生成部の対応命令の拡充(C 経路と同じ意味で lower) | 余計な物ではない |
| `--lazy-ext`、`--inline-dispatch`(不採用)、`--atomic-rmw`(入口) | 通信/変換の削減(C との境界の呼びと import の削減) | 利得が出なかった物(inline dispatch)は採らなかった |

二分探索(`bis-*`)で作った『実行された関数の C コピー』は測定の道具で、成果物の挙動には入らない。最初に分岐する関数 `0x721280` を**特別扱いして除外する処理は入れていない**(原因の特定と生成部の修正が正しい対処で、除外は方針に反する)。

なお、この作業の最後に、ブラウザ用の preview サーバ(ポート 4197)のプロセスが終了した(こちらが止めたのではない)。`hyb1-*` の束を開くには、`cd app && FL_ASSETS_DIR=lift/out-hyb1/serve/assets npx vite preview --host 127.0.0.1 --port 4197 --strictPort` で起こし直す。
