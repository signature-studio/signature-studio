## 8. 『opaque な関数を呼ぶ』制約の中身と、既存の旗 `--unbal-stub --opaque-stub` を足した F2xH9z の結果(実測 + 読み)

**制約の中身**(`lift/crates/fe-wasmgen/src/lib.rs` の `propagate_hybrid`): fe-wasmgen は関数ごとに制御流グラフ(CFG)とフラグ解析を作る。**どちらかが作れない関数は `opaque`**(CFG が無い)になり、呼び出す関数(またはテイルジャンプ先)が opaque だと、**呼び元も直接 wasm にしない**(`calls a function that is opaque`)。opaque になる理由(Elastique の 1,497 関数の report、hyb6): `RSP at a return or tail jump is not its entry value`(switch の親など、継続の入口が別フレームの関数)333、`undecodable instruction or falls out`(デコードできない / 範囲外に抜ける)190、`flag read from a definition without recipe`(`shr r, cl` の後に CF/ZF を読む)24 + 15 など。上位の例: `f_b2f3650`(参照シーンの Elastique の命令の約 19%)は callee `f_b2cf0c0`(『flag read from a definition without recipe: Shr』)が opaque なので C 経路のまま。
**これを緩める既存の旗がある**(決定 0181、エンジンでは未適用・未測定と書かれている): `--unbal-stub`(RSP が入口の値でない関数を opaque にせず、『全レジスタを渡し、要求された結果を全レジスタから返す』保守的な署名の C スタブとして呼ぶ)、`--opaque-stub`(CFG が無い関数を同じ署名のスタブとして呼ぶ)。

census(`tools/census-mod.sh` = `hybn0` と同じ引数で fe-wasmgen を実行された 567 関数に掛ける。`tables/census-elastique-*.tsv.gz`)で、**Elastique の参照シーンの実行命令のうち直接 wasm にできる割合**:

| F2xH7 の旗、費用上限 30M、≥20,000 B を除く(= F2xH9 の `L6s`) | 36.9% | 496 |
| 同、≥20,000 B を除かない(= hyb6 の `L6`) | 44.5% | 500 |

他のモジュール(上限 50M + 2 つの旗): FLEngine 10,754 / 10,858、dsp 352 / 396、Blend2D 235 / 253、QFC 1,110 / 1,128、freetype 373 / 376、ILTools 1,351 / 1,381、oggio 435 / 453。旗で増える物は FLEngine +1,018 関数(参照シーンの命令の 0.1%)、Blend2D +14(1.5%)、**Elastique +21(47.4%)**、ほかはほぼ 0(`tables/census-stub50M-summary.tsv`)。つまり**旗が効くのは Elastique だけ**。

**F2xH9z**(= F2xH7 の L5s + oggio 全部 + 上記の Elastique 521 関数、`--unbal-stub --opaque-stub`、上限 50M。wasm 153,716,085 B)の結果:
- 起動 16 スナップは 84 行全行一致(混成なしと)。
- **参照プロジェクトを開く途中でエンジンが止まる**。Chrome: `exit code 134`(SIGABRT)、3/3 で、`guest return 0xb2d8b54`(Elastique の `f_b2d8b38` が戻る所)。node: `RuntimeError: unreachable`、スタックは `wasm-function[22114]` ← `[22115]` ← `f_b2e9340` ← `fle_hyb_dispatch` ← `f_b2e98e0` ← … で、最初の 2 つは Elastique の直接部の**名前の無い(export されない)内部関数**。直接 wasm の `unreachable` を踏んでいる。読み: 旗でスタブ経由になった関数のどれかの呼び出し規約(戻り先 / RSP / レジスタの保存)が実際のコードと合っていない。Elastique の 21 関数(旗でだけ lower できる物)のどれかを特定する二分(1 回 約 15 分の build)は、時間が足りず**していない**。

**案 1(S1 を直す): 実行頻度の裾を直接 wasm にしない**(基準は命令数だけ。FL の名前は使わない)。『全 18 本の命令の 99.99%』= 3,942 関数にすると直接部は 20.2 → 10.5 MB。C に戻した分(直接の 1/1.34 倍 ≈ 7.2 MB)を引くと wasm の差し引きは約 −2.5 MB と**読む**。
**案 2(P1 を直す): 起動で実行される ≥ 20,000 B の関数は直接 wasm にしない**(F2xH7 の『≥ 20,000 B を除く』を、起動のスクリプトで実行された関数だけに狭める)。L5 の追加 119 関数のうち 95 が起動で実行される。起動で実行されない大関数(再生中だけ使う物)は直接 wasm のまま残すので、ミキサーの CPU は失わない。census で『≥ 20,000 B、起動で実行、sse2-F2x にない』は 88 関数・3.78 MB。
**案 1 + 2 = H9opt**(マージ用の `hyb-U` = 実験中の名前は `hyb-Uopt`: 3,879 関数・直接 7.8 MB)を build して測った: **wasm 148,356,678 B(S1 の線の下 6.53 MB。全部有効より −7.47 MB)、Chrome の first idle は F2xH7 比 −0.42 s(6 組。H9cut は +1.49 s)、ミキサー平均 110.7 ms(周期の 119%。全部有効 112.8 ms、F2xH9 132.9 ms と同等以上)、起動 84 行と参照プロジェクト 87 行は混成なしと全行一致**(`tables/`)。つまり**頻度と『起動で実行される大関数』という FL に依らない基準で、S1 と P1 を直し、ミキサーの利得(F2xH9 比 −22 ms)を保てた**。ミキサーの周期比 119% は残る。
**案 3(ミキサーの CPU): 旗の不具合を直して Elastique の 91.9% を直接 wasm にする**(§8)。census の直接割合 36.9 / 65.9 / 91.9% とミキサー平均 133 / 113〜122 / (未測定)の傾きから、91.9% で約 100 ms(周期の約 108%)と**直線の外挿で読む**。1 つの Worker では周期にぎりぎり届かないので、これだけでは足りない。
**案 4(構造): ミキサー(と Elastique)を 2 つ目の Worker で走らせる**(決定 0234 の mt2 が研究、`FLE_MT3_PRIO` は mt3)。1 Worker の CPU 予算が壁になっている(全部有効でも 121%、91.9% を直接にしても約 108%)ので、この案が本筋。
**案 5(runtime の C): dsp の HLE の核(再生区間の 9%、`idx 23803` 1 関数)と runtime の C(約 10%)**の最適化。§10。

## 10. 再生区間の CPU の内訳(node、F2xH9 の混成あり、V8 の CPU プロファイル。`tables/profile-H9-play-window.txt`)

| 直接 wasm: FLEngine | 33.0% |

| C 経路: 帰属不明(runtime の C、補助関数ほか) | 9.7% |

- Elastique の時間のうち **85% は C 経路**(16.5% 対 直接 2.8%)。census の『直接にできる命令の割合』(F2xH9 で 36.9%)よりさらに C 側に偏るのは、直接 wasm の方が 1 命令当たり速いため。
- 再生区間はどの 11 秒の窓でも上の割合がほぼ一定(FLEngine 直接 31〜39%、Elastique C 12〜19%)で、Chrome のブロックで見えた『Elastique が動く区間だけ重い』(§6 の 40〜64 s の窓で 170〜250 ms)は node の合計では平らに見える(ミキサー・スレッドだけの時間ではないため)。
- 混成なしの node CPU(再生 30 仮想秒): 4.83 CPU 秒/仮想秒 → F2xH9 2.20(0.45 倍)→ 全部有効 1.90(0.39 倍)→ H9opt 1.79(0.37 倍)。参考: Elastique の無い F2xH7 は 1.35。実時間(1.0)には届かない。

## 12. 出典のない選択(S-ship6-*)

- **S-ship6-1** `hyb-L6s`(最初の依頼の F2xH9)で ≥20,000 B の関数を除く基準は F2xH7(決定 0235)のコピー。理由は同じ大きさだけの基準で FL の名前を使わないため。**結果として誤り**(oggio・Elastique の関数は起動で呼ばれず first idle に効かないのに、Elastique の実行命令の 7.5% を C に残した)。代替: 基準なし(= `hyb-Ufull`)。マージ用の `hyb-U` では『起動で実行される物』だけに狭めた(S-ship6-12)。
- **S-ship6-2** L6 の関数の大きさ(`wasm_code_bytes`)は hyb6 の report(`fe-wasmgen-reports-selected.tgz`)から取り、このビルドで作り直していない。このビルドの `lowered-*.txt` の関数数との一致だけ確認した。
- **S-ship6-3** 計測 bundle は 4977340a + `mt3-measure.diff`(計測コードの stderr 行だけを使う。スケジューラは既定の 0)の木。F2xH7・F2xH9・F2xH6 の**計測版**を比べた。出荷版そのもの(計測コードなし)は F2xH9 の CI 冷間ビルド(ci9)だけ。差は runtime の 4 ファイルで、起動と無関係と**読む**が first idle では確認していない。
- **S-ship6-4** 派生ビルド(`mk-var.sh` / `mk-derived.sh`): C がバイト同一の単位の `.o` を別の作業ディレクトリから hard link で戻した(CI のキャッシュが key でやることと同じ)。モジュール表の `.o`(`realmod_table.o`)は 6 モジュールと 8 モジュールで違うので、表がバイト同一のときだけ戻す(最初の F2xH7 の計測版はこれを誤って 8 モジュールの表で作り、エンジンが `fle_realmod_table has 7 entries and 5 real module files were mapped` で止まった。直して作り直した。その版の結果は使っていない)。

- **S-ship6-6** first idle の統計は『同じ回転の中の差の中央値』(n = 6、12、18)。外れ値が大きい(load 5〜28)ので平均は併記のみ。
- **S-ship6-7** node の参照プロジェクトの volume: 現行の `vfs-seed-idle1.tsv`(3 つの代用フォント入り)+ load1 の `vfs-seed-load1.tsv` のプロジェクトの行(`tools/vfs-seed-ship6.tsv`)。ref1 の volume(installer の `oggio_x64.dll` を volume に置く)だと、決定 0233 のとおり名前つき停止になるので使わない。
