### 3.2 `two-module-design.md` の「2 関数で `-O1` が 872 秒」との食い違い（実測）

同じ関数・同じ入力で、設計文書の測定ファイル（`lift/out-design/two/o1/big39.c`。`f_3d04cf0` と `f_3d3a420` を含む 83,889 行。**`f_3d04cf0` の本体は今回の `fn-3d04cf0.c` と diff が空**）を使って測り直した:

| フラグ | `-finstrument-functions` | 時間 | 最大 RSS | 最大 locals |
|---|---|---|---|---|
| `-O1` | つき（現行の `CFLAGS_GEN`） | **24.07 s** | 1,090,596 KB | 18 |
| `-O1` | **なし** | **752.35 s** | 1,978,336 KB | 11 |
| 設計文書の記録（`lift/out-design/two/o1/big39.O1.time`） | なし（`.o` に `__cyg_profile_func_enter` の import が 0。実測） | 872.46 s | 1,971,900 KB | 11〜19 |

- 設計文書の `-O1` の `.o` は **`-finstrument-functions` なしでビルドされている**（`wasm-objdump -x -j Import` で `__cyg_profile_func_*` の import が 0。今回の「つき」の `.o` は 2 つ）。設計文書の `-O0` の `.o`（`big39.O0.o`）も import が 0 で、locals は 389,942（今回の 389,948 と 6 違う。呼び出しフックの分）。**設計文書は、現行のビルドスクリプトのフラグ（つき）とは違う条件で `-O1` を測っていた**（読み。`build_two.sh` の `CFLAGS_GEN` は設計文書の時点でもつきだが、`o1/` の測定は別のコマンドで手で作った `.o` に見える）。
- **30 倍違う原因は特定していない（未確認）**。観察だけ書く（`f_3059460`、`f_3059440` の単独 `.o` で）: つきの `-O1` の `.o` は定義関数 67 個（`-O0` と同じ数。`static inline` の補助関数 `fle_ld`、`fle_st` などの **定義は残るが、本体の中には展開されている**。Blend2D の `f_180171d60` の `-O1` の LLVM IR（`emcc -S -emit-llvm -O1`）で、`fle_st`、`fle_addr` が展開され、その前後に `__cyg_profile_func_enter(@fle_st …)`、`…(@fle_addr …)`、`…_exit` が 1 回ずつ入っているのを読んだ）、なしの `-O1` は 10 個。`f_3059460` の本体の `call` は、つき 8,094（うち `__cyg_profile_func_enter`/`exit` が 5,036）、なし 9,664（フック 0）。本体のバイト数は、つき 424,168 B（`f_3059440`）、なし 509,517 B。**LLVM のどのパスが 30 倍の差を作るかは見ていない**（`-ftime-report` などは未実施）。この差が「フックの呼び出し（副作用のある呼び出し）が残ることで、あとの最適化パスの仕事が減る」のか別の理由かも、未確認。
- 注意: 現行の `build_two_wasm.sh` は `-finstrument-functions` つきである。**つきの `-O1` が出す wasm の実行時間（フックの呼び出しが `-O0` より多い）と、`a4.c` が使うフックの計数（`trace.c` の `__cyg_profile_func_enter` は `fle_dispatch_table` にある関数だけを数える）が `-O0` と同じになるか、は測っていない（未確認）**。15 関数は stage23 §7 の連鎖で 1 回も入られていないので、この 15 関数については実行時の影響は今のところ無い（読み）。
- `-finstrument-functions` なしの `-O1` の 14 関数の時間: 0.42〜425.42 秒（合計 555 秒。うち `f_3d04cf0` が 425 秒、`f_3057340`、`f_3057400`、`f_3057420`、`f_3059220`、`f_30592e0` が各 約 16 秒、`f_3057580`、`f_30575a0`、`f_3059440` が各 約 12.5 秒、`f_3059460` 3.7 秒、`f_3d70550` 〜 `f_3d7d970` が各 約 2.4 秒、`f_3057360` 0.42 秒）。`f_3d3a420`（`f_3d04cf0` と本体の 97% が同じ）はこの設定では測っていない（未完了）。測定の間、別の作業の `cargo test`（clang）が並走していた。**時間は並走を含む**。

## 4. locals が増える構造（実測と読み）

### 4.1 生成 C の一時変数の宣言（読みと数え。HEAD の `fe-lift` の出力）

関数 1 つの C は、**命令ごとに 1 行**（`L_<va>: { /* 0x<va> Mnemonic */ … }`）。一時変数は行の `{ }` の中の宣言だけ（例: `{ uint64_t t = R[3]; R[4] -= 8; fle_st(R[4], 8, t); }`、`{ uint64_t a = …; … }`、`uint64_t rem; uint64_t q = fle_idiv(…)`、`uint64_t s`・`v`（`cmov`、`bt`））。**`X128` という名前の型は生成器（`fe-lift/src`）のどこにも無い**（`grep X128` が 0 件。128 ビットの値は `fle_xmm`（16 バイトの union）で、`X[k]` というグローバル配列に置かれる）。各行の `{ }` は釣り合っている（`fn/` の 21 関数、182,093 行で、括弧が釣り合わない行が **0**）。

| 関数 | C 行 | `uint64_t`/`unsigned` の宣言の数 | 宣言の名前 |
|---|---:|---:|---|
| `f_3059460` | 3,789 | 103 | `t` 100、`v` 2、`s` 1 |
| `f_3d04cf0` | 25,740 | 524 | `t` 488、`a` 33、`rem`・`q` ほか |
| `f_3d76760` | 6,882 | 706 | `t` 706 |
| 15 関数の範囲 | | **73〜706** | |

- 命令の大半（`Movaps`、`Mulpd`、`Addpd` など）は一時変数の宣言を持たない。`X[k] = fle_mx_mulpd(X[k], X[j]);` の形（グローバルの `X` への代入）。
- **宣言の数と locals の数は無関係**（15 関数: 宣言 73〜706 に対して locals 50,926〜389,948）。

### 4.2 locals の正体（実測）

`f_3059460`（locals 51,658）の `-O0` の wasm を `wasm-objdump -d` で読んで、各 local の `local.set`/`local.tee` と `local.get` を数えた（`tools/local_usage.py`）:

| 項目 | 個数 |
|---|---:|
| 宣言された locals | 51,658（i32 31,886、i64 19,772） |
| set 1 回・get 1 回（単一定義・単一使用） | **51,611** |
| set 1 回・get 2 回以上 | 45 |
| その他（set 2 回以上、など） | 2 |
| 一度も使われない locals | 0 |

- wasm の命令列（`-O0`）は、**C の式 1 個ごと**に値を local に入れて、すぐに読む形（`i32.const 72; local.set 29990; local.get 29990; i64.load 3 0; local.set 29991; local.get 2; local.get 29991; i64.store …`）。`-O1` の同じ関数は、同じ式を **スタックの上で式木として作る**（`local.set` が 84 回。`fn-3059460-O1-nopasses`）。**`-O0` の wasm バックエンドは「一度だけ使う値」を local に入れ、局所を再利用しない**（`local.set` 51,664 回に対し local 51,658 個）。
- **`-O0` と `-O1` のパイプラインの差**（`emcc -c -mllvm -debug-pass=Structure` の `Pass Arguments` の行。実測）: `-O0` は `-wasm-reg-stackify` を持つが **`-wasm-reg-coloring` を持たない**。`-O1` は両方持つ。`-wasm-fix-irreducible-control-flow` は両方にある。
- **この C が wasm のスタック式木にならない理由の読み**: 全命令にラベルが付くので LLVM の基本ブロックが細かく分かれる（`f_3059460` の IR は基本ブロック 3,855 個。飛び先でないラベルを外した `unl-3059460` では 100 個）。ただし **ラベルを外しても locals は同じ**（§4.3）ので、基本ブロックの分割が主因ではない。**主因は §4.3 の「既約な goto」**。

### 4.4 `-O1` で locals が 6〜19 に落ちる理由（実測）

- `-Xclang -disable-llvm-passes`（IR の最適化を止める）を付けた `-O1` でも、15 関数すべてで locals は **6**（V8 受理）。**locals を詰めるのはバックエンド（`-wasm-reg-coloring` を持つ）**。`-O0` のバックエンドは詰めない。
- `-O0` のままで `-Xclang -disable-O0-optnone` を付けても locals は変わらない（`f_3059460` 51,658、`f_3d04cf0` 389,948）。

### 4.5 C を可約にしても残る locals（実測）

可約にした `f_3059460`（`red-3059460.c`）の locals は 7,647（`i64` 7,512）で、可約な関数の locals/行 は全関数で 1.5〜2.2 程度（§4.3）。`X[a] = fle_mx_mulpd(X[b], X[c])` のような 16 バイトの値渡しの呼び出しは、`-O0` で値を一時領域にコピーして呼ぶ（`i64.load`/`i64.store` と locals）。**参照渡しの補助関数に書き換えた見積もり**（`byref_est.py`。`fle_mx_mulpd_p(&X[a], &X[b], &X[c])` の形に 1,026 + 180 行）で locals は 7,647 → **7,202**（−445、約 6%）。可約になった後の残りの locals は 1 命令あたり 1〜2 個で、上限の問題にはならない（`f_3d04cf0` が可約化 + ディスパッチループで 54,958 と、なお上限を超える）。
