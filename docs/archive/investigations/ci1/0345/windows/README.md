## 表の作り方

1. 各 trace の `console.timeStamp`(sync-a / sync-b)と直後のページ時計(epoch ms)を対応づけ、trace の時刻(µs)をページ時計に直す(2 点の差 11〜15 µs)。
2. 対象の入力 = trace 区間(sync-a〜sync-b)の中にある、再生中の File click(button-down、kind 2)で、最初の frame まで answered なもの。各 run で 12 件(0343 / 0345 の解析と同じ選択)。
3. 各入力について 2 つの窓を切る。
   - **W** = 入力の時刻 tPage の前後 200 ms(400 ms)。
   - **C** = phase C = tInject(UI Worker が入力を受けた時刻)から最初の frame まで。W の中に入る。
4. UI Worker(`DedicatedWorker thread` のうち RunTask が最多の thread)の v8 CPU profile のサンプルを、窓ごとに集計する。サンプルの重み = そのサンプルの時間差(µs)。列の意味:
   - `(program)`: V8 がどの JS / wasm 関数にも帰属させなかったサンプル。**待ちか native 処理かは、この表では分からない**。
   - `(idle)`: V8 の idle サンプル。
   - `wasm anon self`: self の frame が `wasm-function[N]`(name section に名前が無い関数)のサンプル。
   - `named self`: self の frame に名前がある関数(`fle_*`、`g9_hook`、`poll_waiters` など。`fle_gil_*` は別の列)。
   - `fle_gil_* self`: self の frame が `fle_gil_*` のサンプルの合計。
   - `top self functions`: self 時間の大きい関数の上位 3 つ(ms)。
5. 行の単位は ms(入力 1 回の窓の中の ms)。合計の表だけ、12 入力の合計を入力数で割った ms/入力。窓どうしは重ならない(RT-H の入力の間隔は 2.1〜2.4 s、窓は 0.4 s)。
6. 他の pthread Worker は、この表に入れていない(UI Worker だけ)。

## この表の読み方に必要な注意(判定ではない)

- 関数名: E13 の wasm には name section が無く、`wasm-function[N]` のまま。RT-H の `[1368]` と E13 の `[1367]`、RT-H の `[3035]` と E13 の `[3034]` が同じ関数かは、**確認していない**(RT-H の wasm は import が 1 つ多く、関数 index が +1 になっていることからの推定)。`fle_gil_*`・`fle_desk_compose` のような名前は RT-H にしか付かない(E13 は名前が無いので、E13 側の同じ関数が `wasm anon` に入っている可能性がある)。そのため `wasm anon self` と `named self` は、**E13 と RT-H で単純には比べられない**。`total`・`(program)`・`(idle)` は名前に依らない。
- `(program)` は待ちか native 処理かの区別ができない。
- W の `(idle)` の範囲(12 入力の最小〜最大): E13 run1 3.33〜68.63 ms、E13 run2 4.74〜93.81 ms、RT-H 48.40〜137.40 ms(窓ごとのばらつきが大きい)。
- 1 trace あたり 12 入力。入力ごとの値のばらつきは大きい(`spread.md`)。
- 窓 W の長さの合計は 400.17 / 400.19 / 399.97 ms/入力(サンプルの時間差の合計。窓の定義と一致)。
