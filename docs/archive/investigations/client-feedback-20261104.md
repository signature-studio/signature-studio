# 依頼者の実機での報告(2026-11-04)と、計測ビーコンに届いた依頼者のブラウザの実測

## 報告(原文要点。PM が受領)
依頼者の評価: 「以前と比べて明らかにパフォーマンスは改善している。だがまだ何か操作すればすぐ落ちる状態。『何をすれば落ちる』というより『何をすればまだ落ちない』という印象」。
- 落ちる操作(依頼者が確認): Sampler の Envelope タブのクリック、Settings の General タブのクリック、Browser のフォルダの展開、Playlist をマウスホイール押下でドラッグ、ほか多数。
- 『デコンパイルしたコードを wasm にコンパイルし、必要な API を実装する。これを十分にすれば「動かない」は起こり得ないはず。個別のケースに個々に対応しているのは上のワークフローで不自然』。
- 性能: ネイティブ比でまだ改善の余地が大きい。ウインドウのドラッグ中は描画が全く更新されず、ドラッグが終わっても更新されない。カーソルがホバーしたスクロールバーやボタンが順番に更新される。再生中は 10 fps も出ていないように見える。
- 音が出ない(デモプロジェクトでメトロノームを入れて再生しても何も鳴らない)。
- File→Open や File→Import→MIDI file をクリックしてもファイル選択画面が出ない。プロジェクトを開くにはブラウザが zip を読む必要がある。
- アクティベーション: Image-Line アカウントでのログインがアーキテクチャ上難しいのは想像がつく。オフラインアクティベートは?
- 『Unity WebGL ビルドは wasm↔JS/DOM のシリアライズ/デシリアライズ回数を減らして非常に軽量。その仕組みを参考にできないか(このプロジェクトは WebGL を使っているか?)。少なくとも wasm→worker→メインフレーム→canvas のようなバケツリレーは避けること』。
- 『画面がこんなに小さいのはなぜか。上部ヘッダーと右部のモニターを除く全てのエリアを画面とする、で良いはず』。
PM の確認(コード): ゲストの仮想モニターは lift/runtime/fle_monitor.h の定数 1920x1080(決定 0065 の仮の選択、『ページは値を渡さない』)。WebGL は使っていない(app/src が WebGL を使うのは GPU 名の取得のみ)。描画は『エンジンの窓ごとに 2D canvas(app/src/ui/layer.ts 系)』で、Worker の wasm が窓の面を postMessage でメインスレッドへ送り putImageData する。
依頼者のブラウザ(ビーコン版 3、lift/out-websrv/perf-log.jsonl の remote=tailnet、2026-11-03 18:21Z〜18:45Z の 12 セッション、既定の入口 SHIPH): **Firefox 159.0 / Windows 10 x64、hardwareConcurrency 8、GPU GTX 980 (ANGLE D3D11)、画面 2176x1224 CSS px・devicePixelRatio 1.7647(物理 3840x2160 相当)、crossOriginIsolated true。**
- 最初の idle(P1): 9.9 / 10.3 / 10.4 / 10.8 / 10.9 / 11.0 / 11.3 / 11.8 / 12.8 / 13.0 / 13.2 / 13.3 秒 = 12 回中 10 秒以内は 1 回、中央値 11.2 秒(**依頼者の機械では P1 未達**)。うち download_done が約 5.5 秒(wasm 約 13 MB brotli を tailnet 経由)、compile_done 約 5.8 秒、idle まで +4 秒。
- セッションの終わり方: **12 セッション中 10 が engine exit {reason: stopped, code: 134}(エンジンの停止=『落ちた』)**、2 が code -1(presents 0)。ビーコンは停止メッセージ(fle: … の文)を運ばない。
- 更新: 窓の更新 62.5/s(アイドルの再描画)。エンジンの idle は 23.7/s と記録されたが、**これはエンジンの遅さを示す値ではない**(決定 0211 aud3 の訂正: ビーコンの idle の報告は ReportThrottle〔決定 0170〕で 40 ms に 1 回に絞られるため `ui.engineIdles.recent10s.perSecond` の上限は 25/s。厳密な総数 `ui.engineIdles.total` ÷ 秒数では依頼者の 13 セッションで 799〜1,255/s、中央値約 1,000/s、窓の更新は約 60/s で整合する)。**依頼者の機械でゲストが仮想時間に追いつけないという根拠は、このビーコンには無い**。eventToRaf p95 は 29〜72 ms が多いが、1,229 ms / 2,806 ms / 14,037 ms の停滞も出た。wasm メモリ 0.455〜0.503(2 GiB 中)。
- 依頼者のブラウザは Firefox(こちらの検証は Chrome 156 のみ。/usr/bin/firefox がこの機械にある: バージョンは `firefox --version`。WebDriver BiDi / Marionette で動かせるか各担当が確認)。

## 方針(PM、2026-11-04): 依頼者の指摘は事実として受ける
(1) 『停止(落ちる)』は、これまで『壁に当たったら名前を付けて止まる』方針(進捗の誠実性・忠実性のための設計)で、未実装の API を最初に踏んだ所で止まる開発方式(wall-driven)になっていた。出荷物としては不適切。(2) Win32 の API 面は『踏んだ物を 1 つずつ実装』ではなく『仕様から体系的に網羅』する方向へ変える(担当ごとの課題)。(3) 実機 Windows の挙動の推測は『推測』と書く規則は変えない。偽の成功を返さない(ライセンス判定・ネットワーク応答の偽装は禁止のまま)が、**文書で失敗が定義された API は、停止でなく文書どおりの失敗を返す**道を作る。

## 追加の依頼(同日、依頼者の続報)と PM の受け止め
- 『なぜ画面がこんなに小さいのだ? 上部ヘッダーと右部のモニターを除く全てのエリアを画面とする、で良いはず』 → ゲストの仮想モニターは `lift/runtime/fle_monitor.h` の定数 1920x1080 で、ページは値を渡していない(決定 0212 screen1)。
- 『ファイルシステム管理は FL Studio に元来ない。OPFS をエクスプローラーのように管理できる GUI をライブラリでなるべく手間を掛けずに足し、FL の「開く」は OPFS からの選択 UI を JS で実装するだけにせよ。ユーザーのプロジェクトはフォルダか zip なので、ブラウザ領域へコピーする手順も要る』 → 決定 0216 opfs1(段階 1: ページのエクスプローラー、段階 2: 開く/保存の JS 化、段階 3: OPFS をゲストの実体に)。
- 『音が出ていない』 → 音は決定 0175 の判断で `?audio=1` の opt-in のまま既定の入口に入っていなかった(PM の判断の誤り)。決定 0211 aud3 で既定 ON と実音の確認。
- 『描画経路のバケツリレーを避けよ』 → 実エンジンの既定は表示方式 B(`app/src/main.ts:609`)で、依頼者のビーコンも `present: "B"`。決定 0214 present2。
- 『アクティベーション/オフライン認証』 → 決定 0213 act1(調査と設計。偽装・迂回はしない)。
- 『落ちる』 → 決定 0209 crash1(再現と根治、停止メッセージのビーコン、soft-stop 設計)、決定 0210 api2(API 層の網羅方式の再評価と census)。
