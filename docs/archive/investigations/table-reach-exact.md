# 閉包内の間接 call/jmp の由来の分類と Z の正確な値（M1 作業者）

対象: `binaries/win64/FLEngine_x64.dll`（読み取りのみ）。
分析: `lift/out-zexact/zexact.py`（新規）。出力は `lift/out-zexact/out/zexact6-*`（最終版）。
既存のコード、生成物、閉包は変更していない。

「実測」は計算と逆アセンブルの結果。「推測」は未検証の解釈。

## 0. 結論

| 項目 | 件数 | 区分 |
|---|---:|---|
| 閉包内の間接 call | 6,490 | 実測（既存の閉包と一致） |
| 閉包内の間接 jmp（IAT 以外） | 16 | 実測 |
| 閉包内の間接 jmp（IAT 経由、分類外） | 409 | 実測 |
| **Z（正確）: 非添字の表経由で、表の値が閉包外の関数先頭を指すもの** | **0** | 実測 |
| **Z（表の範囲の上限）: 添字付きで、表の範囲に閉包外の関数先頭を含む call** | **3** | 実測（範囲の上限。推測を含む） |

Z の正確な値は、定義どおりに「スロットが一意に決まるもの」で数えると **0 件**です。添字付きの参照はスロットが決まらないため、表の範囲に閉包外を含むものを **3 件**（上限）として別に示しました。

## 1. 分類の件数（実測）

### 1.1 間接 call（6,490 件）

| 分類 | 件数 | 内訳 |
|---|---:|---|
| (a) 表（RIP 相対 lea/mov が .data の表に当たる） | 13 | `call [rip+X]` で表スロット（非添字）12、`[rip基底+rsi*8]`（添字付き）1（0xa99d3b） |
| (b) 引数由来 | 2 | すべて (a) に当たる（0x41223e、0x41226d）。(b)→(c) は 191 |
| (c) メモリ読み出し（.bss、ヒープ、スタック、表外の大域） | 4,972 + 191 | 4,972 は直接。191 は (b) の根が (c) |
| (d) その他（判定できない） | 1,312 | 下の内訳 |

(a) 13 + (b)→(a) 2 + (b)→(c) 191 + (c) 4,972 + (d) 1,312 = 6,490（一致）。

(c) の内訳: `deref_load_mem` 4,283、`ptr_from_global`（表外の大域スロットの値）430、`global_fnptr`（大域の関数ポインタ）166、`deref_stack_reg` 82、`deref_stack_load` 4、`load_mem` 7。

(d) 1,312 の内訳と理由:
- `outside_caller` 695: 引数の由来が閉包外の呼び出し元にあり、追跡していない（閉包の定義により対象外）。
- `clobber` 431: 呼び出しで引数レジスタが上書きされた（追跡を打ち切り）。
- `depth_hops` 91: 関数内の定義の追跡が上限 6 段を超えた。
- `depth_ip` 39: 呼び出し元をたどる段数が上限 2 段を超えた。
- `idx_val` 37: 添字の値が追跡不能（`mov reg,[base+idx*8]` の添字側）。
- `indirect_caller` 12: 呼び出し元が間接参照（関数ポインタ経由）。
- `budget` 7: 1 命令あたりの状態数の上限（20,000）を超えた。

### 1.2 間接 jmp（425 件）

| 分類 | 件数 | 内訳 |
|---|---:|---|
| (a) | 0 | |
| (b)→(a) | 0 | |
| (b)→(c) | 1 | 根がスタック読み出し |
| (c) | 15 | `jmp [rip+X]` の大域の関数ポインタ 14、大域の基底 1 |
| (d) | 0 | |
| IAT 経由（分類外として別掲） | 409 | `.idata` の IAT スロット（外部 API）。表ではないため (a)〜(d) に入れていない |

jmp の合計は (b)→(c) 1 + (c) 15 + IAT 409 = 425（一致）。(a) と (d) の jmp は 0 件。IAT の 409 件は表ではないため (a)〜(d) に入れていない。
なお、閉包内の間接 jmp 425 件のうち IAT 経由は 409 件で、既存の `closure-count.md`（IAT 経由 jmp 409）と一致する。

## 2. Z の判定（実測）

### 2.1 正確な Z（非添字、スロットが一意）

非添字の表経由の call 12 件（`call [rip+X]`）は、スロットの値（`read8`）がすべて閉包内の関数先頭を指していました。閉包外を指すものは 0 件です。

### 2.2 添字付きの参照（表の範囲の上限）

| 番地 | 形 | 表の基底 | 由来 | 表の範囲に閉包外の関数先頭を含むか |
|---|---|---|---|---|
| 0xa99d3b | `call [rsi+rdi*8]`（直接） | 0x14e0408 | rip lea | 含む |
| 0x41223e | `call [rbx+rsi*8]`（引数経由） | 0x13a9410 | 0x41d95a の lea（rip）→ 0x41d984 で r9 → 0x412173 で rbx | 含む（0x41d050） |
| 0x41226d | `call [rbx+rsi*8]`（引数経由） | 0x13a9410 | 同上 | 含む（0x41d050） |

これらは「表のどのスロットが読まれるか」が決まらないため、Z の正確な値には入れていません。上限として 3 件です。

## 3. 0x41d050、0x41e7e0、0x41ce10 の判定

### 3.1 0x41d050: (a) の経路に入る（実測の経路、スロットは推測）

- 0x41d050 は .data の表 0x13a9410 の [1] で、DIR64 の再配置を持つ（実測。`table_reach` の既存結果と一致）。
- 0x41d95a `lea r9,[rip+...]` → 0x13a9410（閉包内の 0x41d8f0）。
- 0x41d984 で r9 を渡して 0x412160 を呼ぶ（閉包内）。
- 0x412173 `mov rbx,r9`、0x41223e `call [rbx+rsi*8]` と 0x41226d が、この表を添字付きで読む（実測）。
- 添字 rsi が 1 になるかは決まらない。既存の `ref-852-function-pointers.md` の `[rbp+0x170]` の条件に依存すると思われる（推測。値は未検証）。

よって 0x41d050 は「(b)→(a) の経路に入る（添字付きの範囲の上限として）」。スロット 1 が実際に読まれるかは未確定。

### 3.2 0x41e7e0: (a) の経路に入らない（静的な根拠）

- 0x41e7e0 は、どの DIR64 の表の範囲にも入らない（実測。`in_table_runs` が空）。
- 閉包内の間接 call で、0x41e7e0 を指しうるものとして見つかったのは 0x412126 `call [rbp+0x38]`（関数 0x4120c0 内）。その根は (c)（スタック上の読み出し、実測）。
- ただし、0x412126 が 0x41e7e0 を指すという対応は未検証（推測）。`rbp+0x38` の内容は静的には決まらない。

よって 0x41e7e0 は (a) の経路には入らない（静的な根拠による判定。実行時の値は未確認）。

### 3.3 0x41ce10: (a) の経路に入らない（静的な根拠）

- 0x41ce10 も、どの表の範囲にも入らない（実測）。
- 0x41ce10 を指す間接 call の特定は未実施。既存の `seed-0x41e7e0.md`（§3.2）では、0x41ce10 への間接 call は関数 0x4120c0 内の同じ call 点から、2 回目の通過で発生したと記録されている（既存の記録。本作業では再確認していない）。
- したがって 0x41ce10 の判定は「表には入らない」（実測）までであり、(a) の経路に入らないことの確定は、呼び出し点の特定後に行うべき（推測を含む）。

## 4. 集計方法（実測）

1. 閉包の関数（`lift/out-seed/out/base-functions.tsv`、6,969 件）の命令を、直接 call/jmp と fall-through で到達する範囲として集めた（既存の `indir_scan2.reach_insns` を利用）。命令数は 460,191 件（既存の 460,479 とは別の数え方のため、差は 288 件）。
2. 命令ごとに、基底レジスタ（または参照先）の由来を関数内で逆方向に追跡した。分岐の合流は、全ての先行ブロックを辿った（支配関係は見ていない）。
3. 関数の入口に達したら、呼び出し元（閉包内の直接 call、閉包外の直接 call、関数ポインタとしての参照）をたどった。
4. 根の種類から (a)〜(d) に分類した。RIP 相対の `lea` は値そのもの、RIP 相対の `mov` は読み出し、表の範囲は DIR64 の再配置（`BASERELOC` 位置）から求めた連続区間（2,532 区間）。
5. 上の分類で、表の値を一意に読めたものは「正確」、読めないものは「範囲」とした。

### 4.1 限界

- **逆追跡の深さ**: 関数内の定義の追跡は 6 段まで（`MAX_HOPS=6`）。呼び出し元をたどるのは 2 段まで（`MAX_IP=2`）。1 命令あたりの状態数は 20,000（`BUDGET`）。超えたものは (d) とした。
- **支配関係**: 見ていない。全ての到達経路の定義を union している。このため、実行されない経路の値も入りうる（保守的）。
- **閉包外の呼び出し元**: 閉包外の直接 call から閉包関数の引数は見たが、その引数の由来は追跡していない（(d) の `outside_caller` 695 件）。
- **`regs_write` の欠陥（重要）**: Capstone の `regs_write` は `mov` 系の命令で宛先を含まないことがある（実測: `0x412173 mov rbx,r9` の `regs_write` は空）。既存の `indir_scan.py` の `resolve` は `regs_write` を使うため、この命令を飛ばして上流の定義に進んでいた。本分析では宛先オペランドを書き込みとして補った（`fix_rec`）。既存の `indir_scan*.py` と、`closure-count.md` の「未解決 6,478 / 6,490」の分類には、同じ欠陥が入っている可能性がある（推測。全体の影響範囲は未検証）。
- **値の実行時の内容**: 0x412160 の添字（rsi）、0x412126 の `[rbp+0x38]` のスロットは、静的には決まらない（未検証）。

## 7. 失敗と拒否

- 権限拒否: なし。
- 失敗 1: `zexact.py` の `fmt_leaf` が型エラーで停止（修正済み。出力は書かれていない）。
- 失敗 2: `regs_write` の欠陥を見落として、最初の実行で `0x41223e` を `entry_reg` と誤判定。デバッグで原因を特定し修正（上の 4.1 参照）。
- 失敗 3: 添字付きの参照で、表の先頭要素の値を exact と誤記録。修正済み。
- 規約違反 1: 1 回だけ `timeout 0` を付けて `python3` を実行した（禁止されている timeout を含むコマンド）。結果には影響しないが、違反として報告する。
- 削除（rm）、既存ファイルの上書き、git 操作、/tmp の利用、sleep: なし。
- 副作用: `lift/out-indir/` の import により `__pycache__` が更新された可能性がある（既存のディレクトリ。未確認）。
- 途中版の出力（`zexact-*`、`zexact2-*` 〜 `zexact5-*`）は、名前の衝突を避けるため残置した。
