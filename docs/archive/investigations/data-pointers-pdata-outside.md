# pdata 範囲外の .text を指すデータ内ポインタの性質

作成: 2026-10-20（M1 作業者）
対象: `binaries/win64/FLEngine_x64.dll`
スクリプト: `lift/out-ptr/classify_pdata_outside.py`（新規。出力は `lift/out-ptr/`）

この文書は分析のみで、コードと生成物は変えていない。ここでの「実測」は計測結果、「推測」は計測から導いた解釈を指す。

## 0. 母集団（実測）

既存の `lift/out-diag/pointer_census.py` と同じ定義で再現した。

| 項目 | 件数 |
|---|---|
| .text を指す DIR64 再配置の値（非 .text ページ、distinct） | 6,974 |
| うち dispatch 表に既にある | 12 |
| うち pdata の関数 entry（表に無い） | 852 |
| うち pdata の内側（表に無い） | 0 |

上の内訳は前回の計測と一致した。`0x41d050` は pdata の関数 entry（`begin == 0x41d050`）で、これも前回の結論と一致する。

| 先頭命令 | 件数 |
|---|---|
| `endbr64` | 0 |

## 2. パディングに当たる件数（実測）

- int3 で始まるもの: 0 件
- ゼロ埋めで始まるもの: 0 件

pdata 範囲外の値は、パディングの先頭には当たらない。

## 3. 有効な命令列として読めるか（実測・iced-x86 の逆アセンブル）

iced-x86 で、各値から最大 64 命令・512 バイトを逆アセンブルし、無効な命令（`Code.INVALID`）が出る前に、ret / jmp / indirect jmp の終端に着いたかで分類した。

| 逆アセンブルの結果（status） | 件数 |
|---|---|
| invalid: 無効な命令（Code.INVALID）が出た（先頭で出た 139 件を含む） | 5,110 |
| term: 終端（ret / jmp / indirect jmp）に着いた | 855 |
| limit: 64 命令の上限に達した | 145 |

（5,110 + 855 + 145 = 6,110）

ただし「終端に着く」は有効なコードの証拠にならない。データ（文字列・構造体）でも偶然 decode が続くことがある。実例（`0x464c4c`、`0x5871b0`）は、UTF-16 の文字列の途中から decode し、文字列の後の `cc cc` で終わっていた。

v3 の分類（ヒューリスティック）:

| 分類 | 件数 |
|---|---|
| UTF-16LE のデータ | 2,218 |
| ASCII のデータ | 1,657 |
| 無効なコード | 1,452 |
| 有効だが終端が無い / 短い（未判定） | 708 |
| 有効な終端あり | 72 |
| nop で始まる | 2 |
| jmp（相対）のスタブ | 1 |
| 合計 | 6,110（一致） |

## 4. pdata 範囲外の .text の領域による分類（部分実施）

**実施済み:** 上の分類で、相対 jmp の候補が 1 件（`0xe33bfc`、上記参照で判断は保留）、nop が 2 件。`jmp [rip+slot]` の import thunk は 0 件。

**未実施:** ジャンプテーブル、リンカが作る stub、thunk の判定は、件数を数えるまで至っていない。ここは「未分類」として残す。上の jmp スタブ 1 件は、スタブとは判断できず未分類とする。

gap（隣り合う pdata 範囲の間）の計測は、6,110 件すべてで「パディング以外を含む」になった。この指標は範囲が広すぎて情報が無いので、判定に使わない。

## 5. objdump との突き合わせ（実測、限定的）

`lift/objdump-text.txt` は 0x11fb4af までしか無い。

- 有効な終端を持つ 855 件のうち、objdump の範囲内が 846 件、範囲外が 9 件。
- 846 件のうち、objdump の命令境界に一致したのは 342 件。
- 境界に一致した 342 件のうち、先頭の mnemonic が一致したのは 331 件。
- 境界に一致しない 504 件は、objdump の同期ずれか、命令の途中を指しているかのどちらか。区別できていない。

objdump の線形走査は、データを挟むと同期を崩す。したがって「境界に一致しない」は、そのまま「無効」の証拠にはならない。

## 6. 結論: seed に加える価値

**実測:**

- seed 候補の判定（強い基準: 有効な終端、典型的 prologue、直前が境界バイト、00 00 の並び無し、命令数 8 以上）を満たすものは **0 件**。
- 弱い基準（有効な decode、典型的 prologue 無し）を満たすものは 1 件（`0xd6fd22`）。これは objdump で `jne` の直後が `add ah, cl` / `int3` となり、UTF-16 の断片（`75 69 00 cc`）に見える。関数の先頭とは判断できない。

| 判定 | 件数 |
|---|---|
| seed に加える価値がある（有効な関数の先頭と判断できる） | **0** |
| データと判断できる（UTF-16 2,218 / ASCII 1,657 / 無効 1,452 / nop 2 / 有効 decode だが 00 00 の並びか境界無し 71） | 5,400 |
| 判断は弱い（有効 decode、典型 prologue 無し、データの疑い） | 1 |
| 判断できない（未判定。うち jmp スタブ 1 件 `0xe33bfc`） | **709** |
| 合計 | 6,110 |

v3 の seed 判定の内訳（`pdata_outside_values_v3.tsv` の `seed` 列、実測）: `no-seed` 5,329（nop 2 を含む）、`no-seed (…data-like…)` 71、`seed-weak` 1、`undecided` 709。合計 6,110。

**補足:** v2 では「強い seed 候補（有効な終端あり、境界バイトあり）」が 72 件あったが、v3 で `00 00` の並びと典型 prologue の条件を加えたところ 0 件になった。v2 の 72 件は、ASCII や UTF-16 の後の `cc cc` で止まった偶然の decode を含んでいた（例: `0x464c4c`、`0x5871b0`、`0x590700`）。したがって 72 件を seed の候補とは扱えない。

**jmp スタブ `0xe33bfc`:** 相対 jmp の先（`0xe33bf2`）は objdump で `add al, [rax]` と `(bad)` になる。スタブとは判断できず、データの誤デコードの疑いが強い（推測）。

**推測（実測ではない）:** 6,110 件の大半は、関数ポインタではなく、`.text` の範囲に値が入るデータ（整数や文字列の断片）である可能性が高い。UTF-16 文字列の先頭が 2,218 件を占めることは、このことと整合する。ただし、なぜ `.text` の範囲に入るのか（リンカの配置、データ用の値の偶然か）は確認していない。

**根拠の限界:**

- 「判断できない」の 709 件は、まだ逆アセンブルの結果と objdump の突き合わせを行っていない。その中に関数の先頭が混ざる可能性は残る。
- 「データ」の判定は先頭バイトの型に基づく。型の判定が外れると、関数が混ざりうる。
- 関数ポインタとして実際に使われるかは、`.data` の表の参照を見ていないので、確かめていない。

## 7. 残りの作業量

1. 未判定 709 件（うち 708 件は「有効だが終端が無い」）について、もう一段の検証: 関数の先頭として、直前の命令境界（前の関数の ret / int3 の後）と一致するか、呼び出し元（direct call / jmp）があるかを見る。
2. 項目 4 の領域分類（ジャンプテーブル、stub、thunk）を、件数として数える。
3. 6,110 件それぞれの参照元（`.data` の表の位置）が、関数ポインタの表（vtable など）に属するかを確かめる。
4. objdump の範囲外（0x11fb4af より後）の 184 件は、iced の結果だけで判定している。
