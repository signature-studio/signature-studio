# dispatch miss 0x41d050 の原因切り分け

対象: `binaries/win64/FLEngine_x64.dll`（読み取りのみ）。生成 C は `lift/out-imp/after.c`、実行記録は `lift/out-imp/run1.txt`。
修正はしていない。本文の「実測」は読んだ出力または実行したスクリプトの結果、「推測」は未検証の解釈。

## 結論

分類 **(c)**: 0x41d050 は、閉包の外にある関数の entry である（実測）。
表に入っていないのは「表の生成が誤っている」からではなく、閉包（fe-decode の再帰降下）がこの関数に到達していないから（実測と推測の両方を含む。下記）。
値は、`.data` にある関数ポインタ表 `0x13a9410` の要素 `[1]`（VA `0x13a9418`）から、そのまま読まれたもの（実測）。計算で作られた値ではない。

根本の原因の候補は `fe-decode` の閉包の seed である（推測。検証は未実施）。`.data` に置かれた、コードを指す関数ポインタ（再配置が必要な 8 バイト）を seed にしていない。

## 1. 0x41d050 の位置（実測）

- `.text` の内側。`.pdata` の関数先頭（offset 0）。`pdata` の範囲は `[0x41d050, 0x41d088)`（`pe_probe.py pdata 41d050`）。
- `objdump -d` 相当（`lift/objdump-text.txt`）:
  ```
  41d04f:	cc                   	int3
  41d050:	48 83 ec 28          	sub    rsp,0x28
  41d054:	48 8d 04 25 a8 32 00 	lea    rax,ds:0x32a8
  ```
  直前は `int3`（パディング）で、`sub rsp,0x28` から始まる。関数の先頭として妥当。
- `lift/out-imp/after.c` に `f_41d050` は無い（`grep f_41d050` 0 件）。`fle_dispatch_table` にも 0x41d050 は無い（`grep UINT64_C(0x41d050)` 0 件）。
- 閉包の関数数 6,969 は、表の行数（`fle_dispatch_count = 6969`）と一致する。

## 2. 値の作られ方（呼び出しの連鎖と、定義元）

### 呼び出しの連鎖（実測）

| 段 | 命令（objdump） | 内容 |
|---|---|---|
| entry | `1376820` 〜 `1376870: call 0x41d8f0` | `r9d = [rbp+0x3c]`（entry の 3 番目の引数 = edx）。実行時 rdx=1（run1.txt の `rdx=1`） |
| f_41d8f0 | `41d905: cmp r13d,0x1` / `41d909: jne 0x41d94d` | r13d = r9d = 1 のとき、`0x41d170` を先に呼ぶ（entry 3）。その後 `41d95a: lea r9,[rip+0xf8baaf] # 0x13a9410`（表の先頭） |
| f_41d8f0 | `41d961: mov rax,[rip+0x11ce940] # 0x15ec2a8`、`41d96d: mov [rsp+0x28],rdi`、`41d972: mov [rsp+0x30],r13d` | 第 5 引数 = `[0x15ec2a8]`（.bss、zero-fill）、第 7 引数 = mode = r13d（= 1） |
| f_41d8f0 | `41d984: call 0x412160` | 呼び出し元の戻り番地 0x41d989（run1.txt の `#0 ... guest-return=0x41d989`） |
| f_412160 | `412170: mov rax,rcx`、`4121a0: 〜` | `rbx = r9`（表の先頭 0x13a9410） |
| f_412160 | `41223e: call [rbx+rsi*8]`（`rsi = [rbp+0x170]`） | mode = 1 のとき、`412238: mov esi,[rbp+0x170]` で rsi = 1 |

呼び出し元の 3 か所（0x41223e、0x412258、0x41226d）のうち、run1 のエラーは **0x41223e** のもの（推測を含む）。根拠:
- mode = 1 で `je 0x412238`（`412226`/`41222d`）が成立し、0x41223e に進む（`412226: cmp [rbp+0x170],1`）。0x41226d は mode=3 の条件（`41225e`/`412265`）が必要で、mode=1 では通らない（実測）。
- 0x412258（`call [rbp+0x160]`）は mode=1 でも、`[rbp+0x160]` が非 0 なら到達しうる（実測の命令列）。ただし、その場合の値は `[rbp+0x160]` の内容で、表の `0x41d050` とは一致しないはず。`[rbp+0x160]` が 0x15ec2a8（.bss、ファイル上は 0）から来ることは未追跡（推測）。したがって、miss の値の一致から 0x41223e と判断した（推測を含む）。
- 0x41223e の直前に `0x406f90`（GetCurrentThreadId）が返っている（entry 6、戻り 0x4121cc）。次の間接 call がこれ。
- 生成 C の `L_41223e: ... fle_ld((R[3] + (R[6]*8)), 8)` と、objdump の `call [rbx+rsi*8]` が一致。
- 未検証: 0x412258 と 0x41226d が実行時に到達しないことを、トレースで直接確認してはいない。

### 値の定義元（実測）

- `t = fle_ld(rbx + rsi*8, 8)` の `rbx` は表の先頭 `0x13a9410`、`rsi` は 1。
- 読まれる 8 バイトは `0x13a9418`。PE の生データ（`pe_probe.py qword 0x13a9410 0x13a9418`）で `0x13a9410 = 0x41d0e0`、`0x13a9418 = 0x41d050`。
- `0x13a9418` は `.data` にあり、DIR64 の再配置が付いている（`pe_probe.py reloc_covers 0x13a9410` は True。0x13a9418 も同じ表の要素）。つまり、ローダーが書いた関数ポインタ。
- `.text` の中に `0x41d050` へ直接の `call/jmp` は無い（`objdump` 全 `.text` で 0 件）。
- 表の値は実行時に書き換えられていないと推測される（コード中の 0x13a9410 への書き込みは、objdump の範囲内では確認していない。未検証）。

## 3. 分類と根拠

- (a) 関数の内側: **否定**。0x41d050 は pdata の関数先頭（offset 0）（実測）。
- (b) 関数 entry だが表に入っていない（表の生成の誤り）: **否定**。表の生成は閉包のみを対象にしている（`dispatch.rs` の `table(entries)`。`entries` は閉包の関数）。0x41d050 は閉包に入っていない（生成 C に無い）。
- (c) 閉包の外（lift されていない関数）: **採用**。0x41d050 は関数 entry だが、閉包の再帰降下（直接 call/jmp と export/entry の seed）からは到達しない。到達するのは、`.data` の表から間接に読まれたときだけ（実測と推測）。
- (d) その他: 該当なし。

閉包が 0x41d050 に到達しない理由（推測）: `fe-decode` は seed として entry と export だけを使い、`.data` の関数ポインタ表は読まない（`fe-decode/src/lib.rs` の seed 収集、`docs/investigations/closure-count.md` の「定義」節。実測で確認）。

## 4. 修正すべき場所（案。修正はしていない）

- 第一候補: `lift/crates/fe-decode/src/lib.rs` の閉包の seed に、「`.data`（非 `.text`）の DIR64 再配置の位置で、値が `.text` 内を指すもの」を加える。`fe-pe` で再配置を読む必要がある。
  - 0x41d050 は pdata の関数先頭なので、「pdata の begin と一致する値」を条件にすれば、データ中の偶然の値を除ける（推測。条件の妥当性は未検証）。
  - 影響: 閉包が広がる（件数は未計測）。`closure-count.md` が言うように、閉包はすでに下界なので、広がること自体は想定内。
- `lift/crates/fe-lift/src/dispatch.rs`（表の生成）と `fe-lift/src/lib.rs`: 閉包の entry から表を作るので、閉包が正しければ表は自動で直る。表の生成側の変更は不要と推測。
- 変更しないほうがよいもの: 表に閉包の外の全 pdata 関数を入れる案。閉包の設計（閉包内だけを lift）から外れ、件数も大きい（後述）。

## 5. 同型の件数（実測。集計方法を明記）

閉包内の dispatch 先（間接 call 6,478 件）の実行時の宛先は、静的には得られない（データフロー解析は全件未解決。`closure-count.md` の U-E2 節）。このため「閉包内の全 dispatch 先」の件数は、この調査では **出せていない**。

代わりに、イメージ全体で「`.text` 以外のページにある DIR64 再配置の値のうち、`.text` を指すもの」（コードを指す関数ポインタの候補）を数えた。`lift/out-diag/pointer_census.py` による。

| 項目 | 件数 |
|---|---|
| 表（閉包の entry）の行数 | 6,969 |
| コードを指す値（distinct、`.text` 以外のページの DIR64 の値） | 6,974（再配置の位置 8,044） |
| うち表に有るもの | 12 |
| うち表に無いもの | 6,962 |
| 　　pdata の関数 entry（閉包の外と推測） | 852 |
| 　　pdata の関数の内側（entry でない） | **0** |
| 　　pdata の範囲に無い（未分類） | 6,110 |

- 「関数の内側」を指すデータ中の関数ポインタは 0 件（実測）。よって、0x41d050 と同型の (a) は、データ由来の値の中には見つからなかった。
- 6,110 件の「pdata に無い」値（例: 0x4071d0、0x413fcc、0x418c1d）は、linear 検索でも pdata に無いことを 4 件で確認（`pe_probe.py` と照合）。これが関数ではない（データ、thunk、pdata 外の leaf など）かは未検証。
- 閉包内の dispatch 先の正確な件数は、(i) 6,478 件の dispatch を実行トレースで集計する、(ii) データフロー解析で宛先を解く、のどちらかが要る（推測）。

## 6. 検証と制約

- 実行したスクリプト（読み取りのみ、`lift/out-diag/`）:
  - `pe_probe.py`: セクション、VA の値、pdata 包含、再配置、生バイトの検索。
  - `pointer_census.py`: 上記の集計。
- `objdump -d` を 0x1376820〜0x1376880 に対して実行し、`lift/out-diag/objdump_1376820_1376880.txt` に保存（小さなテキスト）。
- `lift/objdump-text.txt` は 0x11fb4af で途切れていて、entry 0x1376820 を含まない（`tail` で確認）。entry 付近は `objdump` を直接使って補った。
- 未検証: 0x412258 と 0x41226d が実行中に到達しないこと（トレースで直接は確認していない）。`0x15ec2a8` の実行時の値（`.bss`。0 とした。`f_412160` の 5 番目の引数の経路は未追跡）。

## 7. 推測と実測の区別（まとめ）

- 実測: 0x41d050 の pdata 関数先頭、`.data` 0x13a9418 の値、`0x41223e` の `call [rbx+rsi*8]`、表の不在、`f_41d050` の不在、閉包 6,969 関数、データ中の関数ポインタの内側 0 件。
- 推測: 閉包がデータ中のポインタを読まないのが直接の原因、0x41223e が実際の miss の場所（トレースでは未確認）、6,110 件の pdata 外の扱い、修正の影響範囲。
