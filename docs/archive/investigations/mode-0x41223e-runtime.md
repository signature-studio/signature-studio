# 0x41223e の mode（rsi）と dispatch 先の実行時の確認

対象: `binaries/win64/FLEngine_x64.dll`（読み取りのみ）。
計測: `lift/out-mode/`（新規。複製した `after.c` に probe を 1 行追加し、ビルド、実行）。
既存の生成 C（`lift/out-imp/after.c`）、既存の harness、既存のトレースは変更していない。

「実測」は objdump、生成 C、実行ログの結果。「推測」は未検証の解釈。

## 1. 0x41223e 周辺の命令（実測。objdump と生成 C の一致を確認）

```
412160 push rbp / r13 / rdi / rsi / rbx   ; 入場
41216d mov rbp,rsp
412170 mov rax,rcx
412173 mov rbx,r9                          ; rbx = 表の基底（呼び出し元が r9 = 0x13a9410）
41217d cmpl [rbp+0x170],2                  ; 0x170 の読み出しのみ
412184 jb 0x41218d
412186 lea r13,[0x15eada8]                 ; (rbp+0x170 >= 2 の時のみ)
41218d .. 4121b8  rep movsq（rbp+0x20 などへのコピー。0x170 は読むだけ）
4121d0 cmpl [rbp+0x170],0                  ; 読むだけ
4121d7 jne 0x4121e5
...
412211 movzbq rax,[rbp+0x170]              ; 読むだけ
412226 cmpl [rbp+0x170],1
41222d je 0x412238                         ; [rbp+0x170] == 1 で 0x412238 へ
41222f cmpl [rbp+0x170],2
412236 jne 0x412241                        ; ==2 でなければ飛ばす
412238 mov esi,[rbp+0x170]                 ; rsi = [rbp+0x170]（32bit、ゼロ拡張）
41223e call *(%rbx,%rsi,8)                 ; 表[rsi] を呼ぶ
412241 cmpq [rbp+0x160],0
```

- **rsi の代入元**: 明示的な代入は `412238: mov esi,[rbp+0x170]` のみ（0x412160 の範囲内）。`rsi` は `412238` の直前で、`[rbp+0x170]` の値そのものになる。注意: `rep movsq`（4121a8、4121b8）も暗黙に rsi を更新するが、いずれも 412238 より前で、412238 と 41223e の間に rsi を書く命令は無い（実測）。
- **[rbp+0x170] の書き込み元（0x412160 の範囲内）**: 書き込みはなし。読み出しのみ（上の命令すべて）。
- 0x41223e に入るのは、`[rbp+0x170] ∈ {1, 2}` のときだけ（実測。上の分岐の並び）。
- 0x41223e の `call` 先は `表[rsi]`。表の基底は `rbx = r9 = 0x13a9410`（呼び出し元 0x41d95a の `lea r9,[0x13a9410]` が設定）。

## 2. 表の内容（実測。`objdump -s` で確認）

`.data`（VA 0x13a9410）の先頭 4 要素:

| 添字 | VA | 値（実測） | 所属（前回調査の記述。未再確認） | 0x41223e に到達しうるか（実測の分岐） |
|---|---|---|---|---|
| 0 | 0x13a9410 | 0x41d0e0 | 閉包外 | 不可（[rbp+0x170]=0 は 0x41223e に入らない） |
| 1 | 0x13a9418 | **0x41d050** | 閉包外 | 可（実測で到達、rsi=1） |
| 2 | 0x13a9420 | 0x41d000 | 閉包内 | 可（分岐上は到達しうる。今回は未実行） |
| 3 | 0x13a9428 | 0x41d090 | 閉包外 | 不可（[rbp+0x170]=3 は 0x41223e に入らない） |

（値は .data のファイル上の値を objdump -s で確認。ImageBase 0x400000 で実行しているため、VA と一致する前提。）

## 3. 実行時の値（実測）

`lift/out-mode/run1.txt`（exit 134 = SIGABRT）:

```
calling entry (no export name) rcx=0x400000 rdx=1 r8=0 rsp=0x7ab3209fffc0
MODE 0x41223e rsi=1 rbp170=1 tgt=0x41d050
fle: indirect call to 0x41d050 is not a known function entry
== stop: SIGABRT
abort kind: fle_dispatch_miss
dispatch target: 0x41d050
```

- **0x41223e に到達した**: はい（実測）。
- **到達時の rsi**: 1（実測）。
- **到達時の [rbp+0x170]**: 1（実測。rsi と一致）。
- **dispatch の宛先**: 0x41d050（実測）。表の添字 1 の値。dispatch 表に無いので abort（実測）。
- 呼び出しの前の状態: `call depth 3`。経路は `f_1376820` → `f_41d8f0`（guest-return 0x1376875）→ `f_412160`（guest-return 0x41d989）→ 0x41223e。

## 4. 0x41d050 が呼ばれたか（実測）

- **呼ばれた試行は 1 回**: 0x41223e の `call *(%rbx,%rsi,8)` が、rsi=1 で 0x41d050 を渡し、`fle_dispatch` の段階で見つからず abort。0x41d050 の実行（関数本体）には入っていない（`function entries` の 7 件に 0x41d050 は無い）。
- 呼び出し経路（実測）: `0x1376820`（entry）→ `0x41d8f0`（`call` at 0x1376870）→ `0x412160`（`call` at 0x41d984）→ `0x41223e`（`call *(%rbx,%rsi,8)`）→ dispatch 0x41d050 → miss。
- なお、既存の `lift/out-imp/run1.txt` と同じ結果（同じ停止点、同じ呼び出し経路、同じ dispatch 先）。

## 5. [rbp+0x170] の書き込み元（閉包内で確認できた範囲）

- **0x412160 の関数内**: `[rbp+0x170]` への直接の書き込みは無い（実測。上の 1 節）。ただし次は未確認: `rep movsq` の宛先（rcx 由来のポインタと r13 由来のポインタ）が rbp のフレームと重ならないこと、および 0x41d8f0 より前に呼ばれる `call 0x406f90` が、フレームへ書かないこと（推測。ポインタの値は実行時に見ていない）。
- **呼び出し元の鎖（実測。objdump で確認）**:
  1. `0x1376820`（entry）: `mov %edx,0x3c(%rbp)`（0x137682f で、edx を自分のフレームに保存）。`mov 0x3c(%rbp),%r9d`（0x1376863）。`call 0x41d8f0`（0x1376870）。
  2. harness は `rdx=1` で entry を呼ぶ（`main.c`、`R[2] = 1`）。よって `r9d = 1`。
  3. `0x41d8f0`: `mov %r9d,%r13d`（0x41d902）。`cmp $1,%r13d`（0x41d905）。1 なので init 分岐（0x41d90b〜0x41d948）に入り、`call 0x41d170`。
  4. 0x41d94d 以降: `mov %r13d,0x30(%rsp)`（0x41d972）。`lea %r9 ← 0x13a9410`（0x41d95a）。`call 0x412160`（0x41d984）。
  5. 0x412160 から見た `[rbp+0x170]` は、呼び出し元の `0x30(%rsp)` と同じ位置（算術で確認。0x412160 は push 5 回と `sub $0x110` の後、`rbp = rsp0 - 0x138`（rsp0 は戻り番地の位置）。`rbp+0x170 = rsp0+0x38`。呼び出し元の `0x30(%rsp)` は `rsp0+8+0x30 = rsp0+0x38`）。
  - よって `[rbp+0x170]` = 0x41d8f0 の `r9d` = 0x1376820 の `edx` = harness の `rdx`（DllMain 相当の reason。この実行では 1）。**この鎖は、逆アセンブルの算術で確認した（実測。実行時の 1 とも一致）**。
  - 注意: 「`r9d` が DllMain の reason である」の解釈は推測（entry の引数の名前は未確認。実行の入力が `rdx=1` であることは harness の実測）。
- 0x41d8f0 の直接の `call` は 1 箇所（0x1376870）。0x412160 の直接の `call` は 1 箇所（0x41d984）（`objdump` の文字列検索。間接 call は対象外）。

## 6. 確認の範囲と限界

- 0x412160 から 0x41223e までの命令は、objdump と既存の生成 C の両方で確認（実測）。
- `[rbp+0x170]` の実行時の値 1 は、この 1 回の実行（harness の rdx=1 の entry）でのみ観測（実測）。他の入力や実行では未確認。
- 0x41223e が 2 回以上呼ばれるかは未確認（この実行は abort で止まるため）。
- `[rbp+0x170]` を書く関数（閉包内の 0x412160 の外）は、この計測では網羅していない。0x41d8f0 の経路は確認したが、閉包内の他の書き込み元は未調査（推測の余地）。

## 7. 失敗と拒否

- 権限拒否、削除、既存ファイルの上書き、git 操作、`/tmp` の利用、sleep/timeout は使っていない。
- ビルドと実行のツール呼び出しには、ツール側の timeout パラメータ（900000 ms）を指定した。`timeout` や `sleep` のシェルコマンドは使っていない。

## 8. 残りの作業量

- 0x41d8f0 の第 4 引数（`r9d`）の由来: 節 5 の鎖として確認済み（逆アセンブル）。ただし、entry の引数の名前（DllMain の reason か）は未確認。
- 0x41d8f0 の直接の呼び出し元: 1 箇所（0x1376870）。実測。
- `[rbp+0x170]` を書く他の閉包内の関数の網羅: 未実施。大きい。
- フル lift の達成（依頼の最終目的）: 本作業の範囲外。この計測では、0x41d050 が表の範囲で正しく呼ばれないことが、dispatch の miss として確認できただけ。
- 表の添字 1（0x41d050）が、本来どの関数を指すべきかの判断: 未実施。
