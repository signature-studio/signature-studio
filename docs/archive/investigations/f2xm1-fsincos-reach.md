## 1. 到達性（質問 1）

### 1.1 方法

- 呼び出しグラフ: `out-x87/out/after-x87.c`（all-pdata、58,695 関数）から、`f_X();`（call と tail jmp）の**直接**辺、関数アドレス定数 `UINT64_C(0x…)` が関数先頭と一致するもの（lea / mov imm の**アドレス取得**辺）、`fle_dispatch(` を含む関数（間接 call あり）を抽出（`graph.py` → `graph.json`）。
- 根（`reach.py`）: InitTable は構造体 0x13768b0（`+0` 件数 942、`+8` 先頭 0x13768e0、要素 16 B）。proc≠0 かつ LD64(proc)≠0 を数えて **895 件（異なる値 895）**（`reach-out.txt`、既存の記録と一致）。DllMain＝PE エントリ 0x1376820、export は `CreateFruityInstance`＝0x1375990、`__dbk_fcall_wrapper`＝0x41d5a0。合計 898 根。
- 注意: 間接 call（`fle_dispatch`、vtable、関数ポインタ変数）の飛び先は追えない。以下は「直接辺＋アドレス取得辺」で追える範囲と、関数ポインタ変数の**読み手の探索**（逆アセンブルと .reloc）の結果。

### 1.2 所在関数の中身（静的、逆アセンブル）

`f_6a2a10`（0x6a2a10–0x6a2a85、f2xm1 は 0x6a2a53）: 引数 rcx=float 配列、edx=個数、r8=float 3 個 {a, b, c}。各要素 v について `x=|v|`、`x>a`（整数比較）なら

`y=((a−x)·c)·log2e`（fldl2e）、`n=frndint(y)`、`f=y−n`、`2^y = fscale(1+f2xm1(f), n)`、`out = a + b·(1−2^y)` を float32 で `fstp`、符号を戻す。

（指数飽和曲線。推測。）

`f_6a3990`（0x6a3990–0x6a39be、fsincos は 0x6a39ad）: `fld1; fadd dword p; fmul qword [0x13e7538]`（値は 0.7853981633974483＝double の π/4、PE から読んだ）`; fsincos; fmul dword g; fstp [rcx]; fmul dword g; fstp [rdx]`。つまり `[rcx]=float32(cos t·g)`、`[rdx]=float32(sin t·g)`、`t=(1+p)·π/4`（等パワーパン。推測）。

隣の `f_6a39c0` は線形版で、fsincos を使わない（x87 は対応済み）。

### 1.3 f2xm1: 関数ポインタ表のスロット 0x15f4b70 に書かれるだけ（実測）

- 直接呼び出し元: **0**。`f_6a2a10` のアドレス定数は 1 か所（0x6a6d4d の `lea rax,[0x6a2a10]`、unit 0x6a6890 内）だけ（`reach-out.txt`）。
- unit 0x6a6890（InitTable index **185**、`cpustruct-out.txt`）は、前半（0x6a6bb7–0x6a6d54）で関数ポインタ 43 個を `.bss` 0x15f49xx–0x15f4bxx のスロットに書き、後半（0x6a6d6c 以降、30 スロット）は `[[0x15e4c78]+0x16] != 0` のときだけ別実装で上書きする（`slots-out.txt`）。0x6a2a10 はスロット **0x15f4b70** へ（後半の上書き先は 0x6a6710）。
- **スロット 0x15f4b70 を読む命令**（`deadslots-out.txt`、`deadslots_full-out.txt`、`deadslots2_full-out.txt`）:
  - rip 相対の参照: 書き手 2 件（unit 内）のみ。読み手 0。
  - .reloc（DIR64 278,531 件）でスロット 0x15f4b70 を指すポインタ: 0 件。（近隣 0x15f4b68 と 0x15f4b80 を指すセルはあり、`call [reg]` で**そのスロット自身**を呼ぶだけ。`cells_full-out.txt`）
  - .text の生の imm32/disp32 で 0x15f4b70: 0 件。
  - 表の途中を指す `lea` で添字アクセスしうるもの: 0x15f4000–0x15f4b77 の範囲に 70 個の `lea` 対象があるが（`leas-out.txt`）、0x15f4898 などは別の構造体（`call 0x4232e0`、0x417fc0 などに渡す）で、0x15f4b70 に届く添字アクセスは見つからなかった（**推測**: 「見つからなかった」は網羅の証明ではない）。
- 結論（静的）: f2xm1 を含む関数は、**アドレスがスロットに格納されるだけで、呼ばれる経路がない**。実行時にも後半の上書き条件 `[[0x15e4c78]+0x16]` は、`.bss` 0x15f32f6 の 1 バイトで、初期値 0、rip 相対の書き込みなし、22 か所の読み手（`[rax+0x12]` / `[rax+0x16]` の test/cmp のみ。`cpustruct-out.txt`、`leas-out.txt`）にも書き込み様の使い方なし。したがって後半は実行されず、スロットは `f_6a2a10` のまま（推測、静的）。ただし**スロットが呼ばれない**ので、これは結論に効かない。
- 補足: all-pdata の BFS（直接＋アドレス取得辺）では、`f_6a2a10` は InitTable index 185 から「到達」と数えられる（アドレス取得辺のため）。呼ばれる到達ではない。

### 1.4 fsincos: 既定の経路で呼ばれる（実測）

- スロット 0x15f4b28（`f_6a3990`）の読み手（`deadslots_full-out.txt`、`deadslots2_full-out.txt`）: ① `f_6a3a00` の `call [0x15f4b28]`（0x6a3a4e）、② `.reloc` 付きセル 0x15e1578（0x15f4b28 を指す）を読む 0x67fec6 と 0x680069（`call [rsi]`、所属は `f_67fe40`、`f_67ffc0`）。
- `f_6a3a00`（0x6a3a00）は、パン値 xmm2 を [−1.0, +1.0] に clamp（定数 0x6a3a5c＝−1.0f、0x6a3a60＝+1.0f）し、`[0x15f49a4]==1` のとき xmm3 に `[0x15f49ac]` を掛けて線形版 `f_6a39c0`（スロット 0x15f4b30）を呼び、**それ以外（初期値 0 を含む）は fsincos 版**（スロット 0x15f4b28）を呼ぶ。`[0x15f49a4]` の書き手は `f_6a3a70`（呼び出し元: unit 0x6a6890 が自身の値 0 を渡す、`f_1363420`）。`f_1363420` は直接呼び出し元がなく、データポインタ 1 件（0x13532cc、`.reloc`）で参照される（静的）。
- `f_6a3a00` の直接呼び出し元（6 件、`deadslots-out.txt`）: `f_d0cc10`、`f_d24ae0`、`f_fe8f30`、`f_127b010`、`f_132ac70`、`f_132ac90`。
- **直接 call だけの BFS（`path-out.txt`）**: 根 3 つから `f_6a3a00` に届く。
  - `CreateFruityInstance`（0x1375990）→0x1375950→0x11efbf0→0x1253610→0x128f9e0→0x128c320→0x1046a30→0x127b010→**0x6a3a00**（8 ホップ）
  - InitTable index **895**（proc 0x12ddfe0）→0x1305fd0→0x12f98f0→0x11ff410→0xf54570→0xf40840→0xf3d5e0→0x1046a30→0x127b010→0x6a3a00（9 ホップ）
  - InitTable index **898**（proc 0x1306110）→同上 9 ホップ。
  - DllMain（エントリ）からは直接 call だけでは届かない。
- 全体: 直接辺のみの上向き閉包は 2,135 関数、直接＋アドレス取得辺で 3,108 関数。根 898 からの下向き閉包は直接のみ 8,427、直接＋アドレス取得 11,499（`reach2-out.txt`）。
- `f_127b010` の入力（静的）: `cvtsi2ss [rbx+0x388]`（int）× float32 `[0x13e757c]`（0.00015624999650754035＝1/6400 を float32 にした値）が xmm2。ゲイン xmm3 は xmm6×`[0x15f49a8]`（`[0x15f49a8]` は unit 0x6a6890 が計算して書く float32、静的値は未確認）。出力は `[rbx+0x80]`（cos·g）と `[rbx+0x84]`（sin·g）。
- ほかの呼び出し元 5 件の p（xmm2、静的）: `f_132ac90` は `cvtsi2ss r9d × [0x15e3ed8]`（倍率は未確認）、`f_132ac70` は引数 xmm3 を素通し、`f_d0cc10` は `[rsi+0xdc]`（float）、`f_d24ae0` は `[rbx+0x28c]+[rbx+0xc8]`（float の和）、`f_fe8f30` は `[rbx+0x198]`（float）。p の範囲は静的には決まらない（`f_6a3a00` の clamp で [−1,1] に入る）。
- `[0x15f49a4]` を 1 にできる経路は `f_1363420`（直接呼び出し元なし、`.reloc` のデータポインタ 1 件）だけ。ユーザー設定のコールバックと見られる（推測）。
- 判定: fsincos は「直接 call 経由で到達する」。間接 call 経由でしか到達しない、または未使用コード、ではない。**実行ではまだ到達していない**（§1.6）。

### 1.5 FLEngine が x87 制御ワードを変えるか（RC/PC、静的）

- 先行記録の「fldcw 48 箇所」は、`lift/objdump-text.txt` が VA 0x11fb4af で切れている（.text は 0x13a44af まで）ための数。`out-x87b/objdump-tail.txt`（0x11fb4a0–0x13a4fff を新規に objdump）で数え直すと **fldcw は .text 全体で 55 箇所**（`trunc_check-out.txt`、新規 7 件は `f_1277cb0`、`f_12cbeb0`、`f_13768a0`）。rip 相対 10 件（参照先の初期値は 0x033F、0x073F、0x0F3F、0x033F、`mode_cw_full-out.txt`）。閉包内の関数で到達可能（根から直接＋アドレス取得辺）なものは 19 関数 38 命令。
- `f_6a3a00` の上向き閉包 3,108 関数、`f_6a3990`、`f_6a2a10` の閉包（2 関数）に **fldcw/ldmxcsr/fninit を含む関数は 0**（`leas-out.txt`）。つまりこれらの呼び出し鎖の中で制御ワードは変わらない。他の経路（先に走った別の関数）が変えて戻していない場合は、runtime の既定 `fle_x87.cw = 0x037F`（PC=64、RC=最近偶数。`fle_x87ctl.c`）のまま。**Windows の実プロセスの初期値**（推測: 0x027F、PC=53）はこの作業では確認していない。
- この 2 命令に対する効き方（実測、`determ-out.txt`）: ホストの f2xm1・fsincos とも **PC を変えても結果は同じ**（100,000 入力で 0 件）。**RC を変えると変わる**（RC が最近偶数以外の CW で、f2xm1 は 1 CW あたり入力の約 50% で変わる。`determ-out.txt` の RC=1 は 1 CW で 49,928/100,000、RC=2 と RC=3 は各 2 CW の合計）。SDM の「PC は FADD…FSQRT の結果にだけ効く」（Vol.1 §8.1.5.2）と一致。

### 1.6 実行では未到達

`out-x87/run-x87.txt`（既存）は `VerifyVersionInfoW`（0x423cc0 ← … ← エントリ）で停止し、x87 に到達していない（`x87-run.md` §5）。InitTable index 185、895、898 と CreateFruityInstance は、停止点の後。この作業では実行を再開していないので、**動的な到達（fsincos が実際に実行されるか）は未確認**。

### 1.7 副次的な発見（既存の記録への影響）

- `lift/objdump-text.txt` が切れている問題: 既存の `out-x87/work/mix.py`（MMX と x87 の混在確認）は mm 命令を `objdump-text.txt` で数えたため、末尾の MMX 関数 `f_12c0c00` と `f_13768a0`（tail に mm 命令 13 件、`tailcheck-out.txt`）を含んでいない。この 2 関数は x87 を持たず、直接 call の下向き 37 関数にも上向き 0 関数にも x87 関数はない（`mmx_tail-out.txt`）。決定 0033 の「両方を含む関数はない」「到達範囲に x87 関数はない」は、この 2 つについても成り立つ。

## 2. 再現可否（質問 2）

### 2.1 (a) ホストの出力は決定的か（実測）

- 入力 80 bit ＋ RC だけで決まる: f2xm1 100,000 入力×3 回の繰り返しで不一致 0、CW を 0x037F から 0x027F、0x007F（RC=0、PC 違い）に変えても不一致 0。RC=1/2/3 では不一致（RC=1: 49,928、RC=2: 100,144（2 CW 合計）、RC=3: 99,924（同））。fsincos の sin/cos も同様（RC=0 は 0、RC=1: 74,980、RC=2: 149,294、RC=3: 150,186）。PC 0〜3 の f2xm1 を RC 最近偶数で比べると全て 0 件（`determ-out.txt`）。
- 隔離実行（FNINIT、CW=(guest&0x0F00)|0x3F、命令、FNSTSW、pop）の 800,000 回で、同じ入力の 2 回の結果が全て一致、実行後のホスト x87 は TOP=0・タグ全 empty（`d1proto2-out.txt`、`d1proto2.c`）。
- 正しく丸めた値との不一致（前任の測定の再確認＋入力域を変えた測定）: f2xm1 200,000 件中 5,696（2.85%、1 ulp）、fsincos 26,840（13.4%）（`probe_trans-out.txt`、既存）。f2xm1 の引数が `f=y−n`（|f|≤0.5）の範囲だと 2.98%（`effect-out.txt`）。fsincos を t=(1+p)·π/4、p は float32 の [0.5,1) 全数で 25.1%（2,102,539/8,388,608）、[0.25,0.5) で 6.7%、(−1,−0.5] で 1.6%（`determ-out.txt`）。

### 2.2 (b) AMD と Intel で異なる、仕様から決まらない（SDM と外部）

- SDM Vol.2 の F2XM1（`lift/out-int2/spec/sdm-vol2.txt` 20620–20659 行）: 「ST(0) を 2^ST(0)−1 で置き換える」、入力範囲は −1.0〜+1.0（外は結果未定義）、C0/C2/C3 は **Undefined**、C1 は丸め上げ。結果の正確さの記述なし。FSINCOS（23740–23780 行）: 範囲 −2^63〜2^63、範囲外は C2=1 でスタック不変、「有限の π の近似のため範囲内でも不正確な結果がありうる。3π/8 未満に縮約した引数にだけ使うのが安全」。
- SDM Vol.1 §8.3.10（`lift/out-mmx/spec/sdm-vol1.txt` 12968–13031 行）: 超越関数の誤差は「nearest(even) で 1 ulp 未満、他の丸めモードで 1.5 ulp 未満」、「入力に対して単調」。FSIN/FCOS/FSINCOS/FPTAN は内部の Pi（66 有効ビット、`C90FDAA2 2168C234 C`、§8.3.8）で縮約するため、π/2 の倍数付近で誤差が大きくなる。**アルゴリズム、どの丸めの値か、ベンダー間の同一性は規定されない。**
- したがって「どの CPU の値に合わせるべきか」は仕様から決まらない。仕様から決まるのは誤差の上限（1 ulp 未満）だけで、正しく丸めた値は上限内。ホストの値も上限内と見られる（f2xm1 は不一致 5,696 件が全て 1 ulp 差、`probe_trans-out.txt`。fsincos の差の大きさは測っていない）。
- 外部（Intel 実機で未確認）:
  - glibc の libc-alpha ML（2024-07-25、A. Monakov）に、x=−0.499999035362962251737L の f2xm1 が AMD で `-0x9.5f609bac112d4dbp-5`、Intel で `-0x9.5f609bac112d4dcp-5` となる例。**このホストで実行すると AMD の値と一致し、正しく丸めた値は Intel の値と一致した**（`monakov-out.txt`、`monakov.c`）。1 例だけで、Intel 実機が常に正しく丸めた値という意味ではない。
  - Stack Overflow の回答・コメント（超越関数は Intel と AMD で値が変わる、AMD K6〜Athlon の FPU 設計経験者のコメント、sinl の hash が Intel と AMD で違った実験）。裏付けは強くない。
- 副次の実測（SDM の記述の確認）: fsincos の π 近似。p=+1.0 で t は double の π/2 より 6.1e-17 小さく、ホストの cos は 6.1230317691e-17、正しく丸めた値は 6.1232339957e-17。SDM の Pi（66 ビット）で `Pi/2−t` を計算すると 6.123031769112e-17 で、**ホストの値と一致**（`pi66-out.txt`、`edge-out.txt`）。ホストが SDM どおりの Pi で縮約していることの確認で、同じ Pi を使う Intel でもここは一致すると推測できるが、確認はしていない。

### 2.3 ステータスワード（実測、`swprobe-out.txt`、`d1proto2-out.txt`）

- f2xm1: 有限・非零の入力で PE=1、C1 は入力の約 36%（丸め上げ）で 1、C0/C2/C3 は**変更しない**（事前に立てた C0/C2/C3 が残る。SDM は Undefined）、非正規化入力は DE・UE も立つ、NaN 入力は IE。
- fsincos: 範囲内で C2 を 0 にし、C0/C3 は変更しない（SDM どおり）。|x|≥2^63 で C2=1（スタック不変、27,894 件）。PE、C1 の出方は f2xm1 と同様。

### 2.4 FLEngine の出力に効く範囲（到達した場合の静的推定）

- fsincos: 出力は `[rcx]`＝`float32(cos t·g)`、`[rdx]`＝`float32(sin t·g)`（左右ゲイン）。呼び出し元 `f_127b010` では `[rbx+0x80]`、`[rbx+0x84]`（チャンネル構造体、`rbx = [0x15e06a0] + ch·0x28f·8`）に書かれ、続けて 0 チェックと除算に使われる。**これらが描画やファイル出力に至るか（ミキサのゲインか）は追っていない**（推測: 音量・パンのゲイン）。他の呼び出し元 5 件の使い方も追っていない。
- f2xm1: 呼ばれないので影響なし（静的）。

## 4. 実装方針の候補（質問 3）

- 「SDM の Pi（66 ビット）で π/2 縮約してから、縮約後の引数の sin/cos を正しく丸める」モデル（`model66.c`、以下 M66）は、ホスト fsincos と f80 で 98.4%（p∈[0.5,1)）、97.5%（[0.25,0.5)）、p=1−k·2^−24（k=0..65536）では 1 件を除き一致。ランダム f80 では 98.8%（`model66-out.txt`）。f80 で bit 一致はしない。**float32 出力は、パン整数 [−13000,13000]×ゲイン 104M 組で不一致 0、p=1 を含む**（`domain-out.txt`、`domain3-out.txt`）。

## 5. 推奨（1 つ）

**D1: f2xm1 と fsincos を、ゲストの PC/RC を載せて、ホストの命令で隔離実行する。**

理由（事実に基づくもの）:

1. A2（生成 stub=0、fail-closed なし）を緩めずに済む。f2xm1 も含めて 2 件とも片付き、B の「例外」を ADR に書かずに済む。
2. fsincos は直接 call だけで CreateFruityInstance と InitTable の 2 unit から到達し、既定のパン法則（`[0x15f49a4]≠1`）で使われる（§1.4）。B は成り立たない。
3. A5 のオラクルの基準は「同じホストでの native との bit-exact」（決定 0035）。A と D2 は f80 で bit 一致せず、到達しうる float32 出力の差は p=+1 の 1 点（A）と 0（D2）。D1 は native と同じ命令を使うので全入力で一致する。
4. 「どの CPU の値に合わせるか」は仕様から決まらない（§2.2）。D1 は「実行している CPU に合わせる」という原本と同じ性質を保つので、この問いを決めずに済む。A/D2 は「正しく丸めた値」を選ぶが、それが Intel 実機と一致することは確認できていない（Monakov の 1 例で一致、外部の 1 点のみ）。
5. runtime は既に x86 限定（`fle_sse.h`）なので、移植性の損失は新たには増えない（推測: `fle_x87.c` 自体は ISO C だが、同じ runtime にリンクされる `fle_sse.h` は `emmintrin.h` を使う）。

D1 の代償（PM が判断する点）:

- 決定 0033 は「x87 を f80 のソフト実装にする」。D1 は、この 2 命令だけ**ホストの命令に依存**する例外を作る。出力は実行する CPU（AMD、Intel）で変わりうる（f2xm1 は到達しない）。
- 代案: **B（f2xm1 のみ）＋ D2（fsincos のみ）**。f2xm1 を「到達しない」ことを根拠に名前付き abort のまま ADR に明記し（A2 の例外 1 件）、fsincos はソフトで実装する。ホスト非依存・決定的だが、f80 の bit 一致は諦める（float32 出力は §3 のとおり全域で一致、ただし p=1 は Pi(66 bit) の縮約が必要）。f2xm1 の「到達しない」は静的な証拠のみ。

## 6. 確認できていないこと

- Intel 実機での f2xm1/fsincos の値（ホストは AMD）。外部の 1 例（f2xm1）のみ。
- fsincos の動的な到達（実行が x87 に未到達）。呼び出し元 `f_127b010` 以外 5 件の入力域と、出力が描画・ファイルに至る経路。
- Windows 実プロセスの x87 制御ワードの初期値（推測 0x027F）。この関数の呼び出し時の RC（静的には鎖の中に fldcw なし）。
- `[[0x15e4c78]+0x16]` が実行時に 0 のままであること（静的に書き手なし、動的は未確認）。スロット 0x15f4b70 の読み手がないこと（網羅の証明ではない）。
- D1 の runtime 版（FNINIT なし、`long double` を使うホストコードとの干渉）、D2 の実装。
- ADR-0009 の「A2」の定義の原文（リポジトリ内に見つからなかった）。
