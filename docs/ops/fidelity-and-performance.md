# lift の忠実性と性能(P1〜P3)

旧プロジェクトの規則を、新規約へ移した物。要約は `AGENTS.md` §6。
旧ポリシー文書と実装には食い違いがあった。**規則だけを移し、食い違いは移していない**(§5)。

## 1 lift の忠実性

- **バグなく動いている FL Studio を lift すれば、バグのないプロダクトが完成する。** バグの原因は 2 つだけ: (a) 我々が**余計なことをしている**、(b) **外部 API(Win32 など)の実装が不十分**(文書の契約に反している・不足している)。対処は (a) の除去と (b) の拡充に注力する。それ以外(FL の挙動を補う・代行する・特別扱いする・場当たりな近道)は採らない。
- **余計なロジックは見つけ次第抹消する。** 「余計」= FL の lift 済みコードが行うべきことを、ランタイムやページが代行・補正・上書きしている物 / FL のクラス名・窓の種類・位置による分岐 / 外部 API の契約の実装でも FL の挙動の観測でもない物 / 場当たりな軽量化(ページ側の窓ごとの canvas の並べ替えや可視・Z 順の決定、画素の重複排除などの局所的な近道)。
- **FL の窓管理(Z 順・前面化・閉じる・配置)は、Detached モードを除き FL Studio 自身が持つ。** 我々は介入しない。不具合は外部 API の拡充(契約どおりの戻り値・副作用・メッセージ)でのみ対処する。ページ・ランタイムは窓の挙動を決めない。
- **性能は「無駄な変換と通信を減らす」ことで出す。** wasm↔JS のシリアライズ・デシリアライズの削減、Worker↔メインスレッドの通信の削減(ピクセルのバケツリレー〔wasm → Worker → postMessage → メイン → canvas〕を避ける)。局所的な軽量化で性能を稼がない。
- 新しい処理・分岐・特別扱いを足すときは、それが (b) 契約の実装か、(a) の除去か、通信・変換の削減かを**決定文書に 1 行書く**。書けないなら足さない。

## 2 規則(きっかけ → やること → 確かめ方)

| # | きっかけ | やること | 確かめ方 |
|---|---|---|---|
| 1 | 余計なロジックを見つけた | **同じターン**に worker へ、除去の差分(旗を作らない。コミット同士で比較)と、症状の再現手順と P1〜P3 の該当測定(前後)を依頼。除去で壊れる物は (b) として API を拡充 | 差分と前後の測定の出力 |
| 2 | 除去・拡充の差分ができた | **単独で**取り込む(適用 → 試験 → commit)。より大きな push(別の大きな変更・ビルドの切替)の条件に括り付けない | `git log` に単独の commit。「後の push に載せる」の文が無い |
| 3 | 新しい処理・分岐・特別扱いを足す | 決定文書に分類行(b / a の除去 / 通信・変換の削減)を書く | `grep -n '分類' <決定文書>`。無ければ足さない |
| 4 | 規則文と自分の解釈が衝突する(例: 「画素の重複排除は余計」と「出力が同一の通信削減」) | 依頼者に尋ねない。**除去実験を先に出し、測定を添えて**「残した/外した」を判断し、決定文書に分類・撤回条件・測定を書く。外して P2/P3 が戻らないなら外す(規則の文面を優先) | 前後の測定、決定文書の行 |
| 5 | 「ゲストに実際と違う値を返す」物(Hz の上限・CPUID の固定・DPI・時刻)を見つけた | (a) として扱い、撤回条件を決定文書に書き、撤回した版を測る。(b) の契約の拡充で済む物(DPI・時刻・Temp)は拡充 | 撤回条件の行、測定 |
| 6 | 依頼者が実機で症状を見つけた | 1 件ずつ直さない。同型の症状を、Wine との系統的な差分試験で探す。原因の帰属(a か b か)を確定してから先へ | 差分試験の出力 |
| 7 | PROVISIONAL(仮の実装)を作る | 期限を付け、一覧を機械生成する(手で更新しない) | 一覧の生成コマンドと日付 |
| 8 | 依頼者の発言を受けた | 「余計」と指摘された物は、その場で除去。説明は除去の後 | 除去の差分 |
| 9 | 依頼者の指示を実装する | 条件の一覧に分解し、その一覧だけを worker に実装させる。足したくなった物は「提案: …」として最終報告に 1 行、足さない | 差分の各行が一覧のどれに当たるかの表。当たらない行 = 0 |

- 点検表(新しい処理を足すとき・既存を見直すとき):

| 問い | 「はい」なら |
|---|---|
| 外部 API の文書上の契約(戻り値・副作用・メッセージ)の実装か | 残す。出典と Wine 差分の試験を付ける |
| FL の観測(診断・ログ・計測)だけか | 製品の経路から切り離す(別の入口を持つ試験・計測の道具として。製品の中にスイッチを置かない) |
| FL の lift 済みコードがやるべきことを代行・補正・上書きしているか | 抹消。必要なら不足している API を拡充 |
| FL のクラス名・窓の種類・位置・文言で分岐しているか | 抹消 |
| 性能のための局所的な近道(重複排除・間引き・窓ごとの特別な描画経路)か | 抹消の候補。通信・変換の削減で置き換えられるか評価(規則 4) |
| 命令の意味(x87・SSE・MXCSR など)を速い近道で実装しているか | (A) 結果が bit 単位で同じ別実装、(B) 厳密な前条件を満たすときだけ近道し外れたら元の経路に戻る実装、の 2 つだけ忠実。いずれもホスト CPU・native との差分試験と変異試験を付ける。前提条件の無い近似は抹消 |
| 単に動かすための仮の実装(PROVISIONAL)か | 契約に照らして実装し直す。残す間は一覧と期限 |

## 3 性能 P1〜P3

| # | 条件 | 測り方(この機械・headless Chrome が基準。依頼者機の値は別枠) | 現状 |
|---|---|---|---|
| P1 | このマシンで起動が 10 秒以内に完了する(ページを開いてから、エンジンが入力を受け付ける状態〔最初の idle〕まで。ダウンロードとコンパイルを含む。初回とキャッシュ後を分ける) | 隔離した headless Chrome の自動測定を、同じ手順で複数回(n と中央値を書く) | 前任の文書の自己判定(再測定していない。[文書]): この機械で満たす。依頼者機 0 件。**再測定が要る** |
| P2 | 所定のプロジェクト(`~/ダウンロード/serina1-serum2.zip`)を開き、UI を 120 fps で動かし、UI 操作への遅延がほとんど無い(目標: 入力→画面の p95 が 17 ms 以下) | フレーム間隔と入力→面の更新までの ms。headless の rAF は 60 Hz のことがあり、120 fps は確認できない場合は、その旨を書く | 前任の文書の自己判定: 未達。**再測定が要る** |
| P3 | 所定のプロジェクトを Song Mode で再生して音が途切れない(AudioWorklet のリング枯渇 0。再生時間と消費フレーム数の比) | 枯渇カウンタ、曲の重い区間を含む再生 | 前任の文書の自己判定: 未達。**再測定が要る** |
| S1 | wasm と、エンジンが読むデータの大きさが、対応するネイティブの 2 倍以下(目標 1.2 倍)。生の大きさと brotli 後の転送量を両方測る | `ls -l` と brotli 後のサイズ | 前任の文書は食い違う [文書]: 旧記録は 1.845 倍(wasm 130,217,196 B)、後の自己判定は「2 倍以内を満たす」(wasm 143,087,706 B)。後者は、旧記録の native 合計(70,572,928 B)の 2 倍(141,145,856 B)を超える計算で、native 側の構成が変わったかは [未確認]。**再測定が要る** |

- 数字は、測定した値だけ。条件(マシン・ブラウザ・ビルドの種類・ネットワーク・n)を併記する。P1〜P3 のいずれかを満たしたら、独立再現(別の実行)を付けて記録する。
- 「現状」欄は旧文書の自己判定で、この規約では**検証されていない**。完了の宣言(`AGENTS.md` §9)には、**この機械の実測値**が要る。
- 現在の性能のままプロジェクトを終了させない。性能を画像の再生・事前に描いた画面・代役で満たしたことにしない(`docs/ops/honesty.md`)。
- 120 fps を満たす計算予算が届くかは、測って決める。届かないなら、測った予算の根拠を報告に書き、削減の作業(HLE・コード生成・GPU 利用・通信の削減)を続ける。「約束できない」で止まらない。
- 数値の基準・履歴の詳細は、旧作業ツリーの docs/milestones/performance-targets.md(新リポジトリには無い。読み取りのみ。場所は `docs/ops/lessons.md`)。新リポジトリの `docs/core/` に、要点だけを持ち込む(別の担当)。

## 6 新しい選択肢を作らない(旧 no-options の要点)

- オプション = 製品またはビルドの振る舞いを複数の選択肢から切り替えるスイッチ(URL パラメータ、localStorage、製品が読む環境変数、`#ifdef`/`-D` の無効側、ビルド変数・プリセット名、lifter の旗、workflow_dispatch の入力)。
- 新しいオプションを作らない。新機能は唯一の経路として入れる。未完成の機能は無効で出荷せず、完成まで作業木に置く。
- 排他の選択肢は、契約に合う方(または測定が良い方)を main が 1 つ選び、他を削除する。理由と測定を決定文書に書く。依頼者に選ばせない。
- 有効にして P1〜P3 を壊すなら、旗を戻して逃げず、コストを下げる作業で直す。
- 比較測定はコミット同士(別ビルド)。製品のコードに比較のための切り替えを残さない。
- オプションではない物: パラメータ(パス・並列数・サイズの上限)、データ(関数のリスト・import 行)、能力検出による自動の別経路(1 か所に決定論的に書き、決定文書に条件と理由)、製品に入らない別の入口の試験・計測の道具。
- 確かめ方: `grep -rnE 'getenv|URLSearchParams|location\.search|#ifdef FLE_|workflow_dispatch' <差分>` の各行を worker が分類し、reviewer が再実行する。
