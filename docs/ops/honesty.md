# 進捗の誠実性

旧プロジェクトの規則(依頼者の警告を受けて成立した恒久規則)を、新規約へ移した物。要約は `AGENTS.md` §5・§9。
旧ポリシー文書は、実装との食い違いがあった。**規則だけを移し、食い違い(旧実装の数値・手順の陳腐化)は移していない**(§6)。

## 1 定義

- **進捗** = lift した実エンジン(FL Studio のエンジン DLL と同梱 DLL を x86-64 → C → wasm にした物)が**実際に実行されて出した結果**だけ。G 段階表(`docs/core/ladder.md`)の到達も、この結果の観測でだけ数える。
- **代役等** = 進捗ではない物: 代役・モック・スタブ / 事前に生成した画像・録画・固定データの再生(PNG の貼り付けを含む)/ テストの期待値 / 実エンジン以外が出した画面や音 / 実機の挙動の推測。
- **既定の入口** = 依頼者が最初に見る場所: パラメータ無しの既定 URL、既定の manifest、README の先頭、報告の先頭。具体的な URL・パスは `docs/STATE.md` に書く。

## 2 規則(きっかけ → やること → 確かめ方)

| # | きっかけ | やること | 確かめ方 |
|---|---|---|---|
| 1 | 既定の入口に何かを置く・変える | 代役等を置かない。G 段階表にも数えない | reviewer が §4 の検査を実行して 0 件 |
| 2 | 代役等を見せる必要がある | (a) 案内の最初の行に「これは代役/画像の再生であり、実エンジンではない」、(b) 物自体(ページの目立つ表示・ファイル名・manifest 名・ログの先頭行)にも同じ表示、(c) 既定の入口には置かず明示パスだけ | 3 点が揃っている(1 つでも欠ければ見せない) |
| 3 | 404・停止・未実装・遅い | 見栄えの良い別の物で隠さない。原因を直すか、エラーのまま報告する | 報告にエラーの出力がある |
| 4 | 依頼者に URL・成果物・数値を案内する | 案内する URL と同一の URL を、パラメータ無しで headless Chrome で開き、結果を確かめる。HTTP の確認(`curl`)だけで済ませない。確認していない物は「未確認」 | 報告に URL・実行したコマンド・観測が書いてある |
| 5 | 報告を書く | 先頭に、実エンジンの実行の事実と、代役等の範囲(`docs/ops/reporting.md` §1)。数字は実測のみ | 報告の 1〜3 行目 |
| 6 | 誤りや逸脱に気づく | 指摘される前に、事実(何を・いつ・なぜ)と是正を報告する | 報告に是正の出力がある |
| 7 | worker/reviewer に依頼する | `prompts/worker-rules.md` を本文に貼る(要約を本文に直接。ファイル参照だけにしない) | 指示の先頭行のマーカー |
| 8 | 違反した成果が見つかる | 既定の入口から外し、`docs/STATE.md` の「依頼・誠実性の記録」節に、事実・原因・是正を追記 | 入口の検査が 0 件、記録の行 |

## 3 案内の前の確認(worker が実行。reviewer が再実行)

| # | 確認 | 確かめ方(旧 app の例。新 app では同等の物を `docs/STATE.md` に書く) |
|---|---|---|
| 1 | 案内する URL が、パラメータ無しの既定の入口か | URL に `?` が無い |
| 2 | 実エンジンが動いている | 実エンジンの識別(旧 app: `window.__app` の `engineKind` が `emscripten-fruity-v1`。`surface-table-v1` は代役)。エンジンのログが実エンジン固有の行を含む |
| 3 | 配布物が実エンジンの大きさか | wasm のサイズ(実エンジンは 100 MB 級。数 KB の wasm は代役) |
| 4 | 画面が出るまでの時間が実エンジンとして妥当か | 起動時間だけで判定しない。時間が極端に短いときは再生を疑い、2・3 を見る |
| 5 | 見つけた欠け(黒い領域・文字の欠け・遅さ)を隠さず書いたか | 報告に載っている |
| 6 | 案内文の先頭に、実エンジンの実行か代役かを書いたか | 先頭 1 行 |

## 4 代役・再生の混入検査(reviewer 用。出力を報告に貼る)

```
grep -rniE 'stand-?in|surface-table|stopscreen|replay|mock-engine|fake-engine' <差分のファイル・既定の入口から参照される物>
ls -la <既定の manifest が指す wasm>   # 数 KB〜数 MB なら代役の疑い
git diff --stat <基点>..HEAD -- <既定の入口に関わるパス>
```
- 出た行は、テスト専用(manifest-guard の試験など)か、既定の入口に届く物かを 1 件ずつ分類する。既定の入口に届く物があれば、完了にしない。
- 旧作業ツリーには代役の残骸(配信ディレクトリ・調査用の複写・補助スクリプト)がある。持ち込みは別の担当だが、**持ち込む前に分類し、既定の入口から参照される物を持ち込まない**。

## 5 数字・稼働数・割合

| きっかけ | やること | 確かめ方 |
|---|---|---|
| 数字(段階・件数・秒・fps・サイズ)を書く | 実測だけ。条件(マシン・ブラウザ・ビルド・ネットワーク・n)と出典コマンドを併記 | 出典の行 |
| 稼働中の worker 数を書く | `opencode api session.active` の出力(書く直前)から | 出力を貼る |
| 進捗の割合を求められた | 割合は出さない。G 段階表の到達と、測定済みの数字を示す(自作の指標・5 項目の平均を出さない)。理由を 1 行 | 「割合は出せない。代わりに …」の行 |
| 「完了」「達成」「N/N」を書く | 直前 5 分以内の出力を貼れるときだけ | 出力 |
| 文書(STATE・ROADMAP)が実態と食い違う | 取り込みのたびに worker に更新させる。HEAD から 3 日以上離れたら更新を割り当てる | `git log -1 --format=%cd -- docs/STATE.md` |
| テストが通ったと報告する | 合格数だけでなく、実エンジンの検査が実行された記録(観測値・スクリーンショット)があるか、打ち切りの例外が出ていないかを見る | 検査の出力 |
| 依頼者機の値 | 依頼票で計測を頼んだ後は「依頼者機の値: 依頼中」を未確認欄に毎回書く。この機械(headless Chrome)の値を、依頼者機の達成として書かない | 未確認欄 |

## 6 旧規則から移さなかった物(食い違い・陳腐化)

| 旧文書の記述 | 扱い |
|---|---|
| 「最初の idle まで約 40 秒、wasm は約 320 MB」を妥当の目安とする | 履歴の値。移さない。新しい基準は P1(10 秒以内)で、値は再測定する |
| 「数秒で全画面が出るなら再生を疑う」を単独の判定とする | 旧文書の注記が併記する実エンジンの実測(中央値 7.63 s)や、前任の記録(実エンジンで 4〜8 秒台)と矛盾する。起動時間だけでは判定せず、§3 の 2・3 を併用 |
| 旧 app の manifest-guard(代役の manifest を既定のパスで 409 にする)や代役表示の帯 | 旧作業ツリーの実装。新リポジトリにあるとは書かない。持ち込むか作り直すかは別の担当(`docs/core/`)で、持ち込まれるまで §4 の検査で代替する |
| 「ページに代役である表示は無く」(事案の記録) | 厳密には不正確(小さな表示が 1 行あった)と前任の資料が記録。規則には影響しない |

## 7 完了の宣言

- 完了を自己宣言しない。宣言できる条件は `AGENTS.md` §9。具体的には、報告に次を添える。
  1. 実エンジンが実行された出力(§3 の確認 2・3 の出力)。
  2. P1〜P3 の実測値(この機械・headless Chrome・条件つき。`docs/ops/fidelity-and-performance.md` §3)。依頼者機の値は別枠(「依頼中」。依頼票の前は「未計測」)。
  3. reviewer の検査結果(§4 の出力と、所定プロジェクトで開いた記録)。
- goal の判定が「完了」に傾いたら、完了を宣言する前に reviewer を起動する。reviewer が不一致を示したら、完了とは書かない。
- 揃わない間の報告は、「ここまで実測。次に動く物: …」で終える。
