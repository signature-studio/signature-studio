## 候補 1: fle_hyb_mx の境界(C-1)
- 分類: (c) 通信・変換の削減(wasm から C への境界)。
- 実測(b440・P2 台本・再生 10 秒・有効 n=3): `fle_hyb_mx` の自己時間の中央値 1.02%、包含の中央値 1.31%(`tools/verify-kit/tools/r44l-agg.mjs` の出力)。R4-4j §4.1 の 1.83〜1.88% とは定義が違う(`evidence/R4-4.md` §6)。
- 期待する削減: 上限は包含の中央値(1.31%)。コピーと MXCSR の再読込がすべて消えても、この値を超えない。
- 測り方: 同じ台本・同じ bundle の構成で n=3 の前後(製品の変更の前後)。Worker CPU ms/s の範囲(有効 3 回の最小と最大)の外に、包含の中央値が出るかを見る。Export の sha256 が変わらないこと(`evidence/R5-4.md`)。
- 撤回条件: (1) 変更の後、`fle_hyb_mx` の包含の中央値が、変更の前の 3 回の範囲の下限より下がらない。(2) Export の sha256 が変わる。(3) 上限(包含の中央値)が、変更の前の 3 回の Worker の時間の範囲(最大と最小の差)より小さい。その場合、変更の効果は測定の散らばりの内に入り、確かめられない。

## 候補 2: fle_desk_scene の提示ごとの記述(変換)
- 分類: (c) 変換の削減(runtime の窓の表から、JS へ渡す記述 `fle_scene_win` への変換)。
- 位置づけ: R4-4j §4.4 では候補にしなかった(間引きは禁止で、内訳が未測のため)。今回は、内訳を製品の外で測る対象として残す。採否は計数の後。
- 実測(b440・P2 台本・有効 n=3): 自己時間の中央値 1.84%、包含の中央値 1.85%。
- 期待する削減: 上限は自己時間の中央値(1.84%)。ただし、この中で変換に当たる部分の割合は未確認。
- 測り方: 製品の外の一時のブランチで、関数の中の区間(`gather`・窓ごとの `find_in`・`sh_get`/`sh_trim`・記述の書き込み)の時間を計数し、その後で変換だけに当たる区間を直す。
- 撤回条件: (1) 区間の計数で、変換の区間の割合が中央値で 0.5% 未満。(2) 直した後の Export の sha256 が変わる。(3) 間引き・重複排除(前の記述と同じ物を送らない等)でしか削減できないと分かったとき(ROADMAP の禁止。局所的な軽量化)。その場合、この候補は採らない。

## 2 候補の合計の上限(数の確かめ)
- 候補 1 の上限(包含の中央値)と候補 2 の上限(自己時間の中央値)の和は 3.15%。Worker の CPU は 1 秒あたり 891 ms(有効 3 回の中央値)。したがって、2 候補がすべて消えても Worker の時間は 3.15% 程度しか減らない。120 fps に要る速さは量で違う(`evidence/R4-4.md` §6)。CPU 時間の比は約 2.05 倍(891 ÷ 52 = 17.1 ms を 8.33 ms にする。52 は R6-35 の Mixer のドラッグ中の提示の数で、再生中は未測)。フレーム間隔の比は約 2.3 倍(19.2 ms ÷ 8.33 ms)だが、これは CPU 時間の比ではない。よって、この 2 候補だけで P2 の 120 fps に届くとは言えない。
