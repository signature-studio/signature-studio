# 0423: ILVideo_x64.dll と FFmpeg の閉包 8 本の規模を測った(census と見積り)。取り込みはしない

分類: 測定(census と見積り)。取り込み・製品の変更・bundle の作成は、この決定では行わない。
撤回条件: (1) 閉包を wasm にコンパイルして測った大きさで、決定 2 の判定が変わったら、決定 2 を改める。(2) VEX(AVX/AVX2)の対応が決まり、未対応の数が変わったら、決定 2 と 4 を見直す。(3) `RM_MAX`(実モジュールの上限 16)を上げる決定が無いまま取り込みに入ろうとしたら、その取り込みは止める。

## 0 範囲と件数(設計の前の確認)

- 対象: `ILVideo_x64.dll` と、その import の閉包 **8 本**(ILVideo 1 + avutil-56・avcodec-58・avformat-58・swresample-3・swscale-5・avdevice-58・avfilter-7)。依頼文の『FFmpeg 6 本』は `avfilter-7` を落としていた(`avdevice-58` が import する。`evidence/R5-6g.md` §0)。
- 入力: インストーラ 26.1.7.5653(読み取りのみ)。8 本とも抽出して、SHA-256 が `evidence/R5-6g/ffmpeg-rows.tsv` の値と一致(その値は旧ワークツリーの m2-inventory/pe-inventory.tsv から転記)。VFS の seed と `ci/extract-dlls.tsv` には 0 件。
- 製品の変更: 0 件(bundle を作っていない。Chrome を動かしていない。build-lock・chrome-lock は取っていない)。fe-lift の release は自分の target dir で作った(製品のコードは変えていない)。

## 1 読んだ事実(数字の出典は evidence/R5-6g.md)

- 生成 C の合計は **938,657,073 B**(8 本)。未対応の箇所は 243,272。そのうち VEX(AVX/AVX2)が、avcodec 79.0%・avformat 74.6%・avfilter 95.4% を占める(avformat の 74.6 は前の版で 75 と丸めていた)。ILVideo の 85 件は import thunk。
- 閉包の画像(SizeOfImage)は 90,791,936 B。線形メモリに写る(現在の 10 本 68,083,712 B と合わせて 151.5 MiB)。
- `RM_MAX = 16`(`lift/runtime/fle_realmod.c:17`)。現在 10 本、閉包を足すと 18 本。
- prune: 閉包の判定表は無い(実行の記録が無い。ILVideo は今の製品で一度も動かない)。`dsp_ippv2` の既存の判定表の類推では、C の 43.1% が残る(類推。FFmpeg の効果ではない)。
- PEQ2 が ILVideo を使うのは、`.WEBP` の拡張子の分岐(`ILVideo_LoadBitmap`)だけ(読み。拡張子の表は 4 件。読み込むファイル名は未確認)。ただし読み込みの失敗時に 0 を呼ぶ経路は、PEQ2 の全体の読み込みに閉包の 8 本を要する。

## 2 S1(wasm ÷ 分母。2 倍以内)

- 現在: 165,776,779 ÷ 88,674,176 = **1.8695**(決定 0408)。
- 閉包を足した分母: 88,674,176 + 76,256,256 = **164,930,432**(2 倍の上限 329,860,864 B)。
- C 型(k_C = 0.209407、R5-6 §5 の係数): wasm 362,338,514 → **2.1969**(2 倍を超える見積り。上限を 32,477,650 B 超える)。
- native 型(k_N = 2.0503): wasm 322,124,778 → **1.9531**(2 倍以内の見積り。余裕 7,736,086 B)。判定は未決(決定 2)。
- 損益分岐(C 型): 生成 C を 16.5%(938.7 → 783.6 MB)減らすと 2 倍の見積りに届く。prune の残存 43.1% を C 型に当てると 1.5191(類推)。

## 3 決定

- 決定 1: 取り込みは行わない(R5-6g の範囲)。ILVideo と閉包の取り込みは、決定 2 の判定と `RM_MAX` の決定の後に、別の R-ID で行う。根拠: 閉包は 8 本で、生成 C は 938.7 MB。VEX の対応が無いと、未対応の大半は実行時に止まる。
- 決定 2: S1 の判定は未決のまま残す。係数(C 型・native 型)で結論が逆になるので、どちらかを選ぶ根拠が無い。決め手は、閉包を wasm にコンパイルした大きさの実測(約 940 MB の生成 C のコンパイル。build-lock と時間が要る)。その実測をやるかは main が決める。根拠: census と見積りでは S1 の判定が決まらない(`evidence/R5-6g.md` §5)。
- 決定 3: PEQ2(R5-6d)は保留を続ける(決定 0411・0416)。根拠: PEQ2 の停止は ILVideo の読み込みに依る。閉包の 8 本が読めるまで、PEQ2 を取り込むと、この停止が再び出る。
- 決定 4: 誤読を訂正する。R5-6f の『拡張子 .PNG の添字 2』は誤り(表は `.BMP`・`.PNG`・`.TGA`・`.WEBP`。ILVideo の分岐は添字 3 の `.WEBP`)。`evidence/R5-6f.md` §6 に訂正を入れた。
- 決定 5: lazy の選択肢は、事実だけを並べる(`evidence/R5-6g.md` §8)。0314v1(lazy VFS)は seed の木の遅延で、wasm(S1 の分子)には効かない。画像の遅延は runtime の変更で、wasm の大きさは変えない。S1 を守る道は、閉包を別の wasm の単位にすること。その場合の S1 の分子の定義は未確認(`performance.md` の文言を読んでいない)。

## 4 読み(解釈。実行していない)
