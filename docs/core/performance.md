## 3 原因の読み(旧。測定ベース。実行していない)

- 120 fps の予算: 1 フレームの計算を 8.3 ms 以内にする。旧 `performance-targets.md` §5 は「native -O2 で約 7 fps(決定 0143 の測定)、wasm はさらに遅い」と書く(2026-11-03 時点。MXCSR 高速化の前後で変わった)。HLE・コード生成・GPU・通信の削減で届くかは**未確定**。届かない場合は測った予算を書き、削減を続ける。
- wasm が native より遅い最大の原因は runtime の -O0 ビルド(0226、`RT_OPT` 既定 O0)。-O2 化で CPU 53 操作の中央値 1.02 倍(同じ session の N1 比)。N2(実物 FL64.exe)は Wine で起動せず未測定。**この修正が現行 E13 に入っているかは未確認**。
- 再生中 T の大半は、入力がエンジンの idle を待つ B(Chrome 17〜122 ms)。協調 1 Worker は Worker の CPU を使い切る(Firefox 97〜100%)。
- 入力→画面の小さい入力は、ブラウザのフレームへの揃えが 7〜9 割(0194)。
- 実スレッド版(RT-A/B)は 5 分再生で数の基準を満たすが本番でない(0312)。依頼者の条件(Mixer 表示・マウス移動)で破綻する(O19)。**未測定: RT で依頼者の条件を再現したか**。

## 4 計測の経路(依頼者機)

ビーコン `POST /__perf`(ページ→同一オリジンの受け口)。本番 Worker は検査して捨て、保存しなかった(`X-Perf-Stored: no`)[文書]。**新アプリでは、受け口が保存することを自分で 1 回送って読み戻して確認する**(ROADMAP R4-1)。依頼者機の値を待たない。報告の未確認欄に「依頼者機の値: 0 件」を毎回書く。
